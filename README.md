# 天意人力资源系统（ty-hr）

**专门面向餐饮业的多门店 HR 系统，采用本地部署、B/S 架构。** 中文名为「天意人力资源系统」，英文名为 `ty-hr`，原 GitHub 项目为 `osborn-studio/ai-hr`。

> **2026-11-16 开发测试版。** 已实现集团/品牌多帐套基础、独立经营公司、部门与档口、岗位职级、跨品牌永久人员编号及有效期履历；新增工资规则核算、双算法绩效及香港核验工具。旧业务模块通过显式映射接续。全部演示资料为虚构数据，当前验证不构成真实客户工资核验或生产验收。

---


## 2026-11-16 新版工作台

本地 B/S 测试入口为 `/workspace`。新增多帐套组织与永久人员身份、薪酬规则核算、双算法绩效、工资单输出和来源导入，保留原36项业务入口；长页面使用二级导航和分页。

完整测试帐套为 **天意集团**，**香香鱼米（CN/CNY）、大富烤肉（香港 HK/HKD）各10家门店**，另设集团总部独立帐套。两地工资与绩效分别核算。所有人员、任职、工资和绩效数据独立虚构。绩效聚合与工资算法由使用者选择配置，无需外部客户确认。

操作、边界与初始化说明见 [新版工作台与测试帐套](docs/53_新版工作台与测试帐套.md)。旧设计和切片说明保留在下文；验证结论以对应版本及实测日志为准。

以下原业务问答保留原型规则说明。其中内地个税、社保和加班算法仅适用于相应地区配置；香港主体由新版入口和地区守卫处理。完整测试通过不等于真实客户配置或生产验收。

## 二、一条命令

```bash
cd ty-hr/code && npm install && npm test     # 609 库 + 305 接口 + 4 持久化 + 5 备份 + 9 契约（1 跳过）+ 40 界面 + 23 全生命周期 + 7 多门店多法人 + 21 权限矩阵 + 9 工资单打包 + 11 档口范围
SEED_SKIP=1 node tools/seed-chain.mjs         # 连锁餐饮演示帐套（10 店/20 人/5 外包/26 账号，在建）
npm run test:db                              # 只跑数据库
npm run test:api                             # 只跑接口
npm run test:persist                         # 只跑持久化（重启不丢库）
npm run test:ui                              # 界面冒烟（本机 Chrome 无头；没有 Chrome 则跳过）
npm run serve                                # 起服务（127.0.0.1:8787，内存库）
npm run serve:persist                        # 起服务 + 落盘到 ./.data（重启不丢）
npm run backup                               # 备份到 ./backups（.tar.gz + .json 清单）
npm run restore -- --file backups/xxx.tar.gz --to /data   # 恢复（先校验和，再装载）
npm run demo                                 # 先跑接口断言、再起同一套库的服务
                                             # → 自检页能读到真实结论，而不是一片 never_run
```

`npm test` 依次运行 `test:legacy` 与 `test:new`；各测试自行建立隔离数据，界面冒烟使用本机 Chrome。内存小的机器上可能被 OOM kill
（`Killed: 9` / exit 137）—— 那不是测试失败，分开跑即可（`npm run test:db` 等）。

> **数据目录不要放在项目里（本机沙箱会拦批量删除）。** `serve:persist` 用 `./.data` 在普通机器上没问题，
> 但这台机器的沙箱会拦截 PGlite 删除 `postmaster.pid`，表现是**运行中随机 500**。
> `npm run demo` 因此把库放在 `${TMPDIR}/aihr-demo`。

打开 <http://127.0.0.1:8787/> 是单页界面：切三个身份（集团HR / A店HR / 无授权），
同一份数据会变三次——考勤从 2 行变 1 行变 0 行，工资条净值从原值变掩码。
**这是"权限模型真的在起作用"最直观的证据，比读 DDL 快。**

无 Docker、无本机 PostgreSQL 也能跑——PGlite 把 PostgreSQL 编译成 WASM，`btree_gist`、`EXCLUDE`、`CHECK`、`plpgsql`、目录查询都在。

### 部署（`code/Dockerfile` + `code/compose.yaml`，⚠️ 未在本机验证）

```bash
cd code && docker compose up --build        # http://127.0.0.1:8787  · 演示口令 demo1234
```

放公网前还有一层：`deploy/Caddyfile`（自动证书 + HSTS + 探针放行，⚠️ 未在本机验证）。

三件事写清楚，因为它们都是**会咬人**的：

1. **数据库在 app 容器里。** PGlite 是「PostgreSQL 编译成 WASM」，跑在 Node 进程内，
   没有独立进程 —— 所以没有「app 容器 + db 容器」这种拆法。代价是**只能单实例**。
2. **必须挂卷**（`/data`）。不挂就是「重启丢库」，比丢会话严重得多。
   `test/persist.test.mjs` 的四条断言守的是同一件事（跑本地目录，不依赖 Docker）。
3. **探针用 `/livez`，不是 `/api/health`。** 后者要 token，未认证是 401；
   用它做探针会永远 unhealthy，然后探针被删掉，然后服务挂了没人知道。
   `/livez` 只证进程存活，`/readyz` 才查库 —— **库挂了不该重启进程，只该挪走流量**。

`HOST` 默认 `127.0.0.1`：不显式设 `0.0.0.0` 就不对外；设了就必须放在反代后面。

### 写路径：从「读有权限」到「写也有权限」（AG 组 15 条，含 2 条源码扫描）

上一节（AE）把「请假」一条流做完整了，但只做完整了**一条**。其余写路径是这样的：

```
POST /api/payroll/run      → 直接 INSERT pay_run，然后 fn_payroll_calc     ← 没有事务
POST /api/perf/seal        → 直接 db.query                                  ← 无留痕
POST /api/settlement/*     → 直接 db.query，操作人写死 'cai_wu'             ← 留痕里不是真人
招聘 · 编制                  → 根本没有写接口                               ← 只有种子 SQL 能做
```

于是有一个洞，而且它在演示里永远不会出现——**因为演示总用权限最大的账号**：

> 一个四维全空的账号，查考勤 0 行（M2 已经证明了），
> 但可以发起一次**全集团算薪**。读被拦住了，写没有。

三条规矩，每条都对应一组断言：

| 规矩 | 落法 | 断言 |
|---|---|---|
| **写判断"能不能动这个对象"，用读用的那四张临时表** | `services/guard.mjs · requireOrg` | AG1 / AG2 / AG10 |
| **灌权限与写必须在同一事务** | 路由只经 `runWrite`（内部 `withTx`） | AG3 / AG13 |
| **失败要能复盘**：业务码映射 + 事务外留痕 | `toHttp` + `logReq` | AG11 |

| 断言 | 证明 |
|---|---|
| AG0 | 服务层用到的 **8 个资源码**全部在 `sys_perm_resource` 里（漏登记不是"权限不足"，是接口直接 500） |
| AG1 | 无授权账号算薪 → **403**（写路径与读路径同一套行闸） |
| AG2 | 越权封账 → 403，且 `attendance_close` **一行未增**（拒绝发生在写之前） |
| **W3** | 绩效未封存 → 算薪 409，且**不留下空批次**（建批次与算薪同一事务） |
| AG4 / AG5 | 需求挂非叶子 → 422；名额超"还能发" → 409（同一组织多张需求的名额合起来算） |
| AG6 | 开需求 → 200，且看板**立刻**可见（写与读读的是同一张表） |
| AG7 | 2 个名额：第 2 个 offer 成功、第 3 个 409 |
| AG8 / AG9 | 子项之和 > 父项 → 422；调编**追加版本** v1→v2，不就地改 |
| AG10 | A店HR 给 C店下编 → 403（权限分配到组织，不是"HR 都行"） |
| AG11 | 写失败留痕落在**事务外**（`ROLLBACK` 带不走它） |
| AG12 | 结算有差异 → 409（不取平均、不取小） |
| AG13 | **源码扫描**：11 条 `/api` POST 路由全部经 `runWrite` |
| AG14 | **源码扫描**：服务层不出现 `withTx`（事务边界只有一处） |

AG13/AG14 是这一组里唯一"不测行为、测形状"的断言，而它们防的是**回归**：
新加一条写路由、忘了走统一出口，它就会缺事务或缺留痕，**而那种缺失不会让任何行为断言变红**——
因为没有断言在看它。读一遍代码能发现，但下一次改动就发现不了。

#### 写这里时踩到的两个真问题

**① 维度有两种 `kind`，判据落在两张表里。**

`requireOrg` 第一版只查 `pg_temp.tmp_scope_org`。而 `payroll_legal_entity` 的 `kind` 是 `entity`，
它的范围落在 `tmp_scope_entity` —— 于是集团 HR 第一次算薪就被判 **403 越权**，
而他明明有这家法人的范围。

这个错不会在只有 org 维度的系统里出现，也不会在只测一种维度时出现。
修法不是加一张表的 `IF`，是**按 `sys_perm_dim.kind` 分支**（新增维度不用改这里）。

**② `pay_run.id` 没有生成方式，而从来没人走到那条 INSERT。**

第五次同一个坑，这次藏得最深：

- Q14/Q15 那两条机器判据扫的是「**被库函数** INSERT 的表」；
- `pay_run` 是**应用层**插入的，扫不到；
- 它一直没暴露，是因为测试总是命中"批次已存在"那个分支（种子给了 `2026-03` 的批次）；
- **第一次真正走到 `INSERT` 就是 23502 not-null violation on id**，看起来像数据缺失。

⇒ 断言要覆盖**首次**分支，不只是重复分支。AG3 就是那条首次分支，
而它现在同时证明了两件事：门禁会拒、拒了不留垃圾。

#### 顺带修掉的一个"看起来齐全"的假象

`/api/settlement/confirm` 原来写死操作人 `'cai_wu'`。留痕表里于是永远有一个
"财务已确认"，而它记录的不是任何一个真实的人。改成取自会话之后，`app_request_log`
里那一行的 `actor` 才回答得了"是谁确认的"。

**留痕写死一个名字，比不留痕更坏**：它让人相信这件事有人负责。


### 三处值得单独说的（AE 组的三条）

**① 连接归属是一句没人写下来过的前提**（AE5）

`app_begin_scope` 把权限灌进 `pg_temp`——而临时表是**会话**的。单连接上没问题，
一旦上连接池就会出现：灌权限用一个连接、业务查询用另一个，于是临时表是空的、
四维全空、**查到 0 行**。

这个失败很安静：不报错、不告警，只是"这个人什么都看不到"。排查方向通常是权限配错了、
组织没挂对，没人会想到"两条语句不在同一会话里"。所以规矩定死：**一次业务请求 =
一个事务 = 一个连接**。

**② 失败尝试的留痕必须在事务外**（AE6）

写在事务里，失败时会随 `ROLLBACK` 一起删掉——**而失败正是它存在的理由**。
行级审计（`sys_audit_log`）答不了"没有改到任何行的请求"：额度不够被拒、越权 403、
重复审批被挡，这些在磁盘上什么都没变。而它们最容易藏着越权探测。

所以 `app_request_log` 写在事务外，成功失败各一条。界面的「自检」页能直接看到
最近 20 条请求与近一小时的失败分布。

**③ 500 不该回显 SQL 原文**（AE2）

原来所有 catch 都是 `500 + e.message`。而 `e.message` 常带表名、约束名、甚至值片段——
直接吐给前端等于把 schema 送出去。现在 500 只回 `{error:'INTERNAL', ref}`，
原文只进服务端日志，`ref` 让用户报障时有东西可检索。

顺带补了一条**只在库里能守的规矩**：申请人不能审批自己的单（`E_LEAVE_SELF_APPROVE`）。
写在服务层的话，运维脚本、MCP 工具、以后的另一个客户端都可以绕过它。
加这条时测试立刻红了——因为原来的用例一直是同一个人申请、同一个人审批。

### 会话：从进程里的一张 Map 到库里的一张表（AH 组 11 条）

原来这一行就是全部实现：

```js
const sessions = new Map();   // token -> userId
```

三个后果不是"将来要考虑"，是**现在就不成立**：

| 后果 | 具体形态 |
|---|---|
| **重启即全员掉线** | 内存里的东西跟着进程走。部署一次，所有人重新登录，而看起来像"系统不稳定" |
| **无法吊销** | 员工离职、手机丢了、token 泄露——没有地方能作废，只能等重启，而重启会连正常用户一起踢 |
| **回答不了审计第一句话** | "这个 token 现在还能不能用"没有答案 |

三条判断与全仓其它部分一致，不另立一套：

| 判断 | 落法 | 断言 |
|---|---|---|
| **存摘要，不存明文** | 库只收 `sha256`（PGlite 没有 pgcrypto，摘要由应用算）；入口校验"是不是 64 位 hex"，明文会在第一行被拒 | AH1 |
| **过期是派生的，不是状态** | 没有 `status` 列，`expires_at <= now()` 就是过期；靠定时任务翻状态的话，任务停三天就多放行一批 | AH2 / AH8 |
| **吊销是显式事实** | `revoked_at/by/reason` 三件套，不可清空、不可复活；吊销别人的会话 → 403 | AH3 / AH7 / AH11 |

校验函数刻意**不返回 NULL，而返回"为什么不能用"**：

```
missing  没有这个 token      → 401 E_UNAUTHENTICATED（前端引导登录）
expired  有，但过期了        → 401 E_SESSION_EXPIRED（重新登录）
revoked  有，被人作废了      → 401 E_SESSION_REVOKED（去问管理员）
ok
```

合成一个布尔，等于把三种处置都推给调用方去猜；而这三件事在**处置上完全不同**。

| 断言 | 证明 |
|---|---|
| AH1 | 库里按 token 明文查 **0 条**、按摘要查 1 条 |
| AH2 | 过期 → 401 `E_SESSION_EXPIRED` |
| AH3 | 吊销后立刻失效，且**带得出吊销原因** |
| AH4 | 没 token 与过期是**不同的码**（不是所有 401 都叫"未登录"） |
| AH5 | 就地延长有效期 → 拒（`E_SESSION_EXTEND`）——否则每个泄露的 token 都变永久的 |
| AH6 | 把会话改成别人的账号 → 拒（`E_SESSION_TAINTED`） |
| AH7 | 清空 `revoked_at` 复活会话 → 拒（`E_SESSION_REVIVE`） |
| AH8 | `sys_session` 里没有 `status` 列；活跃视图自动排除过期与吊销 |
| AH9 | **源码扫描**：进程里不再有存 token 的 Map |
| AH10 | 会话列表只列自己的 |
| AH11 | 吊销别人的会话 → 403（吊销是"我吊销我的"） |

界面上「我的权限」页签多了「我的会话（N 台设备）」，每条带签发/到期/最后活跃与「退出这台」。

**仍然是切片的简化**：`/login` 只按 `?user=` 发 token，没有口令校验。真实系统这里要验密码/SSO，
但"会话怎么存、怎么过期、怎么吊销"这一层已经不再简化了 —— 而这三件事恰好是最容易
被"先放个 Map 以后再改"拖成永远的那三件。

### 绩效：封存才进算薪（AD 组 12 条 + 接口 2 条）

这一块和前十个模块不同：**它要动算薪**。而算薪那条链路上已经有封账冻结、勾稽、
累计预扣三道保护，任何新东西接进来都必须先被约束住——**否则它会成为那条链上
唯一一个"算完还能改"的输入**。

四条先行规则：

| 规则 | 断言 | 为什么 |
|---|---|---|
| **周期必须封存才进算薪** | AD1 | 未封存就参与，等于按一份还会变的分发钱。而"算完再调分"在绩效季是常态——调完之后工资已发、绩效表也"看起来对" |
| **系数在封存时固化** | AD3 / AD6 | 和 `snap_on_duty_break_basis` 同一条：分数与系数是**当时的事实**。读取时现算的话，改一次方案会把去年已发过钱的系数也改掉 |
| **未考核是显式状态** | AD11 | NULL 会让"没考核"与"考核了没录分"同形，而两者处置相反 |
| **强制分布只报不拦** | AD12 | 拦的后果是有人去调分——**而调过的分与真分在表里同形，看不出来** |

实测：A 档 50%（目标 20%，超 30 个点）、C 档 50%（目标 10%，超 40 个点）——
这些数会出现在分布表里，而不是被一条 `RAISE` 挡住然后变成"大家都评 B"。

AD7 是整条链路的收口：封存后算薪通过，**绩效 8000×1.5=12000，应发 20000**，
明细里有 `PERF_BONUS` 行。

跑的时候踩到一个有价值的顺序问题：AD1 第一次跑报的是 `E_ATT_NOT_CLOSED` 而不是
`E_PERF_NOT_SEALED`——因为算薪有两道门（考勤封账、绩效封存），**考勤在前**。
这不是 bug，是门禁该有的顺序：没封账的考勤先用不上"绩效未封存"这条判据。

### 招聘：承诺也要占编（AC 组 13 条 + 接口 2 条）

这一块的价值不在"多一套表"，在**把编制这个抽象额度，变成一个具体的人**。
中间会经过若干次承诺，而**每一次承诺都在占用额度**。

所以核心判据只有一条：**编制说还能招 2 个，招聘就只能发 2 个 offer。**
这条不在库里，编制管理就只是一张报表——谁都可以绕过它发 offer，
而发出去的 offer 又不能不发（那是法律承诺）。

三个必须分清的量：

```
used     已入职（事实）
offered  有效 offer（承诺）
可招     = 额度 − 已下分 − **直属在编**   ← 不含承诺；178 之前这里误用「子树在编」，父节点会双计变负
还能发   = 可招 − offered             ← 含承诺
```

**只算 used 的后果**：同一个编可以同时发出十个 offer，第一个入职的人把位置占了，
后面九个都是法律承诺，而系统在整个过程中一直是绿的。

| 断言 | 证明 |
|---|---|
| AC1 | 开 3 个名额但只能发 2 个 → 拒 |
| AC2 | 第三个 offer 超过需求名额 → 拒 |
| AC3 | 两个有效 offer 计入占用：`offered=2`、`还能发=0`（**不是等入职才算**） |
| AC4 | offer 过期**自动释放**（4/5 是 2 个，4/25 只剩 1 个），而状态栏仍是 `pending` |
| AC5 | 同一候选人不得同时持有两个有效 offer |
| AC6 | 改薪资走追加版本：`v1=7000` 仍在，`v2=7500` 生效 |
| **AC9** | 入职按 offer **最后版本**落三样：任职 / 成本组织 42 / 月薪 7500 |
| AC10 | 已入职 offer 状态回退 → 拒（**回退＝这个编可以再招一次**） |
| AC12 | 需求挂到有下级的组织上 → 拒 |

AC9 是"承诺 → 事实"的唯一关卡：入职后写的三条记录本来就是同一个承诺的三个面。
任何一处不一致，都会在第一次算薪时变成"这人工资不对"，而那时已经发了。

AC4 与 AC12 各修掉一个真问题：
- 过期如果靠定时任务翻状态，**任务停三天就多发三个 offer，而没人会发现**。改成时点派生。
- `AC12` 是看到 `华东区 can_offer = −3` 才发现的：非叶子组织的 `used` 与 `allocated`
  把同一个编扣了两次。正确的修法不是改公式，是**需求只能挂叶子组织**——
  给区域发 offer 时"这个人占哪个门店的编"答不出来，那不是算错，是问题没有答案。

### 审批引擎接电：从「一个人点一下」到「几步、谁审、审到谁为止」（AI 组 7 条 + AR 组 4 条）

`006` 把三张表（模板版本 / 实例 / 任务）和两条冻结判据都建好了，但**没有任何东西往里写**。
请假走的是 `fn_leave_decide_by`：一个人点一下，单子就批了。

那证明了「自审会被拒」，但撑不起真实审批。真实审批要回答三个新问题：

```
有几步？     → 模板定义（jsonb），发布时校验结构
谁审？       → 启动时把审批人**解析成行**，不是每次点的时候现算
到哪算完？   → 或签（any）/ 会签（all）；一人驳回即整单否决
```

五条判断写在 `032` 的文件头，其中三条是这一组真正在防的东西：

| 判断 | 为什么 | 断言 |
|---|---|---|
| **按业务日期选模板版本** | 补录一张上个月的单，用上个月还不存在的流程 = 用未来的规矩审过去的单 | AI1 |
| **审批人是「人」，落成行** | 现算的话，中间改一次组织授权，同一张单的「该谁审」会变，两次查询都「看起来对」 | AI2 / AI7 |
| **申请人不在审批人集合里** | 不是「点了再拒」，是启动时剔除；剔除后为空 → **明确失败**，不是「没人审就自动通过」 | AI4 |

最后一条是这一组最要紧的：**自动通过是最安静的越权**。记录上写着 `approved`，
审批人一栏齐全，而没有任何人看过。

| 断言 | 证明 |
|---|---|
| AI1 | 2 月的单走 v1（1 步），一次批完即 approved，业务单据同步 |
| AI2 | 3 月的单走 v2（2 步），第 2 步会签：两人齐了才推进 |
| AI3 | 不是自己的待办 → `E_APPR_NOT_YOURS`（不是「谁点都算」） |
| AI4 | 审批人只有申请人 → `E_APPROVAL_NO_APPROVER`，且**不留半个实例** |
| AI5 | 一人拒绝：实例 rejected、单据 rejected、额度回到申请前 |
| AI6 | 定义 `seq` 必须从 1 连续 → 跳号在**发布时**就被拒 |
| AI7 | 组织授权沿祖先链解析到人（授在集团 → 门店的人继承） |
| AR1–AR4 | 接口侧同一条链：发起 → 待办出现 → 别人审批 → 单据 approved；非审批人 403；同单不能发起两次；轨迹里是「人」不是角色 |

写的时候踩到一个只有真跑才暴露的错：`mode=all` 的**指定人**步骤，
`act_kind` 被写死成 `approve`，于是它变成了或签 —— 第一个人点完整单通过，
第二个人看到的待办还在。两次读数都「看起来对」。

**边界（写清楚，不假装）**：

- 请假目前有两条路 —— 单签（`/api/leave/decide`）与多步（`/api/approval/*`）。
  同一张单同时只能有一个 running 实例（`uk_ai_one_running`），所以两条路不会各写各的；
  但「一张单该走哪条」是**业务配置**，不该由代码替客户决定。
- 转签 / 加签 / 代理 / 抄送**没有做**：`approval_task.act_kind` 已预留取值，
  但那是产品面（谁能在什么条件下把待办转给谁），先编一个默认反而更坏。
- 账号与员工在本切片里是 1:1（`person_id = user_id`）。审批回写靠这个前提，
  真实系统里这是两套实体，接的时候要改成显式映射。

### 文档数字自证：`npm run verify:docs`

README 顶部那张状态表全是手抄的：迁移数、表数、函数数、判据组数、五套断言条数、
以及「合计 426/427」。它一定会漂 —— 这个仓库里已经有一条规矩叫「断言条数不许手抄」，
而那张表本身就是手抄的。

所以现在有一个工具，**从真实来源数一遍再与文档比**：

```
迁移 / 表 / 函数 / 触发器 / 判据组   →  查库与 db/ 目录
五套断言条数                        →  真跑一遍，取它们自己打的那一行
```

第一次跑就抓到了：

```
断言合计      427    425    不一致
其中通过      426    424    不一致
```

—— 加完入职与补账的断言后，我改了分项的 276/134，却漏了合计行。
**两个数字在同一张表里互相矛盾，而读者只会记住一个。**

两个入口：

```bash
npm run verify:docs            # 报差异，不退出（人看）
npm run verify:docs:strict     # 有差异 exit 1（CI 用）
node tools/verify-docs.mjs --fast   # 只比库对象数，不跑测试
```

`--fast` 存在的原因很实际：断言条数必须真跑五套才知道，而五套连跑在内存小的机器上
会被 OOM kill（exit 137）。**宁可少核几项，也不要一个「跑不动所以没人跑」的工具。**

### 界面冒烟：把「页面还活着」变成一条能跑的判据（UI 组 5 条）

到 059 为止，证明「界面还能打开」只有两种办法：人打开它，或者看 25 张实拍。
而实拍是**过去某一刻**的快照 —— 改完 CSP、改完渲染之后，它们一张都不会变红。
库里 307 条 + 接口 162 条全绿的时候，界面仍然可能一片空白（脚本语法错、
nonce 与标签对不上、某个字段名改了下游变成 `undefined`），这三件都不会让库/接口断言变红。

所以补一套冒烟：用本机 Chrome 的 `--headless --dump-dom` 把渲染完的 DOM 取回来，
对**内容**做断言。不开新依赖，也不需要驱动框架。

| 断言 | 证明 |
|---|---|
| UI1 | 18 个页签都渲染出 `.card`，且没有把 `undefined` / `NaN` 画上来 |
| UI2 | 报表页有「导出 CSV」与「导出留痕」，且指标编码真的出现了 |
| UI3 | 制度页把枚举翻成中文（`不处理`，不是 `none`） |
| UI4 | 门店 HR 的看板只有 A店 那一行，没有「华东区」 |
| UI5 | 0 行页面说人话：「不是没有数据，这个身份看不到」 |
| UI6 | 花名册有「工号」列且显示 E0001/E0002（不是一列「未分配」） |

两个踩到的坑都在断言自己身上，记在这里：

```
① 判据不能拿"页面里有没有 E_ 开头的东西"当错误信号 ——
   演示提示语里就写着 E_OUT_OF_SCOPE / E_HC_OVER_ALLOCATED 这些码当例子。
② 必须只看 #view 那一段并剥掉 <script> ——
   否则"华东区"会从脚本里的示例常量命中，页面明明没有它，断言却是绿的。
```

没有 Chrome 的机器上这套会**跳过并说明**（跳过不算通过）；
`verify:docs` 里它计为「(缺)」，于是「没跑」会以差异的形式露出来，而不是安静地算成通过。

### CSP：把 `unsafe-inline` 从 script-src 里拿掉（NH 组 5 条）

README 里一直写着「`script-src 'unsafe-inline'` 是**已知的让步**」。让步的理由是真的
——界面是单文件、脚本内联。但**让步不等于必须一直让**：内联脚本用 nonce 就够，
不需要把脚本拆成文件。

做法很短：每次请求生成一个 nonce，同时写进 CSP 头与 `<script nonce="...">`。
注入者拿不到**下一次**的 nonce，所以注入进来的 `<script>` 不会执行。

顺手收掉的还有一件更该收的：**接口原来跟着界面一起吃 `'unsafe-inline'`**。
JSON 与 CSV 响应不需要任何脚本能力，现在它们的 CSP 是 `script-src 'none'`。
一个响应类型对应一份能力 —— 之前是「顺手共用一套头」。

| 断言 | 证明 |
|---|---|
| NH1 | 界面 CSP 里不再有 `script-src 'unsafe-inline'`，而是 nonce |
| NH2 | 同一个 nonce 也在 `<script nonce>` 上（只改头不改标签 = 页面白屏） |
| NH3 | nonce 每次请求都换（固定 nonce 等于没有 nonce） |
| NH4 | 接口与探针是 `script-src 'none'` |
| NH5 | 源码里没有 `on*="..."` 内联事件（有的话会被静默挡掉，界面像「点了没反应」） |

`style-src` 仍留 `'unsafe-inline'`：页面里有 27 处 `style="..."` 属性，
CSP3 要用 `'unsafe-hashes'` 逐条列举，成本远大于收益 —— CSS 注入与脚本注入
不是一个量级。这是**写明的取舍**，不是漏掉的一项。

### 登录按来源限流：锁定的另一面（LG 组 5 条 + 接口 LG 组 3 条）

035 做了「同一账号错 5 次就锁」。它挡住的是**猜一个账号的口令**，
而它挡不住另外两件事 —— 其中第二件是它自己造出来的：

```
① 撞库：拿一份泄露的「邮箱+口令」表，对几千个账号各试一次。
        每个账号只错一次 → 永远锁不住，也永远不被记录。
② 拿锁定当拒绝服务：盯着某人的账号连错 5 次，他就登不进来。
        这件事不需要知道他的口令，一个脚本就能做。
```

两件事的共同点：**特征都在「来源」上，不在「账号」上**。所以 058 补的是按来源计数
（`login_attempt` + `fn_login_throttled`），阈值是制度项（默认 30 次/15 分钟）：

| 判断 | 落法 | 断言 |
|---|---|---|
| 打到上限的来源连正确口令也进不来 | 限流判断在**账号判断之前** | LG1 |
| 成功不清零 | 只数 failures；清的话，有一个自己的账号就能无限续命 | LG2 |
| 窗口外不算 | 阈值是「最近 N 秒内」而不是总数 | LG3 |
| 阈值是配置项、且不追溯 | 改成 3 立刻生效，恢复 30 从明天起生效 | LG4 |
| 被限的尝试不记账 | 拒绝一次多写一条 → 越拒绝越接近上限 | LG3（接口） |
| 另一个来源不被连坐 | 来源之间互不影响 | LG2（接口） |
| 哪个来源正在被撞 | `v_login_fail_by_source` | LG5 |

实现里踩到一个真问题：**账号被锁之后，`authenticate` 会直接抛，于是「换个账号继续试」
永远不会让来源计数上涨** —— 而撞库正是这么做的。所以异常路径也要记一条来源失败。
这条是接口断言跑出来的，不是想出来的。

一个必须写明的边界：来源取自 `remoteAddress`，它在反代后面恒等于代理地址。
只有**代理确实会覆盖** `X-Forwarded-For` 时才开 `TRUST_PROXY=1`；
开了而代理不覆盖，等于让攻击者自己选来源 —— 比不限流更坏。

### 离职时的剩余年假：拿不准的口径，做成配置项（LT 组 5 条 + 接口 LP1）

054 里那句「剩余年假怎么结算是薪酬政策，不替客户决定」是对的。但**「不做」与「没得选」是两件事**：
客户问「我离职的人还剩 3 天年假怎么办」，答「系统不管」不是专业回答。

所以 `057` 把它做成制度项 `LEAVE_TERM_HANDLING`（走 021 那套：集团发布、带生效日、只增不改）。
四条规矩照旧：

```
① 默认值 = 上线前的实际行为：none，额度一分不动。
   默认值不许改变既有账 —— 否则升级那天所有离职记录都会变。
② 只允许集团定（allow_org_override=false）：同一个集团两家店给不同答案，
   集团报表就无法解释了。
③ 改配置 ⇒ 行为真的跟着变，而且有反例（LT3）。
④ 边界写清：不追溯、不产生负数、不碰历史考勤与工资条。
```

实现上有一个取舍值得写下来：**作废是「补一个状态」，不是「删掉那几条授予」**。
`leave_usage.state` 多一个 `forfeited`，余额视图从四态变五态
（`available = granted − frozen − used − forfeited`）。删授予行的话，台账上只剩
「少了 5 天」，而「他曾经有 5 天」这段事实就消失了 —— 对账时无从解释。

| 断言 | 证明 |
|---|---|
| LT1 | 默认 `none`：离职后额度一分不动 |
| LT2 | 改成 `forfeit`：余 5 小时核销成 0，台账留一行 `forfeited` |
| LT3 | **改回 `none` 就不动**（反例：读的是配置，不是写死的分支） |
| LT4 | 还有待批请假 → `E_LEAVE_PENDING_ON_EXIT`；先结算再批假会让余额变负 |
| LT5 | 五态自洽且不出现负数 |
| LP1 | 制度页读得到这一项（登记了但界面看不到，等于没接线） |

**折现（`payout`）刻意不做**，理由不是难：折现要单价（按基本工资还是按上月实发）、
要不要计税、要不要计入社保基数、在下个月工资条里出一行还是单独一张单 ——
四个问题每一个都能让财务和 HR 吵起来。那是薪酬政策链上的另一件事，
不该塞进「办离职」这个动作里假装解决了。

一个技术细节：`CREATE OR REPLACE VIEW` **只允许在末尾追加列**。在中间插一列会报
`42P16 cannot change name of view column "available" to "forfeited"` ——
那个报错读起来像「改错了名字」，实际是「列序变了」，所以这里必须 `DROP VIEW` 再建。

### 工号：能分配，但没人分配、也没人看得见（NO 组 4 条 + 接口 NO1）

007 写了 `employee_no`（编号绑 person、永不复用、永不删除）和
`fn_assign_employee_no`（同一编号不得改分配）。规矩是对的，链却断在两头：

```
① 入职时不分配  → fn_hire_from_offer 建了人、任职、归属、月薪，唯独没有工号。
                   于是"新员工的工号"要靠人手 SQL 补，而这件事 HR 第一周就会问。
② 分配了没人看  → 花名册与详情都不返回工号。一条"写了没人看"的记录，
                   与不存在区别不大。
```

两端都接上之后，规则本身做成了**配置项**（前缀 `EMP_NO_PREFIX` + 位数 `EMP_NO_WIDTH`）：
按年份编号、按门店编号、纯流水，不同公司的答案不一样，写死一种另一家第一件事就是要求改。

| 断言 | 证明 |
|---|---|
| NO1 | 入职即分配（前缀 + 补零到 4 位），一个人只有一行 |
| NO2 | 永不复用：退休一个人的号之后，下一个入职者拿 **max+1** |
| NO3 | 花名册带出工号（分配了要看得见） |
| NO4 | 规则是配置项：前缀改成 `H`，下一个号就是 `H0001` 起 |
| NO1（接口） | 走 `/api/recruit/hire` 建的员工，名单上直接带工号 |

实现里两处必须写成这样，否则错得很隐蔽：

```sql
-- ① 按后缀数字比大小：字符串里 'E999' > 'E1000'，而这个错只在跨过 1000 那一刻出现
max((substring(no from '([0-9]+)$'))::bigint)
-- ② 取 max 时**不过滤 retired_at**：永不复用，退休的号也算"用过的"
--    否则空出来的号会在下一个人身上复活，而历史单据指向的是另一个人
```

另外：工号在 `onboard` **之后**分配。反过来的话，onboard 失败会留下一个
「占了号但没入职」的人 —— 而号是不回收的。

### 导出与看板的范围：一份能发给财务的表（RP / DS 组 9 条 + 接口 XP 组 8 条）

报表页从 023 起就能看，但**没有导出**。业务的实际动作不是「看」，是「把这页发给财务」——
而那时人会截图，或者把数字手抄进 Excel。手抄出来的那份，是这个系统里
**唯一没有口径**的数字：它离开系统之后，再没人知道那个 2 是期末还是日均。

补导出这件事，顺手翻出两个更值得写的问题。

**一、报表读路径没有门。** `/api/report` 与 `/api/dashboard` 原来是直接 `db.query`：
没灌权限、也没判 `org`。于是**任何登录账号把 org 参数改一下就能读别的店的工资总额**。
报表函数自己按 `p_org` 算数、不带行闸，所以这道门只能在服务层（`report.mjs` 的 `requireOrg`）。

**二、导出的三件事故，一件都不会报错。** 工资条导出原来是一句 `join(',')`：

```
① 没有 BOM     → Excel 在中文 Windows 上按系统编码打开，列名全是乱码。
                  业务的第一反应不是"编码问题"，是"这文件坏了、系统不行"。
② 不转义       → 值里有逗号（"张,三"）把后面所有列挤偏一格。文件照样打开、不报错。
③ 不防公式     → 值以 = + - @ 开头时 Excel 会**执行**它（CSV 注入）。
                  姓名与备注是外部可填的，而导出的文件会被转发给很多人。
```

所以新增 `app/csv.mjs`：**全系统只有一个 CSV 写出器**，工资条导出与报表导出都走它。
规矩和 `guard.mjs` 同一条 —— 不要「再掩一次」，要只有一份实现。

导出本身还有三条落库的理由（`055`）：导出的数必须与页面**同源**（同一个函数，不另写一句 `sum()`）、
导出要**留痕**（谁、哪期、多少行、内容 sha256）、**被拒的导出不留痕**
（审计表里混进「尝试过但没成」的记录，它会长得和真正的导出一样，于是这一列不再可信）。

| 断言 | 证明 |
|---|---|
| RP1 / RP2 | 0 行不许导（空文件会被读成「这个月没数据」）、没有摘要不许导 |
| RP3 | 审计视角给得出「谁、几次、共几行」，不只是一张流水表 |
| RP4 | 留痕只增不改 —— 改了行数或摘要，它就不再证明任何事 |
| RP5 | 「这一期有没有数据」能回答；格式写错（`2026-3`）直接拒，而不是给一排 0 |
| XP1 / XP2 | 导出是 CSV + BOM + 附件头；**每个指标与页面逐一对上** |
| XP3 | 库里记的 sha256 与**发出去的那份字节**一致（算在最终字符串上，含 BOM） |
| XP4 | 越权导出 → 403，且留痕数不变 |
| XP5 / XP6 | 报表读也过行闸；看板区域行只在自己的范围内 |
| XP7 | `=1+1` / `@SUM` 被中和、含逗号与引号被正确包裹、负数仍是数字 |
| XP8 | 导出必须认证（导出文件是最容易被转发的产物） |

看板那一侧（`056`）的取舍值得单独说：**区域那一行的数，是整棵子树的数**。
所以「部分可见」的区域不能出行 —— 给出来就包含了你没有授权的店；
给一半又会与「各店之和」对不上。规则因此是**整棵子树都可见才出行**，
并且只留最上层的那几个（否则同一个数在几行里各出现一次）。

DS 组的断言刻意**不写死「集团 HR 看到 1 行区域」**：前面的组织版本测试挪过树，
写死期望值的断言会在改组织结构那天变成「测试坏了」，而它其实是在替实现背书。
改成三条性质：每一行的子树整棵可见（不泄露）、范围内的每个组织都被某行覆盖（不漏）、
没有范围 → 0 行。

**一条登记在案的债**：异常清单（`fn_dash_exceptions`）仍是集团口径。它数的是
「全集团有几类异常」，不含明细数值；改成按范围重算要给九类判据各自加范围参数。
所以不停在这里假装做了 —— 它在 `sys_check_registry` 里是一条有主人、有到期日的债。

### 离职：第七个「表在、门没有」，而且这次有连带（TR 组 7 条 + 接口 4 条）

`employment.leave_date` 从 007 就在，注释里甚至写着「离职日当天仍算在职」。
但它**没有写入路径** —— 只能靠种子写，或者直接 UPDATE。

离职比前六次都危险，因为它有**连带**：

```
① 人走了、归属还挂着  → 花名册按任职过滤看不见他，而"这个店几个人"的口径还数着他。
                         两处各自自洽，加起来错。
② 离职没有原因        → leave_date 只有一个日期。而"为什么走"是 HR 一定会问的那句，
                         答不出来时人会去翻微信，然后凭印象写报告。
③ 离职可以重复办      → 第二次把日期改掉，而第一次那天发过的工资不会跟着变。
```

所以 `fn_emp_terminate` 一次做三件事，同一个事务：结束任职、**结束归属区间**、落一条离职记录。
`employment_termination` 只增不改（改/删都触发拒绝）—— 删掉之后「他为什么走」就只剩传闻。

| 断言 | 证明 |
|---|---|
| TR1 | 三件事一起做；归属不留悬空 |
| TR2 | 离职日**当天**仍在名单、次日起不在（闭区间，差一天就是一天的钱） |
| TR3 | 已离职再办 → `E_TERM_ALREADY_LEFT` |
| TR4 / TR5 | 离职日早于入职日、原因太短 → 各有名字 |
| TR6 | 不动历史考勤与工资条 —— 那是已经发生的事实 |
| TR7 | 离职记录只增不改 |

接口侧多一条值得单说的（`TR2` 接口版）：**离职日之前再办 → 409；离职日之后 → 404。**
后者不是"漏了判断"，而是权限门先挡住了 —— 你已经看不到他，系统就不该告诉你
「他还存在，只是已经离职」。

**刻意不做的**：剩余年假怎么结算（折现 / 作废 / 结转）是薪酬政策，不是「离职」这个动作
能替客户决定的 —— 与 042 那条同样的取舍。所以归属与任职都结束了，额度一分没动。

一个技术细节也留在注释里：date 列在 PGlite 里返回的是 `Date` 对象，
`String(d)` 得到 `"Wed Sep 30 2026…"` 而不是 ISO —— 比日期一律走 `toISOString().slice(0,10)`。
这条断言第一次跑就红在这里，报错信息只显示 `[记录=2 …]`，看不出是它。

### 员工详情：点得进去才叫名单（DE 组 4 条）

花名册做完之后立刻露出一个问题：**点不进去**。名单只回答「有谁」，而 HR 真正要看的是
「这个人的任职、归属、额度、最近工资条」。四条判断：

| 判断 | 落法 | 断言 |
|---|---|---|
| **详情与名单共用一个门** | 先把他当花名册查一遍，不在名单里就 404 —— 不另写「这个人是否归我管」 | DE4 |
| **404 而不是 403** | 403 说的是「这个人存在，但你没权看」，它本身就是一条信息 | DE3 |
| **字段按各自资源问** | 身份证按 `employee_roster` 问、实发按 `payslip` 问。拿花名册的资源码去问工资条字段，结果永远是 masked | DE2 |
| **scene 是独立一维** | 身份证在 `list` 配了 visible，`detail` 还得再配一次 | DE1 |

最后一条是被页面证出来的：先把 `list` 配成 visible，花名册正常、详情页却是 `***`。
那一刻很容易判成「权限没配好」，而真相是**两个出口本来就该分别配** ——
003 里 scene 那一维存在的理由就是这个，只是平时看不出来。

DE2 里那句话值得单独抄一遍：**字段属于原资源**。第一次实现时我用
`fn_field_action(user, 'employee_roster', 'net_amount', 'detail')` 去问实发，
得到 `masked` —— 不是权限问题，是**问错了对象**。所以现在的代码里两个字段各自问自己的资源，
而这条差别在界面上表现为「集团HR 看得到实发」，在断言里表现为 `_actions.net_amount`。

### 员工花名册：一个 HR 系统没有「员工列表」（RO 组 5 条 + 接口 3 条）

到 052 为止，界面能看考勤、工资条、审批、编制、招聘、绩效 —— 唯独**没有一处能看
「我们有哪些人」**。`person` / `employment` / `employee_org_assignment` 三张表都在，
可它们只被种子和入职函数写过，从来没有一个读的出口。

这是「表在、门没有」的另一半：前面五次是**没有写入路径**，这次是**没有读取路径**。
而它的失败形态不是报错，是「这个系统看起来没有员工」—— 演示时最难解释的那种。

两条规矩照抄既有实现，一条也不新发明：

| 规矩 | 落法 | 断言 |
|---|---|---|
| **行闸在库里** | `fn_emp_roster` 里那两个 `EXISTS` / `NOT EXISTS`，与考勤、工资条同一套临时表 | RO1 / RO2 |
| **字段掩码 fail-closed** | 身份证没配就是 `masked`；由 `fn_apply_mask` 统一处理，返回 `null` | RO2（接口） |

`RO2` 想证明的是一件容易做错的事：**换个读接口，deny 不需要重新实现一遍**。
user 4 有该组织的授权，但组织在 deny 里 → 花名册 0 行。如果花名册自己写一套过滤，
这条一定漏 —— 而漏的方式是「花名册看得到、点进去看不到考勤」，没人会当成 bug 报。

写这条时踩到两个坑，都写进代码注释了：

1. **SQL 语言函数在 `CREATE` 时就解析。** 第一版 `fn_emp_roster` 写的是
   `LANGUAGE sql`，引用 `pg_temp.tmp_scope_org` → 迁移直接失败，报
   `relation pg_temp.tmp_scope_org does not exist`。那个错看起来像「迁移写错了」，
   实际是「SQL 函数没有延迟解析」。改成 `plpgsql` + `RETURN QUERY` 即可。
2. **`person_profile.id` 也没有生成方式** —— 但 Q14 扫的是「被**函数** INSERT 的表」，
   而这张表一直只被**种子**插入，所以从没被扫出来。第一次想用无 id 的方式插它，
   就是 `null value in column id violates not-null`。
   ⇒ Q14 的覆盖面是「函数插入」，**种子插入不覆盖**。凡「以后可能有别的插入方」的表，
   主键就该有生成方式。

顺带一个产品判断：名单**按任职区间过滤**（截至那天在职的人），不做「所有有过记录的人」。
「归属还挂着但人已离职」是数据缺陷，该由异常清单报，不该混进名单 ——
混进去之后，名单就不再是名单了。

### 入职：招聘漏斗的末端，以及第六次同一个坑（HI 组 3 条 + 接口 4 条）

025 写了 `fn_offer_onboard`（入职 = 落任职 + 归属 + 月薪 + 转 offer 状态），
而且 R 组有断言。但它只被测试调用过 —— **没有接口层**，于是「从 offer 到在职」
这条链在界面上是断的：招聘漏斗的末端走不通。

补这一层时必然要写 `fn_person_create`（本仓**没有任何"新建员工"入口**，
person 只能靠种子插），而那一刻撞上了这个仓库的第六次同一个坑：

```
person.id bigint PRIMARY KEY   ← 没有生成方式
种子用显式 id 插，所以一直没红；函数一插就是 23502 not-null on id
```

**这次是机器判据抓到的，不是运行时炸的。** Q14（「会被函数 INSERT 的表，主键必须有
生成方式」）本来就是为这个坑写的，这是它第一次真的救了场。留证据的做法是先把
`ALTER` 拿掉跑一遍：

```
FAIL  Q14  会被函数 INSERT 的表，主键都有生成方式   [候选 27 张，缺 IDENTITY 1 张：person]
```

两处判断：

| 判断 | 为什么 | 断言 |
|---|---|---|
| **三处同源，不自己插** | 任职 / 归属 / 月薪都取自 offer 最新版本。服务层再写一遍就是两份口径，差别会等到某次改薪才显现 | HI1 |
| **不带 person 就按候选人姓名建档** | 没有这个，入职接口对使用者就是"你必须先知道一个 person_id"——而那个入口不存在 | HI1 |

顺手把「显式 id 播种 + 序列不前进」这个收尾动作**从清单改成扫描**：
`server.mjs` 与 `test/run.mjs` 现在都扫 `information_schema` 里所有 IDENTITY 列统一对齐。
原来是一张表一张表地记 —— 记漏 person 就是这次的 duplicate key。
一张表一张表地记这种事，只要还在手工做，就一定会再漏一次。

### 考勤补账：第五个「表在、门没有」（AS 组 6 条 + 接口 4 条）

016 把 `attendance_adjustment` 的三条约束写得很细（`delta≠0`、只能往后、理由非空），
但**没有任何东西往里写**。于是「封账后唯一的修正通道」只存在于表结构里 ——
报表读不到它，人也没法用它。

这已经是第五次同一个形态：

```
006 审批三张表   →  没人往里写，请假还是"一个人点一下"
010 两阶段写     →  fn_mcp_execute 没有调用方，AI 仍可直连
037 例外表       →  没有开例外的入口
026 绩效结果表   →  没有打分入口，系数永远 NULL
016 补账表       →  没有补账入口，修正通道是一次性的
```

五次里有四次在**做完"补写入路径"之后才被发现**。所以现在加完功能会先问一句：
**这张表/这个函数，谁往里写？** 没有人写 = 没做。

三条判据：

| 判据 | 为什么 | 断言 |
|---|---|---|
| **只有已封账的期间才补账** | 没封账时原记录还能改；两条路改同一个数，报表会把同一件事算两次 | AS1 / AS2（接口） |
| **只能往后** | 「往前调」不是补账，是改历史换了个名字 | AS2 |
| **不改原记录** | 发薪日已按当时的数发过钱，「当时我们以为的」必须还能查出来 | AS4 |

接线是这一组的关键：报表工时从 `attendance_day_store` 改成读 `v_att_effective`
（原记录 + 补账合计）。**不接线的话，补账就是一张"写了但没人看"的表** ——
那比不做更坏，因为它会让人以为这件事已经管住了。`AS4` 断言的就是「报表 +2 而原记录不变」，
这一条同时证明了「另起一笔」与「确实进了报表」两件事。

两处刻意不动：

- **封账快照**（`fn_att_close` 抓的原表 + `fn_att_verify` 重算）不读补账。
  快照必须是「封账那天我们看到的数」，掺进补账它就不再是快照。`AS5` 守这条。
- **不做「改原记录」的快捷方式**。省一次点击的代价是：三个月后没人能回答
  「这笔 8 小时是当时记的，还是后来改的」。

还有一处实现细节值得写下来：`v_att_effective` 用的是 **`FULL OUTER JOIN`**，
因为补账可以指向「原记录里没有的那一天」（整日漏记）—— 那正是补账最常见的用途，
用 `INNER JOIN` 会把这行悄悄丢掉，而报表上少一天班不会有人发现。`AS6` 守这条。

### 绩效打分：把「表在、门没有」补上（AQ 组 9 条 + 接口 5 条）

026 把方案 / 档位 / 周期 / 结果四张表、封存与系数固化都写好了，可是**没有任何东西往
`perf_result` 里写**。于是封存只能在空表上跑，`fn_perf_factor` 永远返回 NULL，
工资条上「绩效工资」永远是 0 —— 而这个 0 **看起来像「这个月没有绩效」**。

这是这个仓库里第四次同一个形态：`006` 的审批三张表、`010` 的 `fn_mcp_execute`、
`037` 的例外表、`026` 的绩效结果表。**对象存在但没有写入路径，等于没做**，
而且失败得比"报错"安静得多。

四条判据，各自对着一种「看起来对」的错：

| 判据 | 为什么 | 断言 |
|---|---|---|
| **打分即定档，系数不写** | 分数定了档才定系数。提前写系数 = 「系数在分数之前就定了」，而封存防的正是这个 | AQ1 / AQ6 |
| **定不了档就不许存** | 方案是人配的，缺口（60–89 空着）比越界更常见，也更晚才被发现 | AQ7 |
| **封存后不许改分** | 改分就是改已发的钱。触发器拦得住，但要有**名字**（`E_PERF_SEALED`，带封存人与时间） | AQ8 |
| **排除必须写原因** | 空原因的「不参与」与「忘了评」在报表上同形，而两者处置相反 | AQ5 |

AQ1 里那个 2.0 值得单说：它不是硬编码的期望值，而是**按周期结束日生效的那一版方案**
算出来的 —— v1（2026-01 生效）A 档 1.5、v2（2026-04 生效）A 档 2.0。
4 月的周期拿到 2.0，才说明取的是 v2。断言里直接查 `fn_perf_scheme_asof('2026-04-30')`
比对，而不是写死常量。

`v_perf_pending` 是这一组另一个产物：按「周期 × 周期内在职的人」展开，缺的标 `missing`。
**只看结果表的界面永远答不出「还差谁」** —— 而封存正好卡在这件事上：
3 人里评了 3 人和 30 人里评了 3 人，在「已评分 3」这个数字上完全一样。

界面上「绩效」页因此多了两块：录入（打分 / 设不参与）与待评名单。
默认打开的周期也从「id 最小」改成**「正在评的那个」**—— 一进来看到上季度已封存、
而要做的事在另一个周期里，那一屏等于白开。

### 工作台与探针：一个回答「今天做什么」，一个回答「还能不能干活」（H 组 5 条）

首页原来直接落在「考勤人日」—— 一上来就是一张明细表，读者不知道先看什么。
现在默认页是**工作台**：五个数字，每个都能点进去。

| 数字 | 来自 | 为什么是这个数 |
|---|---|---|
| 等我审批 | `approval.myTasks` | 只算**当前步**且属于我（或我代理的人）的待办 |
| 抄送我的 | `approval.myCc` | 抄送不产生待办，也就不产生权力 |
| 逾期例外 | `v_exception_overdue` | 例外必须有退出条件；逾期 = 改了规矩还没改回来 |
| 本期未封账 | `fn_att_unclosed` | 未封账 → 算薪门禁不放行（不是「提醒」） |
| 判据组未通过 | `fn_chk_coverage` | 含 `never_run` —— 没跑过不等于通过 |

关键不是这五个数，是**它们不许自己算一遍**：`/api/home` 调的是各服务同一个函数。
首页自己写一遍 `count`，就会立刻出现「首页说 3、点进去 4」这种两个都像对的差 ——
与看板层同一条规矩（看板不许自己 `sum`）。

`H4` 就是这条的断言：五个数逐个与各自接口比对。`H5` 证明**身份从会话取、不从参数取**：
拿 t3 的 token 带 `?user=2`，得到的仍是 t3 自己的 0。

---

探针是另一件事，而它是被一句注释欠下的债。`Dockerfile` 里当初刻意**不写** `HEALTHCHECK`，
理由写得很清楚：

> `/api/health` 需要 token，未认证是 401，拿它做探针会永远 unhealthy。
> 要么加一个不需要认证的 `/livez`，要么别加 —— 别加一个假的。

现在是前者：

```
GET /livez    只证进程活着（不查库：库挂了不该重启这个进程）
GET /readyz   查一次库；查不动回 503，让编排器把流量挪走
              只回 ok / db_ms / checks_known 三个数
```

为什么 `/readyz` 只回三个数：探针是**最容易被外部扫到**的地址。
表名、版本、连接串对外部没有用处，对攻击者很有用。`H2` 的断言里有一条正则，
专门查响应体里有没有 `pg_` / `sys_` / `postgres` / `version`。

`H3` 是配套的边界：免认证**只给探针**，`/api/attendance` 与 `/api/payroll/slips` 仍然 401。
「开一个口子」和「开一扇门」的区别，就在这条断言里。

顺带修掉一处「看着对、跑不起来」：`Dockerfile` 原先写 `COPY code/package.json`，
但它自己就在 `code/` 下 —— `docker compose up`（上下文 = `code/`）会直接失败。

### 换驱动：把「支持连接池」从一句话变成一份契约（D 组 8 条）

`app/db.mjs` 现在有两个驱动，而真库这条路本机没有 PG —— **跑不了**。
跑不了的路，至少要有**可判定的契约**，否则「支持连接池」就只是一句话。

写这一层的时候撞到的是一个**真实缺陷**，而且它只在并发下出现：

> 第一版 `withTx` 直接在单连接上 `exec('BEGIN')`。PGlite 只有一条连接，
> 于是 A 的 `BEGIN` 撞上 B 的 `BEGIN`（PG 只警告、不报错），
> B 的 `COMMIT` 把 A 尚未提交的写入**一起提交了**；A 再 `ROLLBACK` 已经晚了。

实测（改驱动前）：

```
表里的行: ["fast","slow"]   ← slow 那个事务明明 throw 了
```

单线程跑测试永远看不见 —— 所有 382 条断言都是顺序执行的。

修法不是加锁，是**让连接成为资源**：单连接驱动上排队（一个 promise 链做互斥），
池化驱动上取一条、用完归还，并在**每条连接**第一次使用时执行 `app_init_session()`
（临时表是会话的 —— 池里新开一条连接就是空会话，这正是 AE5 那个洞）。

| 断言 | 证明 |
|---|---|
| D1 | 并发事务互不污染：慢事务回滚后，它的行不该被别人的 `COMMIT` 带走 |
| D2 | 回滚不留痕 |
| D3 | 同一事务多条语句落在同一会话（pid 不变；四张临时表可写可读） |
| D4 | 抛错之后仍可开新事务并提交（没卡在「事务中」） |
| D5 | 事务外的单语句**不会插进**别人开着的事务（读不到未提交数据） |
| D6 | 池化驱动下并发事务拿到**不同**连接（PGlite 上如实标 SKIP） |
| D7 | 8 个并发 HTTP 请求：全部 200、行数一致不为 0（不死锁、不串权限） |
| D0 | 驱动选择（`pglite` / `pg`）在启动时就确定，不靠运行时猜 |

两处细节值得单独说：

- **`app_init_session()` 必须在 `BEGIN` 之前跑。** 临时表是 `ON COMMIT PRESERVE ROWS`，
  但如果它在事务里创建，那次回滚会把表一起删掉，下一条语句就是 `3F000`。
- **跳过不算通过。** 第一版把 SKIP 记成 `ok=true`，于是打出
  「断言 8 条 · 通过 8 · 跳过 1」—— 一个自相矛盾的行，正是这个仓库最反对的那种绿。
  现在汇总行分开写：`执行 7 · 通过 7 · 失败 0 · 跳过 1（跳过不算通过）`。

**仍未验证的**：真 PostgreSQL 这条路。`pg` 放在 `optionalDependencies`，
`DATABASE_URL` 存在时启用；换库之后必须重跑全部断言，尤其 `AE5`（临时表是会话的）
与 D1–D7。这话写在 `db.mjs` 的文件头，不写在博客里。

### 加签与抄送：结论 vs 通知（AP 组 8 条 + 接口 4 条）

041 转签是「换人」，045 代理是「代签」。还差两件事，而它们经常被混成一件：

```
加签：还要有人签   → 它改变审批能否推进，所以它是「决定」
抄送：还要有人知道 → 它不改变任何结论，所以它是「通知」
```

混成一个 `cc=true` 开关的后果很具体：抄送的人被算进「这一步还剩几个待办」，
流程永远差一个人；或者反过来，需要签的人只被通知了一声，单据就过了。

所以这里是**两张表、两条路径**：加签落 `approval_task`（`act_kind=countersign`），
抄送落 `approval_cc`（不参与任何推进计算）。

四条判据，都是「不加就会错」的：

| 判据 | 为什么 | 断言 |
|---|---|---|
| 只能加在**当前步** | 加到已结束的步骤，那次结算已经算过了，加了也不生效 | AP4 |
| 只能加在**还没人动过**的步 | 本步一旦有人通过，结算条件已成立；或签下剩余待办已被 skip | AP4 |
| 不能加**申请人** | 自审的另一个入口，与 032 启动时剔除申请人同一条理由 | AP2 / AP4（接口） |
| 必须写**原因** | 加签是「我临时改变了谁能决定这件事」，事后要答得出为什么 | AP5 |

**一条刻意的取舍**：加签**不校验**加签人的角色。
加签这个动作的语义就是「临时指定一个人来签，不管他平时是什么角色」——
能被加签的人，通常正是没有那个角色的人。校验角色等于禁止加签。
但「不能加给申请人」和「必须写原因」这两条不放松。

| 断言 | 证明 |
|---|---|
| AP1 | 加签后本步**不会**因为或签人点了就推进（`act_kind=countersign`），加签人签完才 approved |
| AP3 | 重复加签同一个人 → `E_APPR_ADDSIGN_DUPLICATE`（不是 23505） |
| AP6 | 抄送幂等（两次只一行），且**不产生待办** |
| AP7 | 抄送的人去审批 → 拒（「知道了」不等于「同意了」） |
| AP8 | 标记已读只能标自己那一条（别人的 → 403） |

界面「审批」页多了三块：待办表带**任务号**（加签要按任务号指定）、
「临时加签」表单、「抄送我的」清单（「知道了」即已读，记录不删）。

### 开放层的只读半边：同一个门的第二个入口（MS7–MS13）

010 只给了**写**一张门禁：没有 plan 就写不进去。只读一直是敞着的，
而只读恰恰是 AI 用得最多的部分，也是泄露真正发生的形态。

三个洞，一个修法：

| 洞 | 后果 | 修法 |
|---|---|---|
| 只读不落审计 | AI 读了 200 条工资条，一条记录都没有 | `fn_mcp_audit_read`：`shift_run=false` 也记 |
| 只读可能绕过掩码 | 页面掩了、开放层没掩 —— 掩码成了「页面上的装饰」 | 只读工具**不写 SQL**，调 `payroll.listSlips` |
| 只读可能绕过行闸 | AI 读到的行数与这个人自己看到的行数不一致 | 同上：调 `attendance.listDaily`，走同一张临时表 |

这不是「注意别写错」，是**把第二条路封掉**：开放层里没有一处自己拼的 SELECT，
于是它没有第二次机会把掩码写漏。

`affected` 的含义也随之分叉，这处细节值得单说：

```
写：affected = 这次影响了几行
读：affected = 这次返回了几行
```

一个只该看 2 行的人读到 200 行，这个数字会说话 —— 而「调用过一次」不会。
界面上因此多了一张「按调用者用量」：**限流挡的是频率，这张表看的是形态**。

第二个写工具 `headcount_set` 一并补上，为的是证明门槛没有偷偷降低：
它的 `preview` 必须回答**四个**问题（改前 / 改后 / 会不会超已下分 / 上级还剩多少），
而 `MS11` 证明摘要锁对第二个工具同样生效（预览 11、执行 99 → 拒）。

| 断言 | 证明 |
|---|---|
| MS7 | 同一条工资条，集团HR 经开放层看到净值，A店HR 拿到 `null`（不是 `0`，也不是明文） |
| MS8 | 只读也落审计，`shift_run=false`，`affected` 是返回行数 |
| MS9 | 写工具直接 read → 拒；只读工具去 plan → 拒（`E_MCP_TOOL_MISMATCH`） |
| MS10 | 预览给出四个数，不是「影响 1 行」的橡皮图章 |
| MS11 | 摘要锁对第二个写工具同样生效 |
| MS12 | 执行后额度真的变了（走的是同一条 `fn_hc_set`） |
| MS13 | 无授权账号经开放层读考勤 = 0 行，集团HR 读到 2 行 |

**一条边界写清楚**：`leave_balance` 只查调用者本人的额度。查别人的额度需要一条
「代理他人」的授权模型，而那套模型现在不存在 —— 收下 `employee_id` 却不校验，
比不收更坏（它会让人以为这件事已经管住了）。

### 代理：人不在，责任还在（AN 组 4 条）

041 的转签解决的是「**这一单**怎么办」。代理解决的是另一个问题：「我下周整周不在」——
每一单都转一次不现实。

三条判断：

| 判断 | 落法 | 断言 |
|---|---|---|
| **代批不改变责任人** | 待办的 `approver_id` 仍是原审批人，代理人只是被授权动手；另记一条 `act_by_delegate` 说明"谁按的手" | AN1 |
| **按业务日期判代理** | 代理区间 `daterange(...) @> 业务日期`，不是「今天」——补录旧单要找当时的代理关系 | AN2 |
| **代理有期限、不重叠、不代自己** | 上限 90 天（与 `HANDOVER_READONLY` 同一条判断）；排斥约束保证"现在谁在代理"唯一 | AN3 / AN4 |

AN1 里的那个细节值得单独说：**任务归属没变**。
把 `approver_id` 改成代理人看着更省事，但事后查"这单该谁审的"，会答成代理人 ——
那不是事实。责任留在原审批人身上，授权只体现在"他能动手"与那条日志里。

### 备份：一份能核对的文件，不是一句「已经备过了」（B5 条）

落盘（`PGLITE_DATA_DIR`）解决的是「重启不丢」，**不是「删错了能回去」**。
卷坏了、迁移写错了、有人 UPDATE 了一整列 —— 这三种都不是重启问题。

所以备份要做三件事，缺一件就不算备份：

| 要素 | 落法 | 断言 |
|---|---|---|
| **产物**：一个自包含文件 | `dumpDataDir('gzip')` → `.tar.gz` | B1 |
| **清单**：这个文件里**应该有多少** | 表数 / 函数数 / 14 张关键表行数 / sha256 | B1 |
| **可核对**：恢复之后拿清单去比 | `restore` 先验校验和、再装载、再比对 | B2 |

三种「看起来成功」的失败，各有一条断言：

- **B3 文件坏了**（改一个字节）→ `E_BACKUP_CORRUPT`，装进去只会得到一堆坏页。
- **B4 装错库了**（校验和仍对，但清单说 999 行）→ `E_BACKUP_MISMATCH`，
  **不做「尽力恢复」**——尽力恢复的结果是「一半的数据 + 看起来正常」。
- **B5 备的是空库**。没设 `PGLITE_DATA_DIR` 时 PGlite 会安静地建一个空库：
  备份「成功」、文件 4 MB、清单全 null。这种成功比失败更贵——出事那天才会发现。

一条边界写在工具的文件头：`dumpDataDir` 是**快照语义**，不包含备份完成之后的写入。
要严格一致请停服备份 —— 这句话必须写出来，不能只写「支持热备」。

```bash
npm run backup                                        # → backups/aihr-<时间>.tar.gz + .json
npm run restore -- --file backups/aihr-....tar.gz --to /data
```

**真跑过一次的完整链路**（不是只跑单元断言）：

```
起服务（PGLITE_DATA_DIR=/tmp/e2e-a）→ 把 A店编制从 12 改成 11（留个可辨识的标记）
→ 停服 → backup → 5.7 MB + 清单（74 表 / 132 函数 / headcount_budget=6 / sys_session=3）
→ restore --to /tmp/e2e-b → 核对通过
→ 从 /tmp/e2e-b 起服务 → 能登录（口令与会话都在库里）→ A店编制仍是 11 → 例外数据也在
```

这条链路里最容易忽略的一步是**从恢复出来的库起服务**：
只 `restore` 不看数据，等于只验证了"文件能解开"。

### 限流：跑飞的脚本要在第二秒就被挡住（AM 组 3 条）

到 042 为止，写路径有事务、行闸、业务码、留痕、一次性 plan —— 但**没有频率限制**。
一个跑飞的脚本能在 10 秒里开 500 张请假单，而每一张都「合规」。

三条判断：

| 判断 | 落法 | 断言 |
|---|---|---|
| **限写不限读** | 只统计写路径；读有行闸，且给读计数会让每次翻页都写一次库 | AM1 |
| **账在库里** | `app_request_log(actor, at)` 已有索引；放进程内存则重启清零、多实例各算一套 | AM1 |
| **被限的请求不写日志** | 写了就是自我放大：拒绝一次 → 多一条日志 → 更接近上限 → 拒绝更多 | AM2 |

阈值是配置项 `RATE_WRITE_PER_MIN`（默认 120/分钟）：一个人正常操作远到不了，
而脚本一秒钟就能撞上。AM3 是反向证明 —— 用量清空后**同一个操作立刻恢复**：
限的是频率，不是这个人。

代价写在代码里：被限的请求不进留痕，所以「被限了多少次」在请求日志里查不到，
要用 `v_rate_usage` 看各账号的实时用量来补。

### 请假要不要多步：做成配置项，并用反例证明它真的接线（AL 组 6 条）

到 041 为止，请假有两条审批路径：

```
单签  /api/leave/decide  →  fn_leave_decide_by   （一个人点一下）
多步  /api/approval/*    →  引擎（模板 / 会签 / 转签）
```

两条路同时存在，是这套代码里最明显的一处「同一个决定有两种实现」。
但**这件事不该我替客户选**：三个人小店要单签，三百人连锁必须多步 ——
「哪种假别必须多步」是管理决定，不是技术默认。

所以做成配置项 `LEAVE_APPROVAL`（`single` | `multi`），**默认值 = 上线前的实际行为**（单签），
并且**按业务日期取值**（与模板版本同一条规矩：补录旧单按当时的规矩办）。

| 断言 | 证明 |
|---|---|
| AL1 | `multi` 下申请**同一事务内**就开审批实例（不是「申请完再有人记得去发起」） |
| AL2 | `multi` 下从单签入口批准 → `E_LEAVE_USE_APPROVAL`，并指向正确入口 |
| AL3 | `multi` 下走引擎逐级批完 → 单据 approved（回写只在一处） |
| AL4 | 7 月改回 `single`：不建实例、单签照常可用 |
| AL5 / AL6 | 接口侧同一条反例：单签 409、引擎走通 |

**AL4 才是这一组的重点。** 配置项最常见的失败不是「没登记」，是「登记了但没接线」——
改了配置，行为不变，而报表上一切正常。所以这一组必须包含**改回来**的那一步：
6 月多步、7 月单签，同一套代码、同一个函数，只因为日期不同就走了不同分支。

顺带修掉一个显示 bug：制度页原来用 `Number(value)` 比较，枚举/文本项（`cascaded`、
`require_approval`、`single`）比较结果是 `NaN !== NaN` → **永远被标成「本单位覆盖」**，
而且值本身显示空白。接口现在同时回 `value_num` 与 `value_text`，页面按字符串比较。
这类「看不出错」的显示问题，比接口报错更难发现。

### 转签：审批人不在时唯一合法的出路（AK 组 5 条 + AR5）

审批人在**启动时**就解析成行（032）。这在正常路径上是对的，但必然遇到一个问题：
**审批人自己不在**（休假、出差、离职）。

三条"出路"，只有一条对：

| 做法 | 后果 |
|---|---|
| 管理员直接改 `approval_task.approver_id` | 改得动，但**没有痕迹**——事后答不出"这单为什么是他批的" |
| 让申请人重提 | 单据重来一遍，前面批过的人白批 |
| **转签**（`fn_appr_transfer`） | 记下谁转的、转给谁、为什么 |

四条判据：

| 判据 | 断言 |
|---|---|
| 只能转**自己的**、**当前步**的待办 | AK1（原审批人立刻无权处理） |
| **不能转给申请人** | AK2 —— 否则"启动时剔除申请人"那条就白写了 |
| 不能转给自己，且必须写原因 | AK3 |
| 日志只增不改 | AK4 |

**AK5 是跑出来才发现的**：转给"这一步已经在等他审的人"时，撞的是
`uk_at_inst_seq_approver` 唯一约束，前端只看到 `23505 / CONFLICT`。
现在它有一个名字：`E_APPR_TRANSFER_DUPLICATE`（"他已经是这一步的审批人，不需要转签"）。
这类"约束挡住了，但错误说不清原因"的位置，每一处都值得补一条有名字的拒绝。

**没做**：加签（同一步临时增加审批人）、代理（区间内由他人代审）、抄送。
`approval_task_log.action` 已预留 `addsign` / `cc` 取值，但那是产品面
（谁能在什么条件下加签、代理要不要审批），先编一个默认比不编更坏。

### 强制改密：把「建议改密」变成「不改就用不了」（AW 组 5 条）

035 把口令做进了库，`must_change` 列也留了，但**没有任何东西读它** ——
于是种子口令永远有效，而它会出现在每一份交接文档里。

两条判断：

| 判断 | 落法 | 断言 |
|---|---|---|
| **未改密就用不了** | 除 `/api/me/password` 外一律 428（Precondition Required）；200 + 提示语会被前端忽略 | AW1 / AW3 |
| **改密要踢掉旧会话** | 改密成功 → 吊销该账号其余会话，只留当前这条 | AW4 |

AW4 是这一组真正的重点：改密的动机通常是「口令可能泄露了」，
而旧 token 还能用到 12 小时后 —— 那么「改密」只是心理安慰。

还有两个细节：

- **428 不是 403。** 403 会让用户以为权限不够，于是去找管理员 —— 而他并不需要管理员。
- **改密接口必须走同一套失败计数**（AW2）。否则它就是一个不需要锁定的口令试错通道。

| 断言 | 证明 |
|---|---|
| AW1 | 临时口令登录 → 其它接口 428 `E_PWD_CHANGE_REQUIRED` |
| AW2 | 旧口令错 → 401 `E_AUTH_BAD_CREDENTIAL` |
| AW3 | 改密成功 → 当前会话继续可用，接口从 428 变 200 |
| AW4 | 旧会话立刻 401 `E_SESSION_REVOKED`，新口令能重新登录 |
| AW5 | 新旧口令相同 → 422 `E_CRED_SAME`（「改了个寂寞」比不改更坏：它让人以为改过） |

### 导出：掩码最常破的地方（AV 组 3 条）

字段掩码在列表页做对了，**导出忘了** —— 这是数据泄露最经典的一条路径，
因为导出的文件会被转发，而它看起来"只是一份表格"。

所以这里的做法不是"在导出里再掩一次"，而是**复用同一个 `listSlips`**：
掩码只有一份实现，导出只是换了个输出格式。

| 断言 | 证明 |
|---|---|
| AV1 | 同一批次导出：集团HR 有净值、A店HR 该列为空（不是 `0`，也不是 `***`） |
| AV2 | **源码扫描**：export 段里没有 `fn_field_action` / `fn_apply_mask`，只调 `listSlips` |
| AV3 | 导出必须认证（无 token → 401） |

空列而不是 `0`：CSV 会被程序读，`0` 会被当成真实金额，`***` 会让整列变成字符串。
这是 `fn_apply_mask` 那条"掩码返回 NULL 不是 0"在文件格式上的同一个判断。

### 例外：必须有退出条件（AJ 组 6 条 + AU 组 2 条）

这套系统里已经出现过几次「临时放开」：超编走审批通道、判据豁免、跨期补账。
它们的共同点不是"允许例外"，而是**例外必须带一个"什么时候结束"**。

没有退出条件的例外不是例外，是**改了规矩而没人说**。

| 判断 | 落法 | 断言 |
|---|---|---|
| **`expires_at` 不许为空** | 建例外就必须给天数；期限为 0 直接拒 | AJ1 |
| **期限有上限，超了就拒** | 不是静默截断——截断会让人以为自己批了 90 天 | AJ2 |
| **必须有责任人** | 没人认领的例外没人会去关 | AJ3 |
| **关闭 = 写三件套，不是删行** | 删行后「这里曾经有过一个例外」就消失了，而那是复盘要看的东西 | AJ4 / AJ5 |
| **到期必须看得见** | `v_exception_overdue`，带逾期天数；接口把它暴露出来 | AJ6 / AU1 / AU2 |

AU2 是一条容易被忽略的判据：逾期清单与生效清单**必须互斥**。
一条例外同时出现在两边，意味着「还剩几天」有两个答案，而两个都"看起来对"。

五种例外类型的上限是**写死的业务判断**，不是技术默认：
超编放行 90 天、判据豁免 30 天、考勤补账 60 天、手工调薪 7 天、结算差异容忍 30 天。
改这个数就是改管理口径 —— 所以它在表里，不在代码里。

### 认证：门锁很好，门是开的（AT 组 6 条）

会话那一节（AH）把「token 怎么存、怎么过期、怎么吊销」做完了。而在这之前
`/login?user=3` 就能拿到 user 3 的令牌 —— **认证这一层根本不存在**。

四条判断：

| 判断 | 落法 | 断言 |
|---|---|---|
| **口令不进库** | 库里是 `scrypt$N$r$p$salt$hash`，校验在应用侧（PGlite 没有 pgcrypto） | AT4 |
| **计数在库里** | 失败次数与 `locked_until` 落在 `sys_user_credential`，不在进程变量里 | AT3 |
| **锁定期间正确口令也进不去** | 先判锁定、再验口令（反过来写，猜对的那一次照样能进） | AT3 |
| **错口令与「没这个账号」回同一个码** | 分开就等于送一个「账号是否存在」的查询接口 | AT2 |

写的时候踩到一个**只有跑起来才会发现**的坑，而且是这个仓库里同一类错的第三次：

> 第一版 `fn_auth_result` 在失败时 `RAISE EXCEPTION`。于是外层事务回滚——
> **「又错了一次」这个事实随回滚消失**，`failed_count` 永远停在 1，永远锁不住。

修法不是加一个 `COMMIT`（做不到），而是把**入账与裁决分开**：
`fn_auth_result` 只入账并返回 `ok / bad / locked`，提交之后再抛错误码。
和 027 那条「失败留痕必须写在事务外」是同一个道理，只是这次账在表里。

| 断言 | 证明 |
|---|---|
| AT1 | 正确口令 → 200 拿 token |
| AT2 | 错口令 → 401 `E_AUTH_BAD_CREDENTIAL`（与「没有这个账号」同码） |
| AT3 | 连错 5 次 → 423 `E_AUTH_LOCKED`；锁定期间**正确口令也是 423** |
| AT4 | 库里没有明文；同一口令两次派生结果不同（有盐） |
| AT5 | 摘要必须带算法前缀（库判）；长度按策略拒（应用判） |
| AT6 | 重置口令 → 计数清零、锁定解除 |

**演示口令 `demo1234`，四个身份共用。** 它写在种子里、也写在界面上 ——
因为「藏在代码里的默认口令」比「写明白的演示口令」更危险：
前者没人会记得换，后者每个人看一眼就知道该换。

### 开放层：AI 不能直接改数据（MS 组 6 条）

`010` 写了 `fn_mcp_execute` 的五条门禁（无 plan / 工具不符 / 摘要不符 / 过期 / 已用 / 超阈值），
但**没有任何客户端走它** —— 也就是说，在这个切片里，AI 想改数据仍然可以直接 UPDATE。

补上接口层之后，规矩才真的成立：

```
POST /api/mcp/plan     tool + args  →  sys_mcp_plan 一行（工具名 + 参数摘要 + 影响面 + ttl 300s）
POST /api/mcp/execute  plan + args  →  fn_mcp_execute 过六条门禁 → 才调业务函数
GET  /api/mcp/tools    目录里只列真的接上了的工具
GET  /api/mcp/audit    每次写入一条审计
```

三条判断：

| 判断 | 落法 | 断言 |
|---|---|---|
| **摘要与键序无关** | 规范化 JSON（键排序）再取 sha256 | MS5 |
| **预览要给出影响面** | `preview()` 返回 affected_count 与逐行 diff，落进 plan | MS3 |
| **目录只列真接上的工具** | 放一个没实现的工具进目录，AI 会拿到「成功」而数据没变 | MS1 |

| 断言 | 证明 |
|---|---|
| MS2 | 没有 plan 直接执行 → 409 `E_MCP_NO_PLAN` |
| MS3 | 预览（影响 1 条）→ 执行 → 单据真的建了 |
| MS4 | 同一个 plan 执行第二次 → 409 `E_MCP_PLAN_USED` |
| MS5 | 预览 1 天、执行 3 天 → 409 `E_MCP_ARGS_CHANGED` |
| MS6 | 每次写入落一条审计（`shift_run=true`） |

写的时候撞到一个 PGlite 细节：`args_digest` 是 `bytea`，传 `'\x...'` 字符串会在
**参数绑定处**报 `Invalid input for bytea type` —— 那个错发生在发送前，看起来像服务故障。
必须传 `Buffer`。这类"类型不匹配伪装成服务故障"的错，只有真跑才会遇到。

### 看板层：先异常、再总量（AB 组 7 条）

看板不是"把指标排一排"。指标排一排的结果是二十个数字，**没有一个告诉你今天该做什么**。
所以顺序是有讲究的：

```
① 异常（今天要处理的事）—— 看完可以关掉页面
② 总量（规模与趋势）    —— 决定要不要往下看
③ 明细（点进去）        —— 只有前两层出了问题才需要
```

两条硬判据，缺一条看板就会变成装饰：

| 判据 | 断言 | 为什么 |
|---|---|---|
| **异常清单每类都出行，含 0** | AB1 | 只列非零项的仪表盘，在"全部正常"与"根本没检查"之间**没有区别**——两者都是一片空白，而空白最容易被读成"没事" |
| **看板不许自己再算一遍** | AB2 / AB3 / AB5 | 看板里写 `sum(work_hours)` 很自然，但那会立刻产生第二份实现：看板 1240、报表 1238，两个都像对的，而核对它需要有人同时打开两个页面并起疑心 |

| 断言 | 证明 |
|---|---|
| AB2 | 看板的数与明细行数一致（超编 1/1、未配编 5/5） |
| AB3 | 日报逐日相加 **==** 月报（同一个月报与日报共用一个 `fn_rpt_hours_between`） |
| AB4 | 各区之和 == 集团总（人数 6/6、工时 0/0） |
| AB6 | 「缺确认单的段」单独成行：有单的日子是 0，缺单的日子是缺陷 |
| AB7 | 告警类数 = 非零类数（6/9），不是把 9 类都算成告警 |

顺手做了一次**口径收敛**：原来 `fn_rpt_hours` 直接按自然月过滤，门店日报又要"某一天"。
如果各写一遍，就会出现"日报加起来不等于月报"，而两处都自洽。
现在内层是 `fn_rpt_hours_between(org, from, to)`，月报只是它的一次调用——AB3 就是用这条判据验的。

### 报表层：三路径交叉核对（AA 组 9 条 + 接口 2 条）

报表层最典型的失败不是"算错"，是**同一个指标有三份实现**：集团看板一遍、
门店日报一遍、导出再来一遍。三份都"看起来对"，而它们之间的差没人核对过——
直到有人问"为什么这两个数不一样"，那时才发现有三份是旧口径，**而没有任何一处在报错**。

三条纪律：

| 纪律 | 落法 |
|---|---|
| 一个指标只有一份实现 | 一个函数，报表引用它，不重写它 |
| 口径必须显式 | 比率类必须给分母；时点类必须给基准（期初/期末/日均） |
| **交叉核对** | 同一总量用三条互不相同的路径算，必须相等 |

| 断言 | 证明 |
|---|---|
| **AA1** | 工时：`A 子树一次算` = `B 叶子分别算再相加` = `C 明细直接求和` |
| AA2 | 人数同上（证明"按组织分组"没有漏行、也没有重复计数） |
| AA3 | 人数不声明基准 → 报错（**没有默认值**） |
| AA4 | 月中入职一人：期初 4 / 日均 4.5 / 期末 5——**三个不同的量，不是一个数换名字** |
| AA5 | 面板里没有未登记的指标 |
| AA7 | 空期间仍出 7 行且为 0（省略行会让"这个月是 0"与"这里没有这个组织"同形） |
| AA8 | 报表函数不含 `current_date`/`now()`（含了的话"上个月的报表"永远复现不出来） |

**AA3 是本组第一次跑就抓到真错的一条。** 我写的守卫是 `IF p_basis NOT IN (...)`，
传 `NULL` 时它求值为 **NULL 而不是 true**，于是 `IF` 不进分支——**守卫自己被 NULL 绕过去了**，
接下来 `ELSE` 分支静默按"日均"算。断言说"不声明基准要报错"，实际返回了一个数。
这正是"`NOT IN` 含 NULL 恒空"那条，犯在我自己的守卫上。

### 编制与人力预算：逐级下分（Z 组 14 条）

编制不是"人数上限"这种技术参数，它是**资源分配**：集团批 1000 个编，区域拿 200，
门店拿 40。谁多拿一个，谁就少一个。所以这一层的核心不是"拦住超编"，
是**把分配关系本身表达对**。

**口径已定：逐级下分**（`HEADCOUNT_MODE = 'cascaded'` 是默认值）。
`group_pool`（集团一个池子）保留为可选，默认关闭。

| 断言 | 证明 |
|---|---|
| Z1 | 子项之和超过父项 → 拒（**下分是分配，不是复制**——"给区域 100"不是"每家店各 100"） |
| Z3 | 占编由归属**派生**，不落列 |
| Z4 | 额度表里没有 `used` 列（存了就会被入职/离职/调动三条路径各改一次，必然漂） |
| Z5 | 调编走**追加版本**：现额度 1，历史版本 v1=6 仍在 |
| Z7/Z8 | 就地改额度 / 删版本 → 拒。改了它，**上个月超编的事实会随着额度调高而消失** |
| Z9 | 没配额度的组织被单独列出（否则"忘了下编"与"编制充足"同形） |
| Z10 | 超编走审批通道时放行但留痕（谁、依据、插入那一刻的占用） |
| Z11 | 口径改成 `reject` 后，同样的超编写入被拒（口径是配置项，不是写死的策略） |
| Z12 | `group_pool` 模式下额度只在集团层，给下级下编 → 拒 |
| **Z13** | **「可下分」与「可招」是两个数**：C店（叶子）可下分 1，可招 −2（已超编）；西南区（父节点）10 − 已下分 4 − **直属** 0 = **6**，不拿子树那 4 人再扣一遍（178） |
| **Z14** | **三层「可招」都 ≥ 0**：集团 20−20−0=0、华南区 20−20−0=0、F店 8−0−5=**3**（缺 3 个）、G店 12−0−12=0（满编）。★ 这个数回到「还能招几个」的意思——缺岗为正、满编为 0、**超编才为负** |

Z13 是这一组里最容易被忽略的一条：`available = quota − 已下分`，`hireable = quota − 已下分 − 直属在编`。
把它们混用，一个区域"还能往下分 3 个"会被读成"还能招 3 个"，招到第 2 个就超编，**而每一步都合规**。

`hireable` 里"已占"必须是**直属**，这一条是 178 修的（`178_hc_hireable_direct.sql`）：
`allocated` 是**直接子节点**额度之和，`used` 是**子树**人数 —— 在父节点上这两个数覆盖的是同一批人，
相减必然为负，而且**补编补不掉**（要让集团非负，额度得 ≥ 已分 + 在编 = 762，等于编制翻倍）。
在此之前 `022_headcount.sql:132` 的注释写的就是"**自身**已占"，实现却是子树 —— 是代码与注释不符，
所以修法是把实现改回注释，不是改注释。

**两个口径相反，而且都对，别混**：

```
缺岗（slack / 组织页那一列） = 额度 − 子树在编      ← 额度是下辖之和，人数也必须用汇总
可招（hireable）            = 额度 − 已下分 − 直属在编 ← 额度已扣过下级，人数只用直属
```

一句话：**额度是汇总 → 人数用汇总；额度已扣过下级 → 人数只用直属。**
在父节点上"缺岗"和"可招"会同时出现一个很大的正数和一个 0，它们不矛盾——只是在回答两个问题。

还有一条设计判断写进了文件头：**超编不由系统假装不存在**。真实业务里超编一定会发生
（并购、旺季、交接期）。只做拒绝的结果是把人挂到别的门店去——**数据变干净了，事实没有变**。
所以超编要么先调编，要么带依据走审批通道，且两者都可查。

### 集团制度下发与门店覆盖（Y 组 12 条）

组织授权解决的是"**谁能做什么**"。集团统一管理的另一半是**制度本身统一下发**。

这一层最常见的错法是"每家店一张配置表，集团给个默认值"——那不是统一管理，
那是**没有管理**：默认值一旦可被任意覆盖，集团改一次口径，几十家店各按各的旧值跑，
而每一家都能说"我这是配置的"。

所以有两层，缺一层都不成立：

| 层 | 内容 | 断言 |
|---|---|---|
| ① | 集团发布制度值（带版本、带生效日），未覆盖单位**立即跟随** | Y4 |
| ② | **"这一项允不允许被覆盖"由集团逐项声明**，不是所有项都能改 | Y7 / Y8 |

② 是最容易被省掉的一层。如果任何项都能被门店覆盖，"集团统一"就只是一句默认值——
而"哪些必须统一、哪些可因地制宜"**本身是一个管理决定**，不能由技术默认成"都能改"。

| 断言 | 证明 |
|---|---|
| Y2/Y3 | 覆盖只沿自己的祖先链生效，**不横向传染**到兄弟单位 |
| **Y7** | 集团改成"不许覆盖"后，存量覆盖**存在但不生效**，且被单列出来 |
| Y8 | 覆盖层级：`floor=region` 时门店自己改的不生效，区域改的生效 |
| Y9 | 集团改值前能报出影响面：**跟随 N 个 / 已覆盖 M 个，两个数都要** |
| Y11 | 制度真的接到了口径上（`fn_att_default_basis`） |
| **Y12** | 制度变更**不改变已写入的行**——口径是快照事实，不是读取时现算的缓存 |

Y7 是这一组里最要紧的一条：**开关一关，一批两年前的旧值会同时复活，而那天不会有任何人预期到。**
所以"存在但不生效"必须能被单独列出来，不能靠"反正读不到"。

Y12 是接线的底线：制度只在**写入时**生效，写进去之后由 `snap_on_duty_break_basis` 固化。
若在读取时按当前制度现算，集团改一次口径会把去年已经按老口径发过钱的工时也改掉。

### 组织级授权：集团统一管理（W 组 9 条 + 接口 X 组 4 条）

前面所有授权的主体都是**账号**。那适合"每家店各管各的"，不适合集团：

> 集团把「门店 HR」这个角色授给**华东区**，华东区下 47 家门店的 HR 应当全部生效，
> 而不是让实施把 47 条授权逐条敲一遍。
> 更麻烦的是新开一家店：逐条授权下它**不会**获得任何权限，
> 症状是"新店 HR 登录进去什么都看不到"——看起来像账号配错了。

所以授权主体有两类：**账号**与**组织**。

| 断言 | 证明 |
|---|---|
| W1 | 授在华东区(30) → A店(10) 的人**继承**到 |
| W2 | 授在 A店(10) → 华东区(30) 的人**不**继承（方向单向） |
| W3 | 每条权限带 `direct` / `org@组织`（审计要回答"他为什么有"） |
| W4 | 到期即失效，靠**时点派生**，不靠定时任务改状态 |
| W5 | 撤销是显式事实（`revoked_at`），不是删行——删行会让"这里曾有过授权"消失 |
| W6 | 组织停用 → 授权失效，且**停用前能报出影响面**（几条授权 / 几个账号） |
| **W7** | 组织授权**真的灌进了行闸**，不只是登记一条记录 |
| W8 | 同一角色两条来源都留着（解释得清），而灌入行数不变（分母不虚高） |

W7 是这一组的要害：判据写了不接线，等于没写。`app_begin_scope` 原来直接读
`sys_user_role`，现在读 `fn_effective_roles`——**组织授权会真的改变一次查询的结果**。
改完之后 A 组 16 条断言仍全绿，说明改造没破坏既有行为。

界面上加了一个「门店 HR（组织授权）」身份：它在 `sys_user_role` 里**一行都没有**，
权限全部来自"挂在 A 店 → 华东区被授权"这条链，「我的权限」页签会显示 `组织继承 · 经由 华东区`。

### 外包协同：两份数才是对账（V 组 12 条）

两个结构性判断写在文件最前面，后面所有东西都由它们决定：

**① 外包人员不是 `person` 的一种。** 建成 `person` 的话，所有"按 person"的清单
（个税、社保、工资条、编制）会**自动包含**他们，而排除要靠每个查询记得加条件——
加对 12 处，第 13 处会忘，忘了的表现是"外包工出现在个税名单里"。独立表意味着
**排除是默认，包含才需要显式写**。

**② 真对账需要两份独立的数。** 同一张表存"我方/对方"两列那不是对账，是自洽性检查——
它只能发现录入错误，发现不了"我们记的班次不一样"。所以两份表、两条写入路径。

| 断言 | 证明 |
|---|---|
| V2 | 供应商账号的 RLS 隔离（`SET ROLE` 成非超级用户才测得出来） |
| V3 | 未设会话变量 → 0 行（fail-closed，不是全表） |
| V4 | 差异三种形态分开报：`only_ours` / `only_theirs` / `hours_differ` |
| **V5** | **两份数各自保留**：我方 22h/660 元、对方 13h/390 元——不取平均、不取小、不取大 |
| V6 | 有差异的单不可确认（差异不会被"顺手结掉"） |
| V8/V9 | 已确认不可改金额、不可退回 draft |

V5 是这一组的原则：**取任一边都是替双方做了一个他们没有同意的决定，而单据看起来是完整的。**

写的时候抓到一个 PG 细节：「缺失」在会话变量里有**两种形态**——从未设过是 `NULL`，
设过又 `RESET` 是**空串**。只判 `NULL` 时，第二种会在 `::bigint` 上直接报错，
而报错会被上层 catch 成 500，看起来像服务故障而不是"没登录"。

### 验收体系接电（T 组，6 条 + 接口 U 组）

`002` 建了登记表、`fn_chk_coverage` 也写好了，但**从来没有东西往里写过一行**——
所以覆盖率永远是 `never_run`。一个从不上报的报表，与没有报表在效果上相同，
而它更坏的地方是：**它长得像一个已经在跑的东西**。

`018` 补了三件：唯一写入口 `fn_chk_record`、19 组判据的登记、四桶汇总。

| 断言 | 证明 |
|---|---|
| T1 | 每组断言都写进了 `sys_check_run`，**写入失败也不许吞** |
| T2 | 覆盖率对这 16 组不再是 `never_run`，全部落 `pass` |
| T4 | 未登记的判据 → 拒绝记录（否则留下没人读的结论） |
| T5 | 记 `skipped` 会被"黄必须有人认领"拦住——**两条约束的交叉，不是设计的** |
| T6 | 四桶分开报，不给"通过率 95%" |
| U1 | 接口四组同样入库（否则 M/N/O/S 永远 `never_run`） |

**组号必须分域**：数据库侧 `SUITE.X`，接口侧 `SUITE.API-X`。早先两侧都用 `SUITE.M/N/O`，
于是"接口的 O 组"覆盖了"数据库的 O 组"——**覆盖率仍然显示 pass，因为最后写进去的那次是绿的**。
撞号不会报错，它只会让一组判据的结论凭空消失。

接线时判据自己抓出一条真错：`sys_check_run.id` 没有生成方式，`fn_chk_record` 一插入就撞主键——
**这正是 Q14 要抓的那一类**，而它是在接线的同一刻变红的。

**"自检"页签只读登记表，不跑断言。** 跑是 CI 的事，看是这里的事——
两者混在一起会出现"为了看一眼就顺手跑一遍"，而跑一遍会改结论。

### 组织树版本切片（R 组，9 条）

`014` 解决了"某一天他在哪个 org"，但 **org 这棵树本身没有版本**：

```
2026-03  A店属于 30(华东区)
2026-09  区域重组，A店改挂 31(上海大区)
现在查 "2026-03 这个人属于哪个区"  →  返回 31，而 31 在 2026-03 还不存在
```

报表会显示"华东区去年三月业绩为零"，每一行都能追到，每一行都是错的。

| 断言 | 证明 |
|---|---|
| R1/R2 | 时点切版本：8/31 挂 30，9/1 挂 31（生效日当天即变） |
| **R3** | **改完树之后查 2026-03，答案仍是 30** |
| R4 | 早于第一个版本的时点 → 报"不可判"，**不静默用当前值顶替** |
| R5/R6 | 已发布版本的快照不可增改（历史只能新增版本，不能补写） |
| R7 | 已发布版本的生效日不可改（改它＝把过去整体换一版，报表不报错只换数） |
| R8/R9 | 发布最新版必须覆盖现行树，缺节点即拒并点名 |

解法不是给 `org_unit` 加历史列，是**整棵树按版本快照**：一次重组 = 一个新版本 = 一份完整快照。
**历史不是被维护的东西，是没被改写的东西。**

一条边界也写进了代码：完整性检查**只对最新版**成立。用今天的要求去检查 2026-01 那版，
会得到一条永远修不好的红——它缺的节点那时根本还没拆出来。

### 考勤封账：时间边界（Q 组，15 条 + 接口 4 条）

同一条考勤人日，封账前后不是"权限不同"，是"它还算不算数"不同。

| 断言 | 证明 |
|---|---|
| Q1 | 有考勤但未封账 → **算薪被拒**，且点名是哪家店（不是"先按未封账数据算着"） |
| Q2 | 封账冻结了一个**可复核的数**：行数 / 工时 / 摘要，三样都进表 |
| Q4–Q6 | 封账后 INSERT / UPDATE / DELETE 考勤全拒（只测 UPDATE 是固定漏洞） |
| Q7 | 封账改回 `open` → 拒（每一步都是合法 UPDATE） |
| Q8 | **删掉封账行** → 拒（删一行＝解封，且不留"这里曾封过"的痕迹） |
| Q10 | **关掉触发器**改数据 → 摘要抓得到；还原后校验回空 |
| Q11 | 补账只能往后（`apply_period > 工作月份`），结构上无法追溯修改 |
| Q12 | 补账理由空白 → 拒（空格能通过 `NOT NULL`） |
| Q13 | 封一个没有考勤的期间 → 拒（否则日后填数据只能解封） |
| Q14/Q15 | 机器判据：会被函数 INSERT 的表主键必须有生成方式；且分母非空 |

**Q10 是这一组里最要紧的一条。** 只有触发器时，"封账后没人改过"是一个**没有证据的断言**——`ALTER TABLE ... DISABLE TRIGGER` 一句就能改，改完一切看起来正常。只有摘要时，改本身拦不住。两条合起来才是：**拦得住，且拦不住的也查得出。**

### 算薪全流程：走真钱（P 组，8 条）

| 断言 | 证明 |
|---|---|
| P2 | 应发 = 月薪 8000 − 事假 735.63 = 7264.37（只认 approved 的天数） |
| P3 | 社保 = 夹逼后基数 × 8% = 640，**基数不因请假而变** |

这是切片，不是服务。

## 五、通过「真跑」发现的缺陷（读文档发现不了的）

这十条都是**执行才暴露**的。前六条在数据库层，后四条全在**应用层** ——
而应用层的四条有一个共同点：它们只会在「第一次真正走到那条分支」时出现，
演示与手工点测都走不到。

1. **`app_begin_scope` 按原文建不出来。** `04` 原文写 `END $$ LANGUAGE plpgsql;`，而 `LANGUAGE plpgsql` 在 `AS $$` 之前已声明一次 → `42601 conflicting or redundant options`。正确是 `END;` + `$$;`。已修文档。
2. **四张会话临时表没人创建。** 文档只写函数里 `TRUNCATE pg_temp.tmp_scope_*`，没写谁建。不建则第一个请求报 `3F000 invalid_schema_name`——而这个错误看起来像 schema 权限问题，不像"少建一张表"。已补 `app_init_session()`，并做成断言 A0。
3. **7 天 / 90 天上限无承载列。** `TEMP_ACT_AS` 原本可授十年，插入成功、不报错、不进任何红。已补 `ck_ur_kind_span`，断言 A8/A8b/A8c 覆盖拒绝侧、边界内、以及"ROLE 不受限"。
4. **`guard_kind varchar(8)` 装不下它自己的合法值。** 合法值是 `'CONSTRAINT'`（10 字符）——**这一列永远存不进约束类守卫**，而错误只在插入时报 `value too long`。已放宽到 16。这条是「列宽与它自己的 CHECK 值域不自洽」，读 DDL 几乎不可能看出来。
5. **覆盖率视图用了 `current_date`，同一个查询换一天两个答案。** 我在 `fn_chk_effective` 上已经修过这个毛病（改带参函数），视图里又犯了一次。已改成 `fn_chk_coverage(as_of)`，B8 用固定日期断言。
6. **入口函数的歧义保护被自己的断言取消。** 原设计靠 `p_fact_from DEFAULT NULL` 让旧两参调用报歧义错；但同节断言要求 `count(*)=1`，只剩一个函数时两参调用静默取 NULL。两者互斥。已删默认值、断言改 `pronargdefaults = 0`（A1 覆盖）。
7. **`pay_run.id` 没有生成方式，而那条 INSERT 从来没有测试走过。** 第五次同一个坑：Q14/Q15 只扫「被**库函数** INSERT 的表」，而 `pay_run` 是**应用层**插入的。它一直没红，因为种子总是先给一个批次、测试永远命中「批次已存在」分支。第一次真正走到 `INSERT` 就是 `23502 not-null violation on id`。⇒ 断言要覆盖**首次**分支（AG3 就是那条），不只是重复分支。
8. **写路径的行闸查错了表。** `payroll_legal_entity` 的 `kind` 是 `entity`，它的范围落在 `tmp_scope_entity`，而 `requireOrg` 第一版只查 `tmp_scope_org` → 集团 HR 算自己的薪被判 **403 越权**。修法是按 `sys_perm_dim.kind` 分支，不是加一个 `IF`。
9. **写路径漏登记的资源码会让接口直接 500。** `app_begin_scope` 第一个动作是查 `sys_perm_resource`，未登记就 `E_RESOURCE_UNREGISTERED`。加算薪/招聘/绩效/编制/结算五个写入口时漏登记，症状是「接口 500」，看起来像服务故障。已补 `028`，并用 AG0 做差集守着。
10. **断言组没登记，结论写不进登记表，而报告上它只是「不存在」。** 新加 AG 组后 `fn_chk_record` 报 `E_CHK_UNREGISTERED`——**这个设计是对的**（不许跑没人知道的检查），但它自己的失败形态是「静默少一组」。已补 `029`。

## 六、两条不能违反的工程纪律

1. **`executed` 必须如实报，且带版本与时刻。** `1031/1032 通过`（609 数据库 + 305 接口 + 4 持久化 + 5 备份 + 8 契约通过 / 1 跳过 + 40 界面 + 23 全生命周期 + 7 多门店多法人 + 21 权限矩阵 + 9 工资单打包；另有 11 条「档口范围」断言单独跑，不进这个合计）的含义是「在 PostgreSQL 18.6 上、这些断言通过」，不是「系统正确」。设计基准是 PG 16，换版本要重跑。
2. **断言条数不许手抄。** 本文件里的条数由 `node test/run.mjs` 的输出填，不心算、不顺推。**作者本人已因此错过两次**（16→扩 B 组 9 条写成 26；44→扩 F 组 7 条写成 52）。这条不是提醒别人，是提醒写这段话的人。
3. **断言必须钉到具体表达式，不许钉"对象存在"。** 例：不是"约束存在"，而是 `pg_get_constraintdef` 里 grep 到 `round(` 而不是 `abs(`。**建不起来是好消息，建起来了但建错了才是要测的那件事。**
