# 21 · 工资调整单（人为调整 · 历史版本 · 按月 · 导入覆盖）

> 对应迁移：`106_salary_adjust.sql`、`107_adjust_midmonth.sql`
> 对应代码：`app/index.html`（`viewAdjust`）、`/api/salary/adjustment*`
> 对应断言：`run.mjs` 的 SAL1–SAL3、`ui.test.mjs` 的 UI16

## 1. 为什么是"单"而不是一次 UPDATE

现实里"这个月给谁调多少"是一张单据：**谁调的、从多少调到多少、为什么、什么时候生效**。
四件事缺一件，一个月后就没人说得清"他这 14500 是怎么来的"。

所以：

| 关心的事 | 存在哪 |
|---|---|
| 当前薪资是多少 | `salary_standard` + `salary_structure_item`（按 `effective_from` 天然带版本） |
| 某次是谁改的、从多少到多少、为什么 | `salary_adjustment`（before/after 快照 + 原因 + 来源） |

**调整单不改当前值**，它只解释历史。当前值在"应用"那一步才被写。

## 2. 数据形状

```sql
salary_adjustment(
  code            ADJ-202611-0001
  period          2026-11
  person_id, employment_id
  before_monthly  14500.00      -- 建单那一刻的月薪
  after_monthly   13000.00
  before_items    [{item_code, amount}, ...]   -- 建单那一刻的结构
  after_items     [{item_code, amount}, ...]
  delta           -1500.00
  source          manual | import
  reason          测试后调回原薪资
  status          draft | applied | cancelled
  created_by/at, applied_by/at
)
```

## 3. 三条硬规矩

### 3.1 只能拆固定项

调整单填的是"结构"（基本工资/岗位津贴/餐补/通讯），不是"结果"。
把个税、社保写进结构，会让**政策**变成**约定** —— 下个月社保比例变了，那个数不会跟着变。

`E_SS_ITEM: 调整单只能填固定工资项（收到：IIT）`

### 3.2 应用不可回退

`draft → applied` 是单向的。要改就再开一张。

理由：允许改已应用的调整单，等于允许改历史工资的解释，而工资条已经发出去了。
（`E_ADJ_NOT_DRAFT: 调整单 ADJ-202611-0001 当前是 applied，只有草稿能应用`）

### 3.3 导入覆盖也走单据

工资表导入（每人金额）应用时，**为每个人生成一张 `source='import'` 的调整单**。

否则会出现："手工调的"有 before/after 痕迹、"导入覆盖的"没有 ——
而后者一次能改几十个人，出事时更该查得到。

## 4. 按月：生效日在期间首日，判断在职用期末

这两个容易混：

| | 用哪个日期 | 为什么 |
|---|---|---|
| 调整**生效** | 期间**首日**（11-01） | 与 `salary_standard.effective_from` 一致，10 月算薪读不到 |
| 判断**是否在职** | 期间**期末**（11-30） | 11-14 入职的人在 11-01 还不存在，但他的 11 月工资恰好最需要调 |

107 修的就是这个：106 用首日判断，导致"月中入职的人调不了薪"，而报错是
`E_NO_EMPLOYMENT`（看起来像"这个人没有在职记录"）。

## 5. 界面

**工资调整**页签（日常组）：

- 顶部：期间选择、刷新、"从工资表导入覆盖"（跳到工资条页的导入区）
- 表格：姓名 / 当前月薪 / 本期调整单 / 差额（涨绿跌红）/ 来源 / 状态 / 操作
- 点「调整」→ 以**当前结构为模板**的表单：改哪项填哪项，合计实时显示
- 草稿行上才有「应用」「作废」
- 下方「调整历史」：最近 50 张，含单号、期间、前后金额、差额、来源、原因、状态、应用时间

## 6. 断言

| 断言 | 守的是 |
|---|---|
| SAL1 | 建单留 before/after 快照与差额；只能拆固定项（个税被拒） |
| SAL2 | 应用后月薪与结构同步生效；同一张单再应用被拒（`E_ADJ_NOT_DRAFT`） |
| SAL3 | 调整只影响本期及以后：07 月的月薪标准没被 08 月的调整改掉 |
| UI16 | 调整页：期间选择 + 人员表格 + 调整入口 + 调整历史 |

## 7. 未做

- **批量调整**（一次调一个部门/一类岗位）：现在只能一个人一张，或走导入覆盖。
  做的话要引入"调整方案"概念（一批人 + 规则），那是另一个量级的功能。
- **审批**：调整单目前是"建 → 应用"两步，没走审批引擎。
  现实里 5000 以上的调整通常要老板签，这一层应该接 `approval` 而不是另写。
- **生效日期可调**：现在固定"期间首日"。真实场景有"从 15 号起算"，那需要
  按天折算 + 与考勤口径联动，不是改一个日期字段能解决的。
- **调整单与工资条的关系**：调整在生效期内、工资条已算过的情况下，
  需要"重算"才能反映；系统不会自动重算（重算等于改历史，必须是人决定的动作）。

## 8. 年终奖：为什么单独一张工资条

年终奖（全年一次性奖金）的计税方式与月薪完全不同：

| | 月薪 | 年终奖 |
|---|---|---|
| 算法 | 累计预扣，年初到当月累进 | 奖金 ÷ 12 找月度税率，税 = 奖金 × 税率 − 速算扣除 |
| 社保 | 计基数 | **不计**（社保为 0） |

所以它不能塞进月度工资条：

- 塞进 `gross` → 当月累计预扣顶到高档，**之后 11 个月的税全被抬高**；
- 塞进 `tax_amount` → 勾稽还能平，但"这一次的税是哪一种"再也分不出来。

实现：`pay_run.kind='bonus'` 单独一批 + `annual_bonus` 表（一年一人一条，唯一约束挡住"一年发两次"）
+ `fn_iit_bonus(amount)`（税率表放在函数里 —— 政策 2027-12-31 到期，到时只改这一个函数）。

临界点值得记住：`36000` → 税 1080（3%）；`36001` → 税 3390.10（10% 跳档）。
**多 1 元，多缴 2310** —— 这是真实存在的坑，AB2 断言把它钉住了。

界面在「工资调整」页下半部分：录入（人 + 金额 + 备注）、看到预估税额、
「算这一年年终奖」生成单独批次。

## 9. 提成：从"手敲一个数"到"按规则算"

提成原来是一个手工数字。10 个门店 30 个销售，每月手敲必错，而错了只能对账才发现 ——
那时候钱已经发了。

现在三件事串起来：

| 表 | 作用 |
|---|---|
| `commission_basis` | 销售额（一人一月一个数，可录入可导入） |
| `commission_rule` + `commission_rule_tier` | 阶梯规则（可按岗位/部门/全局） |
| `commission_record` | 算出来的提成（`approved` 才进工资） |

**阶梯是累进的**（分段计费），不是"达到就全额按高档"：

```
销售额 60000，规则 0–10000 3% / 10000–50000 5% / 50000+ 8%
→ 10000×3% + 40000×5% + 10000×8% = 300 + 2000 + 800 = 3100
（全额跳档会算成 60000×8% = 4800，而它会让"多卖 1 元少拿 500"真的发生）
```

**规则取用顺序**：岗位 → 同部门 → 全局，越具体越优先。
同一层有多于一条启用规则时**直接拒**（`E_COMM_RULE_AMBIGUOUS`）——
让系统挑一个"看起来合理"的，等于把口径问题藏起来。

**落账覆盖**：同期重复应用是覆盖那一条 `approved`，不是新增 ——
两条会让算薪把提成加两遍（CM3 守着这条）。

真实结果（DM 帐套，2026-11）：

```
销售额 60,000 → 提成 3,100 → 应发 13,000 + 3,100 + 全勤奖 0 = 16,100
五险一金个人 2,275（养老1040 + 医疗260 + 失业65 + 公积金910）
个税 264.75 = (16100 − 2275 − 5000) × 3%
实发 13,560.25
```

## 10. 报销：为什么先只做"留痕"，没直接接审批引擎

报销原来只有 `status`，改状态不记人。财务问"这笔 3000 的差旅谁批的"，系统答不上来 ——
而报销恰恰是最容易出事的一类单：金额小、频次高、和实际业务对不上时没人发现。

110 补两列：`approved_by` / `approved_at`，并用约束钉住语义：

- 有结论（approved/rejected/paid）**必须**有结论人；
- `pending` **不许**带结论人 —— 还没批却说批了，是两处口径打架。

**为什么不直接接 approval 引擎**：引擎是通用的（模板 + 版本 + 任务 + 加签/转签/抄送），
接它需要先定三件事：

1. 几级审（一级？金额超 5000 加二级？）
2. 谁审（直属主管？部门负责人？财务？）
3. 阈值多少起审（500？1000？全走？）

这三件是**客户的业务决策**，不是代码能替他定的。在客户定下来之前，
先保证"谁批的有记录"，比硬塞一个我猜的流程更负责。

接引擎时需要动的地方（已探明，不用重新调研）：

- `fn_appr_biz_applicant/date/org` 三个 CASE 加 `'expense'` 分支
- 一张 `EXPENSE` 模板 + 已发布版本（definition 里写节点与审批人解析）
- 提交报销时调 `fn_appr_start('EXPENSE','expense', id, app_today())`
- 审批通过后回写 `expense_claim.status`（推荐在查询时按实例状态同步，
  而不是让审批引擎反向依赖报销表 —— 依赖方向反了之后，两边都不能独立演进）
