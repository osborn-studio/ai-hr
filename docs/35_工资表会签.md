# 35 · 工资表会签

> 算完薪到封账之间，这张表要出去三趟。以前系统里这段路是**空的**。

## 1. 问题

`pay_run` 只有 `status='sealed'` + `sealed_at` —— 没有 sealed_by，更没有"谁看过"。

而真实场景里：出纳核金额、财务核个税与社保、业务负责人核奖金。异议往往出在
「某个店长发现自己奖金少了」，这些沟通发生在微信里，系统里查不到。
出事时连"当初谁看过"都答不上来。

## 2. 只做签字，不做审批流引擎

| 不做 | 为什么 |
|---|---|
| 可配置多级审批 | 那是另一个产品；这里要的是"这张表谁签过" |
| 按岗位自动找人 | 人在休假就签不了；现实里是"发给老王看"，所以由**发起人指定人** |
| 签一半算通过 | 有异议就不许封账，否则会签只是装饰 |

**默认不强制**（`PAY_SIGNOFF_REQUIRED = off`）：不改变上线前"算完就能封账"的行为。
要强内控的客户打开它 —— 这是"口径有两种合法答案"的事，做成配置项而不是替客户选。

## 3. 一条容易写反的判据

第一版把封账条件写成「制度强制时，会签必须全部通过」。结果页面上出现：

```
待签 1 · 异议 1 · 可以封账
```

因为当时的默认是 off，于是"有异议也能封账"。这跟会签的意义正好相反。

改成两句话：

```
能封账 = 批次是 draft 且
        ( 没发起会签 且 制度不强制        -- 与上线前一致
        | 发起过会签 且 全部 approved )    -- 一旦发出去，就按结果算
```

**制度只决定"要不要发起"，不决定"发起了能不能无视结果"。**

这条判据只有一处：`fn_signoff_status` 的 `can_seal` 与 `fn_pay_run_seal` 的门禁
用同一段逻辑 —— 各算一遍就会出现"页面说能封、点了封不了"。

## 4. 表结构

```sql
pay_signoff_role(code, name, seq, is_active, default_user_id)
  -- 预置：cashier 出纳 / finance 财务负责人 / biz 业务负责人

pay_run_signoff(
  pay_run_id, role_code, role_name,       -- 角色名快照（改名后历史单据仍可读）
  seq, assignee_user_id, status, decided_at, decided_by, note,
  UNIQUE (pay_run_id, role_code)
)
```

三条约束值得单说：

1. **`ck_prs_decided`：状态与时刻同生同灭。** 非 pending 必须有 decided_at。
   —— 作废（void）也要给时刻，这条当场拦住了我第一版（作废时只改 status）。
2. **`ck_prs_objected`：提异议必须写原因（≥4 字）。** 只写"有问题"的话，发起人无从修改。
3. **`uk_prs_role`：一张表 × 一个角色 = 一行。** 重发起时用 ON CONFLICT 更新，
   而不是插新行 —— 否则历史会越滚越长，还会出现"两个财务都签过"。

### 为什么 assignee 不挂 `sys_account` 外键

系统的登录身份是 `user_id`（`sys_user_credential`），而 `sys_account` 是**建帐时开出的账号档案**。
可以有身份没档案（迁移直接建库、钉钉同步进来的帐套、测试库）。挂外键的后果是
这类环境会签直接建不起来，报的还是"账号不存在"——看起来像配错了人。

名字用 `LEFT JOIN sys_account` 取，取不到就显示 `账号 123`：
**显示得丑一点，比整行消失好** —— 整行消失会让人以为"没发起会签"。

## 5. 重发起时"已签的保留"

```sql
ON CONFLICT (pay_run_id, role_code) DO UPDATE
  SET assignee_user_id = EXCLUDED.assignee_user_id,
      status = CASE WHEN 旧.status = 'approved' THEN 'approved' ELSE 'pending' END,
      ...
```

签过的意思不能因为换个签字人就丢；但未签的、提异议的必须回到 pending ——
这一轮要按新的数重新签。旧行不删：可追溯"上一次是谁、什么意见"。

## 6. 断言

| 组 | 条数 | 钉住什么 |
|---|---|---|
| `SIG1-8`（库） | 8 | 默认不强制也能封；强制但没发起被拒；三行待签时不能封；**代签被拒**；异议不写原因被拒；有异议不能封 + 重发起保留已签；签完能封且记 sealed_by |
| `SIG1-6`（接口） | 6 | 会签页数据（角色/候选签字人/可写）；发起；代签 403；封账 409 且点名卡在谁；改派后签完封账成功；封账后不能再签 |
| `UI32` | 1 | 算薪页有会签卡，且写明"会签不是审批流""异议是要改数的信号" |

`SIG5`（库）与 `SIG5`（接口）都刻意覆盖"**重新发起**"这条路径 ——
它是"有异议 → 改数 → 重签"的落点，也是唯一能产生 void 行的路径。

## 7. 踩过的坑

1. **`ck_prs_decided` 撞在作废上**：`SET status='void'` 没给 decided_at，直接被约束拒。
   作废也是一种"决定"，必须带时刻。
2. **`string_agg(... ORDER BY ...)` 的位置**：ORDER BY 写成语句末尾的 `ORDER BY s.seq`
   会得到 `column s.seq must appear in the GROUP BY clause` —— 看起来像漏了 GROUP BY，
   实际是聚合函数自带排序这个语法。
3. **OUT 参数名 `id` 与列名冲突**：`fn_signoff_status` 同时返回 `id` 和查询里的 `s.id` →
   `column reference "id" is ambiguous`。加 `#variable_conflict use_column`（与 136 同一个坑）。
4. **封账不可逆**：测试里想"封完账再清场"会撞 `E_PAYSLIP_FROZEN` / `E_PAYRUN_REOPEN`。
   测试批次留在专用期间（2027-09/10），不为清理去绕过冻结约束。
5. **撞了写操作限流**：会签要在几十毫秒里连点 7 次写（发起/签字/改派/封账），
   把 `RATE_WRITE_PER_MIN`（默认 120/分钟）撞掉了，导致后面 HOLY 组的确认请求 429。
   测试里临时抬高阈值 —— 限流本意是拦脚本，不是拦一个 HR 正常点几下。
