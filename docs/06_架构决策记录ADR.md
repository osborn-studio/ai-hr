# 架构决策记录（ADR）与私有化修正

> 2026-11-14 ｜ 这是**最后一层决策**，覆盖此前所有文档的对应条款  
> 内容：架构师提出的 15 个阻断项裁决 + 工资记录红线措辞修正 + 私有化部署的 4 项连带影响

---

## Part A：架构 15 项裁决

### A1 MCP 传输形态 → **stdio + 本地 HTTP，两种都做**

| 通道 | 地址 | 用途 |
|---|---|---|
| stdio | 本地进程 | 同机 AI 客户端（桌面端），零配置入口 |
| HTTP | `127.0.0.1:8xxx`（默认仅回环） | 同机其他客户端、调试 |
| HTTP over TLS | 内网域名（可选开启） | 团队共享、跨机接入 |

默认**只监听 127.0.0.1**，开放内网监听需显式配置 + 单独授权，避免默认把 HR 数据暴露到内网任意主机。

### A2 MCP 宿主 → **独立网关进程，与业务应用同机不同容器**

理由：MCP 是长连接，与业务进程同宿会互相拖死；独立进程可单独重启、单独限流、单独升级。本地部署多一个容器，成本可忽略。

**不引入消息队列**：网关直接内网 HTTP 调业务 API，失败重试即可。

### A3 身份上下文 → 三元组 + 角色服务端解析

```
oauth_client_id（哪个 AI 客户端）
+ end_user_id（代表哪个员工操作）
+ tenant_id（本地版恒为 1，保留字段）
+ effective_roles（服务端按 end_user 实时解析，禁止客户端传）
```

AI 永远是"代表某个人操作"，不存在"AI 自己"这个主体。审计时两者都要记。

### A4 三轴求值顺序 + 字段级一律掩码

```
① 数据范围 → 这一行能不能看到
② 字段级   → 能看到哪些字段
③ 功能权限 → 只读还是可写
```

**字段级不拒绝、只掩码**。理由：拒绝会让 AI 无法回答"这个员工在不在职"，掩码能回答存在性但不泄露内容。

### A5 写工具幂等 → 必须带 `idempotency_key`，服务端 24h 去重

读工具不要求。写工具缺失 key 直接报错，不做兜底。

### A6 审批状态 → **不提供独立"已批准"工具**

只给两个：

- `submit_*` → 返回 `status=pending_approval` + `approval_id`
- `get_approval_status(approval_id)` → 查状态

**不提供** `approve_*` 工具。理由：AI 一旦能调"批准"，人工审批环节就形同虚设。审批必须由人在 Web 端完成。

### A7 审计表 → 独立 `mcp_call_log`，保留 3 年，按月分区

存：客户端、代表用户、工具名、参数摘要、影响记录数、结果状态、耗时、请求体哈希。

大字段只存摘要 + 哈希，不存全量请求/响应体（隐私 + 体积）。

### A8 限流 → **AI 与人类同权同流，但 MCP 客户端单独限速**

统一走请求队列，**不设 AI 专用优先级**（避免 AI 挤占员工打卡）。但 MCP 客户端限速 60 次/分钟，防 AI 刷接口。

### A9 视图 → **普通视图 + 索引，不上物化视图**

万人级数据量，物化刷新引入一致性延迟和运维负担，不划算。

### A10 万级组织树 → 虚拟滚动 + 分层懒加载 + 后端分页

全量树只在导出时生成。首屏只加载前两层。

### A11 算薪规则引擎 → **规则表 + 公式 DSL，不做插件热加载**

本地版客户不会写插件，热加载是安全风险。DSL 足以表达餐饮算薪（条件 + 公式 + 优先级 + 封顶保底）。

### A12 历史数据迁移 → P0 只导三类

花名册、薪资档案、假期余额。**考勤历史与工资历史不进**（清洗成本极高、查询价值低），提供只读归档库满足历史查询。

### A13 首年规模 → 1 万员工 / 500 门店 / 5 万条考勤日/天

PostgreSQL 单实例足够，**不做读写分离**。留出升级到小集群的路径。

### A14 移动端 → **H5 响应式 + 协同平台内嵌，不做原生 App**

排班表与打卡在 H5 上做专项优化（虚拟滚动、大按钮、离线缓存）。

### A15 首个租户 → 安装时由实施顾问创建

集团节点 + 首个法人 + 超管账号，写进部署向导。**不做自助注册**。

## Part B：工资记录红线措辞修正（原措辞会让调动当月发不出工资）

### 错误写法

> 同一 `person_id + pay_period` 存在多条不同 `legal_entity` 的记录 → **一律阻断结账**

**问题**：跨法人调动当月必然触发。员工 15 日从 A 调到 B，A 发 1–15 日、B 发 16–31 日，两条记录**合法且必然**。一律阻断等于调动当月无法发薪——这正是客户问的那个场景。

### 定稿：凭单放行

```
同一 person_id + pay_period 存在多条不同 legal_entity_payroll_id 的记录时：
  ① 必须关联一张生效的「跨法人调动单」
  ② 两段任职区间连续、不重叠（A 止日 = B 起日 − 1）
  ③ 满足 → 放行，标记 is_transfer_pair = true（用于年度汇算提示）
  ④ 不满足（无调动单 / 区间重叠 / 区间断裂）→ 阻断结账并列出具体原因
```

唯一键 `(person_id, pay_period, legal_entity_payroll_id)` 不变，只是把「一律阻断」改成「凭单据校验后放行」。

## Part C：私有化内网带来的 4 项连带影响（必须进 PRD）

### C1 税务与银行接口反转

| 原（SaaS 设想） | 改（内网本地版） |
|---|---|
| 税务接口直连 | **导出标准报盘 + 线下报送（首选）**；直连降为可选插件，需客户自备专线/网关，单独验收 |
| 银行代发实时回盘 | 人工导入回盘文件 |
| 社保在线申报 | 导出申报文件 + 导入回执 |

### C2 社保政策库必须做「离线政策包」

无云端下发通道，所以：

- 加密政策包（客户 IT 导入）
- 导入时校验签名与版本
- 记录生效期间，历史月份按当时版本重放
- **「政策更新」从后台运维变成客户 IT 参与的运维动作**，要写进实施手册与运维 SOP

不写清这条，上线后第一个月社保基数调整就会卡住。

### C3 多主体「一次登录批量申报」不成立

SaaS 版可以多主体免 U 盾批量申报，内网版是**各主体各导一份、各自报送**。

这是**能力降级**，对外话术与竞争对比里不能沿用原说法。

### C4 移动端可达性需向客户确认（影响 P0 验收标准）

纯内网下，手机访问要么连 VPN、要么用专有 App。这会动摇「一线员工免邮箱、移动端可达」这个门店核心卖点。

**必须确认客户是否有 DMZ 或移动接入方案**；不确认则工资条与移动报表的 P0 验收标准写不出来。

## Part D：待确认清单（合并后 5 项，按优先级）

| # | 待确认 | 影响范围 | 不确认的后果 |
|---|---|---|---|
| 1 | **客户是否有外网出口 / DMZ** | 工资条、移动报表、招聘对外触点、MCP 内网共享 | P0 验收标准写不出，移动端卖点不成立 |
| 2 | 是否覆盖港澳/海外主体 | 税制、假期、MPF 等 | 架构要预留多币种多税制，否则二期重构 |
| 3 | 是否存在「一个成本中心覆盖多店」 | 成本中心能否拆到档口粒度 | 绩效系数与成本无法同源，门店看板数据不可信 |
| 4 | 储值消费的营业额确认时点 | 人力成本率当月是否虚低 | 店长奖金随促销节奏波动 |
| 5 | 派遣/外包工时是否进本系统考勤 | 门店人效是否虚高 | 最贵的一块人力被藏起来 |

已销项：跨法人借调双主体申报（借调不拆，场景不存在）、锁数回滚（已改为解锁重锁 + 留痕）、300+ 法人主体（按 5–50 设计）。
