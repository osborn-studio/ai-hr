# 37 · 个税与社保申报表

> 系统算得出每个人的个税与社保，却**报不出去**。财务每月打开电子税务局，
> 把数从工资条里一个一个抄进格子。抄错了当月就得更正申报；
> 抄慢了员工在个税 APP 里看到"未申报"就来问 HR。

## 1. 为什么这不是"再加一个导出"

导出报表是把系统里的数搬到纸上。申报表不同，它**替公司向税务机关作出陈述**：

- 数错了 → 更正申报，要写说明、要走流程；
- 少报了人 → 欠缴，追缴 + 滞纳金；
- 报的是没定稿的数 → 下个月数一变，上个月的申报就是错的。

所以它有三条比普通报表严格得多的规矩，全部落在库里（`141_iit_si_return.sql`）：

| 规矩 | 实现 | 违反时 |
|---|---|---|
| 只从**封账批次**出 | `fn_declare_run` 只认 `sealed/paid` | `E_DECLARE_NOT_SEALED` / `E_DECLARE_NO_RUN` |
| 金额与工资条**同源** | 全部列从 `payslip` 读，不重算税 | 断言 `DECL3` 逐项比对 |
| **导出留痕** | `tax_declare_export` 只增不改 | `E_TDE_NO_UPDATE` / `E_TDE_NO_DELETE` |

两条错要分开报：**没批次**（去算薪）和**没封账**（去封账）是两个动作，
合成一句"还不能出表"，人就会先去算一次薪 —— 而那一期其实算过了。

## 2. 个税表：累计预扣必须带累计

《个人所得税扣缴申报表》里工资薪金那一段是**累计口径**，因为累计预扣法的全部内容就是：

```
本月应扣 = 按累计应纳税所得额查表得到的累计税额 − 已预扣
```

所以表里必须有：累计收入额、累计减除费用、累计专项扣除、累计专项附加扣除、
累计应纳税所得额、累计应纳税额、累计已缴税额、应补(退)税额。

三个口径写在这里，也写进了 CSV 表头（文件离开系统后就没人问得着了）：

**① 减除费用 = 5000 × 本年已申报月数。**
月数取"本法人本年已封账的月份数"，不是按 `hire_date` 数日历月。
两者在"月中入职""漏了一个月"时会分叉，而申报表上的累计数必须与**真报上去的
那几个月**的累计数一致。

**② 累计已缴 = 本年此前各月已封账工资条的 `tax_amount` 之和（含本月）。**
库里没有"已申报"这个状态（那是税务局那边的状态），所以用"已封账"作最接近的口径。
有未封账月份时，应补(退)税额会不为 0 —— 那正是"这个月要补申报"的信号，
**不压成 0**。

**③ 免税收入与其他扣除一律 0。**
本系统不登记这两项（生育津贴、商业健康险之类），有这类情形的员工要在电子税务局
单独调整。写在表头，不逐行啰嗦。

### 一个必须说清的坑：算薪的顺序

累计预扣要读**上一期已封账**的数。如果二期算的时候一期还是 `draft`，
累计就是 0，本月按"只有这一个月"算 —— 而二期一封账就改不了了，累计永久少一个月。

这不是假设。做这一版时第一次跑真实数据就撞上了：

```
张三  收入 8,000  累计应纳税所得额 2,360  应补退 −70.80
备注：累计勾稽差 −2,360.00（工资条上的累计数与"累计收入−累计各项扣除"对不上…）
```

申报表把它**点名报出来**（`remark` 列 + 页面上"2 行带备注"），而不是让一个
对不上的数混在表里报上去。处置很清楚：先封一期，再重算二期（未封账前可重算）。

## 3. 社保表：0 与"空"是两件事

个人应缴从**工资条明细**读（`SI_PENSION` / `SI_MEDICAL` / …每险种一行）。
单位应缴工资条里没有 —— 工资条只扣个人，单位缴的那部分是"公司成本"，从来没存过。
所以它只能算：`缴费基数 × 单位费率`，基数走与算薪**同一个入口** `fn_si_base_eff`
（有申报基数用申报基数，没有回退月薪标准）。

"另算"就必然可能"算得不一样"，所以表中带一列对账：

| 情形 | 输出 | 为什么 |
|---|---|---|
| 工伤、生育（个人不缴） | 个人额 **0** | 真的不缴 |
| 工资条里没有该险种的明细行 | 个人额 **空** | **不知道**，不是 0 |
| 按基数重算的个人额 ≠ 工资条真扣的 | 备注点名差额 | 基数或费率改过、没重新封账 |

第二行是最要紧的一条。历史上只记 `SI_EMPLOYEE` 合计的工资条就是这种形态
（104 之前的结构）—— 那时按险种列不出来。把"没登记"写成 0 会让人以为
"这个人这个险种免缴"，而社保申报少一个险种是要补申报的。

汇总表因此多一列 `个人额未登记人数`：不为 0 就说明**这张表还不能报**。

## 4. 表头注释：文件离开系统之后

CSV 前几行是 `#` 开头的注释，带：表名、法人、期间、批次号、封账时间与封账人、口径说明。
理由很朴素：这份文件会被打印、被转发、被塞进档案袋，而**那之后就没有系统了**。
收到的人至少要知道它是按什么口径算的、对应哪一批已封账的工资。

如果本期还有年终奖批次，表头会多一行提醒：

```
# 注意：本期另有年终奖批次 12（sealed），它不在本表，需按"全年一次性奖金"单独申报
```

年终奖放进工资薪金表是多缴，漏报是少缴。系统只提醒，**不替你合并** ——
两种申报方式在税法上都成立，选哪个是公司的决定。

## 5. 掩码与导出：同一页上看起来"不一致"，其实是刻意的

| 出口 | 证件号 | 理由 |
|---|---|---|
| 页面 | `310101********1234` | 看的人不报，不需要完整号 |
| 导出 CSV | 完整 18 位 | 半掩的号在电子税务局里报不上去，等于交一张废纸 |

花名册的导出配的是一律掩码（053 的 9002），理由是"文件会被转发"。
申报表反过来，交换条件是三条：**只有薪酬写权限的人能导、每次导出留痕、
导出的只是这一家法人这一期**。

权限这一层不新造资源码，直接要 `payroll_run` 的写权限 ——
"能算薪、能封账"的人就是"能申报"的人；老板能看表、不能导。

## 6. 顺带抓到的一个真 bug：险种有两个名字

第一次跑真实数据，社保汇总里 `失业保险 个人额未登记 2 人`。

顺着查下去：`si_policy.item` 写成 `unemploy` 时，算薪**照扣了这笔钱**
（算社保用的是比例，不看名字），但工资条上**没有失业险这一行** ——
因为算薪里那串 `CASE` 只认 `unemployment`。

三层后果，一层比一层难发现：

1. 员工看工资条，明细里少了失业险，实发少的钱却是对的 —— 他以为自己被多扣了；
2. `v_payslip_consistency` 会红（明细之和 ≠ 应发 − 社保 − 个税），但那要人去读；
3. 申报表按险种列不出来 —— **这就是它被发现的路径**。

根因不是哪一处写错，是同一个东西有两个名字，而映射在两个地方各写了一遍
（申报表的 `fn_si_item_code` 与算薪里的 `CASE`）。修法不是在出口兼容三种拼写，
是在**入口归一**（`142_si_item_vocab.sql`）：

```sql
NEW.item := fn_si_item_canon(NEW.item);   -- unemploy → unemployment，housing → housing_fund
```

- 认不出的键**原样保留**，不猜（猜错会把它并进别的险种，比不归一更糟）；
- 别名撞上规范键（同城同日两条）→ `E_SI_ITEM_DUP`，不静默删一条；
- 存量数据同步改正，顺带把 `si_policy.id` 补上 `IDENTITY`（第十次同一个坑）。

修完之后：失业保险 85.00，勾稽视图 0 行，申报表 6 个险种齐全。

## 7. 两份"不做"

**① 不做各地电子税务局的导入模板。** 一省一样，做了也跟不上。
出的是**标准对账表**，供人抄或自己转成当地模板。

**② 不做"参保主体 ≠ 发薪法人"。** 库里的工资条只挂发薪法人，没有 `si_entity` 这一维。
真做要把参保主体落到 `employment` 上，那是一次数据模型改动 ——
不做半个，半个的结果是申报表按错的法人出，而表看起来是对的。
