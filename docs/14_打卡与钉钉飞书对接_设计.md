# 14 · 打卡与钉钉/飞书对接（设计，未实现）

> 状态：**设计稿**。截至 `064_ledger.sql`，本仓**没有**打卡页面，也**没有**与钉钉/飞书的任何对接。
> 现有的是"考勤人日"（`attendance_daily_store`）——它是**结果表**：一天的工时、在岗、休息扣除。
> 它从哪里来，一直是个空白：现在只能靠种子或补账写入。
>
> 这份文档要回答三件事：打卡怎么落、钉钉/飞书怎么接、以及**为什么这两件事不能直接写进
> `attendance_daily_store`**。

---

## 一、先说清楚这条链路（这是最容易做错的地方）

```
  打卡数据（原始事件）          考勤日结果（计薪口径）           算薪
  punch / ext_punch      →     attendance_daily_store     →    payslip
  （几点几分、在哪、什么设备）    （8 小时、扣 1 小时休息）        （扣款/加班）
```

三条判断，缺一条就会出现"数据对不上但没人能解释"：

1. **原始打卡 ≠ 工时。** 打卡是"人按了一下"，工时是"这一天算几小时"。
   中间隔着：排班（应到几点）、休息扣除（`BREAK_DEDUCT` 制度项）、
   跨零点班次、外勤、忘打卡补卡。把打卡直接当工时，第一天就会错。
2. **结果表只能有"一份口径"。** 现在 `attendance_daily_store` 由封账快照、
   补账（`v_att_effective`）、报表三处读。如果打卡模块**另建一套工时计算**，
   就会出现"打卡页面 8 小时、报表 7 小时"，而两个都像对的。
   **所以打卡只往"原始数据"里写，工时仍由现有那一条链路算。**
3. **外部系统的数据是"证据"，不是"结论"。** 钉钉给的是打卡记录，
   飞书给的也是打卡记录；它们各自的"考勤结果"口径与本系统不同（休息扣除、
   加班认定、跨天归属）。**只接原始记录，不接它们的结算结果** ——
   接结论等于把两套口径混在一个字段里。

## 二、打卡（自建）

### 2.1 数据模型（新增两张表，不动现有表）

```sql
-- 原始打卡事件：只增不改
punch (
  id           bigint identity PK,
  employee_id  bigint NOT NULL,
  punch_at     timestamptz NOT NULL,     -- 服务器时间（不信客户端时钟）
  kind         varchar(8)  NOT NULL,     -- in | out
  source       varchar(16) NOT NULL,     -- app | web | device | dingtalk | feishu
  -- 位置：允许为空（外勤、GPS 关闭）。空不等于"没打卡"，两者必须在界面上不同形
  lat numeric(9,6), lng numeric(9,6),
  store_id     bigint,                   -- 解析出的门店（可空：不在任何围栏内）
  distance_m   int,                      -- 与门店中心距离，围栏判定留痕
  device_id    varchar(64),              -- 设备指纹：一人多机是异常，不是错误
  ext_id       varchar(128),             -- 外部系统主键（幂等键）
  created_at   timestamptz NOT NULL DEFAULT now()
)
-- 幂等：同一外部记录重复拉取不会变两条
UNIQUE (source, ext_id) WHERE ext_id IS NOT NULL

-- 打卡规则：一个门店一条，集团可下发（走 021 的 policy_def，不另造配置）
punch_rule (
  store_id bigint PK,
  radius_m int NOT NULL DEFAULT 300,
  require_gps boolean NOT NULL DEFAULT true,
  allow_web   boolean NOT NULL DEFAULT true
)
```

### 2.2 五个必须写在代码里的判断

| # | 判断 | 不做会怎样 |
|---|---|---|
| 1 | **时间是服务器时间**，客户端时间只作参考并单独存 | 手机改时间就能改工时 |
| 2 | **打卡不写工时**，只写 `punch` | 工时出现第二份实现（见上文第 2 条） |
| 3 | **围栏外打卡允许但标记**，不是拒绝 | 拒绝会让外勤/信号差的人打不上，然后他们会互相代打 |
| 4 | **一天只有一对有效 in/out**，多次打卡取最早 in、最晚 out，并**保留全部原始行** | 中午外出吃个饭就变成加班 |
| 5 | **忘打卡走补卡单**（审批流），不直接插 `punch` | 补卡不留痕，等于谁都能改历史 |

### 2.3 页面（参照钉钉，但只做必要的那几屏）

- **打卡页**（手机首屏）：一个大按钮 + 当前时间 + 门店名 + 距离；打完之后显示"今日 09:02 上班 / 18:05 下班"。
- **我的考勤**：本月每一天一行（正常 / 迟到 / 缺卡 / 休息），点进去看那天的原始打卡。
- **店长视角**：本店今日"已到 / 未到 / 缺卡"三个数，点进去是人。
- 手机优先（`viewport` + 媒体查询 + 底部导航），Pad 与桌面同一套页面，不装 App。

## 三、与钉钉 / 飞书对接

### 3.1 只做三件事，且三件事都要"对照表"

| 域 | 方向 | 落法 |
|---|---|---|
| **组织架构** | 外部 → 本系统（单向） | `ext_org_map`：外部部门 id ↔ 本系统 `org_unit.id`；未匹配的进"待对照"清单，**不自动建** |
| **人员** | 外部 → 本系统（单向） | `ext_person_map`：外部 userid ↔ `person.id`；同名不同人必须人工确认（同名是常态，不是异常） |
| **考勤记录** | 外部 → 本系统（单向拉取） | `punch`（source=dingtalk/feishu，`ext_id` 幂等）；**不拉"考勤结果"** |

**为什么全部单向**：双向同步的冲突规则（谁覆盖谁）永远说不清，而说不清的那一天
通常是月底算薪那天。需要回写外部系统的，做成"导出/推送"的独立动作，不在同步里做。

### 3.2 账号绑定：三种关系要分开

```
sys_account（本系统账号）
   └─ ext_identity（外部身份）  provider: dingtalk | feishu
        ├─ ext_user_id          外部唯一 id（不是手机号：手机号会换）
        ├─ union_id / open_id   飞书有 union_id（跨应用稳定）与 open_id（应用内），存 union_id
        ├─ bound_at / bound_by  谁在什么时候绑的
        └─ status: active | revoked
```

- **一个人可以同时绑钉钉和飞书**（历史原因：公司换过 IM）。所以是 1:N，不是 1:1。
- **绑定入口两个**：① 管理员在"账号"页手工绑（有对照表可搜）；② 用户自助：扫码/OAuth 登录后
  把当前会话与外部身份绑上（必须已登录本系统，否则等于送账号）。
- **解绑要留痕**（`revoked`，不删行）：删了之后"这个人曾经绑过谁"就没了，
  而排障时最需要的就是这一句。

### 3.3 同步作业的六个必须

| # | 必须 | 理由 |
|---|---|---|
| 1 | **幂等键**（`ext_id`） | 重跑、补拉、断点续传都不能产生第二份 |
| 2 | **只增不改**（原始记录） | 外部改了历史打卡，要能看出"改过"，而不是静默覆盖 |
| 3 | **对不上就不动**（未匹配的组织/人进待办） | 自动建组织会造出一堆"未命名部门"，而它们会进报表口径 |
| 4 | **每次同步留一份运行记录**：拉了多少、新增多少、跳过多少、失败几条 | "昨天少了 3 个人"没有运行记录就永远查不出 |
| 5 | **失败可重试、可重放**：失败的行单独存，不整批回滚 | 整批回滚会让一次网络抖动变成"今天没数据" |
| 6 | **限流与增量**：按 `updated_at` 增量拉，外部接口按分钟限流 | 全量拉一个月，第一次就超限 |

### 3.4 与现有考勤链路的关系（关键：不能绕开行闸）

```
外部打卡 → punch（source=dingtalk/feishu）
            ↓  （按排班与规则折算）
      attendance_daily_store   ← 与自建打卡**同一条**折算路径
            ↓
      v_att_effective（+补账）→ 报表 / 算薪 / 封账快照
```

- 折算函数**只有一份**：`fn_att_build_day(employee, date)` 读 `punch` + 排班 + 制度，
  写 `attendance_daily_store`。自建打卡与外部对接都调它，不各写一遍。
- 封账之后**不许再重算**：封账快照是"那天我们看到的数"。外部补拉的历史打卡，
  只能走补账（`fn_att_adjust`）进报表，不能改快照 —— 与现有纪律一致。
- 行闸照旧：`attendance_daily_store` 的读写都过四维；外部数据不享受任何"系统账号"特权。

## 四、实施顺序（不破坏现有功能）

每一步都能独立上线、独立回滚，且每一步都要有断言：

1. **打卡（自建）**：`punch` / `punch_rule` + `POST /api/punch` + `fn_att_build_day` + 打卡页。
   断言：服务器时间、围栏外标记、一天一对 in/out、补卡走审批、折算与现有报表口径一致。
2. **组织与人员对照**：`ext_org_map` / `ext_person_map` + 对照页面（左外部右本地，未匹配单列）。
   断言：未匹配不自动建；同名不同人必须人工确认；对照变更留痕。
3. **考勤拉取**：钉钉/飞书各一个 adapter（同一接口：`listPunches(from,to)`），
   写入 `punch(source=...)`，幂等键去重。断言：重跑不翻倍、失败单行可重试、运行记录齐全。
4. **账号绑定**：`ext_identity` + 管理端绑定 + 自助绑定（OAuth 回调）。
   断言：1:N、解绑留痕、未绑定的人登录本系统不受影响。

**现在这一步之前要先做的事**（本仓当前状态）：

- 建帐向导界面（帐套 / 加门店 / 加账号）未做；
- H5 响应式未做（打卡页是第一个真正需要手机的页面，建议与它一起做）。

## 五、不做什么（写清楚，免得被当成漏项）

- **不做双向同步**（见 3.1）。
- **不接钉钉/飞书的"考勤结果"**（休息扣除与加班认定口径不同，接进来就是两套账）。
- **不做人脸/指纹打卡**：那是硬件与合规问题（生物信息），不是这一层该决定的。
- **不做"代打卡检测"的算法**：只留证据（设备指纹、距离、时间），把判断留给店长。
  一个会自动判定的代打卡检测，误判一次就会让一个正常员工被通报。
