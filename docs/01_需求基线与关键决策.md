# 连锁餐饮集团一体化人力资源平台 · 需求基线与关键决策

> 版本 v0.1 ｜ 2026-11-14 ｜ 状态：设计输入，待负责人确认  
> 本文件是本项目的**唯一需求基线**。后续 PRD、架构设计、接口定义均以此为准；本文件中裁决过的口径，下游不得各自另立标准。

## 一、一页纸结论

做一套面向**连锁餐饮集团**的商业级人力资源平台，覆盖"组织人事—排班考勤—薪酬算薪—招聘—绩效—学习考试—灵活用工与外包协同"完整链路，原生支持**多法人、多组织、多门店**，并把全部业务能力以 **MCP 协议对外开放**，让任何 AI 客户端（对话助手、Agent、自建应用）都能在同一套权限与审计下读写 HR 数据。

三条与普通 HR 系统的分水岭：

1. **组织不是一个树，是四张皮。** 人员归属、排班、打卡、工资成本是四个独立维度，餐饮跨店支援必须靠这个才能算对钱。
2. **工时是唯一事实源。** 排班、打卡、加班、假期、算薪全部围绕一张"工时事实表"收敛，任何模块不得自建工时口径。
3. **AI 不是外挂，是原生接口。** MCP 层与业务层同源同权，不做事后补的开放 API 外壳。

本轮交付**只做设计**：需求基线（本文件）→ PRD → 技术架构与 MCP 协议设计 → Demo 方案。实现代码另行启动。

## 二、产品定位与边界

### 2.1 定位

| 维度 | 定义 |
|---|---|
| 客户 | 直营为主、含加盟的连锁餐饮集团，门店数 30–3000，员工数 500–10 万 |
| 形态 | 多租户 SaaS 为主，支持单租户私有化部署（集团级客户） |
| 组织 | 集团 → 区域/城市 → 门店 三级，法人主体可多个且与经营层级不重合 |
| 用户 | 集团 HR、区域 HRBP、门店 HR/店长、员工、劳务供应商、财务、管理层、AI 客户端 |
| 边界外 | 不做通用 OA、不做 IM、不做财务总账（通过接口与外系统对接） |

### 2.2 三条产品原则

1. **门店能自己跑起来。** 店长在手机上一屏之内能完成：看今天的班、补人、审批请假、确认工时。
2. **集团能一杆子看到底。** 任意门店、任意时点的人效、人力成本、流失率可下钻到人。
3. **每个口径都可配置、可追溯。** 拿不准的业务规则一律做成租户级配置项，默认值等于上线前的实际做法，改动留痕。

## 三、角色与权限骨架

### 3.1 角色清单

| 角色 | 数据范围 | 核心诉求 |
|---|---|---|
| 集团 HRD | 全集团 | 制度统一、编制管控、集团报表 |
| 集团薪酬专员 | 全集团（薪资字段可见） | 多主体算薪、社保政策、成本归集 |
| 区域 HRBP | 所辖区域 | 跨店调配、招聘补给、流失干预 |
| 门店 HR | 单店/多店 | 入离职、排班、考勤异常、工资条答疑 |
| 店长 | 本店 | 排班、补人、审批、看当日人效 |
| 部门主管 | 本部门 | 排班确认、绩效评分 |
| 员工 | 本人 | 打卡、查班表、请假、工资条、学习考试 |
| 劳务供应商 | 仅本供应商供人 | 接单、报名、到岗、对账 |
| 财务 | 全集团（金额可见、个人信息脱敏） | 发薪、对账、成本 |
| 管理层 | 全集团（聚合视图） | 看板、预警 |
| AI 客户端 | 按授权 scope | 通过 MCP 读写 |

### 3.2 权限模型

采用 **RBAC + 数据范围 + 字段级** 三层：

- **功能权限**：模块/按钮/接口粒度。
- **数据范围**：本人 / 本部门 / 本部门及下级 / 指定门店集合 / 指定法人 / 全集团，六种规则可组合。
- **字段权限**：薪资、身份证、银行卡、家庭信息等敏感字段独立授权，未授权返回掩码而非报错。
- **敏感操作**：导出、批量改薪、删除考勤记录，强制二次确认 + 水印 + 审计。

> MCP 调用继承同一套权限模型，不设"AI 专用后门"。

## 四、核心领域模型

### 4.1 组织：一个实体，四个视角

组织节点只有一个实体 `org_unit`，通过 `org_type` 区分 集团/区域/法人/门店/部门/班组，但**任何员工在任一时刻有四组归属**：

| 维度 | 用途 | 变更影响 |
|---|---|---|
| 人员归属组织 | 花名册、汇报关系、审批流、编制 | 影响审批与统计口径 |
| 排班组织 | 谁给这个人排班 | 影响排班权限，不影响算薪 |
| 考勤打卡组织 | 打卡范围/设备/门店归属 | 影响异常判定 |
| 工资成本组织 | 人力成本归到哪 | 影响成本报表，不影响发薪主体 |

餐饮跨店支援的典型场景：员工 A 归属甲店，本周排班在乙店，打卡在乙店，成本仍记甲店（或按配置分摊）。**四维分离是这套系统能算对钱的前提。**

- 组织版本化：每次组织调整生成新版本并带生效日期，历史报表按当时版本还原。
- 组织架构图：树/缩进/组织图三种视图，支持按维度切换、按人展开、拖拽调整（调整走审批，不直接落库）。

### 4.2 员工：一个自然人，多个任职

- `person`（自然人）与 `employment`（任职关系）分离。一人可在集团内有多段任职（跨法人调动、离职复职），历史不覆盖。
- 用工类型：全职 FT / 长期兼职 LTPT / 兼职 PT / 小时工 / 实习 / 劳务派遣 / 外包。**一个员工一个计薪方式**，不做混合计薪；同一门店可以混排不同计薪方式的员工。
- 员工生命周期：预入职（扫码建档）→ 入职 → 试用期 → 转正 → 调动/调薪 → 离职 → 复职，每步有审批、有生效日期、有留痕。

### 4.3 工时：唯一事实源

一张 `worktime_fact` 收敛所有工时来源：

```
(员工, 日期, 组织, 来源[排班|打卡|手工|导入], 计划工时, 实际工时,
 加班工时[平时|休息日|法定], 请假[类型+时长], 缺勤类型, 状态[待确认|已确认|已封账])
```

- 排班、打卡、请假、加班申请都写入这张表，冲突以"优先级 + 人工确认"解决，不静默覆盖。
- 月度封账后不可改，更正走"调整单"，原记录保留。
- 薪资只读封账后的工时事实，不直接读打卡原始记录。

### 4.4 薪酬：方案 + 快照 + 规则

- `pay_scheme`（薪资方案）绑定：法人主体 + 适用用工类型 + 薪资项结构 + 计算规则参数。
- 算薪时对每人生成 `payroll_snapshot`：把当时的时薪/月薪/社保基数/个税累计/考勤汇总全部快照下来。**算完再改主档不影响已算结果**，重算必须显式发起。
- 规则引擎：条件（组织/用工类型/岗位/工龄/在职天数）+ 公式（引用因子）+ 优先级，支持封顶保底、异常阻断、人工覆盖留痕。

## 六、十二项关键口径裁决

> 这些是研究中被识别出的冲突点或易错点。**在此一并定死，下游不得另立标准。**

| # | 议题 | 裁决 | 理由 |
|---|---|---|---|
| 1 | 组织是几个维度 | **四维**：人员归属 / 排班 / 打卡 / 工资成本 | 跨店支援场景下，两字段会算错成本与加班 |
| 2 | 一个员工能否混合计薪 | **不能**，一个员工一个计薪方式；同店可混排 | 混合计薪会让工时单价、加班基数、社保基数全部歧义 |
| 3 | 在职天数算法 | **唯一算法**，做成公共服务，薪酬/假期/绩效统一调用 | 三处各算一次必然对不上账 |
| 4 | 月计薪工时基数 | **参数化到薪资方案**，默认 174（21.75×8），不硬编码 216 | 原口径来自特定地区实践，不能当通用标准 |
| 5 | 加班如何分列 | **按类型分列**：平时 1.5 / 休息日 2 / 法定 3；法定节假日另设独立薪资项，不混入加班 | 混列会导致成本归集与合规报表失真 |
| 6 | 工时单价取数 | **算薪时快照**，不实时回查主档 | 事后调薪污染历史工资 |
| 7 | 跨店同日工时 | **按人按日合并**再判是否超 8 小时起算加班，不按单店分别判 | 否则员工跨两店各 5 小时，两边都不算加班 |
| 8 | 连续病假跨月 | **滑动窗口**：向前回溯连续病假天数，跨月不重置 | 跨月重置会少扣或多付 |
| 9 | 假期余额 | **四态**：应得 / 实得 / 借用（预支）/ 结转存量，四者分列不合并 | 合并成一列后无法还原预支与过期 |
| 10 | 考勤与计薪口径 | **双口径**：出勤天数（判勤）与计薪天数（算钱）分离 | 判勤看是否到岗，算钱看是否计薪，两者不等价 |
| 11 | 健康证过期 | **硬阻断排班**，不是提醒 | 餐饮食安合规红线 |
| 12 | 成本归集 | 默认记**人员归属组织**；分摊只在报表层做，不写回明细 | 写回明细会让明细账与成本账互相污染 |

## 七、拿不准的口径：一律做成配置项

> 原则：**不替客户选，做成租户级开关**。默认值 = 上线前的实际做法；改动留痕、可停用不可物理删、危险项需填理由。

| 配置项 | 取值 | 默认 | 说明 |
|---|---|---|---|
| 成本归集方式 | 归属组织 / 排班组织 / 打卡组织 / 按工时分摊 | 归属组织 | 影响门店人力成本报表 |
| 临时工结算周期 | 当日结 / 周结 / 月结 | 月结 | 可按门店或用工类型覆盖 |
| 加班是否需事前申请 | 需申请 / 事后认定 | 事后认定 | 门店场景事后认定更现实 |
| 法定节假日加班处理 | 付 3 倍 / 优先调休 | 付 3 倍 | 调休需配套余额规则 |
| 年假发放方式 | 按天 / 按月 / 按工龄 / 按在职比例 | 按在职比例 | 影响新员工首年假期 |
| 年假结转 | 可结转 / 折算工资 / 清零 | 可结转，次年 Q1 过期 | 需与假期余额四态联动 |
| 试用期时长 | 1/2/3/6 月 | 3 月 | 按合同期自动建议 |
| 缺卡处理 | 视为旷工 / 按排班计 / 需补卡 | 需补卡，超时视为旷工 | 超时阈值可配 |
| 工资条可见项 | 全项 / 仅收入项 / 自定义 | 全项 | 餐饮一线员工常只看实发 |
| 劳务供应商可见范围 | 仅本供应商人员 / 含工时明细 | 仅本供应商人员 + 工时 | 工时是结算依据，必须可见 |
| 排班最小发布提前量 | 0/1/3/7 天 | 3 天 | 影响员工知情权与合规 |
| 离职当日是否结算 | 是 / 否（并入下月） | 是 | 餐饮高频离职，当日结更稳 |

## 八、MCP 开放层：本产品的核心差异点

### 8.1 设计原则

1. **同源同权**：MCP 与 Web 端共用同一套 service 层与权限模型，不做平行实现。
2. **能力即工具**：每个业务动作是一个 MCP tool，粒度对标"一个人能做的一件事"，不是对标 REST 接口。
3. **读写成对**：查询类工具返回结构化结果 + 自然语言摘要；写入类工具必须支持 dry-run 与二次确认。
4. **默认最小权限**：MCP 客户端拿到的是 scope 组合，不是超级令牌。
5. **全量审计**：每次调用记录 谁（客户端/用户）、做了什么、动了哪些记录、结果如何。

### 8.2 工具分层

| 层 | 示例能力 | 写权限 |
|---|---|---|
| 查询类 | 查员工、查班表、查考勤、查薪资（脱敏）、查组织树、查编制缺口 | 只读 |
| 分析类 | 人效分析、流失预警、成本对比、招聘漏斗 | 只读 |
| 办理类 | 发起请假、换班、补卡、加班申请 | 写，走审批 |
| 管理类 | 批量排班、调薪、发起算薪、封账 | 写，需人工确认 + 二次授权 |
| 治理类 | 建组织、改权限、导数据 | 写，需管理员身份 + 强审计 |

### 8.3 必须回答的边界

- AI 能不能直接发工资？**不能**。算薪可以触发，发薪必须人工在 Web 端确认。
- AI 能不能看到全部薪资？**按 scope**，且返回时默认脱敏，需显式申请明文（并留审计）。
- AI 改错了怎么办？**全部走调整单**，不物理覆盖，可回滚。

## 九、Demo 设计要点

- **角色账号**：集团 HRD、集团薪酬、区域 HRBP、门店 HR、店长、员工、劳务供应商、财务、管理层，各一套。
- **Seed 数据**：一个虚构餐饮集团，2 个法人、3 个区域、12 家门店、约 400 名员工（含全职/兼职/小时工/派遣）、真实感的排班与考勤、3 个月薪酬历史。
- **演示剧本**：至少 5 条主线——① 新店开业 30 天配齐人；② 跨店支援算薪不出错；③ 小时工当日结；④ 健康证过期阻断排班；⑤ AI 通过 MCP 查"华东区本月人力成本超支门店"。
- **全部使用虚构名称**，不得出现任何真实客户、真实品牌、真实门店名。

## 十、与既有资料的关系（内部参考）

本基线吸收了三类既有积累，均只取**功能与规则**，不取名称与数据：

1. **早期协同办公平台的人事/假勤/薪酬产品线资料**——提供排班、假期、薪酬、招聘、绩效的功能骨架与场景清单。
2. **连锁餐饮客户项目的薪酬实战规则**——提供门店用工类型、工时到薪资的换算口径、假期扣款、津贴计算的真实规则（已脱敏抽象为通用规则）。
3. **人力资源服务公司（HRO）方案沉淀**——提供客户/订单/候选人/雇员/结算/毛利的业务链与模块划分。

**交付物中一律不出现上述任何真实客户名、品牌名、产品名。**
