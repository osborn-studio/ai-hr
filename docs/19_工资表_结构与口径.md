## 1. 一张工资表长什么样（真实数据）

示例员工 · 香香鱼米 · 2026-11

| 工资项 | 金额 | 占比 |
|---|---|---|
| 基本工资（BASE） | 9,000.00 | 69% |
| 岗位津贴（POST_ALLOW） | 3,000.00 | 23% |
| 餐补（MEAL） | 600.00 | 5% |
| 通讯补贴（COMM） | 400.00 | 3% |
| **月薪标准** | **13,000.00** | 100% |

口径：每日标准工时 **8 小时** · 月计薪 **21.75 天** · 法定节假日**带薪**。

2026-11 算出来的工资条：

| 项目 | 金额 |
|---|---|
| 应发 | 13,000.00 |
| 社保个人部分（13000 × 8%） | −1,040.00 |
| 个人所得税（累计预扣，3%） | −208.80 |
| **实发** | **11,751.20** |

个税核对：(13000 − 1040 − 5000) × 3% = 6960 × 3% = 208.80 ✓

## 2. 三条边界（都是"不做就会算错钱"的那种）

### 2.1 总额只有一个来源

`salary_standard.monthly_amount` 是月薪总额；`salary_structure_item` 只解释**它由哪些项组成**。
两者不一致时 `fn_salary_structure_set` 直接拒（`E_SS_SUM`），**不做按比例缩放** ——
缩放会让用户以为设的是 13000，发出来却是别的数。

### 2.2 拆结构不改变金额

算薪仍以 `monthly_amount` 为基数，结构只决定工资条**明细行怎么拆**：

```
BASE = 月薪总额 − 其它固定项之和
```

所以加结构前后，任何人的应发、社保、个税、实发**一分不变**（SL4 守着这条）。
默认值 = 上线前的行为，这是全项目一致的原则。

### 2.3 提成是工资，报销不是

| | 提成 `commission_record` | 报销 `expense_claim` |
|---|---|---|
| 进应发 | 是 | **否** |
| 计税 | 是 | **否** |
| 工资条明细 | 有 `COMMISSION` 一行 | **没有** |
| 付款 | 随工资发 | 单独一张单、单独付款 |
| 参与条件 | `status='approved'` | `approved` / `paid` 才计入合计 |

混进工资条会让个税算错，也会让"应发合计"在财务口径上失真。

## 3. 口径做成制度项，不写死

| 制度项 | 默认 | 为什么是配置 |
|---|---|---|
| `PAY_WORK_HOURS_DAY` | 8 | 标准工时 / 综合工时决定加班与日薪 |
| `PAY_DAYS_PER_MONTH` | 21.75 | 直接影响事假扣款（SL8 有反例：改 20 → 2 天事假扣 800 而非 735.63） |
| `PAY_LEGAL_HOLIDAY` | paid | 法定假带薪还是按最低工资，各地不同 |

`fn_leave_deduction` 原来把 21.75 写死在 SQL 里，现在读制度项 —— **默认值与原来同值**，
所以升级当天所有人的扣款不变，但客户改制度会真的生效。

## 4. 一个必须修掉的坑：账号 id ≠ 人员 id

`resolveEmployee` 原来直接 `WHERE em.person_id = userId`，靠的是"种子里 account.id 恰好等于 person.id"。
钉钉同步进来的帐套立刻错位（admin 没有人员，后面的账号全部错开一格）：

- 示例员工：账号 **6** / 人员 **5**
- 结果：她打开工资条、打卡、请假，全部落到**杨继勇**头上
- 页面不报错，只是"数不对"

修法：先按 `sys_account.person_id` 取人员，账号没挂人员时才退回把 userId 当人员 id
（测试与内部调用会这么传）。一条 SQL，但影响所有"我的"功能。

**这类错不会让任何断言变红** —— 因为断言用的是同一套错误假设。它只在拿真实数据跑时才暴露。

## 5. 同一天重设结构要能覆盖

087 关旧版本时只关 `effective_from < p_from`，于是"同一天改了拆分比例再存一次"会撞排他约束。
拆结构本身就是在试数字，第一次拆不顺手是常态。088 修正为：

- 同一天重设 → **整组替换**（工资条明细在算薪那一刻写进 `payslip_item`，不依赖这一行）；
- 跨天调整 → 关旧版（`effective_to = p_from − 1`），历史不动。

## 6. 断言

| 断言 | 守的是 |
|---|---|
| SL1 | 各项之和 ≠ 月薪总额 → `E_SS_SUM`（不按比例缩放） |
| SL2 | 把个税（算出来的）拆进结构 → `E_SS_ITEM` |
| SL3 | 结构 6000+1500+500 = 8000，合计对得上才让存 |
| SL4 | 工资条按结构拆成多行，拆完应发仍是 8000 |
| SL5 | 拆明细之后勾稽仍成立（`v_payslip_consistency` 为空） |
| SL6 | 提成计入应发并计税（应发 +2000、个税跟涨） |
| SL7 | 报销不进应发、不计税、不进明细 |
| SL8 | 月计薪天数改 20 → 2 天事假扣 800；改回即复原 |
| UI13 | 工资条页 = 我的工资表（口径 + 结构或空态） |

## 7. 基础数据前提（新帐套上线前必配）

1. `si_policy`：城市 + 险种 + 生效日 + 基数上下限 + 个人/公司比例。空库上算薪会
   `E_SI_POLICY_MISSING` —— 这是**有名字的失败**，比算出 0 社保好。
   上海示例：pension 0.08/0.16，基数 7384–36921（真实参数以客户所在地为准）。
2. `tax_param`：年度减除费用（2026 = 5000/月）。
3. `salary_standard` + `salary_structure_item`：月薪与结构（`tools/seed-salary.mjs`）。

## 8. 未做（登记为后续）

- **个税专项附加扣除**（子女教育/房贷/赡养老人）：现在只算 5000 起征点，真实申报会少算扣除；
- **社保多险种**：现在只算养老 8%，医疗/失业/公积金未接；
- **报销审批流**：现在是 pending → approved/rejected 的直改，没走 approval 引擎；
- **提成规则**：现在按金额录入，没有"按订单额 × 比例"的规则引擎；
- **年终奖单独计税**：需要另一套税率表。
