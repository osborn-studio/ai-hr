## 1. 那个推论错在哪

当时的推理：

> 启动命令是 `node app/server.mjs > /tmp/aihr-8788.log 2>&1`，`2>&1` 会把栈写进日志；现在日志只有一行 `listening`、没有栈 → 只能是外部 SIGKILL（OOM）。

它有**两个独立的漏洞**，任一个都足以让结论不成立：

**① `>` 是截断重定向，不是追加。** 每次启动都会把文件清空重写 —— 所以"只有一行 `listening`"**正是任何一次正常启动的样子**。它同时符合"被杀"和"被重启"，无法区分。

```sh
printf 'A\nB\nC\n' > /tmp/x.log ; printf 'only-one-line\n' > /tmp/x.log ; wc -l /tmp/x.log
# → 1   前一次的 3 行已被清空
```

**② SIGKILL 不给进程写日志的机会。** 信号直接终止进程，没有任何 handler 会跑 —— 所以**被杀时本来就不会有栈**。"没有栈"是被杀时的**预期表现**，不是它的**证据**。

把这两条合起来看，这个推论的方向是反的：它把"被杀时的正常样子"当成了"被杀的证明"。

> 这条的普适形式：**用"某处没有留下痕迹"去证明"某事发生过"，先要证明"如果它发生过，痕迹会留在那里"。** 日志被截断、进程被强杀，都恰好让痕迹**不会**留在那里。

## 2. 三个观测量（我实测过，数字是取到的真值）

判"死没死"不要只看日志，看这三样，且**按顺序**：

| 观察量 | 命令 | 活着 | 死了 | 备注 |
|---|---|---|---|---|
| **端口是否还在听** | `lsof -iTCP:8788 -sTCP:LISTEN -n -P` | 退出码 `0`，输出含 `(LISTEN)` | 退出码 `1`，输出为空 | ★ **别透过管道看 `$?`** —— 见 §2.2 的现场反例 |
| **健康检查是否回** | `curl -sS -m 3 -o /dev/null -w '%{http_code} %{time_total}\n' http://127.0.0.1:8788/api/health` | **任何 HTTP 状态码都算活着**：`200`、`401`、`403`、`404`… | `http_code=000`（一个字节的 HTTP 都没回来） | ★ **`401` 是"活着且要求鉴权"**，不是"接口坏了"（实测本仓 `/api/health` 就回 401） |
| **请求是怎么失败的** | 同上，看 `curl` **退出码** | `0` | `6` / `7` / `28` / `52` / `56`，含义各不相同 | 这是本轮最关键的一条 |

> **"活着"的判据是"回了 HTTP"，不是"回了 200"。** 只看 200 会把所有要鉴权的接口读成"服务挂了" —— 而这类接口恰好是健康检查/管理面最常见的形态。
>
> **500 也是活着**（进程在，只是这条请求炸了）、**429 也是活着**（在正常工作，只是自己把自己拦住了）。**只有 `http_code=000` 才是死** —— 那是"一个字节的 HTTP 都没回来"。看到 500/429 就去查进程，是最常见的一步错。

### 2.1 五种失败形态，`http_code` 全是 `000` —— 只有退出码能分开

这五种我都在这台机器上**亲手复现过**（`7` 直接打空端口；`52`/`56` 用一个"接受连接但不回 HTTP"的临时 TCP server 打的；`6` 打一个不存在的域名）：

| 形态 | `curl` 退出码 | `http_code` | `total` | 含义 | 该查什么 |
|---|---|---|---|---|---|
| **解析失败** | **6** | `000` | ≈0（实测 0.0013s） | 域名解析不出来：**根本没到网络层**（DNS 挂了 / 域名拼错） | 地址拼写、`/etc/hosts`、DNS |
| **拒连** | **7** | `000` | ≈0（实测 0.0002s） | 没人监听：进程不在 / 没 bind / 端口改了 | 进程、端口、是否被 restart |
| **超时** | **28** | `000` | ≈ `-m` 的值（实测 2.011s @ `-m 2`） | **进程在，但不回**：单连接被占 / 慢查询 / 死锁 | SQL 计划（见 §5） |
| **空回复** | **52** | `000` | ≈0（实测 0.0004s） | accept 了但**一个字节都没发就正常关闭**（FIN：优雅退出中、或 handler 提前 return） | 应用日志、启动/退出路径 |
| **连接被重置** | **56** | `000` | ≈0（实测 0.0003s） | **RST**：进程崩了 / 被 kill 在请求中间 / 中间层掐断 | 系统日志（§4）、崩溃/重启记录 |

```
# 实测（原始输出，可照着复现）
解析失败 curl: (6)  Could not resolve host: no-such-host...  http=000 total=0.001300s connect=—（未发起连接）
拒连     curl: (7)  Failed to connect ... after 0 ms         http=000 total=0.000201s connect=0.000000s
超时     curl: (28) Operation timed out after 2011 ms        http=000 total=2.011320s connect=0.000204s   ← 黑洞地址，-m 2
空回复   curl: (52) Empty reply from server                   http=000 total=0.000410s connect=0.000159s
重置     curl: (56) Recv failure: Connection reset by peer    http=000 total=0.000333s connect=0.000171s
```

**读法（按顺序，别跳）**：

1. **`total` 只分"慢"和"快"**：≈ `-m` 的值 → `28`（慢，查 SQL）；≈0 → 另外四种"快死"，**`total` 分不出它们**。
2. **"快死"的四种只能靠退出码**：`6`（没到网络层）/ `7`（没人听）/ `52`（听了但零字节正常关闭）/ `56`（连接被 RST）。四者的 `http_code` 都是 `000`、`total` 都≈0 —— **`http_code` 和 `total` 在这里都没有信息量**。

> 补一句 `52` 与 `56` 的区别，因为两者都"瞬间失败"，含义却相反：
> **`52` 是"对方干净地关了"**（FIN，通常是主动退出/优雅停机），**`56` 是"对方被拽断了"**（RST，通常是崩溃、被 kill、或中间层掐断）。
> 所以看到 `52` 该去查"它是不是在正常退出"，看到 `56` 才该去查"它是不是被杀"（§4）。
> 同理 `6` 与 `7` 也容易混：**`6` 是"地址都不认识"，`7` 是"地址认识但没人接"** —— 处置完全不同。

#### ✅ 更稳的写法：不要用 `$?`，让 curl 自己把退出码打进输出（curl ≥ 7.75）

`$?` 是 shell 状态，**任何管道、任何中间命令都会覆盖它**（见 §2.2 的现场反例，今晚这个坑踩了三次）。curl 有 `%{exitcode}`，直接把真值写进同一行：

```sh
curl -sS -m 3 -o /dev/null -w 'http=%{http_code} exitcode=%{exitcode} total=%{time_total}s\n' URL
```

实测（本机 curl 8.7.1，`%{exitcode}` 自 7.75 起可用）——**同一个命令，接管道时 `$?` 骗人而 `%{exitcode}` 不骗人**：

```
$ curl … -w '… exitcode=%{exitcode}' … | tail -1 ; echo "shell exit=$?"
http=000 exitcode=7                     ← 真值在输出里
shell exit=0                            ← ★ 这是 tail 的，不是 curl 的
```

`%{exitcode}` 的好处不是"少写一个变量"，是**它和读数在同一行里，管道、`tail`、`tee` 都改不了它**。

#### ⚠️ 有代理时，`6` 会被"翻译"成 `502`（而且 `exitcode=0`）

实测（这台机器**显式配置**了代理）：

```
$ curl -m 5 -w '%{http_code} exitcode=%{exitcode}' http://nope.invalid/
http=502  exitcode=0     ← 解析失败被代理变成了"网关错误"，而且退出码是 0（一切"正常"）

$ curl -m 5 --noproxy '*' -w '%{http_code} exitcode=%{exitcode}' http://nope.invalid/
http=000  exitcode=6     ← 这才是真的：解析不了
```

**两条纪律**：

1. **要判"解析/连通"这类网络层事实，加 `--noproxy '*'`**（或者确认 `NO_PROXY` 覆盖目标）。否则你测的是**代理**，不是服务。
2. **看到 `502`/`503`/`504` 且 `total` 很小，先怀疑中间层**，别急着说"服务返回了 502"。本仓将来要挂 nginx，这条会变成常态噪声。

> **`NO_PROXY` 必须显式核一次，不能说"一般没问题"。** 本机是 `NO_PROXY=127.0.0.1,localhost,::1`（**配置，不是运气**），所以本文件里打 `127.0.0.1` 的 `6/7/28/52/56` 五组实测都有效。
> 换台机器先跑这一行：`echo "$NO_PROXY"` —— **覆盖了目标 host，读数才算数；没覆盖，你可能在测代理，而且它以 `502 + exitcode=0` 的形式出现（看起来最像"正常"）。**

⚠️ **`time_connect` 不要用来判断连通性。** 实测四种情形它都接近 0：

```
拒连 0.000000s   空回复 0.000159s   重置 0.000171s   黑洞超时 0.000204s
```

连"到底连上没有"都证明不了（黑洞超时看起来比空回复还"连得上"）。**判据只用退出码 + `total`。**

### 2.2 先验证工具本身，再看它的结论（这条最省事，也最容易被跳过）

上面那张表成立的前提是：**你的 `lsof` / `curl` 在你这个环境里真的能出结果**。走查这次做对了一件事，值得抄：

> 他看到 `lsof -iTCP:8788` 返回空，**没有立刻下结论**，而是先拿已知在跑的服务打了一次 —— `ControlCenter 5000/7000`、`DingTalk 8440`、`Electron 18488` 都列得出来。
> **所以 8788 的"空 + 退出码 1"是有意义的，不是权限问题。**

反过来我今天就踩了：`ps -o lstart=` 和 `log show` 在沙箱里直接 `operation not permitted` —— **如果不去分辨"没有"和"不许看"，就会把"沙箱拒绝"读成"没有这个进程"**。

**规矩**：任何"空结果"当证据之前，先用同一条命令打一个**已知存在的对象**。打不出来 → 是工具/权限问题，不是事实。

**同一类错我自己还犯过一次（值得记下来，因为它比规则更防得住人）**：我第一版复现 `52` 的脚本用 `spawnSync` 跑 curl —— 它**阻塞了 node 的事件循环**，于是临时 server 根本没 `accept`（连接躺内核 backlog 里），curl 只能等满 `-m` 报 `28`。**我"测"出来的 28 是仪器坏了，不是被测现场的样子**；改成异步 `spawn` 后才拿到真的 `52`。
——这和"用被截断的日志推断被杀"是同一类错误：**测量工具本身没验过，读数再一致也没意义。**

**还有一个读数陷阱：`$?` 会被管道吃掉 —— 今晚这一条踩了三次（这是本文件里最高频的坑）。**

```sh
lsof -iTCP:8788 -sTCP:LISTEN -n -P | head -3 ; echo "退出码=$?"
# → 0     ★ 这是 head 的退出码，不是 lsof 的（走查踩，真值 1）

curl … -w '… exitcode=%{exitcode}' … | tail -1 ; echo "退出码=$?"
# → 0     ★ 这是 tail 的（走查当天第二次踩，真值 6）

lsof -iTCP:8788 -sTCP:LISTEN -n -P > /tmp/lsof.txt ; echo "退出码=$?" ; wc -l < /tmp/lsof.txt
# → 1  0      ★ 这才是 lsof 的：1 = 没人监听、0 行
```

**一眼自检**：只要写成 `… | 某命令 ; echo $?`，`$?` **一定**不是你以为的那个命令 —— 它是管道最后一节的。

**根治办法**：别用 `$?`，用 `%{exitcode}` 让 curl 把退出码打进同一行（见 §2.1），**管道、`tail`、`tee` 都改不了它**。`lsof` 没有这种变量，就用 `> file` 落盘再取。

**★ 比上面更隐蔽的一种：两个操作数是同一个东西。** 今晚有人要证明"留档的脚本与 HEAD 只有注释差异"，跑的是：

```sh
diff <(git show HEAD:seed-chain.mjs | strip) <(strip seed-chain.mjs)
#          ↑ HEAD                                ↑ 工作区
```
而那时 **HEAD 与工作区本来就是同一份（都是 `970656da`）** —— 空输出是必然的，**那次比较从头到尾没碰到"留档"**。它返回 0、输出为空、看起来"验证通过"，其实回答的是另一个问题。

这类错误的共同特征是：**命令一定成功、结论一定为真、但与你问的事无关**。所以凡是"两个对象比对"，先打印两个对象的身份再比：

```sh
A=$(git show HEAD:$P | shasum -a 256 | cut -c1-12); B=$(shasum -a 256 $P | cut -c1-12)
echo "L=$A R=$B"; [ "$A" = "$B" ] && echo "⚠ 两个操作数同一份，本次比较无意义"
```

**判据**：`L == R` 是"我在拿一个东西跟它自己比"的可判定信号。同理，任何"只有空输出才算通过"的检查（diff / grep / 断言），都必须先说清**比的是哪两份**，否则它只在证明"这文件等于它自己"。

顺带一条：`grep -v "^[+-][+-]"` 这种"过滤 diff 表头"的写法两头都不准 —— 顶格的 `+--` 会被连内容一起吞（假绿），缩进的漏出来（假红）。要过滤注释就先**归一化文件再比文件**，不要拿 diff 的行首前缀当判据。

### 2.3 一个真实例子：**同一个端口，两个相反的判定**（这正是本节最该记住的）

同一个 `8788`，前后两次测，结论完全相反 —— 而两次都判对了：

```
【时刻 A】curl :8788/api/health  → exit=7  total=0.000154s      ← 拒连
          lsof -iTCP:8788 ...    → exit=1、0 行                 ← 没人听
          控制组：同一条 lsof 能列出 ControlCenter 5000/7000、DingTalk 8440、Electron 18488
          ⇒ 判定：**真死**（那一刻确实没进程）

【时刻 B】lsof -iTCP -sTCP:LISTEN -n -P | grep node
          → node 73122 ... TCP 127.0.0.1:8788 (LISTEN)           ← 换了 PID，活着
          curl :8788/api/health  → http=401  exit=0  total=0.000929s
          ⇒ 判定：**活着且要求鉴权**（401 不是故障）

【时刻 C】再过一会儿同一端口：PID 79412                       ← 又换了一台实例
```

三条教训：

1. **判据要能"同向才算数"**：单看 `curl exit=7` 可能是打错端口，单看 `lsof` 空可能是工具没权限。**控制组排除后者，两路一致排除前者** —— 这是时刻 A 敢下结论的原因。
2. **任何判定都是"某一刻 + 某个 PID"的**：把结论写成"8788 是死的"，而不是"8788 在某个时刻（那时 PID 还是上一个）是死的" —— 下一个人就会拿一条过期结论当现状。
   ★ 本文件自己就差点犯这个错：v2 写的是"8788 = 真死"这个**现在时**判断，而它很快变成 PID 73122、又变成 79412 活着服务。观察必须带时间戳和 PID，否则它只是一个传闻。
3. **不带 PID 的耗时数字，跨实例不可比**：`0.57–0.98s` 是 `PID 73122` 那台的成绩；换成 79412 那台再测，数是另一回事（可能是冷启动、可能配置不同）。**报"这个接口 0.9 秒"而不说"在哪台实例上"**，和报"服务死了"是同一类问题。

### 2.4 共享环境观测纪律（本轮最大的噪声源，不是仪器）

这台机器上今晚 `8788` 被重启了**至少 7 次**（PID `34118 → 43230 → 73122 → 79412 …`）。走查有一次连打 10 次全 `000`，读成"tree 把服务打死了"，**实际是别人在同一分钟内重启了服务** —— 那不是仪器坏，是**观测窗口被第三方污染**。

三条纪律：

1. **判"服务死了"之前，先确认这一分钟没人动过它**：问一句、看 PID 是否换了、看 supervisor 重启计数。
2. **连打类实验，先记 PID，打完再取一次**；PID 变了 → **整批作废**，不是"服务中途挂了"。
3. **"我 curl 没反应"不是证据**；**"我 curl 没反应 且 PID 没变"** 才是。

```sh
PID0=$(lsof -tiTCP:8788 -sTCP:LISTEN)        # 打之前
# … 连打 N 次 …
PID1=$(lsof -tiTCP:8788 -sTCP:LISTEN)        # 打之后
[ "$PID0" = "$PID1" ] || echo "★ PID 变了（$PID0 → $PID1），这一批读数作废"
```

> 这一条和 §2.2 是一对：**§2.2 防"仪器坏了"，§2.4 防"被测对象被别人换了"**。两者都不出现时，读数才算证据。

**★ 顺带一条"我们其实没防住"的实话 —— "有断言"和"防住了"是两件事。**

这个 bug（PG 通用计划，60 店库上第 6 次请求 168ms → 31s）**仓库里没有能测出它的回归断言**：

## 3. 要让日志本身可信，得先改启动命令

- **别用 `>`，用 `>>`**（追加），或者 `| tee -a`。截断重定向会让"上一次的遗言"在下次启动时消失 —— 而事故现场最需要的恰恰是上一次的遗言。
- 追加会让文件无限长大 → 配 `logrotate` 或每天一个文件名（`/tmp/aihr-$(date +%F).log`）。
- 想要"哪一行是这一次启动写的"，就**自己打一行分隔**：`echo "=== start $(date -Is) pid=$$ ===" >> log`。比事后靠时间戳猜可靠。
- **别用 `2>&1 | tee` 去看护进程**（管道会把 SIGKILL 之外的真实退出码也吃掉）；要看护就用带重启的 supervisor，它自己会记重启次数 —— 那就直接回答了"被杀还是被重启"。

## 4. 真要判 OOM / 被杀，得去系统侧，不在应用日志里

应用日志里**永远**不会有 SIGKILL 的证据（原因见 §1②）。要看的是内核/系统：

```sh
# macOS：jetsam（内存压力杀进程）事件
log show --last 30m --predicate 'eventMessage CONTAINS "jetsam"' --style compact | tail -20

# Linux：OOM killer
dmesg -T | grep -iE 'killed process|out of memory'
```

判据是**有没有这条内核记录**，不是"应用日志里有没有栈"。

> ⚠️ 这两条命令**本文没有在本机验证过**：沙箱拦了 `ps` / `log show`（`operation not permitted`）。它们按 macOS / Linux 的标准用法写，第一次在真机上用请先确认本机有这两条命令、且 `log show` 有读日志的权限（通常不需要 sudo，但受限的 TTY 上可能被拒）。**§2 那三个观测量是实测过的**，这一节的两条是待核。

## 5. 这次事故的正面教训（比上面几条更省时间）

那次真实的形态是：**请求 200、行数对、数据全对，只是从第 6 次开始慢 180 倍**。从 15 秒超时的客户端看，它和服务挂了一模一样。

所以排查顺序应该反过来 —— **先花 30 秒问"它是不是只是慢"，再花半小时查"它是不是死了"**：

```sh
# 一次请求打三个数：状态码 / 连接耗时 / 总耗时；-m 给足（30s）
curl -sS -m 30 -o /dev/null -w 'http=%{http_code} connect=%{time_connect}s total=%{time_total}s\n' \
  http://127.0.0.1:8788/api/org/tree
```

`total` 是 `29.x` 而 `connect` 是 `0.00x` → **服务活着，某个查询在拖**。这时候该看 SQL 计划，不该看内存。
（这次的答案是 PG 通用计划：同一语句执行 5 次后改用通用计划，`plan_cache_mode=auto` 是默认值；`179` 把每条连接强制成 `force_custom_plan`。**阈值 5 属于 PG，不是我们的代码** —— `179` 文件头把三条排除实验都记了，别重走。）
