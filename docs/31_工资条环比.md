# 工资条环比：说清"这个月为什么少了 300"

> 记录日期：2026-11-15 ｜ 迁移 136 ｜ 断言 480 / 208 / 27

## 1. 这是 HR 被问得最多的一句话

现在系统能给出的答案是"你自己看明细"。明细能看出**每一项是多少**，看不出**哪一项变了**——
人要在十几行里逐行比对，还要记得上个月长什么样。

这一版把这件事拆成两半：

| 函数 | 回答 |
|---|---|
| `fn_payslip_diff` | 哪一项变了（逐项对比，标 `changed` / `added` / `removed`） |
| `fn_payslip_explain` | 为什么变（归因，每一句带具体数字） |

## 2. 归因只能放库里，不能在前端拼

前端拼解释只能看工资条自己（逐项差额），看不出"因为 7 月调基"这种跨表原因。
而**"为什么"恰恰是员工问的那件事**。差额是现象，归因才是答案。

所以归因要跨四张表：

| 归因 | 数据来源 |
|---|---|
| 出勤天数变了 | `att_period_report`（HR 确认过的那份才是算薪口径） |
| 加班工时变了 | `fn_att_ot_split`（三档分开，不混成一个总数） |
| 调薪 | `salary_standard` 的生效日落在本月 |
| 社保调基 | `si_base_declare` 的生效日落在本月（133） |
| 一次性项 | 明细里出现/消失 `AL_CASHOUT` / `ANNUAL_BONUS` / `SEVERANCE` |
| 个税跳档 | `cum_taxable` 与税额的变化（累计预扣会随月份往上升档） |

## 3. 不硬编理由

能对上账的才说，对不上的老实说"其余项目也有变动，需要人工核对"。

这一条比看起来重要：硬编一个原因（比如"因为绩效下降"）可能完全猜错，
而 HR 会照着这个错原因去跟员工解释——比不给原因更糟。

`DIF2` 也是这个思路：基准月没有工资条时，直接说"无法环比 —— 可能是新入职、上月未算薪"，
而不是把每一项都标成 `added`（那样看起来像"这个月突然多了十几项"）。

## 4. 一个差点写错的求和

`DIF1` 断言"明细差额合计 = 两个月应发之差"。第一版写成：

```js
d.filter(x => !/^SI_/.test(x.item_code) && x.item_code !== 'IIT')
```

跑出来差 **720 元**。原因：扣款项不止社保和个税——年终奖还有单独一行 `BONUS_TAX`（108）。

工资条上的"应发"是**扣之前**的数，而明细里混着扣款项（金额为负）。
求和时必须把扣款项全摘出去，否则差额永远对不上，而人会以为是环比算错了。

## 5. 断言

| 断言 | 钉的 |
|---|---|
| `DIF1` | 应发项差额合计 = 两个月应发之差（一分不差） |
| `DIF2` | 基准月没工资条 → 说"无法环比"，不是一片新增 |
| `DIF3` | 归因第一句是应发合计变化，带两个具体数字 |
| `DIF4` | 一次性项被单独点出来（不是混在"某项变了"里） |
| `DIF5` | 归因按 `seq` 连续编号（前端直接按序展示） |
| `DIF1-4`（接口） | 两段返回、第一条是应发、无法环比、期间写错 400 |
| `UI26` | 工资条页有「与上期对比」入口 |

## 6. 界面上在哪

工资条页（`#payslip`）→「最近一期工资条」卡片 →「与上期对比」。

点开显示两段：上面是归因列表（人能直接读的句子），下面是逐项对比表
（上期 / 本期 / 差额 / 变动类型）。差额为正标绿、为负标红。

## 7. 还没做的

| 项 | 为什么 |
|---|---|
| 跨多期趋势 | 现在只比上一期。要看"最近 6 个月实发怎么走的"，那是另一张图，不是这张表 |
| 自动推送给员工 | 现在 HR 点开看。要推到员工端，得先有"员工自助"那一层（现在只有 HR 视角） |
| 归因的置信度 | 现在所有归因都平铺。理论上可以算"这一条解释了多少差额"，但四舍五入后容易给出误导性的百分比 |
