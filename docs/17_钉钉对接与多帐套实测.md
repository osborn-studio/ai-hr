# 钉钉对接与多帐套：实测记录

> 这份文档记的是**真跑过**的东西：真钉钉组织、真账号、真打卡流水、真 PostgreSQL。
> 没有跑通的步骤不写进来；写进来的每一行都对应一条命令或一条断言。

---

## 一、钉钉后台需要做什么（客户视角）

结论：**读组织、读人员、读考勤打卡，一件事都不用改**——用已经授权的应用就能读全公司
（本次实测读到了 16 个部门、31 个人、17 条打卡流水）。

真正需要在钉钉后台动的，只有"要不要秒级"这一个选择：

| 需求 | 要不要改后台 | 做法 |
|---|---|---|
| 组织/人员/打卡**分钟级**同步 | ❌ 不用 | 轮询 `attendance +check-record`，每 30–60 秒一次（本仓已实现） |
| 打完卡**秒级**出现 | ✅ 要 | 企业内部应用 → 事件订阅 → 考勤打卡事件 → 回调地址（需公网 HTTPS 或 Stream 长连接） |
| 从钉钉发起请假/补卡，回到本系统审批 | ✅ 要 | 订阅审批事件（`user_oa_approval_*`），本仓已有 OA 事件能力 |
| 用钉钉扫码登录本系统 | ✅ 要 | 应用加"扫码登录"权限，并把 `login` 换成 OAuth 回调 |

**当前实现选的是轮询**，理由写在 `tools/watch-dingtalk.mjs` 头注释里：
零配置、可中断、可回放，而幂等键在库里（`punch(source, ext_id)` 唯一），
所以"轮询多次"与"事件推送多次"是同一种安全。要换成事件，只需把
`listPunches()` 换成回调写同一个 `fn_punch_ingest`，上层一行不用改。

### 权限点（如果要自建应用直连）

不是用 `dws`（本仓现在走的通道），而是自建企业内部应用时，至少要这些：

```
Contact.User.Read            读成员
Contact.Department.Read      读部门
Attendance.Record.Read       读打卡原始流水（+check-record）
Attendance.Group.Read        读考勤组（可选）
```

`dws` 这条路已经把这些包好了（含 token 刷新、限流退避、多企业切换），
所以 `app/services/dingtalk.mjs` 只做三件事：调命令、抹平返回形状、转成中间结构。
**要换直连，只改这个文件的 `run()`**，上层不用动。

## 二、同步了什么（真实结果）

```
帐套 DM（香香鱼米，独立库 aihr_demo）
├── 16 个部门（按钉钉部门树原样建，kind='dept'，可嵌套）
├── 31 个人（各自挂在自己的部门，工号 E0001–E0031，账号 dmXXXXXX）
└── 17 条打卡原始流水（source='dingtalk'，ext_id = 钉钉记录 id）
```

命令两条：

```bash
# 全量（组织 + 人员 + 打卡）
DATABASE_URL=postgres://.../aihr_demo node tools/sync-dingtalk.mjs \
  --ledger YH --name "香香鱼米" --period 2026-11 --punch-days 10

# 增量（只拉打卡，10 秒内跑完）
DATABASE_URL=postgres://.../aihr_demo node tools/sync-dingtalk.mjs --only-punch --punch-days 1

# 挂着等打卡（每 30 秒一次）
DATABASE_URL=postgres://.../aihr_demo node tools/watch-dingtalk.mjs --every 30
```

幂等已实测：同一份流水导两次，第二次全部记为 `重复`，`punch` 表行数不变。

## 三、四条口径（决定了同步出什么）

1. **只接原始流水，不接"考勤结果"**。钉钉的 `+check-result` 是它按自己的考勤组规则
   算的迟到/缺卡结论，休息扣除与跨天归属口径与本系统不同。接结论 = 两套账混进一个字段。
2. **组织按钉钉树建**，不折叠成"一家店"。076 之后部门可嵌套，
   于是"人事行政部/实施部/财务部"都是真部门；连锁餐饮把部门起名叫"XX门店"即可。
3. **对不上不动**。同级重名按父范围查重；已映射的人只刷新姓名与部门快照；离职是状态不是删除。
4. **归属是区间的**。换部门 = 关旧行 + 开新行，不删历史（`ex_eoa_no_overlap` 守着）。

## 四、多帐套：一个帐套一个库

`tools/new-ledger.mjs` 六步开库（库名白名单 → CREATE DATABASE → 跑迁移 →
建帐套与根组织 → 建管理员 → 回控制库登记）。控制库只记"哪个帐套连哪个库"。

路由靠 **token 前缀**（`<帐套编码>.<随机串>`）：

| 断言 | 证明 |
|---|---|
| RT1 | 控制库列出多个帐套，且不回库名 |
| RT2 | 登录带帐套 → token 带前缀 |
| RT3 | 该 token 在自己的帐套上可用 |
| RT4 | 把前缀改成另一个帐套 → 401（会话不在那个库里） |
| RT5 | 不存在的帐套 → 404，**不回落**到默认库 |
| RT6 | 两个帐套的组织互不可见 |
| RT7 | 在线开库（接口）→ 第三个帐套立刻能登录 |

`node test/multi-ledger.test.mjs` 跑这一组（需要真 PostgreSQL；没有则跳过并说明）。

## 五、这一轮跑出来的四个真问题

1. **`app_begin_scope` 用 `current_date`**（会话时区 UTC = 昨天）→ 今天配的权限
   在行闸里"还没生效" → 老板登录看到 **0 人**，而库里 31 个人都在、psql 手敲全对。
   修：077 改成 `app_today()`。这是"漏了最要紧那一处"的典型（071 只改了三个函数）。
2. **`fn_account_create` 的授权生效日用 `current_date`** → 新建账号登录成功、下一步全 403。
   修：071。
3. **批次计数在事务内自增** → 回滚后计数不还原，`total = ok+skip+fail` 约束炸。
   修：计数移到事务外（`run.mjs` 里那次是镜像问题：计数随回滚消失）。
4. **`employee_org_assignment` 关旧行时 `valid_to < valid_from`** → `ck_eoa_span`。
   修：当天新建的归属直接删（它一天都没生效过），有历史的才关区间。

## 六、还没做

- **事件订阅**（秒级打卡）：要钉钉后台配合，见第一节。
- **写回钉钉**：单向是有意的 —— 两边都能改必然产生"谁赢"，而那个答案会随时间变。
- **人脸/指纹打卡**：不做。它需要设备与生物特征合规，不属于这套系统的边界。
