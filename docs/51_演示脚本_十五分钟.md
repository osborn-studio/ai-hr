## 2. 主线一：组织与编制——"三个数为什么不能相加"（4 分钟）

**路径**：人事组织 ▾ → 组织架构

屏幕上应该看到（这一屏就是"集团—城市—门店"三层）：

| 位置 | 数字 |
|---|---|
| 节点数 | 集团 1 · 城市 6 · 门店 **60** |
| 集团编制 | **396** |
| 门店编制合计 | **388** |
| 门店缺口合计 | **14**（4 家缺 3、1 家缺 2，其余满编） |
| 档口实例 | **261** |

然后点开任意一家店 → 门店档口段，能看到这家店的档口、每个档口的编制与到岗。

**要讲的一句话**（这是这套系统最容易被问倒的地方，讲清就赢了）：

> "**396 不是门店编制**。门店那 60 家加起来是 388，另外 8 个是集团和城市手里留的**机动编**——
> 留给新店开张、临时顶班、店长储备。所以集团那一行显示'缺 22'，
> 其中只有 14 是真缺人，8 是**故意空着**的机动编。"

如果对方追问"那到底缺几个人" → 回答 **14 人（5 家店）**，不要说 22。

**如果数不对先怀疑什么**：切换过月份（组织页读的是**所选日期所在月**的编制）。
演示固定看 **2026-06** 或当月；看别的月份会进入"沿用"状态（见 §3）。

## 3. 主线二：编制"定了就一直用"，但要标出来（新能力，4 分钟）

**路径**：人事组织 ▾ → 编制（或组织架构页上直接切月份）

把日期切到 **2026-09**（一个从没单独定过编的月份）。屏幕上应该是：

| 位置 | 2026-06 | 2026-09 |
|---|---|---|
| 集团编制 | 396（本期定的） | **396 沿用 2026-06** |
| 门店档口编 | 各档口按本期配 | **沿用 2026-06**（汇总行写"M 个档口沿用上期定编"） |

**要讲的一句话**：

> "客户的真实诉求是'定了一次就一直用，要改的时候才动'。所以没配的月份不再是空的，
> 而是**沿用上一期**。但沿用有个副作用——**'忘了配'和'这期不需要人'会变得一模一样**。
> 所以我们把出处标出来：这里写'沿用 2026-06'，让人一眼知道这个数**不是这期核过的**。"

**再切到 2026-04**（早于最早一期）：应该显示 **未定编 / 空**，不是 0。
这一条要主动讲，因为它证明系统**不会把"从来没定过"编成一个数**：

> "从没定过的节点，我们宁可显示'未定'，也不显示 0 —— 0 是'定了但一个编都不给'，
> 空是'还没定'，这两件事的处置完全不同。"

## 4. 主线三：档口与岗位——餐饮特有的一层（4 分钟）

**路径**：人事组织 ▾ → 组织架构 → 点开一家门店 → 档口段

讲三件事，每件一句：

1. **档口 = 门店里的"部门"**，但档口不是组织节点，它挂在门店上（`store_station`）。
   一家店可以配不同数量与种类的档口。演示库里一家标准店是 8 个：
   **前厅服务档 / 收银档 / 水台档 / 炉灶档 / 砧板档 / 打荷档 / 上什蒸锅档 / 洗碗保洁档**
   （有的店少一两个 —— 这正是"不同门店配不同档口"）。
2. **门店数人头、档口数岗次** —— 一个人可能在两个档口有岗（头灶兼打荷），
   所以"Σ档口编（**283**）"不等于"门店编（**388**）"，也不该相等。
   全库另有 **261 个档口实例**、档口侧缺岗 14。**这几个数不能相加**：门店数的是人头，
   档口数的是岗次，一个人两头都算就会翻倍。
3. **缺岗明细点得开**：点"缺 3"能看到缺的是哪个档口的哪个岗位，而不是只说一句"缺 3 个人"。

**如果被问"厨师长能不能只看自己档口的人"** → 答：**能做，默认关**。
说法：

> "有一个能力位（`people_station_scope`），开了之后花名册/考勤/排班三处只返回本档口的人；
> **认不出你在哪个档口时返回 0 行，而不是退回看全店** —— 收窄类权限必须安全失败。
> 默认不授给任何角色，所以今天看到的还是全店。"
>
> **不要现场授位演示**：演示库每个档口只配了 1 个岗 1 个人，授完花名册会从 11 人变 1 人，
> 那不是 bug，是演示数据配不齐，但现场很难解释。

## 5. 收尾：算薪与工资条（3 分钟）

**路径**：薪酬 ▾ → 算薪 → 选 2026-08 批次；再点 工资条

| 位置 | 数字 |
|---|---|
| 三期批次 | 2026-06 / 07 / 08，各 **sealed** |
| 每期工资条 | **374 张** |
| 2026-08 应发合计 | **2,644,512.00** |
| 打印分组 | **60 组**（按门店） |

**要讲的一句话**（关于遮挡）：

> "工资条的实发金额默认是遮住的（`••••`），点一下才展开。这不是加密，挡的是'扫一眼、
> 截个图、顺手复制'。而且**遮的原则是口径统一**：一屏里只要出现别人的行，就全部先遮；
> 只有一个人的清单（他自己）不遮 —— 自己的钱遮住反而像系统坏了。"

**权限那一句**（有人一定会问）：

> "所有人默认只看得到自己的工资条。只有授了'薪酬全量读'的人才能看整批 —— 这一层是**人员闸**，
> 在行闸之后。店长能看到本店的人，但**工资条只返回他自己那一行**。"

## 6. 常见追问与标准答案

| 问 | 答 |
|---|---|
| 多少人 | 60 家店 / 374 人在编 / 68 个账号 |
| 能多人同时用吗 | 演示版是单进程（数据在进程里），**一次一个人操作最顺**；上线形态换真 PostgreSQL |
| 能外网访问吗 | 能，走反向代理加 HTTPS；配置位与四条硬要求写在 `docs/50` |
| 数据是真的吗 | 组织/人员/算薪是**虚构的演示数据**，按真实连锁业态的规模与结构编的 |
| 开机自启吗 | 有 launchd 脚本，装一次即可（`docs/50 §5`），建议定稿后再装 |
| 缺勤/加班怎么算 | 走考勤人日 → 封账 → 算薪，**封账之后改数不影响已算过的工资** |
