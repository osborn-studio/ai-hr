# 32 · 算薪预演

> 目的：改参数之前先看影响面。**这一页的价值不在"算得准"，而在"点什么都不会变"。**

## 1. 问题

调津贴、调社保基数、改制度项之前，没人说得清"这一改会多花多少钱、谁变化最大"。
原来的唯一办法是**改了再算** —— 而算完之后工资条就已经落账了，想反悔要重算，
重算又动了历史月份的累计预扣。

HR 因此形成一种行为：不敢试。要么凭经验拍，要么干脆不改。

## 2. 两条硬要求

| 要求 | 为什么 |
|---|---|
| **数要对** | 必须用真的算薪函数 `fn_payroll_calc` 跑，不能另写一套近似算法。两套算法一定漂 |
| **零痕迹** | 跑完之后库里不能多一行、不能少一行、不能改任何金额 |

第一条排除了"用公式估一下"的写法；第二条排除了"先算真、再删掉"的写法
（删的时候只要有一个分支漏了，就会留下一条 `pay_run` 或一张 `payslip`）。

## 3. 怎么做到零痕迹

用 PL/pgSQL 的**块级异常**：

```sql
BEGIN
  -- 建批次（如果需要）→ 算一遍（基线）→ 应用覆盖 → 再算一遍 → 取数进变量
  v_out := jsonb_build_object(...);
  RAISE EXCEPTION '%', v_tag;   -- 哨兵：认得出的"错"
EXCEPTION WHEN OTHERS THEN
  IF SQLERRM <> v_tag THEN RAISE; END IF;   -- 别的错照常上抛
END;
RETURN v_out;
```

- `BEGIN ... EXCEPTION` 块入口有隐式 SAVEPOINT，异常发生时回滚到块入口 ——
  块内所有 `INSERT/UPDATE` 全部撤销，**包括为预演临时创建的 `pay_run`**；
- 局部变量的值**不随回滚丢失**，所以结果能带出来；
- 哨兵用 `md5(random()::text || clock_timestamp())` 生成，不会跟真实错误撞；
- 不是哨兵的异常（考勤未封账、绩效未封存、一个人都没算出来）**原样上抛**。

### 为什么不用 SAVEPOINT + ROLLBACK TO

服务层拿到的是连接，回滚会把审计留痕一起滚掉；显式 `RELEASE` 之后又没法回滚。
哨兵异常是**纯函数内**的、对调用方无感的做法 —— 调用方看到的只是一个正常返回的 jsonb。

## 4. 支持哪些覆盖

| 键 | 例 | 说明 |
|---|---|---|
| `salary_pct` | `5` | 月薪标准整体 ×(1+pct/100) |
| `salary_add` | `300` | 每人月薪 + 固定额 |
| `si_base_pct` | `8` | 已申报社保基数整体 ×(1+pct/100) |
| `policy` | `{"PAY_OT_AUTO":"on"}` | 制度项改为该值（**本期 1 号**生效） |

- 月薪只改"算薪会用到的那一条"（每个任职 `effective_from` 最大且 <= 期末），
  改全部历史行会把过去月份一起改掉 —— 那就不是"预演本月"了；
- 制度项的生效日放在本期 1 号：只影响本期及以后，不动历史；
- 涨薪可能把 `monthly_amount` 变负，用 `GREATEST(..., 0)` 兜住（表上有 `>= 0` 约束）。

## 5. before 规则门搬进了库里

137 之前，"算薪前过 before 规则"那段逻辑在 `services/payroll.mjs` 里：
用 JS 拼变量（所有已启用项 = 0，再覆盖月薪/提成/考勤），逐人 `fn_salary_rule_run`。

预演也必须报"这批人里有 N 条 before 规则会拦住算薪"，否则会出现
**"预演说没问题、真算被拦"** 的分裂。而如果预演自己再拼一遍变量，那就是两套逻辑各自漂。

所以提成 `fn_payroll_gate(period, entity)`，服务层改成调它、只负责留痕与汇总。
变量的口径现在只有一个出处。

## 6. 输出

```jsonc
{
  "headcount": 5,
  "base":  { "gross": 47300, "net": 41174.63, "si": 5625.12, "tax": 500.25 },
  "after": { "gross": 49665, "net": 43316.20, "si": 5782.32, "tax": 566.48 },
  "delta": { "gross": 2365,  "net": 2141.57,  "si": 157.20, "tax": 66.23 },
  "movers": [ { "name": "王五", "delta_net": 535.44, "top_item": "BASE", "top_delta": 600 } ],
  "negative_net": [],          // 实发变负的人
  "blocked": [],               // before 规则会拦住的人
  "no_effect": false,          // 改动对本期完全没有影响
  "applied": ["月薪标准：5%"],
  "warnings": ["..."]
}
```

- `movers` 带 **主因那一项**：HR 只知道"他少了 320"是不够的，还得点开两张工资条对 ——
  而这段对话通常发生在电话里；
- `negative_net` 是"参数改坏了"最直接的信号：扣款超过应发，一般是社保基数或扣款项配错；
- `no_effect` 要**明确说出来**。让人自己盯着一排 0 猜，他们会以为预演坏了，然后再也不点。

## 7. 为什么只让改一个制度项

界面上制度项是"一次一个"。同时改三项会影响因果 —— 看到总额变了，但不知道是哪一项起的作用，
而这正是预演要回答的问题。想比较两个方案的组合效果，就分别跑两次看 `delta`。

## 8. 边界（明确不做）

- **不预演"改公式"**：`salary_item.formula` 的改动会影响所有月份，语义上不属于"本期预演"；
- **不预演"改考勤"**：考勤是事实，不是参数。改了就该走考勤报表的调整与审批；
- **封账后不能预演**：算薪函数会拒，预演也不该给出一个"其实算不出来"的数（`E_PAY_PREVIEW_SEALED`）。

## 9. 踩过的坑

1. **`abs(x->>'delta_net')::numeric`** —— `::` 作用在 `abs()` 的结果上，而 `abs(text)` 不存在。
   报错 `function abs(text) does not exist` 看起来像 abs 用错了，实际是类型转换写在了外面。
2. **预演期间不能只按 `period DESC` 取一条**：库里可能存在一期"一个人都算不出来"的批次
   （在职区间/月薪标准对不上），预演会抛 `E_PAYROLL_NO_ELIGIBLE`，
   而断言会误以为是预演本身坏了。测试里改成"逐个候选期间试到 200 为止"。
3. **`pay_run` 的唯一键是 `(period, legal_entity_id, calc_version, kind)`**（108 加的 kind），
   测试里按三列 `ON CONFLICT` 会报 "no unique or exclusion constraint matching"。
4. **截图必须点到结果面板**：静态截图只能拍到按钮，而这个功能的价值全在点完之后。
   用 CDP（`--remote-debugging-port` + `Runtime.evaluate` 点击 + `Page.captureScreenshot`）驱动，
   并且按"最后一张卡片的下沿"定高 —— `scrollHeight` 会把主体 `min-height` 的空白一起截进来。

## 10. 断言

| 组 | 条数 | 钉住什么 |
|---|---|---|
| `PPV1-7`（库） | 7 | 零痕迹（批次/工资条/明细/制度项条数与金额）、无覆盖时差异为 0、调薪 5% 的影响面、制度项覆盖真的接线、实发为负被抓出、封账被拒 |
| `PPV1-8`（接口） | 8 | 接口层零痕迹、总结文案、Top 变动人带主因、类型错/项不存在 → 400、无权限 → 403 |
