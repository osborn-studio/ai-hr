# 节假日、病假与假种：法定是默认值，不是天花板

> 记录日期：2026-11-15 ｜ 迁移 125–127 ｜ 断言 416 / 177 / 19

## 1. 一个必须先分清的区别：放假 ≠ 法定节假日

111 建 `legal_holiday` 时只有一个 `is_workday` 布尔，把三件事混成了一件：

| 类型 | 例子 | 加班费 | 应出勤 |
|---|---|---|---|
| **法定节假日**（11 天/年） | 10/1–10/3、除夕至初三、5/1 | **300%** | 不算工作日 |
| **调休放假** | 10/4–10/7、9/30 之后的调休 | **200%**（休息日） | 不算工作日 |
| **调休上班** | 10/10（周六） | 正常工资 | **算**工作日 |

混在一起算的后果很具体：国庆 7 天假，只有 10/1–10/3 是 300%。全按 300% 算多付近一倍，
全按 200% 算是**少付（违法）**。所以加了 `holiday_type`：`legal` / `rest` / `workday`。

### 数据来源（不猜）

国务院办公厅《关于 2026 年部分节假日安排的通知》（2025-11-04）：

| 节日 | 放假 | 调休上班 |

算出来的应出勤（这些数字可以直接跟 HR 的日历对）：

| 月份 | 应出勤 | 算法 |
|---|---|---|
| 2 月 | **16 天** | 20 个周一至周五 − 春节 6 个工作日假 + 2 个周六上班 |
| 6 月 | **21 天** | 22 个周一至周五 − 端午 1 天 |
| 10 月 | **18 天** | 22 − 国庆 2 个工作日法定 − 3 个工作日调休 + 1 个周六上班 |

> 这份安排每年 11 月才公布，写死在迁移里只能覆盖 2026。
> 所以同时给了维护入口（接口 + 界面），客户自己灌下一年 ——
> 系统不该因为"新的一年没数据"就把应出勤算错，但它也没法替你猜政策。

## 2. 病假：不是"按事假处理"

之前病假按事假全扣。这不只是少给钱，是**违法**：病假期间必须支付病假工资。

依据：

- 《劳动保险条例实施细则修正草案》第 16 条（按连续工龄）：
  不满 2 年 **60%**｜2–4 年 70%｜4–6 年 80%｜6–8 年 90%｜8 年以上 100%
- 《关于贯彻执行〈劳动法〉若干问题的意见》第 59 条：
  病假工资不得低于**当地最低工资的 80%**

实现：`fn_sick_pay(person, period)`

```
病假工资 = 病假天数 × 日薪 × 工龄对应比例
        且 ≥ 天数 × (最低工资 × 80% ÷ 21.75)
```

日薪仍用 21.75（法定折算口径），与事假扣款同一个分母。

## 3. 默认法定，界面可改，改要权限

客户说得很直接：**不要完全按法定，默认是，但要能改，改的权限至少 HR 主管以上**。

所以这一版的设计是：

| | 谁能改 | 改不改得动 | 硬底线 |
|---|---|---|---|
| 月计薪天数 21.75 | boss / hr_ops | ✅ | — |
| 加班倍数 1.5 / 2 / 3 | boss / hr_ops | ✅ | **低于法定直接拒**（触发器） |
| 病假比例 60–100% | boss / hr_ops | ✅ | **低于 60% 直接拒**（约束） |
| 最低工资 | boss / hr_ops | ✅ | 必须 > 0 |
| 假种带薪比例 | boss / hr_ops | ✅ | 0–1 |

三件事必须同时做到，少一件就会出事：

1. **看得见法定默认值** —— 否则没人知道自己是"改了"还是"本来就这样"（界面上当前值与法定值并排）；
2. **每次改都写原因** —— 否则三个月后查不出这个 21.5 是谁定的；
3. **只有 HR 主管以上能改** —— 店长改一个加班倍数，全公司下个月都按它算。

资源码是独立的 `payroll_policy`，只授给 `boss` 与 `hr_ops`。
**薪酬专员（payroll_spec）不算** —— 他是执行者，不是定政策的人。

硬底线不进界面：加班倍数、病假比例低于法定时保存会被拒。这不是"灵活"，是违法。

## 4. 假种：官方预置 + 公司自定义

126 之前 `leave_type` 是**一张空表**。后果很隐蔽：`fn_leave_approved_days(person, period, 'PERSONAL')` 永远返回 0，
于是"事假扣款"从来没真的扣过 —— 不是算法错，是数据里根本没有假种。

现在：

| 假种 | 带薪比例 | 说明 |
|---|---|---|
| ANNUAL 年假 | 100% | 带薪（法定） |
| SICK 病假 | **空 = 按工龄** | 60–100%，不低于最低工资 80% |
| PERSONAL 事假 | 0% | 无薪（全扣） |
| MARRIAGE 婚假 | 100% | 法定 3 天，地方可加 |
| MATERNITY 产假 | 100% | 生育津贴由社保付，工资照发不扣 |
| BEREAVEMENT 丧假 | 100% | 法定 1–3 天 |
| COMP_TIME 调休 | 100% | 加班换来的 |

三条规矩：

- **官方假种不能删**（`E_LEAVE_TYPE_SYSTEM`）：删了历史请假单会指向空白；
- **官方假种代码不能改**：算钱按代码取数，改了会静默失配（表现是"请假不扣钱了"，没人会立刻发现）；
- **公司可以自定义**：加一个"哺乳假 100%"，它自动参与计算，不需要改代码。

为什么是 `pay_ratio`（0–1 的比例）而不是"是否带薪"两个状态：
现实里有"半薪病假""80% 工资的工伤假"。两态表达不了，而多一列成本极低。

算钱的口径统一到一处 —— `fn_leave_deduction` 按假种逐项算：

```
扣款 = Σ 各假种天数 × 日薪 × (1 − 带薪比例)
病假例外：扣「日薪 − 病假工资」（按工龄，有下限）
```

## 5. 这一轮踩的坑

| 坑 | 症状 | 教训 |
|---|---|---|
| **假种表是空的** | 事假扣款永远是 0，没人发现 | 算法对 + 数据空 = 静默失效。断言要测"扣了钱"，不能只测"没报错" |
| **leave_type.id 不是 identity** | 迁移写死 1..7，与种子/测试撞主键 | 老表没有 identity 时，id 只能 `max(id)+1` 逐条取；一条 INSERT 里取会拿到同一个值 |
| **测试写死假种 id** | 1 变成"年假"，事假额度查到年假上 | 测试也要按 code 查 id |
| **RAISE 参数数量** | `too many parameters specified for RAISE` | 占位符个数与参数个数必须一一对应 |
| **`fn_policy_effective` 没有 effective_from** | 政策页 500 | 它只回值，不回生效日；要生效日就单独查 `policy_value` |

## 7. 还没做的

- **综合工时制**：需劳动行政部门审批，加班按周期内超出部分算，目前只支持标准工时；
- **补休抵扣**：休息日加班"能安排补休的不付 200%"，目前一律按 200% 算（多付，不少付）；
- **未休年假折现**：应按日工资 300%（含正常工资，即额外 200%）；
- **产假生育津贴**：现在按"工资照发不扣"处理，社保津贴冲抵的部分还没做；
- **下一年度节假日**：需客户在界面上维护（或提供导入）。
