# 38 · 累计预扣的链条

> 个税不是按月独立算的。本月应扣 = 按累计应纳税所得额查表得到的累计税额 − 已预扣，
> 所以"这个月"的税依赖"前面每个月"。这条依赖以前没有在系统里表达出来。

## 1. 一只脚踩在"已封账"上

`fn_payroll_calc` 算一个人的税之前，先把他本年此前各月的累计读出来（`133_si_declare.sql:573`）：

```sql
SELECT COALESCE(SUM(p.cum_taxable),0), COALESCE(SUM(p.tax_amount),0)
  INTO v_cum_prev, v_cum_paid_tax
  FROM public.payslip p JOIN public.pay_run pr ON pr.id = p.pay_run_id
 WHERE p.employee_id = e.person_id
   AND left(pr.period,4) = left(r.period,4)
   AND pr.period < r.period
   AND pr.status IN ('sealed','paid');

v_tax := public.fn_iit_month(v_cum_prev + v_taxable, v_cum_paid_tax);
```

这段只有一个过滤条件是对的：**本年、此前、同一个人**。另外两个该有的过滤
（同一扣缴义务人、同一种所得）没有，而"只能读已封账"这一条本身也有代价。

## 2. 顺序一错，就永久错

"只读已封账"的用意是好懂：只信任定稿的数。但它把这个系统的算薪变成了
**必须严格按月份顺序做**，而系统没有任何地方声明这个前提。

先算 2 月、再补 1 月：2 月算的时候 1 月还是 `draft`，读不到，累计少一个月，
本月按"只有这一个月"扣税。等 1 月补上，2 月的数**不会跟着变** ——
因为 2 月一封账就改不了了（`E_RUN_SEALED`，见 139）。

结果不是"差一点"，是**永久少缴或多缴**，直到汇算清缴才暴露，而那时责任已经不在系统里。

这也是 37 里那个"累计勾稽差"备注被做出来的原因：申报表是唯一会把这件事点名的地方。

## 3. 四个后果

**① 顺序依赖。** 上面那段。draft 期间还能重算，一封账就定型，所以错的是"顺序"，
不是"某人手抖"。

**② 前期改动污染下游。** 1 月封账后又重开、改了月薪重算 —— 2 月已封账的累计
建立在旧数上，而 2 月改不了。系统里两个批次各自都"合法"，合起来是错的。

**③ 跨法人混算。** 原 SQL 没有 `legal_entity_id` 过滤。同一个人在两家发薪法人
各有一份工资，两家的所得被加进同一个累计。而累计预扣是按**扣缴义务人**分别累计的：
两家各自向自己所属的税务机关申报，谁的累计里都不该有另一家的数。

**④ 年终奖混进工资薪金累计。** 原 SQL 没有 `kind` 过滤。108 之后年终奖是独立批次
（`kind='bonus'`）、单独按"全年一次性奖金"计税，它的 `cum_taxable` 不该进综合所得累计。
进了就是**多缴** —— 而年终奖批次通常紧挨着某个月的工资批次，撞上的概率并不低。

四个后果里，①③④ 都源于"过滤条件写少了或写死了"，② 源于"没有回头看的机制"。

## 4. 三条新规矩

全部落在 `143_iit_chain.sql`。

**① 算薪读累计：按期取最新版本、不分状态、限同法人同 kind。**

`draft` 也读。理由很直接：要让"先算哪期都行"，就必须读得到还没封账的那些期。
读到 draft 不是信任它，而是**承认它现在是这个值**；它一变，下游就会被门禁拦住重算（下面②）。
"取最新版本"指同一期可能有多次算薪（`calc_version`），取最高的那一版，不叠加。

**② 封账门禁。** `fn_pay_run_seal` 加一条硬拦：

| 错误码 | 条件 | 为什么拒 |
|---|---|---|
| `E_SEAL_UPSTREAM_DRAFT` | 本年此前还有未封账的批次 | 累计是"累计到本期"，前期没定稿，本期就建立在一份还会变的数上 |

**只有这一条是硬拦**，而"本期的累计对不上当前前期"（`stale_count`）**只提示、不拦**。
这个取舍试过才知道：

- stale 判据拿"应当是多少"去比对工资条上存的值，而**手工调整过、或从旧系统导进来的
  历史工资条本来就可能与公式对不上** —— 那不是"前期改过"，是数据来源不同；
- 把它做成硬拦，第一次误伤之后人就会绕过它（去直接改库），门禁反而失效；
- 而真正的"前期改了、本期没重算"，已经被下面③的**后验**挡住了。

**③ 重算门禁：不是"不许重算"，是"重算之后下游必须仍然对得上"。**

`fn_payroll_calc` 末尾（不是开头）对每个下游已封账批次调一次 `fn_payrun_chain`，
只要有一期失真就 `E_PAYROLL_DOWNSTREAM_SEALED` 并**整体回滚**——同事务的 RAISE，
库里什么都没变。

为什么用后验：规则的本质是**一致性**，不是顺序。写成"下游有封账就一律不许重算"，
会把"重算一遍结果没变"这种完全无害的动作也拦掉；而后验只拦真改坏的情形。

三条合起来是一句话：**顺序自由（draft 随时重算）、封账有向（自前向后）、
封完不许动上游（动了就整体回滚）。**

## 5. `fn_payrun_chain(p_run)` 的六个返回值

门禁的判断不写在 `fn_pay_run_seal` 里，而是单独一个函数返回一行，
页面与封账各取所需 —— 一份实现，两处用。否则就会出现"页面说能封、点了封不了"，
39 的会签状态那次已经吃过这个亏（`fn_signoff_status` 同一个做法）。

| 返回值 | 回答的问题 |
|---|---|
| `upstream_draft` | 前面还有几期没定稿？（不为 0 就不能封） |
| `downstream_sealed` | 后面已经有几期封了？（重算时用来判断"会不会动到已封账的下游"） |
| `stale_count` | 本期的累计对不上当前前期数据的人有几个？（→ 建议重算，**不拦**封账） |
| `stale_names` | 具体是谁？（只说"3 个人"人不知道去重算哪几个） |
| `can_seal` | 现在点封账，会不会被拒 |
| `reason` | 被拒的话，给一句能照做的话 |

后两个是给界面用的，前四个是给排错用的。`stale_names` 单列出来的原因很朴素：
一次错位往往不止一期，让人一期一期试是最费时间的。

## 6. 为什么不在封账时自动重算

一条备选方案：封账时若发现前期变过，就悄悄把本期重算一遍再封。

不做。封账的语义是"**确认这份数**"，自动重算就变成"重新算一份"——
签字的人签的就不是他看过的那份了。会签、发放回单（36）、申报表（37）
全都建立在这份数没变过的前提上。

所以宁可拒一次、让人点重算。多一次点击，换"签的就是算的"。

## 7. 一个必须说清的剩余限制

这次改造**不会自动修历史**。如果库里已经存在"上游 draft + 下游已封账"的错位数据，
`fn_payrun_chain` 会把它算进 `stale_count`，但没有任何自动动作去改它 ——
改已封账的数是禁止的（`E_PAYRUN_REOPEN` 拦着，139），这条规矩不为修数据破例。

能做的只有两件：

- 申报表（37）的"累计勾稽差"备注会把这些行点出来，这是发现路径；
- 处置走**更正申报**，不由系统改数。

写在这里是因为它不显眼：改造上线后门禁全部生效、新数据都对，
但历史那条错位的记录仍然在表里，且**系统是对的**——它只是不再往里加新的错位。

## 8. 顺带修掉的两个真 bug

改"累计读哪些行"的时候，原来那段 SQL 的两个缺口一起补了 —— 它们不是这次要修的，
是同一次读代码时躲不掉的：

- **跨法人混算**：原 SQL 没有 `legal_entity_id` 过滤。同一个人在两家发薪法人，
  两家的所得被加在一起累计 —— 而累计预扣是按**扣缴义务人**分别累计的。
- **年终奖混进综合所得**：原 SQL 没有 `kind` 过滤。年终奖是单独计税的
  （全年一次性奖金），它的 `cum_taxable` 进了工资薪金的累计就是多缴。

两个都不报错，只让税算多或算少。

## 9. 一条判据改了三版

这次"过期了能不能封"改了三版，值得记下来，因为每一版都是被具体场景推翻的：

| 版本 | 写法 | 被什么推翻 |
|---|---|---|
| 第一版 | 过期就**硬拒** | 项目里所有"手工造/导入历史"的工资条都过期 → 第一跑就红一片；这种拒绝会被绕过（去直接改库） |
| 第二版 | 过期**只提示**，不拦 | 评审一句话点破：**去掉硬拦之后，"封一张过期表"这条路再没有断言守着**，默认分支被误删也不会有人发现 |
| 第三版 | 默认拒 + **确认放行**（`p_accept_stale`） | 这就是现在的样子：误报有人兜（勾一下就过），真错有人拦（不勾就拒），而且"知情同意"在审计日志里留下痕迹 |

配套还有一条：`can_seal` 必须与门禁的**默认行为**完全一致 —— 第二版时两者不一致（页面绿按钮、点下去报红），评审直接指出这是本文件开头自己警告过的错。

## 10. 断言

| 层 | 钉住什么 |
|---|---|
| 库（CHAIN 10 条） | 先算 2 月再算 1 月，累计仍然含 1 月；跨法人不互相累计；`bonus` 批次不进累计；同一期两个版本不重复计；**三期等额时累计是 1/2/3 份而不是 1/2/4 份**（这条钉的是 133 就有的 `SUM(cum_taxable)` 重复累加）；上游 draft 时封账被 `E_SEAL_UPSTREAM_DRAFT` 拒；过期时默认被 `E_SEAL_CHAIN_STALE` 拒、确认（第三参数）才放行；重算让下游失真时被 `E_PAYROLL_DOWNSTREAM_SEALED` 拒且整体回滚 |
| 接口 | `E_SEAL_UPSTREAM_DRAFT` 是 409 不是 500；`/api/payroll/signoff` 把 `chain` 六列带给界面 |
| 界面 | 封账按钮旁显示链条提示（前期未封 / 累计已过期），按钮禁用时 `title` 就是那句 `reason` |

断言条数以实际写进 `143` 的为准，这里不预先报数。
