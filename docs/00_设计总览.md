# 连锁餐饮集团人力资源平台 · 设计总览

> 2026-11-14 ｜ 版本 v1.0 ｜ 本文件是整套设计的入口，其余文档为其展开
> 形态：**本地网络版 B/S 架构**（客户内网私有化部署，浏览器访问）

---

## 一、一句话

一套面向**连锁餐饮集团**的全模块人力资源平台，支持多法人、多区域、多门店的三级管理，把「人事组织—入转调离—排班考勤—假期—薪酬—招聘—绩效—学习考试—灵活用工—外包协同」打通，并以 **MCP 协议**把全部业务能力开放给任何 AI 客户端调用。

**三条分水岭**：
1. 组织不是一个树，是四张皮——人员归属、排班门店、打卡门店、成本归属分开存。
2. 工时是唯一事实源，且有八份快照——事后调薪、改规则、调组织，都不污染已算完的工资。
3. AI 不是外挂，是原生接口——MCP 与 Web 端同权同审，但审批权不交给 AI。

## 四、五个结构性设计（与市面产品的本质差异）

### 1. 四维组织归属 + 版本化

| 维度 | 回答什么 | 合并会出什么事 |
|---|---|---|
| 发薪法人 | 谁发工资、谁报个税 | 无法出表 |
| 社保主体 + 城市 | 在哪参保 | 集团代缴场景无解 |
| 成本组织 | 钱记谁账上 | **门店毛利直接算错** |
| 考勤组织 | 在哪个店出勤 | 跨店员工成本归错店 |

四个维度**不可合并**，且全部带生效期。任何"过去某一天"的计算，按业务发生日取当时版本，**禁止读主档当前值**。

### 2. 事实层与结果层分离

```
原始打卡 punch（append-only，无业务外键）
    ↓ 匹配
日结果 daily（一人一日） → 门店明细 daily_store（已匹配班段）
    ↓ 确认 → 锁定
计薪取数（只读 locked）
```

好处：设备时钟错、重复上报、误刷、异地打卡，全部沉在事实层，**不污染结果层**；重算只动结果、不动事实。

### 3. 两套账，但只有一张法定工资表

- **实发账**：一人一期间一主体一条记录，对税对社保只认它
- **管理成本账**：按门店/绩效单元分摊，服务经营分析
- **借调计价差**：两者差额，**各店相加恒等于零**，是解释项不是利润，不进任何合计

好处：客户要的"谁用人谁掏钱"能落地，同时工资表与主档永远一致，年度对账不会失真。

### 4. 八项快照

工时单价 / 技能归属 / 组织归属 / 计费口径 / 规则版本 / 政策包版本 / 薪资档案版本 / 期间日历版本。

> 凡是参与算钱的中间结果，必须能固化，不能靠回溯推导。

### 5. MCP 原生开放

- 101 个工具，覆盖全部业务域（读 60 / 写 41，**不提供任何 `approve_*`**）
- 与 Web 端**同权同审**，无 AI 专用后门
- **不提供 `approve_*` 工具**——审批权不交给 AI
- 写操作必须 dry-run + 二次确认 + 幂等键
- 薪资、证件默认脱敏，明文需申请并留审计

## 五、角色与权限

| 角色 | 数据范围 | 核心动作 |
|---|---|---|
| 集团 HRD | 全集团 | 制度下发、编制总控、跨组织调配、集团报表 |
| 集团薪酬 | 全集团 | 多主体算薪、社保政策、成本归集 |
| 区域 HRBP | 所辖区域 | 跨店调配、招聘补给、流失干预 |
| 门店 HR | 单店/多店 | 入离职、排班、考勤异常、工资条答疑 |
| 店长 | 本店 | **排班、补人、审批、看当日人效（移动优先）** |
| 员工 | 本人 | 打卡、查班表、请假、工资条、学习考试 |
| 劳务供应商 | 仅本供应商人员 | 接单、报名、到岗、对账 |
| 财务 | 全集团（金额可见、个人信息脱敏） | 发薪、对账、成本 |
| AI 客户端 | 按授权 scope | 通过 MCP 读写 |

权限三轴：**功能权限 × 数据范围（六种规则可组合）× 字段级**。敏感字段未授权返回掩码而非报错。

## 六、技术形态

| 项 | 选型方向 |
|---|---|
| 部署 | 客户内网服务器，Docker 单机或小集群，离线升级包 |
| 架构 | B/S，浏览器访问，PC Web + 手机 H5 |
| 租户 | 单实例单集团（不做多租户隔离，保留字段为将来留口） |
| 规模 | 1 万员工 / 500 门店 / 5 万条考勤日/天，不做读写分离 |
| AI 接入 | MCP 网关独立进程，stdio + 本地 HTTP，默认只听回环 |
| 数据 | PostgreSQL 单实例，普通视图 + 索引，不上物化视图 |

**明确的架构取舍**：不引微服务、不引消息中间件、不做多租户、不做原生 App。理由是本地部署环境装不起也运维不起。

**条款的唯一出处**（新写一条"必须/不得"之前先查这里，不要两册各写一份）：

| 这条"必须" | 谁能判它对错 | 归哪 |
|---|---|---|
| 必须 `GENERATED ALWAYS AS IDENTITY` | 只有库（`attidentity = 'a'`） | `04` |
| 必须掩码不报错 | 业务能判（"这个字段我该不该看见"） | `03`/`07` |
| 必须用 `round(…,2)` 不用 `< 0.01` | 只有库 + 一个签过字的单位口径 | `04` |
| 必须"改主意是新增一条" | 业务能判（争议时要不要出示时间线） | `03`/`07` |

> **分界线是"判错的人是谁"，不是"用词像不像代码"。**
>
> 一句话版：**凡"必须/不得"后面跟的是 SQL 关键字、函数名或类型名，这条就该去 `04`；留在 PRD 的那一条，必须能被业务判断对错。**
>
> 用词只是最容易看出来的表面特征——它好用，是因为**关键字不在业务词汇表里**，所以"这句我判不了"在写的时候就显形了。

**两个执行者，两个落点，不是二选一**：

- 写 PRD 的人（会写出"必须 `ON DELETE RESTRICT`"这类句子）→ 看本表；
- 接任务卡的人（会实现这些句子）→ 看 `13` 派单须知第六条。

**只放一处必漏**：规矩写在"被违反的那一刻能读到的地方"才有用，而这两类人违反它的时刻不在同一个文件里。

**可以半自动检查，但要与 K4 分开出口**：扫 `03`/`07` 里所有"必须/不得"句，句中含反引号包裹的 SQL 关键字（`SELECT`/`CHECK`/`GENERATED`/`IDENTITY`/`round`/`COALESCE`/`ON DELETE`/`DEFAULT`…）即列出。**列出来的不是违规，是待判**——人工只需回答"这句业务能不能判"，两类各归各册。

> ⚠️ 这条扫描与 `07` 的 K4（扫公式表命中即阻断）**同一形态、极性相反**：K4 是负向（命中即阻断），本条是正向（命中只是"要人看一眼"）。**同一个扫描器不能共用一个出口**——否则正向提示会被当成负向阻断，然后被加进白名单，然后一起失效。

## 八、实施路径（建议）

| 期 | 范围 | 目标 |
|---|---|---|
| 一期 | 组织人事 + 排班 + 考勤 + 假期 + 薪酬 + MCP 基础 | 核心闭环跑通，能发一次真工资 |
| 二期 | 招聘 + 绩效 + 学习考试 + 外包协同 + 报表 | 全模块覆盖 |
| 三期 | AI 排班 L2、智能补位优化、自助分析 | 智能化 |

**一期验收的硬标准**：跑完一个完整月度周期（排班 → 打卡 → 异常处理 → 封账 → 算薪 → 工资条 → 成本分摊），且跨店支援场景的成本归集与实发账可勾稽。

## 九、必须由负责人拍板的三件事

| # | 事项 | 当前默认 |
|---|---|---|
| 1 | 直营为主还是含加盟 | 先直营（加盟涉及结算与管控分离，二期） |
| 2 | 是否覆盖港澳/海外主体 | 不覆盖（税制与假期体系差异过大） |
| 3 | Demo 优先演示哪两条主线 | ① 跨店支援算薪不出错 ② 划线排班 + 缺人智能补位 |

## 十、必须向客户确认的五件事

1. 是否有外网出口 / DMZ（决定移动端与招聘自助是否可用）
2. 是否存在「一个成本中心覆盖多店」（决定能否输出单元级成本率）
3. 储值消费的营业额确认时点（影响人力成本率与店长奖金）
4. 派遣/外包工时是否进本系统考勤（影响门店人效真实性）
5. 跨法人调动的合同处理（新签还是主体变更协议）

## 十一、三条贯穿全系统的原则

1. **主档只回答「现在归谁」，时序表回答「当时在哪」。** 凡涉及过去某一天的计算，禁止读主档当前值。
2. **凡是参与算钱的中间结果，必须能固化，不能靠回溯推导。**
3. **阻断型校验必须先证明它在合法业务上不会误伤。** 会误伤的阻断，实施方最后一定加人工跳过关，规则就废了。

以及一条产品红线：**审批权不可委托给 AI。**
