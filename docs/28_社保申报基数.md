# 社保缴费基数：按"上年度月平均"，一年定一次

> 记录日期：2026-11-15 ｜ 迁移 133 ｜ 断言 461 / 199 / 25

## 1. 133 之前是怎么算的

```sql
v_si_one := fn_si_base('上海', si.item, v_monthly, v_period_end) * rate
```

也就是**每月按当月月薪标准**算一次、夹一次上下限。两个问题，都属于"看起来合理、对账时答不出来"的那一类：

**① 基数每年只该定一次。** 7 月调基之后一年内不随月薪变动。现在的实现里，某人 9 月涨薪 2000，
9 月的社保基数当场跟着涨 —— 而社保局那边收到的是 7 月申报的那个数，两边永远差一截。

**② "月薪标准"≠"上年度月平均工资"。** 法定口径是「职工本人上年度月平均工资」，它含奖金、津贴、加班费。
用月薪标准当基数，旺季奖金多的人会少缴 —— 而少缴是欠缴，会被追缴并加收滞纳金。

依据：

- 《社会保险法》第 60 条：用人单位应当自行申报、按时足额缴纳；
- 《社会保险费申报缴纳管理规定》（人社部令第 20 号）第 8 条：缴费基数按职工本人上年度月平均工资申报；
- 各地实施办法：下限 = 当地上年度全口径平均工资的 60%，上限 300%；调整时间各地不同（上海 7 月、部分城市 1 月）。

## 2. 三个设计取舍

### ① 不做"自动调基"，生成的是建议值

`fn_si_declare_build` 写的是 `source='calc'` 的记录，HR 核过才算数。理由：基数报错了要走**更正申报**，
比补一张请假单麻烦得多。这与节假日骨架是同一套思路：系统算、人确认。

### ② 上下限不预置

各地每年 7 月公布，写死等于明年一定错。`si_policy` 里已经有 `base_floor` / `base_ceiling`，
这版只是让"用哪个月的"说得清：申报基数用**申报生效日**那天的上下限，不是每月重新夹。

### ③ 默认不计入年终奖工资条

`SI_BASE_INCLUDE_BONUS` 默认 `off`：年终奖是独立工资条（108），各地对"是否计入缴费基数"口径不同。
默认沿用上线前行为（不含），客户按当地口径自己开。

## 3. 回退分支：不改变任何历史月份

```sql
fn_si_base_eff(employee, city, item, wage, on):
  申报基数 = fn_si_declared_base(...)
  IF NULL  → fn_si_base(city, item, wage, on)      -- 133 之前的行为
  ELSE     → fn_si_base(city, item, 申报基数, on)   -- 只做夹逼
```

第二条分支把申报基数当成"工资"传进去，等于**只做夹逼、不做别的** —— 夹逼只有一处实现，
不另写一份 `LEAST/GREATEST`。

`SID1` 断言：没有申报记录时两个函数的返回值完全相等，所以历史月份重算不变。

## 4. 两层"不覆盖"

| 场景 | 规则 |
|---|---|
| 重跑生成 | `source='manual'` 的行**金额一律不动** |
| 手工改 | 必须落在上下限内，越界直接拒（`E_SI_BASE_RANGE`），不静默夹到上限 |

第二条为什么重要：静默夹掉会让人以为"我报上去了"。而实际报的是上限，下次对账又要重新查一遍。

## 5. 一个"注释写对了、SQL 没跟上"的坑

`ON CONFLICT` 那段第一版是这样：

```sql
SET monthly_avg = EXCLUDED.monthly_avg,
    base_amount = EXCLUDED.base_amount,          -- ← 无条件覆盖
    source = CASE WHEN si_base_declare.source='manual' THEN 'manual' ELSE 'calc' END
```

注释写着"手工改过的行不覆盖金额"，SQL 里金额却照旧覆盖。`SID5` 立刻抓到：
改 12000，重跑一次变回 7384，而 `source` 还标着 `manual` —— 数据自相矛盾
（标签说是人改的，金额却是系统算的）。修法是每个字段都加 `CASE WHEN ... manual THEN 原值`。

## 6. 顺带修的两处

**① `pay_run.kind` 为 NULL 的批次被整月过滤。** 生成基数的条件是
`v_inc_b OR pr.kind = 'monthly'`，而 108 之前建的批次没有 `kind` —— `NULL = 'monthly'` 恒为 NULL，
于是"这个人上年度没发过薪"。而他明明发了。改成 `COALESCE(pr.kind,'monthly')`。

**② 默认年度会显示空白。** 调基通常在年中做**下一年度**的准备（7 月做的是 7 月起生效的那一年），
如果页面只显示"当年"，HR 刚录完 2027、下次进来看到 2026 一片空白，会以为没保存。
现在：当年没有记录就显示最近一次定过的年度，并且年度可以手改。

## 7. 断言

| 断言 | 钉的 |
|---|---|
| `SID1` | 无申报记录回退月薪标准（历史重算不变） |
| `SID2` | 申报基数 = 上年度应发月平均，夹上下限（独立算一遍对账） |
| `SID3` | 月薪 8000→30000，申报基数不动（一年只定一次） |
| `SID4` | 申报基数按当期上下限再夹一次 |
| `SID5` | 手工改的值不被重跑冲掉 |
| `SID6` | 算薪源码里真的调了 `fn_si_base_eff`（接线证据，不只是建了张表） |
| `SID7` | 手工改越界 → 拒 |
| `SID8` | 上年度没发过薪的人不生成 |
| `SID1-4`（接口） | 页面带上下限、生成、手工改、越界拒 |
| `UI24` | 政策页说清"上年度月平均 / 一年只定一次 / 60%·300%" |

`SID6` 值得单说：它查的是 `pg_proc.prosrc LIKE '%fn_si_base_eff%'`。
"建了函数但算薪没调它"是这类改动最常见的失手 —— 库能建、接口能读、页面能显示，
只有工资算错。这条断言让那种情况直接变红。

## 8. 还没做的

| 项 | 为什么 |
|---|---|
| 上下限的年度维护界面 | 现在只能在 `si_policy` 里录（有费率就要录上下限，本来也是同一张表）。单独做一个"每年录上下限"的向导，价值不如把现有那张表做好 |
| 基数与上下限不一致的批量提示 | 每年 7 月上下限一调，去年申报的数可能全部越界。现在靠"取数时再夹一次"兜住，但没有"今年有几个人被顶到上限"的报表 |
| 补缴/退费的追溯 | 基数报错了要更正申报，涉及补缴。这是**申报业务**不是算薪，需要与社保局交互的那一层 |
| 公积金单独基数 | 公积金基数上下限通常与社保不同，现在共用 `si_policy` 的上下限。要做得分险种存上下限 |
