## D1 字段命名统一定死

| 概念 | 定稿 | 理由 |
|---|---|---|
| 人 | **`employee_id`** | 主档一自然人一行（借调不拆、调动走多段任职），`employee_id` 实质就是自然人 ID。引入 `person_id` 会造成两套 ID 并存 |
| 发薪主体 | **`payroll_legal_entity_id`** | 与 `legal_entity_si_id` 形成 `xxx_legal_entity_id` 统一语序 |

```sql
UNIQUE (employee_id, pay_period, payroll_legal_entity_id)
```

组织侧 7 张表按此统一，其余文档出现 `person_id` / `legal_entity_payroll_id` 的一律视为别名，落库前替换。

## D2 人员分类：**三维**，不可互相推导

| 维度 | 字段 | 枚举 | 驱动什么 |
|---|---|---|---|
| 归属 | `ownership_type` | 自有 / 派遣 / 外包 / 第三方平台 | 算不算自己人（进不进工资表、算不算人效） |
| **法律形态** | `legal_employment_form` | 全日制 / 非全日制 / 劳务关系 / 承揽 | **社保口径、终止条件、工时法定上限** |
| 计薪方式 | `employment_type` | FT / PT / LTPT / 日薪 / 计件 | 怎么算钱 |

### 为什么第三维不能省

「非全日制」在劳动法下是独立制度：仅工伤必缴社保、终止无需经济补偿、有法定日/周工时上限、可存在多重劳动关系。系统若只知道 `PT`（按小时算钱），就判断不了要不要缴社保、能不能随时终止、是否超工时——**这三条正是餐饮最容易踩的合规红线**。

### 为什么不能由前两维推导第三维

两类真实场景会推错：

| 场景 | 推导会得到 | 实际 |
|---|---|---|
| 全日制但按小时计薪（划线排班员工） | 非全日制 | 全日制，社保照缴 |
| 非全日制但月结（兼职店长） | 全日制 | 非全日制，社保仅工伤 |

推错就是社保口径错，而社保错是最难修的错误（跨月补缴 + 滞纳金）。

### 连带修正

日/周工时上限的**默认值由 `legal_employment_form` 决定**，考勤组只能收紧、不能放宽。原设计"考勤组自己配一个数"会让非全日制员工按全日制上限校验，合规校验形同虚设。

## D3 加班：三个字段构成完整语义

| 字段 | 作用 |
|---|---|
| `ot_hours`（拆三列：平时/休息日/法定） | 事实层，**所有现场人员照记** |
| `ot_pay_bearer` | **`self` / `agency` / `none`** —— 这笔钱谁承担 |
| `ot_pay_amount` | 金额层，仅 `bearer=self` 时 > 0 |

`ot_pay_amount = 0` 有两种语义，混在一起劳务对账就分不清：

- `bearer=none` → **本就没有这笔钱**（自有非全日制）
- `bearer=agency` → **这笔钱付给别人**（派遣/外包，进计费工时 → 劳务结算单）

副产物：门店报表可直接标「无费工时（归属供应商）」，「工时多、工资没多」的投诉从设计上消失。

## D4 工时上限：按整段班次归集，绝不先切分再求和

```
daily_total_hours_by_person(emp, date)
  = Σ 所有「归属日 = date」班次的整段时长
归属日 = 班次开始日
```

**先按归属日归集班次，再对整段求和。**

反例（这是最隐蔽的漏算）：8.5 小时夜班 22:00–06:30，若按自然日切分 → 2 + 6.5，两段都不超阈值，**加班凭空消失**。同一个人、同一家店就发生了，比跨组合并漏判更隐蔽。

另一处必须区分：

| 单元 | 定义 |
|---|---|
| 计量单元 | **班次**（跨零点不拆） |
| 判定单元 | **员工当日累计**（跨班次、跨门店合并） |

午市 4h + 晚市 4.5h 各自不超 8h，合计 8.5h 应算 0.5h 加班——按班次判会漏。

## D5 跨零点：两套日期基准并列使用

| 判定对象 | 基准 |
|---|---|
| 成本归属、工资期间归属 | **归属日 = 班次开始日**，跨零点不拆 |
| **法定加班时段与倍率认定** | **按实际发生时刻**，不看归属日 |

例：11-14 23:00 至 11-15 03:00 → 整段进 11-14 的成本与工资；但 11-15 00:00–03:00 若落法定节假日，仍按节假日倍率。

**两件事在同一行数据里，但日期基准不同**，实现时极易写成同一个，必须显式提示。

## D6 撤回 `payable_days`

- FT 月薪的折算分子是「本月在职天数 N」（入离职日期派生），**不是出勤天数**
- `payable_days` 只服务日薪制与 PT 按天计费，由薪酬口径派生，**不需要考勤算**
- 考勤三字段契约固定：`total_hours` / `attendance_days` / `各假种天数`
- 「到岗 0 小时 → `attendance_days` = 1」保留（勤工津贴基数用它）

理由：两边各算一遍，会在「到岗 0 工时 / 半天班 / 跨零点夜班」上分叉，分叉后没人说得清哪个对。

## D7 阻断型校验总原则（上升为设计规范）

> **阻断型校验必须先证明它在合法业务上不会误伤。**
> 会误伤的阻断，实施方最后一定加人工跳过关，规则就废了。
> **「凭单据放行」优于「无条件放行」，也优于「绝对阻断」。**

落地：跨法人调动当月两条工资记录 → 有调动单 + 区间连续不重叠 → 放行并标 `is_transfer_pair`；无单/重叠/断裂 → 阻断。

## D8 参数补充

| 参数 | 维度 | 定稿 |
|---|---|---|
| `pt_ot_pay_enabled` | **按参保城市 + 生效期 + 版本** | 不做全局开关（跨省连锁会陷入两难） |
| 借调计价差复核阈值 | 相对 20% **且** 绝对 > 500 | 告警分级：提示 / 复核 / 强阻断（Σ≠0） |
| `ot_compensated_hours` | — | 语义 = **已抵冲**（实际已休掉的小时） |
| `legal_employment_form` 的「承揽」 | — | **独立枚举值**，不与「劳务关系」合并 |

承揽独立成值的理由：两者在系统行为上相近（无劳动关系、按结果计费），但**税务处理不同**（劳务报酬 vs 经营所得），合并后个税必错。

## D10 承揽人员不得进排班池（法律风险，非体验问题）

> **给承揽方的人员排班，会把「真外包」做成「假外包、真派遣」。**

承揽的法律特征是「承揽人自行组织劳动、自负盈亏、不受定作人指挥」。一旦店长给承揽方的人排班、指定几点到几点在哪个岗位，就等于我方对劳动过程实施指挥管理——而这正是司法实践中判定用工性质的第一顺位标准。后果不是系统问题，是**补社保、补经济补偿、连带工伤责任**。

### 规则

| 人员形态 | 进排班池 | 进考勤 | 进人效 | 说明 |
|---|---|---|---|---|
| 自有（全日制/非全日制） | ✅ | ✅ | ✅ | — |
| 劳务关系 | ✅ | ✅ | ✅ | — |
| **派遣** | ✅ | ✅ | ✅ | **进池恰是其法定特征**：用工单位指挥管理、派遣单位承担雇主责任 |
| **承揽** | ❌ | ❌ | ❌ | 只做「在场人员登记」（安保、健康证核查用） |

**一句话写进 PRD**：**承揽不列人、不进池；派遣/劳务列人、进池。**

若业务方要求管到"几点到岗"，说明该业务本就不是承揽，应改签派遣或劳务——属签约问题，系统只需给提示，不提供开关绕过。

## D11 PRD 编写规范（三条）

1. **凡是写"必须/不得/应当"的地方，如果落不成一个字段或一条校验，就要怀疑这条原则是不是还没想清楚。**
2. **凡是 PRD 里同时出现"给用户看"和"给机器看"的口径，必须拆成两句话写。**
3. **凡是带生效期的配置，必须同时写"历史期间按当时版本重放"这一句。**
