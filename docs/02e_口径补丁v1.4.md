## F1 用工维度重构为正交两维（替换 02d 的 V3）

原 `employment_nature` 把「归属」和「工时制」揉在一个枚举里（"自有全职"同时编码了两遍信息），导致"派遣 + 月薪制"这种真实存在的组合要靠两个字段各填一次才能表达，容易填错。

| 字段 | 取值 | 回答什么问题 |
|---|---|---|
| `ownership_type` | 自有 / 派遣 / 外包 / 第三方平台 | **算不算自己人**（决定进不进工资表、算不算人效） |
| `employment_type` | FT / PT / LTPT / hourly | **怎么算钱**（决定计薪口径） |

**收益**：
- 「自有全职」= `自有` + `FT`，不再是一个复合枚举值
- 加班条件变干净：`ownership_type=自有 AND employment_type=FT`
- 人效口径只需过滤 `ownership_type=自有`，不用枚举两个值
- 「派遣 + FT」从"难以表达"变成"天然可表达"

## F2 跨天班次：归属日 = 班次开始日，跨零点不拆行（规则反转）

原推断「跨天班次归下班日」作废。

**反例**：11-14 17:00 至 11-15 01:30 的夜班，若按自然日切分，会变成"上月 1.5 小时 + 本月 6.5 小时"，而员工和店长都只认为自己上了一个班。

**定稿**：工时归属日 = **班次开始日**，跨零点不拆行。

**强制配套**：工时明细必须存**绝对时间戳** `start_at` / `end_at`（含日期），不能只存"日期 + 时刻"。否则跨零点时段的重叠校验会失效——次日那段被算到次日，两条记录求不出交集，兼岗校验形同虚设。

## F3 异常清单拆两类（升级为设计原则）

| 清单 | 内容 | 消费方 |
|---|---|---|
| **考勤异常清单** | 缺卡、异地打卡 | 店长待办 + HR |
| **数据完整性告警** | 同店同日重叠、assignment 与 daily 不匹配、主档与 primary_post 不一致 | IT / DBA，**不进业务待办** |

**原则**：业务待办里只放业务能处理的异常。

理由：店长看到"重复打卡"会去问员工，其实是脚本 bug（第三类已被数据库 EXCLUDE 挡在写入前，出现即说明有人绕过约束写库），问不出结果还消耗掉他对整张清单的信任。**一旦店长不信待办，整个异常闭环就废了。**

## F4 借调计价差：通用勾稽式（替换 02b P1 / 02d 的写法）

### 术语

「借调差异」→ **借调计价差**，与「毛利」严格分开：

| | 借调计价差 | 毛利 |
|---|---|---|
| 数学性质 | **Σ = 0**（内部转移，双边对冲） | **不恒为 0**，这才是利润 |
| 进不进利润表 | 不进 | 进 |

### 算法（比"按天摊 6667"更严谨）

```
B 店 = 4000                      （外部计价，实际结算依据）
A 店 = 10000 − 4000 = 6000       （残差，不是机械分摊值）
合计 = 10000 ≡ 实发
```

通用式：

- 按外部计价结算的主体：`Ci = Pi`
- 其余主体：`C_rest = S − ΣPi`
- **恒等式 `ΣCi ≡ S`，无例外**
- `Di = Pi − S × 该主体工时分摊比例`，**`ΣDi ≡ 0`，不进任何合计、不进应发、不进成本总额**

### 校验三条

1. `|Di| / 应摊额 > 20%` → 进复核清单（**不阻断**，跨城支援有差旅补偿时超额合理）
2. 双边对称：`from_cost_org` / `to_cost_org` 都非空且不相等 + `transfer_id`
3. 同一 `transfer_id` 的行金额之和 ≠ 0 → **阻断提交**（DB 层加检查约束兜底）

**禁止只写单边**——单边挂账就是虚增成本。

### 为什么差异不能加总

> 同一笔成本被两套分摊基数各算了一遍——按天摊是一套，按任务价是另一套。两套基数只能择一入账，另一套仅可用于校验，绝不能相加。

## F5 归属版本表拆两张（修正我上一版设计缺陷）

### 缺陷

我上一版说「四维各一个 org_id + 同一 employee 区间不重叠」。但：

| 维度 | 同一时点取值个数 |
|---|---|
| 人事归属组织 | **1 个** ✅ |
| 出勤/排班门店 | **可多个**（A 店早市 + B 店晚市）❌ |
| 排班组归属 | **可多个**（主组 + 兼岗组 + 支援组）❌ |

「区间不重叠」⇒ 一人一时点只能一行 ⇒ 多值维度被堵死。**这正是前面被推翻两次的错误。**

### 定稿：按单值/多值拆两张，用视图还原

**表 A `employee_org_assignment`（归属版本，一人一时点一行）**

只放天然单值的维度：`legal_entity_payroll_id`、`legal_entity_si_id` + `si_city`、`primary_org_id`（人事归属/主门店）、`cost_org_id`（默认成本）、`employment_type`，加 `effective_date` / `end_date` / `change_reason` / `source_order_id`。

约束：`EXCLUDE USING gist (employee_id WITH =, daterange(...) WITH &&)`

**表 B `employee_store_assignment`（额外出勤门店，一天可多行）**

`source` 枚举**去掉 `primary_post`**，只保留 `concurrent_post / temporary_support / manual_adjust`。

理由：主岗门店已在表 A，表 B 再存一份就是同一事实两个来源，必然漂移。

**视图 `employee_workplaces_v`**：`表A(primary_post) UNION ALL 表B` —— 排班侧原有查询只换 FROM，逻辑不改。

### 一致性规则（进 PRD）

1. 表 B 任意一行，同一时点必须有表 A 覆盖（不能"有出勤门店、无归属记录"）
2. 变动成对写：一次调动 = 表 A 关旧开新 **+** 表 B 关旧开新，**同一事务**
3. 表 A 的 `primary_org_id` 必须是门店类型节点，不能是区域/部门

## F6 每日快照：不做（裁决）

| 方案 | 判断 |
|---|---|
| 区间表（SCD2） | **主方案**：省空间（一年约 3–8 行/人）、as-of 一次查询、变更原因可追溯 |
| 每日全量快照 | **不做**：10 万人 × 365 天 = 3650 万行/年，且只能回答"某天是什么"，回答不了"为什么变" |

**保留开关**：若客户有上市合规/劳动争议举证要求，加「每日组织存档」可选模块，**只写不读**（查询仍走区间表）。

默认关闭。
