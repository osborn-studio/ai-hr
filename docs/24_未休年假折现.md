# 未休年假折现：300% 里已经含了工资

> 记录日期：2026-11-15 ｜ 迁移 129 ｜ 断言 429 / 184 / 20

## 1. 最容易多付一倍的那一处

法条原文（《职工带薪年休假条例》第 5 条）：

> 对职工应休未休的年休假天数，单位应当按照该职工日工资收入的 **300%** 支付年休假工资报酬。

《企业职工带薪年休假实施办法》第 10 条把这件事说清楚了：

> 前款所称年休假工资报酬包含用人单位支付职工正常工作期间的工资收入。

所以 **300% 里已经包含了那几天的正常工资**。员工还在职、当月工资照发，折现时只能**再补 200%**。

按 300% 全额再发一遍 = 实际付了 400% —— 多付一倍，而且**没有人会投诉**。
这种错会一直留在账上，直到审计翻到。

| 场景 | 工资照发了吗 | 该补多少 | 系统里的值 |
|---|---|---|---|
| 在职，年底折现 | 是（当月工资单已含） | **200%** | `extra_200`（法定默认） |
| 离职，当月工资已结到离职日 | 是 | **200%** | `extra_200` |
| 离职，那几天完全没发过 | 否 | 300% | `total_300`（优于法定，成本翻倍） |

`total_300` 保留但不做默认：有些企业就是按 300% 一次性结清，不再细究工资是否另发。
把它做成选项而不是写死，理由和加班倍数、病假比例一样 —— **默认值等于法定，超出法定的做法允许但要提示**。

断言钉住的是这个关系本身：`ALC5` 断言 `total_300` 的金额**正好**是 `extra_200` 的 1.5 倍。

## 2. 天数：累计工龄取档，折算向下取整

两条口径，任何一条错都会让金额差出一大截：

**① 按累计工龄，不按本单位工龄**（第 3 条）：满 1 年不满 10 年 5 天、满 10 年不满 20 年 10 天、满 20 年 15 天。

系统只能看到本单位的入职日。一个人 30 岁入职、此前工作 8 年，**第一年就该有 5 天**，
而"新员工没有年假"是很多企业的实际做法 —— 那是不合法的。所以 `employment` 加了一列
`prior_work_years`（入司前累计年限，默认 0 = 只按本单位算，即上线前的行为）。

**② 折算后不足 1 整天不支付**（第 12 条）：

```
应休未休 = floor(全年应享 × 已过日历天 / 365 − 已休 − 已折现)
```

用的是 `floor` 不是 `round`。`round` 会把 0.6 天变成 1 天 —— 多付一天的钱。
`GREATEST(..., 0)` 兜住负数（休多了不该倒扣工资）。

`ALC3` 钉的是这个：应享 15 天、7 月 1 日（已过 182 天）→ `15×182/365 = 7.479` → **7 天**。

档位表 `annual_leave_tier` 可改，但有一条库级约束 `ck_alt_legal`：

```sql
days >= CASE WHEN years_from >= 20 THEN 15
             WHEN years_from >= 10 THEN 10
             ELSE 5 END
```

企业可以给 7 天、12 天（优于法定），不能给 3 天。`ALC2` 用"满 20 年只给 3 天"做反例。

## 3. 057 留下的五个问题，逐个回答

057 当初把折现刻意不做，理由写得很实：单价、计税、社保基数、出哪张单、要不要审批 ——
五个问题每一个都能让财务和 HR 吵起来。这一版逐条给出答案，答案都写进了代码注释。

| 问题 | 答案 | 为什么 |
|---|---|---|
| ① 单价 | 前 12 个月应发，**剔除加班费**（第 11 条），不足 12 个月按实际月数；再 ÷ 21.75 | 法条明写剔除加班费；没给剔提成的理由，所以提成**不剔** |
| ② 计税 | 不特殊处理，进工资条一行，走累计预扣 | 它是工资性收入，按"偶然所得"单独计税是错的 |
| ③ 社保基数 | **不进** | 基数按**月薪标准**申报（105 的规矩）；一次性折现不该改变申报基数 |
| ④ 出哪张单 | 进当月工资条一行 `AL_CASHOUT` | 另开单会让"应发合计"分成两处，对账必然手工相加 |
| ⑤ 审批 | **登记 → 算薪落账**两步，单据可查可作废 | 折现是发钱，要留痕；单据化之后改制度项也不会改掉历史月份的钱 |

基数里额外剔了 `AL_CASHOUT` 和 `ANNUAL_BONUS`（法条没要求，是我加的）：

- 不剔 `AL_CASHOUT`，今年折一次、明年基数被自己抬高，形成正反馈；
- `ANNUAL_BONUS` 是一次性年终奖，混进"月平均"会让 12 个月里有一个月异常高。

## 4. 折现不写额度台账，作废才能自动加回

第一版把折现写成 `leave_usage` 的一个新状态 `cashed`，然后发现一个死结：

> 作废折现单要把额度还回去。如果冲减写在台账里，就得再造一条"反向行"抵掉它 ——
> 而 `available` 的公式里**没有反向行这一项**（`granted − frozen − used − forfeited`），
> 于是作废之后额度永远少一块，且看不出来少在哪。

改成：折现天数**直接由 `leave_cashout` 派生**，`v_leave_balance` 用 `status <> 'void'` 汇总。

```sql
c AS (SELECT employee_id, leave_type_id, SUM(days) AS cashed
        FROM leave_cashout WHERE status <> 'void' GROUP BY 1,2)
...
available = granted - frozen - used - forfeited - cashed
```

好处是作废只要改一个状态，额度立即回来，不需要反向行，也不会漂。
`ALC7` 断言：作废后可折天数 = 作废前（5 天 → 5 天）。
`ALC8` 断言：折了 11 天之后，到年底只剩 2 天可折（不是又冒出 15 天）。

同一年只允许一张有效单（部分唯一索引 `ux_lc_once`），重复登记抛 `E_ALC_EXISTS`：
报错要读得懂。撞唯一索引的 `23505` 读起来像"数据库出错了"，不像"你今年已经折过了"。

## 5. 算薪里只读、不自动算

`fn_payroll_calc` 里这一段的写法很关键：

```sql
SELECT COALESCE(SUM(c.amount), 0) INTO v_al
  FROM public.leave_cashout c
 WHERE c.employee_id = e.person_id
   AND c.settle_period = r.period AND c.status = 'pending';
```

**它不判断"这个人该不该折"，只取已经登记好的单**。自动算的话，改一次制度项，
重算历史月份时"应发"就变了 —— 而发出去的工资条不能变。

代价是重算要幂等。第一次算薪把单标成 `paid`，第二次重算读不到 `pending`，那笔钱会静默消失。
所以函数开头先把**本批次**关联的单退回 `pending`：

```sql
UPDATE leave_cashout c SET status='paid' ...
-- 重算前：
UPDATE leave_cashout c SET status='pending', payslip_id=NULL
 WHERE c.status='paid'
   AND c.payslip_id IN (SELECT p.id FROM payslip p WHERE p.pay_run_id = p_run);
```

只退本批次的单，别的法人主体的单不能碰。`ALC7` 连算三次，断言金额不变。

## 6. 离职结算：只折年假，剩下的作废

`LEAVE_TERM_HANDLING` 从 `none / forfeit` 扩成 `none / forfeit / cashout`。

`cashout` 模式下：

1. **落在离职当月**，不落到下月 —— 离职的人下个月不在工资单里，落错月份这笔钱再也发不出去；
2. 只折**年假**（法定只保护年假报酬），调休/婚假等仍然作废；
3. 折完之后**剩余额度一并作废**。这一条是测出来的：折现只折"应休未休"那部分（按工龄折算），
   而授予额度里可能还有往年结转，折 7 天之后还剩 17 天挂在离职员工名下 ——
   余额页上看起来像系统算错了。

`ALC9` 断言：离职后产生 2027 年折现单（落在 2027-06、4 天、×2）、且**剩余悬挂额度 = 0**。

## 7. 这一轮踩的坑

| 现象 | 真因 |
|---|---|
| 作废之后额度少一块 | 冲减写进了 `leave_usage`，而 `available` 公式里没有"反向行" |
| 第 2 次折现报 `23505` | 没先拦"同年已折"，直接撞部分唯一索引；补一个 `E_ALC_EXISTS` |
| 重算之后那笔钱消失 | 第一次算薪标了 `paid`，重算读不到 `pending`；函数开头退回 |
| 离职员工还剩 17 天年假 | 折现只折"应休未休"，授予额度里的往年结转没作废 |
| 页面 500 `column p.name does not exist` | `person` 表是 `full_name`；工号在 `employee_no` 表，不是 column |
| 手机端指标卡挤成一条竖条 | KPI 用了内联 `grid-template-columns`，内联优先级高于媒体查询，手机断点失效 → 改成 `.kpi4` 类 |
| 改病假档位却把年假档位改了 | 两处都是 `<div class="tier-grid">` + `tiers.map`，替换时命中了第一处；断言 `UI18` 才没让它过去 |

最后一条值得单独说：那次改动让**病假档位从 5 列变成 3 列**，而库断言与接口断言全绿 ——
只有界面断言（`UI18` 检查"档位/假种/节假日同屏"）没有覆盖列数，是靠截图看出来的。
所以这一轮同时给年假折现页加了 `UI19`（口径 / 档位 / 试算 / 台账 / 候选人 同屏）。

## 9. 还没做的

| 项 | 为什么没做 |
|---|---|
| 跨年度结转额度参与折算 | 现在是"当年度 × 已过天数 / 365"，往年结转只作为**封顶**用。真要按结转年逐笔折算，得先有"额度归属年度"这个字段，而现在 `leave_grant` 只有有效期区间 |
| 综合工时制的年假折算 | 综合工时按周期总工时算，日工资的折算分母不同（不是 21.75）。要做先把工时制度做成一等公民 |
| 折现的个税单独申报 | 现在是合并计税（正确做法）。有些地区要求单独填一张表，那是申报口径，不是算薪口径 |
| 批量折现（一次给全公司折） | 折现是逐人确认的动作（有人放弃、有人要留到明年）。批量入口会让"放弃"这件事没有地方表达 |
