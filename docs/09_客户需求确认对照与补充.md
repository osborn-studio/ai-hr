# 客户需求确认对照与设计补充

> 2026-11-14 ｜ 输入：某连锁餐饮客户《需求确认》、某协同平台问题反馈、餐饮行业假勤方案
> 用途：把客户已签字的需求逐条对照本设计，标出「已覆盖 / 需补充 / 刻意不同」，并落地新增条款
> 脱敏：材料中的客户名、品牌名、厂商名、门店名一律不出现，正文用「客户」「协同平台」「竞品方案」指代

## 一、三份材料的分量不同，不能同样对待

| 材料 | 性质 | 对设计的约束力 |
|---|---|---|
| **需求确认表**（9 条，逐条标"满足/不满足/待定"） | **客户已签字的验收口径** | **最高**。写着"不满足=定制开发"的那条，就是我们必须在标准产品里做掉的 |
| **问题反馈**（6 个问题） | 客户在竞品上真实踩到的坑 | 高。**这是"竞品已交付但用不下去"的一手证据**，比功能清单有用 |
| **方案 PPT**（能力 + 客户案例） | 竞品能力基线 | 中。抄它的功能，但要知道它哪几处在实战中塌了——就在第二份材料里 |

**关键判断：第二份材料比第三份值钱。** 功能清单告诉我们"要做什么"，问题反馈告诉我们"做出来之后哪里还会被骂"。竞品那三个客户案例里反复出现的"划线排班、跨店支援、年假按月发、最大请假时长"，恰恰是它自己产品在解决的问题——说明这些是行业刚需，不是加分项。

## 二、9 条需求逐条对照

| # | 客户需求 | 竞品判定 | 本设计状态 | 要做的事 |
|---|---|---|---|---|
| 1 | 店长录入员工信息、批量导入 | 满足 | **已覆盖**（`employee_create_prehire` 单条直建/批量需确认） | 补一条：店长录入的**权限边界**——只能录本店、只能录到自己能管的字段 |
| 2 | **二次入职，同步以前花名册档案** | 满足 | **已覆盖**（02g I9 章编号绑 `person`，历史天然连续） | 无需新增。**但把"二次入职"作为 I9 的验收用例写死** |
| 3 | **特殊工号规则 + 跟随部门调度生成新工号** | **不满足→定制开发** | **需补充**（I9 只做了三级，缺"随调度生成"这一层） | **见第四章 4.1，这是本次最大缺口** |
| 4 | 员工 7 天试岗期 | 满足 | **需补充**（现有设计只有试用期，没有试岗） | 见第四章 4.2 |
| 5 | 一天多班次，明确打卡时间范围 | 满足 | **已覆盖**（`attendance_daily_store` 一天多行 + 班段起止） | 补"打卡时间窗"参数（早到/晚走多少分钟内有效） |
| 6 | **月末剩余调休超 0.5 天算加班费，其余转次月** | **待定**（竞品要店长手工调） | **需补充** | 见第四章 4.3。**客户标"待定"说明竞品也做不好，这是差异化机会** |
| 7 | 年假允许预支 + 余额统计报表 | 满足 | **部分覆盖**（四态余额有"预支"，但缺发放节奏） | 见第四章 4.4（按月平均发放） |
| 8 | 考勤报表支持店长在线编辑加班时长 | 满足 | **已覆盖**（人工覆盖 + 留痕 + `IS DISTINCT FROM` 校验） | 补：编辑加班时长必须**走调整单**，不允许直接改结果行（否则重算会覆盖掉） |
| 9 | 数字大屏按权限可视化 | 满足 | **已覆盖**（看板 + 五档数据范围 + 指标六件套） | 补：大屏是**公开屏**，权限必须比个人端更严，按屏而非按人授权 |

**9 条里 6 条已覆盖、3 条要补。** 那 3 条里第 3 条是客户明确标"不满足"的——**这是我们必须在标准产品里做掉、而不是当定制卖的那一条**。

## 三、从问题反馈提炼的 5 个设计要点

这 6 个问题没有一条是"功能缺失"，全是"功能有了但用不下去"。这类证据对设计的价值最高。

### 3.1 客户想建一个不关联员工的管理员账号（`adminHr`）

**这说明权限模型绑死在"人"上会让客户没法交接。** 人事岗位换人时，把权限一个个从旧人身上摘、给新人戴上，摘漏一个就是越权。

**我们的设计缺口**：现有架构写的是"AI 永远代表某人，不存在 AI 自己"。这对 MCP 是对的，对 Web 端登录却不完整——**共用管理账号是真实需求**。

定法（见第四章 4.5）：
- 允许建**服务账号**（`account_type = SERVICE`），可登录 Web、有角色；
- **服务账号不可调用 MCP**（MCP 必须代表自然人，否则审计无主体）；
- 服务账号做的**审批类、金额类、封账类**操作，必须另填"实际操作人"（下拉选本店在职员工）。

**"账号"与"责任人"解耦，但责任必须落到某个自然人身上**——这是唯一能同时满足"好交接"与"可追责"的做法。

### 3.2 补卡了，系统却没显示

这是一个**链路断在中间**的典型：补卡单批了，但考勤结果没重算。

我们的设计里这条链是：补卡单 → `attendance_punch` 新增 → 重算 `daily`/`daily_store` → 状态回 `raw` → 再走 `confirmed`。

**必须补的一条**：补卡审批通过后**必须在同一事务里**把对应 `daily` 打回 `raw` 并投递重算任务；**不允许"批完等晚上跑批"**。否则店长当天查不到、以为没生效，会重复提交——这恰是客户遇到的问题。

同时：重算任务的投递必须落 `outbox` 表，进程挂了重启能续。

### 3.3 想知道"员工能看哪些、能改哪些"（人事 / 考勤分别）

这是权限可解释性问题，不是权限能力问题。**客户问的不是"能不能控"，是"控成什么样了，在哪看"。**

要补一个页面：**某员工的权限透视**——按模块列出"可查看范围 / 可编辑范围 / 来源（角色/页面授权/临时授权）"。这个页面比权限配置页更重要，因为它是唯一能让店长自己回答"为什么他看不到"的地方。

### 3.4 花名册人员与考勤人员是否一一对应

**答案必须是不对应，而且要能解释差异。** 三类差异：

| 差异 | 原因 |
|---|---|
| 花名册有、考勤没有 | 无考勤组（内勤/管理岗不打卡）；或刚入职未绑考勤组 |
| 考勤有、花名册没有 | **异常**。工号能解析但无任职记录 → 必须进异常清单 |
| 两边都有但对不上 | 考勤机工号与法人工号不同步 |

**要做一个"花名册 ↔ 考勤 人员对账"报表**，三类差异各自计数、可下钻。第二类是数据缺陷，必须每日告警。

### 3.5 假期规则（年假发放与使用）要能看、要能配

客户原话是"开通权限，用于查看年假的发放和使用规则设置"。说明**规则本身在产品里是可见可配的**，不是硬编码。

这与我们"拿不准的口径做成配置项"一致，但补一点：**规则配置页必须能反查"当前谁按这套规则、余额怎么算出来的"**。只给配置不给追溯，等于让人凭信任用。

## 四、需要新增的设计条款

### 4.1 工号必须四级，第三级随调度生成（客户标"不满足"的那条）

客户的需求是「**特殊工号定制规则，且跟随员工部门调度生成新工号**」。

这句话验证了"编号必须分层"，但**我原先定的三级不够**——三级里的第三级是考勤机编号（设备侧），客户要的是"部门工号"（管理侧）。

**修正为四级**：

| 层级 | 字段 | 唯一范围 | 变不变 | 谁维护 |
|---|---|---|---|---|
| 1 集团人员编号 | `person.person_no` | 全集团 | **终身不变** | 集团 HR |
| 2 法人工号 | `employment.company_employee_no` | 法人内 | **换法人变** | 法人 HR |
| 3 **门店/部门工号** | `employment.store_employee_no` | 门店/部门内 | **调度就生成新的** | 门店/部门 |
| 4 考勤机编号 | `employment.device_no` | 设备内 | 换设备变 | 门店 |

**第 3 级的生成规则要能配**（这是客户说"特殊定制规则"的部分）：

```
{store_code}-{dept_code}-{seq}     如 SH01-QC-0157
{store_code}{year}{seq}            如 SH0120260157
{legal_prefix}-{seq}               如 SH-0157
```

三条硬约束：

1. **换第 3 级工号时，第 1 级绝对不变**。这是客户"二次入职能看到历史"能成立的唯一原因——调度换号在员工看来是"换了工号"，在系统里是"同一个人的又一段任职"。
2. **历史工号必须全部保留**（`store_employee_no_history`），不能覆盖。旧工号印在旧的排班表、工资条、劳动合同上，覆盖了就对不上。
3. **老工号不许回收给新人**（与 I9.3 一致）：`SH01-QC-0157` 曾经是张三，李四永远不能再用这个号。

**这一条的验收标准要写死**：某员工从 A 店调到 B 店 → A 店工号失效归档、B 店生成新工号、集团编号不变、查看全部历史仍能一次拉出。

### 4.2 试岗期：法律上不成立，但业务上必须有

客户要「员工 7 天试岗期」。

**必须先说清一件事**：法律上没有"试岗期"这个概念。**只要用工就建立劳动关系**，试岗第 1 天起就要签合同、缴社保（非全日制按当地规定）、算工龄。所谓"试岗不签合同、不行就走人"，在仲裁里一律按违法用工处理——**双倍工资 + 补社保 + 经济补偿**。

所以设计上不能做一个"试岗期=无劳动关系"的状态机，那是在帮客户违法。

**正解：把「试岗」做成一类特殊的短期用工合同 + 试用期的前置阶段**：

| 字段 | 取值 |
|---|---|
| `employment_form` | 全日制 / **非全日制** / 劳务（按实际工时定，不是按"试岗"定） |
| `trial_flag` | `true`（7 天内） |
| `trial_start_date` / `trial_end_date` | 按客户配置（默认 7 天） |
| `probation_end_date` | 试岗通过后起算，与试岗不重叠 |

三条硬规则：

1. **试岗期必须有合同**。哪怕是 7 天，也要签（短期劳动合同或非全日制的口头+书面确认）。系统**不提供"无合同试岗"的建档路径**——这是合规红线，不给开关。
2. **试岗期工资不得低于当地最低工资**，且必须计入工资表（不能现金发、不进系统）。系统对"试岗期无工资记录但有人在岗打卡"直接告警。
3. **试岗期内终止用工，仍走离职流程**（不是"删除建档"）。删除会让这个人从来没存在过，而他已经打卡、已经产生用工事实。

### 4.3 调休月末清算：超过阈值折现，其余结转（客户标"待定"）

客户要「月末剩余调休时长，超过 0.5 天算加班费，其余转入次月」。

这条竞品标"待定"，要店长手工调——**说明它没做成规则，只做了个数据展示**。这是差异化点。

做成配置（三项，缺一不可）：

```yaml
comp_time_carry_unit: 0.5        # 结转/折现的最小单位（天）
comp_time_settle_mode: both      # payout | carry | both
comp_time_payout_multiplier: 1.5 # 折现时按什么倍率（默认 1.5 倍）
comp_time_expire_months: 3       # 结转后的有效期，到期仍不休则再次清算
```

**关键规则（客户那句话的精确实现）**：

```
月末剩余 = R
R ≤ 0.5 天  → 全额结转次月
R > 0.5 天  → 向下取整到 0.5 的倍数记为「结转 C」，剩余 (R − C) 若 > 0 则折现
             例：R = 1.8 天 → C = 1.5 天结转，0.3 天 → 不足半个单位，并入结转
             例：R = 2.2 天 → C = 2.0 天结转，0.2 天 → 不足半个单位，并入结转
```

**注意这里有个客户没说清的边界**：`R = 1.8` 时，0.3 天不足 0.5，是折现还是并入结转？两种做法都合理。

**做成配置 `comp_time_rounding ∈ {carry_up, payout}`，默认 `carry_up`**（不足一个单位的零头并入结转）。理由：折现要发钱，零头折现会产生大量几分钱的分录，财务对账成本远高于那点钱。

**折现的钱进哪一期**：进**当月**工资，科目单列「未休调休折现」，且**不计入加班费基数**（它本身就是加班费的替代，再计入基数会重复放大）。

### 4.4 年假按月平均发放，不是年初一次性给

客户要「年假允许预支」，竞品方案里反复强调「年假按天/月平均发放」——**三个客户案例都把这条列为痛点**，说明这是行业刚需。

我们的四态余额（应得/实得/预支/结转）算的是**全年应得**，缺的是**发放节奏**：

```yaml
annual_leave_accrual: monthly_avg   # annual_upfront | monthly_avg | daily_accrual
```

| 取值 | 员工 3 月底可用额度（年假 10 天） |
|---|---|
| `annual_upfront` | 10 天（年初一次给） |
| **`monthly_avg`（默认）** | **2.5 天**（10 × 3/12，按月累计） |
| `daily_accrual` | 2.5 天（按天累计，精度更高但体验差） |

**为什么默认按月而不是年初一次给**：

- 年初一次给 → 员工 1 月休完 10 天、2 月离职 → **多休的假扣不回来**（已发工资，且法律不支持追扣已休年假）；
- 按月累计 → 离职时最多多休当月那不到 1 天，损失可控。

**但"预支"必须同时存在**：客户明确要「允许预支年假」。所以配置成 `allow_advance: true` 时，员工可提前支取全年额度，**但预支部分必须记 `advance_flag`**，离职清算时优先扣回。

这就是四态余额里「预支」那一态的真正用途——**它不是统计字段，是清算依据**。

### 4.5 服务账号：账号可共用，责任必须落实到人

见 3.1。三条实现：

```sql
sys_account (
  account_type  text NOT NULL,   -- PERSONAL | SERVICE
  employee_id   bigint,          -- SERVICE 账号可为空
  ...
)
```

1. `SERVICE` 账号**不可调用 MCP**（MCP 的每次调用必须落到具体自然人）；
2. `SERVICE` 账号执行**审批类 / 金额类 / 封账类**操作时，必须填 `actual_operator_employee_id`（下拉选在职员工），写入审计；
3. `SERVICE` 账号**不可持有"复核/审批"权限的第二签字**——两级审批中必须有一级是自然人账号。

第 3 条是关键：如果两级审批都是共用账号，那"双人复核"就成了一个人点两次。

### 4.6 离职人员数据保留期

竞品方案里提到"离职员工假期数据保留 90 天"。我们没定过保留期。

```yaml
offboard_data_retention_months: 24    # 默认 24 个月（覆盖两个完整年度，够仲裁与审计）
offboard_leave_balance_retention_days: 90   # 假期余额单独更短，与竞品一致
```

**两者保留期不同的理由**：工资、合同、考勤是仲裁与税务稽查的证据，要留足；假期余额是员工个人可查的运营数据，留太久反而成为持续的数据安全暴露面。

## 五、竞品能力基线：抄什么、不抄什么

### 要抄的（行业刚需，不做就进不了场）

| 能力 | 为什么是刚需 |
|---|---|
| **划线排班**（任意给某人加临时班次，不必先建班次再入组） | 三个客户案例都提到；临时工当天来当天排 |
| **一天多班次** | 餐饮白班+晚班是常态，单班次模型直接出局 |
| **跨店支援 + 自动换考勤组 + 到期自动回原组** | 竞品靠"人员调度套件审批单"实现，客户认可；**手动换组是最大的操作负担** |
| **批量排班**（按人员/班组/班次 × 按小时/天/周期） | 千人门店不批量就没法用 |
| **复制粘贴排班** | 上面那条的落地形态，最省事的交互 |
| **合规管控**（排班上限/连续排班/月最少休息/风险预警） | 避免劳务纠纷，是给老板看的价值 |
| **限制性规则**（未排班能否打卡/未排班选班次/能否改已发生排班） | 这三个开关决定现场能不能跑起来 |
| **批量加班/补卡/请假一张单** | 竞品明确对比"基础版只能一个个提"，这是效率差 |
| **年假按月平均发放 + 最大/最小请假时长 + 过期提醒** | 三个案例都列为痛点 |
| **请假证明限时提交**（图片/文字） | 餐饮请假滥用是真实问题 |

### 不抄的（或要做得不一样）

| 竞品做法 | 我们的处理 |
|---|---|
| 排班审批默认开 | 做成配置，**默认关**——排班是店长日常动作，每张周表都要审批，人会绕过 |
| 排班提醒推到"被提醒人" | 保留，但**加"排班未覆盖率"指标**——提醒发了不代表排了，只有覆盖率能说明 |
| 假期过期"清零或转加班"二选一 | 做成三选（清零/转加班费/结转），且**必须先提醒 N 次再执行**，直接清零是劳动争议高发点 |
| 员工自助排班（自己给自己排） | **不做**。自己排班 = 自己决定加班，等于让员工决定加班费 |
| 排班"合规性规则"只做提示 | 我们做成**阻断 + 凭单据放行**（有据可依时才放），因为提示会被无视 |

## 六、给客户的三条反提（需求确认单里没写但必须谈）

这三条不是加需求，是**验收前必须说清的边界**，否则交付时会被当成缺陷：

1. **"试岗 7 天"必须签合同**。客户业务上叫试岗，系统里不能做成无劳动关系。这条谈不下来就不接——违法用工的责任在用工方，但系统是帮凶。
2. **共用账号能做，但审批不能全靠共用账号**。客户要 `adminHr`，可以给；但两级审批里必须有一级是自然人，否则双签没意义。
3. **调休清算的零头怎么处理（1.8 天里那 0.3 天）** 需要客户定一次。做成配置了，但**默认值必须客户书面确认**——因为这条会真金白银影响每个人的工资，默认错了就是批量少发或多发。
