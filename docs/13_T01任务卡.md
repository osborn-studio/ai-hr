## 通用验收形状（五张卡共用）

每张卡的验收都按**四件套**写，缺一件不算完成。这是 `T00.1` 定下的形状，全项目统一：

```
① 正例      干净数据下，该通过的通过
② 造违规    断言变红——且红在"那一条具体断言"上，不是"任一错误"
③ 修复后    只改数据转绿；不许改断言（改断言转绿 = 该条作废，不是通过）
④ 阴性对照  常驻 SELECT 1=0 必须显示失败
```

> **为什么 ② 要红在具体断言上**：造一个错版本让"建表失败"，只证明"这个库建不起来"；让"读回来的实现是错的"被抓到，才证明"建起来了但建错了"能发现。**建不起来是好消息，建错了才是要测的那件事。**

## T01.1 认证：登录、JWT、会话表、可吊销（1.5 人周）

**一句话目标**：一个用户能登录，能拿到令牌，**管理员能让他立刻失效**——不是等令牌过期。

**输入**

| 项 | 出处 | 注意 |
|---|---|---|
| 权限点清单 13 域 315 点 | `10` §1 / §0.7 | 报数从合计行取，不手抄 |
| 动作动词表（16 个，封闭） | `10` §0.3 | 新增动词要先改文档 |
| `session_user` 与 `current_user` 的区别 | `02g` §I49 | 审计记 `session_user` |
| RLS 四个绕过口 | `04` §6.0；`02g` §I46 | 认证层不是权限层，别混 |

**交付物**

1. `sys_user` / `sys_session` / `sys_login_attempt` 三张表的迁移（含索引）
2. 登录、刷新、吊销三个接口 + 一个中间件
3. `sys_config` 里三个开关，**接线并有反例**：`auth.concurrent_policy`（`single`/`max_n`/`unlimited`）、`auth.token_ttl_seconds`、`auth.lock_after_failures`
4. 一份"吊销生效时延"实测记录（毫秒）

**表的关键形状**

```sql
sys_session(
  id            bigserial PRIMARY KEY,
  user_id       bigint NOT NULL REFERENCES sys_user(id),
  token_hash    bytea  NOT NULL,          -- 存 hash，不存原文
  issued_at     timestamptz NOT NULL,
  expires_at    timestamptz NOT NULL,
  revoked_at    timestamptz,              -- NULL = 有效
  revoked_by    bigint REFERENCES sys_user(id),
  revoke_reason text,
  session_user  text NOT NULL,            -- ★ 不是 current_user
  client_ip     inet,
  ua            text
);
CREATE UNIQUE INDEX ux_session_token ON sys_session(token_hash);
CREATE INDEX ix_session_user_alive ON sys_session(user_id) WHERE revoked_at IS NULL;
```

**验收脚本**

| # | 做什么 | 期望 | 为什么这条能证伪 |
|---|---|---|---|
| ① | 登录 → 带 token 访问受保护接口 | 200，`sys_session` 新增一行且 `revoked_at IS NULL` | — |
| ② | **吊销**该会话 → **立即**用同一 token 访问 | **401**，且错误码是 `E_SESSION_REVOKED`（不是 `E_TOKEN_INVALID`） | 若实现成"等 JWT 过期"，这里会是 200。**这一条是整张卡的核。** 错误码分开是因为"令牌无效"与"会话被吊销"处置不同——前者让用户重登，后者要让用户知道是被踢了 |
| ③ | 重新登录 → 再访问 | 200 | 证明 ② 不是把账号锁死了 |
| ④ | 并发策略切 `single` → 同账号第二次登录 | 第一次的 token 变 401 | 配置项必须接进判据。**只登记不接线 = 没有这个配置** |
| ⑤ | 把 `auth.token_ttl_seconds` 改成 1 → 等 2 秒 | 401 `E_TOKEN_EXPIRED` | 同上 |
| ⑥ | 常驻阴性对照 | `SELECT 1=0` 显示失败 | — |

**明确不做**

- 不做 SSO / OAuth / 钉钉扫码。**这版是内网私有化，账号由 HR 建。** 接外部 IdP 属于 T06 之后的事。
- 不做短信验证码。内网环境没有短信通道，做了也无处发。
- 不在 token 里塞权限位。**权限随时会变，塞进 token 就得等它过期。** 每次求值（T01.2）现查。

**已知薄弱点（写进交付说明，不要藏）**

- 每次请求查一次 `sys_session` 会带来一次 DB 读。这是"可立即吊销"的代价，**接受它**，不要为了性能改成纯 JWT 无状态——那等于放弃吊销。
- 令牌劫持无法防御（内网也一样）。这不是缺陷，是边界，写进 `11` §7 那类说明里。

## T01.2 三轴权限求值：功能 → 数据 → 字段（2.5 人周）

**一句话目标**：一次查询同时受三层约束，**顺序不能反**，且**四维全空等于没有权限**。

**输入**

| 项 | 出处 |
|---|---|
| 入口函数唯一签名 `app_begin_scope(p_user, p_resource, p_fact_from)` | `04` §6.0.3.7 |
| 四维定义：`payroll_legal_entity_id` / `legal_entity_si_id`+`si_city` / `cost_org_id` / `attendance_org_id` | `04` §6.0；`02g` §I50 |
| 四维全空 = 无权限 | `12` §T01.2 判据；`02g` §I50 |
| deny 是独立集合，用 `NOT EXISTS` 排除 | `04` §6.0；`02g` §I44 |
| 未登记资源 → `E_RESOURCE_UNREGISTERED`；`FACT_SNAPSHOT` 缺日期 → `E_FACT_DATE_REQUIRED` | `04` §6.0；`02g` §I49 |

**交付物**

1. `app_begin_scope` **只有一个** `CREATE OR REPLACE FUNCTION`（旧版必须改名隔离，不能靠"新签名覆盖旧签名"——PG 按签名重载，覆盖不了）
2. `tmp_scope_org` / `tmp_scope_entity` / `tmp_scope_emp` / `tmp_scope_deny` 四张会话临时表
3. 求值器：功能 → 数据 → 字段，三段短路
4. 每个受控资源的 `sys_perm_resource` 登记行
5. **一份"五维负样本"清单**（见验收 ⑦）

**求值序（反了就全错）**

```
1. 功能权限  无该点 → 403，不看数据
2. 数据权限  四维全空 → 返回 0 行（不是报错，不是全表）
             四维之间 OR，单维内 AND
3. 字段权限  掩码，不报错（见 T01.3）
```

**验收脚本**

| # | 做什么 | 期望 | 证伪点 |
|---|---|---|---|
| ① | 有权限用户查受控表 | 返回该维范围内的行 | — |
| ② | **四维全空**的用户查同一张表 | **0 行** | 这是整张卡最容易做错的一格。做成"全空=全放行"会得到全表，而**它在演示时看起来完全正常**——因为演示账号通常有权限 |
| ③ | **未登记资源**探针 `app_begin_scope(1,'zz_unregistered',NULL)` | 抛 `E_RESOURCE_UNREGISTERED` | 默认拒绝。**必须配阳性对照**（先跑一个正常资源确认探针本身能通），否则"永远抛错"与"从没检查"同形 |
| ④ | deny 命中一个组织 | 该组织的行消失，**且 `tmp_scope_org` 的 allow 行一条没少** | 若实现成"从 allow 里删掉"，会丢掉"这个组织被显式拒绝过"这件事，事后无法复查 |
| ⑤ | `FACT_SNAPSHOT` 资源不传 `p_fact_from` | 抛 `E_FACT_DATE_REQUIRED` | 忘了传若静默变成"按当前判定"，测试环境通常是对的（测试数据没有调动历史），**线上才炸** |
| ⑥ | 重载数 | `public` 内 `app_begin_scope` 的 `proname` 计数 = **1** | 旧版留在库里 = **绕过全部检查不需要任何特权，照旧调用旧签名即可** |
| ⑦ | **五维负样本**：分别只给一维 | 五个用例各返回 0 行（除被给的那一维） | 五维度只处理两维是常见缺陷。**只测"给了两维能查到"永远发现不了漏三维** |
| ⑧ | 常驻阴性对照 | 显示失败 | — |

**明确不做**

- 不做"组织树自动含下级"作为唯一路径。祖先保留是策略，不是默认——**默认行为必须是"只给我被授的那几个节点"**。
- 不做前端过滤。所有过滤在 SQL 层，前端过滤等于没有过滤（改一下请求就行）。

**已知薄弱点**

- 临时表是会话级，连接池复用时必须 `ON COMMIT DROP` 或显式清理。**漏清理会让上一个用户的权限残留到下一个人**，而这种现象表现为"偶尔看到不该看的数据"，极难复现。写进交付说明，并加一条连接归还时的清理断言。
- 有 DB 凭据者不受应用权限约束（`04` §6.0）。这是边界，不是缺陷，写进对客说明。

## T01.3 字段权限：掩码不报错（1.5 人周）

**一句话目标**：无权看的字段返回**掩码值**，不是错误。

**输入**

| 项 | 出处 |
|---|---|
| 字段权限只掩码不报错 | `04` §6；`10` §0.4 |
| 审批节点可见性与角色矩阵**同源** | `12` §T01.3 判据 |
| 一个状态在两处存必然不一致 | `02g` §I59 |

**交付物**

1. `sys_node_field_policy`（节点 × 字段 × 角色 → 可见/掩码/可写）
2. 掩码渲染器：`***`（字符串）/ `NULL`（数值，且**报表上显示 `—` 不是 0**）
3. 一份"字段 × 节点 × 角色"的渲染矩阵（机械生成，不手写）

**为什么掩码不报错**

报错本身泄露信息：**"这个字段存在，而且敏感"**。掩码返回的是"这里有个值，你看不到"，这是允许泄露的；报错返回的是"这里有个你无权访问的东西"，这多泄露了一层。

**验收脚本**

| # | 做什么 | 期望 | 证伪点 |
|---|---|---|---|
| ① | 有权用户读薪资字段 | 返回原值 | — |
| ② | 无权用户读同一字段 | 返回掩码，**HTTP 200** | 若返回 403 → 红。**这一条要故意做成能红**：把实现改成抛错，确认 ② 变红，再改回 |
| ③ | 数值字段被掩码 | 报表上显示 `—`，**不是 0** | 显示 0 会被当成"这个人是 0 元"，而它其实是"你看不到" |
| ④ | **同一字段在列表页与详情页** | 掩码结果**完全一致** | 两处各写一套掩码规则是这类功能最常见的缺陷，而它在单页测试里发现不了 |
| ⑤ | 审批节点可见性 vs 角色矩阵 | 改角色矩阵 → 审批节点可见性跟着变 | **同源才算通过。** 两处各配一份 = 两处必然漂移（§I59） |
| ⑥ | 常驻阴性对照 | 显示失败 | — |

**明确不做**

- 不做"字段级加密"。掩码是展示层，**不是存储层**。加密解决的是"库被拿走"，那是 T01.4 边界之外的事，写进对客说明。
- 不做"掩码可配置成部分显示"（如 `138****1234`）。**这一版只做全掩码**。部分显示需要按字段类型定义规则，是另一个工作量，且它给人一种"脱敏过了"的错觉。

## T01.4 审计：写操作留痕、不可删（1.0 人周）

**一句话目标**：任何写操作留痕，**且审计表没有 DELETE 路径**。

**输入**

| 项 | 出处 |
|---|---|
| `session_user` 必被记录 | `02g` §I49 |
| 审计由被审计者自己写 → 对"停用自己"必然失明 | `02g` §I66.3 |
| 表级封锁强度 = 权限链最弱环 | `02g` §I62 |
| `TRUNCATE` 与 `DELETE` 必须分别测 | 同上 |

**交付物**

1. `sys_audit_log` + 记录触发器（**在 DB 层，不在应用层**）
2. 审计表的权限收紧：`REVOKE UPDATE, DELETE, TRUNCATE ON sys_audit_log FROM app_role`
3. 一份"审计表能被怎么破坏"的枚举清单（见验收 ④）

**为什么记录点必须在 DB**

如果记录器是应用里的一个函数，那么"停用记录器"这个动作本身就记不到——因为记录器已经被停了。**凡审计由被审计者自己写，审计对"停用自己"必然失明。** 补法只有两条：心跳，或把记录点前移到数据库。这里选后者。

**验收脚本**

| # | 做什么 | 期望 | 证伪点 |
|---|---|---|---|
| ① | 改一行员工数据 | `sys_audit_log` +1 行，含 `session_user`、旧值、新值、时间 | — |
| ② | 用 `app_role` 执行 `DELETE FROM sys_audit_log` | `permission denied` | — |
| ③ | 用 `app_role` 执行 **`TRUNCATE sys_audit_log`** | `permission denied` | **必须单独测。** 只测 DELETE 是这类功能的固定漏洞——`TRUNCATE` 不触发 `ON DELETE` 触发器，也不走行级权限 |
| ④ | 枚举破坏路径，逐条验 | 每条都有机制或明确"未覆盖" | 清单：`DELETE` / `TRUNCATE` / `DROP`+`CREATE` / `ALTER` 换约束 / 表 owner / 写该表的 definer 函数 / 导入 / 复制到新表。**"没有机制"的必须写成已知未覆盖并登记，不许留空** |
| ⑤ | 停用审计触发器后做一次写操作 | 该次写操作**应该仍然被记**（或：必须有一条心跳告警） | 记不到才是常态。**若既记不到、又没有心跳，这条就是"我们说要保证但没有任何东西保证"** |
| ⑥ | 常驻阴性对照 | 显示失败 | — |

**明确不做**

- 不做审计日志的 UI 检索。**只做写入与最基本的按时间/人筛选。** 复杂检索是 T04 报表的事。
- 不做日志归档。内网环境容量足够，归档策略等 T06 按实际量定。

## T01.5 审批引擎：模板/版本分离、发布即冻结（2.0 人周）

**一句话目标**：审批模板改版**不影响在途单据**，且**发布后不能再改**。

**输入**

| 项 | 出处 |
|---|---|
| 42 张单据 | `10` §5；报数从合计行取 |
| 模板与版本分离、发布即冻结 | `04` §7；`12` §T01.5 判据 |
| `approve_*` 工具 = 0，审批权结构性不可委托 AI | `04` §11；`11` §6 |
| 防自锁 | `04` §7.4 |
| 弱路径会吃掉强路径 | `02g` §I64.3 |

**交付物**

1. `approval_template` / `approval_template_version` / `approval_instance` / `approval_task` 四张表
2. **发布冻结触发器**：`status='published'` 的版本，`UPDATE` 定义类字段直接拒绝
3. `approval_instance.template_version_id` **NOT NULL 且不可改**（在途锁定）
4. 一份"哪些操作会绕过冻结"的枚举（见验收 ⑤）

**表的关键形状**

```sql
approval_template_version(
  id            bigserial PRIMARY KEY,
  template_id   bigint NOT NULL REFERENCES approval_template(id),
  version_no    int    NOT NULL,
  status        text   NOT NULL CHECK (status IN ('draft','published','retired')),
  published_at  timestamptz,
  published_by  bigint REFERENCES sys_user(id),
  definition    jsonb  NOT NULL,           -- 节点、条件、审批人解析规则
  UNIQUE (template_id, version_no)
);
-- 发布即冻结：不是靠应用层判断，是靠触发器
CREATE TRIGGER trg_atv_freeze BEFORE UPDATE ON approval_template_version
  FOR EACH ROW WHEN (OLD.status = 'published' AND NEW.definition IS DISTINCT FROM OLD.definition)
  EXECUTE FUNCTION raise_published_version_immutable();
```

**验收脚本**

| # | 做什么 | 期望 | 证伪点 |
|---|---|---|---|
| ① | 发起一张单据 → 两级审批 → 完成 | 状态走完，`approval_task` 两条记录都含处理人 | — |
| ② | 直接 `UPDATE` 已发布版本的 `definition` | **DB 拒绝**（不是应用层拦） | 应用层拦可被绕过——**能连库的人不受应用权限约束** |
| ③ | 发布 v2 → 查在途单据的 `template_version_id` | 仍是 v1 | 若跟着变成 v2，说明版本没锁死在实例上。**这一条在"只测新单据"时永远发现不了** |
| ④ | 走完的单据 vs 在途单据 | 走完的仍显示 v1 的定义 | 历史可追溯：**不能因为改了模板，历史审批记录的含义跟着变** |
| ⑤ | 枚举绕过冻结的路径 | 每条有机制或登记未覆盖 | 清单：`DELETE` 该版本 / `INSERT` 同 `version_no` 新行 / 改 `status` 回 `draft` 再改 / `ALTER` 去掉触发器 / 改触发器函数体 / `TRUNCATE`。**"改 status 回 draft"是最容易被漏的一条**——它是合法的 `UPDATE`，只是走了一条弱路径 |
| ⑥ | 防自锁：把唯一审批管理员改成无审批权 | 被拒，或有一个不可绕过的兜底账号 | 防自锁做不到时，第一次误操作就要靠改库恢复 |
| ⑦ | `approve_*` 类 MCP 工具数 | **= 0** | 审批权结构性不可委托 AI。这条是产品承诺，要能被数出来 |
| ⑧ | 常驻阴性对照 | 显示失败 | — |

## 派单须知（给接卡的人）

1. **卡里的判据不要改。** 觉得不对，先提出来，不要自己改完再报"已完成"。改了判据再通过，等于把这条判据删了。
2. **"造违规"那一步必须真的红一次。** 报告里要贴红的输出。只贴"改回后变绿"的，按未完成算。
3. **报数从合计行取。** 点数、单据数、工具数，一律抄合计行，不手算、不顺推。这条已经错过一次。
4. **已知薄弱点要写进交付说明，不要藏。** 藏在代码注释里的边界，等于没写——注释不会被复制到汇报里。
5. **五张卡都完成后，`T01` 才能标 done。** 单卡完成只说明那一段通了，`T01` 的出口是"三轴一起通"，不是"五张都写完了"。
6. **看到"必须/不得"后面跟的是 SQL 关键字、函数名或类型名，先停下问一句：这句业务能不能判？** 能，照做；不能，说明它写错了册子——**它该在 `04`，不该在 PRD 里当需求**，报回去让人改，不要照着实现。判据见 `00` 的"条款的唯一出处"表。
