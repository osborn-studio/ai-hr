## 0. 本册定位与写法

### 0.1 这份清单解决什么问题

| 问题 | 谁答 | 本文档 |
|---|---|---|
| 系统里一共有多少个"能点的动作" | **产品** | ✅ §1 权限点清单 |
| 每个角色按什么维度看数据 | **产品** | ✅ §2 数据范围映射 |
| 某个动作业务上该不该给某个角色 | **产品** | ✅ §1 的"谁需要 / 不授予谁"两列 |
| 权限怎么存储、怎么校验、缓存怎么失效 | 架构师 | ❌ 不在本文档 |
| 审批流的节点怎么配、会签/或签怎么算 | 架构师 + 研究 | ❌ 不在本文档 |

> **为什么先做这两张清单、不等模型**：权限点清单是"名词表"——模型定的是"这些名词怎么存、怎么查"，不是"有哪些名词"。名词缺失，模型再好也补不回来；而名词一旦多了少了，后面每个界面都要返工。

### 0.2 命名规范

```
{域}.{资源}.{动作}
例：org.node.move        组织节点移动（拖拽）
     schedule.plan.export 排班表导出
```

| 段 | 取值 | 说明 |
|---|---|---|
| 域 | `org` / `employee` / `schedule` / `attendance` / `leave` / `payroll` / `recruit` / `perf` / `learn` / `flex` / `report` / `system` / `audit` | 共 13 域，与第一、二册章节一一对应 |
| 资源 | 业务对象单数（`plan` / `daily` / `bridge` / `settlement`） | 不用菜单名，不用页面名。**可带对象子类限定词**，见下 |
| 动作 | 见 0.3 动词表 | **16 个，封闭；不许自造，也不许拼接** |

**资源段可以带限定词，动作段绝不可以。** 同一对象的不同子类或不同状态，限定词进资源段——`plan_draft` / `plan_published` / `plan_locked` / `tree_history` / `cert_detail` / `profile_sensitive` / `headcount_ledger`。资源段是**开集**（业务对象本来就多，锁死没意义），但有两个约束：**① 每个资源名必须在 §1 清单里登记过，没登记的不许用；② 限定词必须是业务对象词（`_ledger`/`_detail`/`_draft`/`_receipt`），不许是版本或批次词（`_v2`/`_new`/`_batch`/`_tmp`）**。后者是鉴权字符串漏检的主要来源：`plan_edit_v2` 一旦上线，谁也不知道 `plan_edit` 还管不管用。

**为什么动作段不能拼接**：一旦允许 `edit_draft` 这种写法，就必然出现 `edit_draft_v2`、`editDraft`、`edit_draft_batch` 三种拼法，而权限校验是字符串匹配——拼法一多，**漏检就是静默的**：接口写着 `edit_draft`，库里配的是 `editDraft`，人照样能改，日志里看起来"已鉴权"。所以动作段只允许 16 个精确值，状态进资源段、入口不进权限（见 0.5）。

### 0.3 动作动词表（16 个，封闭词表，新增需改本文档）

> 本表分三组。**分组的用途**：A 组是"对数据做了什么"，B 组是"在流程里承担了什么责任"，C 组是"改变了对象之间的结构关系"。三组混在一起就分不清"我有写权限"和"我能承担这个责任"——后者不能由前者推导。

**A 组｜数据动作（8）**

| 动词 | 含义 | 可批量 | 为什么必须独立 |
|---|---|---|---|
| `view` | 查看（数据返回且可读） | — | — |
| `export` | **导出（数据离开系统）** | 是 | 唯一会把数据带出系统的动作 |
| `create` | 新建 | 是 | — |
| `edit` | 修改已有对象的属性 | 是 | — |
| `delete` | 删除（物理或逻辑） | 是 | 与 `edit` 分开：不可逆 |
| `void` | 作废（保留记录 + 追加冲销） | 是 | 与 `delete` 分开：记录还在，要能举证 |
| `seal` | 封存/结账（不可逆） | — | 封账后连超管也不能改，只能反封账（另开点） |
| `publish` | 发布（使对象对他人可见/生效） | — | 发布前只有自己看得到，影响面差一个量级 |

**B 组｜流程动作（5）**

| 动词 | 含义 | 可批量 | 为什么必须独立 |
|---|---|---|---|
| `approve` | 审批（含会签一票、复核） | 是 | 审批是"承担责任"，不是"改数据"，不可由 `edit` 推导 |
| `execute` | 执行已批决定，落地成事实数据 | 是 | 与 `approve` 分开：**审批人与执行人可以是不同角色**（调动、离职、封账都如此） |
| `act_as` | **代他人操作** | 是 | 能改 ≠ 能替别人改；后者是替他人担责 |
| `grant` | 授权给他人（含临时授权） | — | 与 `act_as` 分开：一个自己代做，一个授权别人做 |
| `config` | 配置规则/参数（改的是"以后怎么算"） | — | 与 `edit` 分开：影响"以后每一次"，且出事时全集团同时错 |

**C 组｜结构动作（3）**

| 动词 | 含义 | 可批量 | 为什么必须独立 |
|---|---|---|---|
| `move` | 移动（改父子/归属关系，影响整棵子树） | — | 不是 `edit` 的一个字段：移动会改变子树下所有人的归属口径与历史查询结果 |
| `merge` | 合并（两对象并一，改历史归属） | — | 不可逆，且会重写历史 |
| `run` | 执行批处理任务（同步/巡检/重算） | — | 一次触发影响一批数据，与"改一条"完全不同风险 |

### 0.4 三条硬规则（本次专门按这三条过一遍）

| # | 规则 | 为什么 |
|---|---|---|
| **1** | **"看"与"导出"必须是两个权限点** | 导出是唯一会把数据带出系统的动作。合并成一个点，等于把"带出权"顺带授给所有能看的人——**离职带走一份花名册，事后无法追责** |
| **2** | **"改"与"删"必须是两个权限点**，且删除类**只授到具体角色，不授到"部门/岗位"** | 一个部门里有 20 个人，只要 1 个人能删就够了；授到部门 = 20 个人都能删 |
| **3** | **"代他人操作"必须是独立权限点**，不许用"有该功能的写权限"推导 | 能改排班 ≠ 能代店长改排班。前者是"改自己的活"，后者是"替别人承担责任"，性质不同 |

### 0.5 颗粒度判定：什么时候该拆成两个点

| 情形 | 拆 | 不拆 |
|---|---|---|
| 数据是否会离开系统 | 看 / 导出 **拆** | — |
| 是否不可逆 | 改 / 删 **拆**；作废 / 删除 **拆**；封存 / 反封存 **拆** | — |
| 是否替他人承担责任 | 代操作 **独立** | — |
| 是否由不同人承担（审批 vs 执行） | **拆**（`approve` vs `execute`） | — |
| 影响"这一次"还是"以后每一次" | 操作 / 配置 **拆**（`edit` vs `config`） | — |
| 只是同一动作的不同入口（PC / H5 / 批量 / 扫码） | — | **不拆**（入口不是权限） |
| 只是同一动作的不同对象范围（本店 / 跨店 / 全集团） | — | **不拆**（用 §2 数据范围表达） |
| 只是同一对象的不同状态（草稿 / 已发布 / 已锁定） | **状态进资源段**，`plan_draft.edit` / `plan_published.edit`，不是 `edit_draft` | — |

> 最后三条最容易拆过头。**"手机端排班"不是权限点，"能改另一个门店的排班"才是**——前者是入口，后者是数据范围。
>
> 状态为什么要单列：草稿改错了只有自己知道，已发布改错了员工已经看到、已经据此安排生活，已锁定改错了要动已结算的工时——**三者的代价差一个量级，不能共用一个开关**。但状态不是新动作，所以进资源段（`plan_draft` / `plan_published` / `plan_locked`），动作段仍是 `edit`。

**实测结论（替换原 C1 的预估）**：

- 实际 **315 点**，均值 **24.2 点/域**。原预估区间 180–220 **低估约 45%**；三域初稿外推的 330–390 **高估约 10%**。原因是 P1 域（`report`/`system`/`audit`/`learn`）点数天然少，拉低了均值。
- **点数不是均匀分布的**：`schedule`(40) / `payroll`(38) / `attendance`(31) / `employee`(31) 四域占 44%。**这四域就是配置界面的性能压力点**——分组与搜索必须优先在这四域做。
- **`audit` 只有 9 点不是"做得少"，是审计域本身只有这么几件事**（看、导出、配置、复核、申请、登录、重放、报告、封存）。为了凑数而拆点，会让审计权变得"看起来很多但每个都不完整"。
- 若某域点数看上去少（如 `perf` 18 / `learn` 17），是因为**故意不设的点**写在各域开头——**少的部分都在那里有名字**。

| `schedule.plan.create` | 新建排班（空白 / **复制上周** / 套模板） | 店长、门店 HR | — | 三种来源是"入口"不同，不拆成三个点（§0.5） |
| `schedule.plan_template.config` | 维护排班模板 | 区域 HR、集团 HR | 店长 | 模板影响全区域，店长只引用 |
| `schedule.plan.publish` | **发布排班** | 店长、门店 HR、区域 HR（辖区） | 供应商、承揽 | 与 `plan_draft.edit` 分开：发布使员工可见并进工时事实；03 §5.8.4 明确含区域 HRBP |
| `schedule.plan_urgent.publish` | **紧急发布**（低于提前量 / 带未消警告发布） | **区域 HR 及以上**（必须填理由） | **店长、门店 HR** | 03 §5.8.4 的 `publish_urgent`。**与正常发布分开是硬规则**：低于提前量发布意味着员工可能已经排了别的事，责任必须上收一级 |
| `schedule.plan_bulk.edit` | **划线批量套用**（批量改一格以上） | 店长、门店 HR | 区域 HR | 03 §5.2.5 要求与单个编辑分开：**避免临时授权者批量改坏班表**。批量一次影响一批人，与改一格不是一个风险等级 |
| `schedule.plan_published.void` | **撤回发布**（员工**未读**时；还原班表） | 店长、区域 HR | 门店 HR | 判据是**员工是否已看过**，不是过了多久（见下） |
| `schedule.plan_correction.create` | **发更正通知**（员工**已读**后；不还原班表） | 店长、门店 HR | — | 已读后只发更正，不还原——他可能已经据此安排了生活 |

> **撤回发布为什么拆成两点、为什么不设时间窗口**：
>
> ```
> 员工未读 → schedule.plan_published.void     撤回，还原班表（他还来得及不知道）
> 员工已读 → schedule.plan_correction.create  只发更正通知，不还原班表
> ```
>
> 判据是**员工是否已看过**，不是"发布后 2 小时内"。2 小时是拍脑袋的阈值——它和"员工是否据此安排了生活"没有关系，而撤回的全部意义恰恰是"他还来得及不知道"。**一个已经开始通勤的人，你要撤回的不是班表，是他的早起。**

#### 1.3.5b 「强制 / 越权」三档不可混同（通知对象与善后完全不同）

> 凡涉及"强排""越权""覆盖"的地方，**不许写成一句"或（越权）"**。混成一句的结果是：**已发生的越权只通知员工**（他不知道该找谁），**未发生的越权不留痕**（因为它"没成"）。而这两件事恰好都是最需要留痕的。

| 档 | 含义 | 由哪个权限点产生 | 通知谁 | 善后 | 审计 |
|---|---|---|---|---|---|
| **① 被强制**（强排） | 有权的人排了，员工不情愿 | `schedule.plan_published.edit`（店长有权） | **员工 + 其主管** | 记录异议，**不影响生效**（门店不能空转） | 强制记录（含理由） |
| **② 越权生效**（已发生） | 无权的人排了**且已发布** | 不应存在；实际来自代操作过期、临时授权错配、角色配错 | **员工 + 被越权方主管 + HR** | **复核，可能撤回** | **高优先级事件**，进月度审计报告 |
| **③ 越权被挡**（未发生） | 无权的人尝试，被拒 | — | **只记审计，不通知**（通知了等于告诉对方"这里有个门"） | 无 | **必须留痕**：拦截不留痕 = 无法发现有人在试 |

> **三档的关键差别**：①是业务常态（要有异议通道，不需要拦截）；②是**事故**（要复核，要能撤回）；③是**信号**（要留痕，因为它往往是②的前兆）。把③归到"什么都没发生"，就等于放弃了唯一能提前发现②的机会。

### 1.5 `leave` 假期（对应 03 第 7 章）

> **数据范围维度**：考勤组织（门店）+ 参保主体（城市政策包按参保地取）。**城市政策包取参保主体所在城市，不取门店所在城市**——同一个人可能在北京参保、在天津门店上班。
> **依赖**：`leave.balance.*` 依赖 `payroll` 的工龄与在职状态；`leave.request.approve` 必须与 `schedule` 联动（批假后班表要能改）。
> **故意不设的点**：① `leave.balance.view_all`——"看所有人余额"就是 `balance.view` + 数据范围，不另开点；② `leave.request.delete`——请假单只能撤回不能删，删了余额算不清；③ `leave.mobile.apply`——入口不是权限。
>
> **一条必须写进本域的硬规则（v0.5 新增）**：**调休凡是"实际算了休息"的分支，必须同时产出一条假期台账行。** 否则工时侧认为休了、假期侧认为没休——**假期余额不变、可用加班工时先被扣掉，等于双扣**。这条与 03 §6.3.3「调休额度只能由 `ot_compensated_hours` 抵冲生成」是同一处，权限上必须落在 `attendance.comp_time.grant` 与 `leave.balance_ledger.view` 之间：**台账行是抵冲的凭证，不是余额的附属显示**。

### 1.6 `payroll` 薪酬（对应 07 第 3 章）

> **数据范围维度**：**四个维度全部用上，且不合并**——发薪法人（谁能算这个法人的钱）、参保主体（基数与缴费）、成本组织（成本账）、考勤组织（取数来源）。这是 13 个域里唯一四维全用的域。
> **依赖**：读 `attendance.daily` 中 `confirm_status=confirmed` 的行（只读、字段名写死）；`payroll.adjust.*` 依赖 `employee.profile` 的薪资档案；`payroll.period.seal` 依赖六道闸门全通过。
> **故意不设的点**：① `payroll.record.delete`——工资记录不可删，只能作废重算新版本；② `payroll.payslip.export_all`——批量导出就是 `payslip_others.export` + 数据范围，不另开；③ `payroll.seal.cancel`——"取消封账"不存在，只有反封账（走审批）；④ `payroll.super_admin.grant`——**不存在**，超管是静态名单。

#### 1.6.1 域管理员与"不得自审自付"（业务侧判据，供架构对齐）

**这一条不是权限点，是结构性禁止，必须由引擎实现，不能写成制度条款。**

| # | 判据 | 为什么必须是结构性的 |
|---|---|---|
| **PA-1** | **发薪法人域管理员唯一**：`(payroll_legal_entity_id)` 上只能有一个 `DOMAIN_ADMIN` 角色实例，换人须走"移交"而非"新增" | 两个域管理员 = 两份工资表可能都被算出来，最后谁也不敢删 |
| **PA-2** | **本人是制单人 → 该审批节点对本人不可见且不可被指派**（不是"应该回避"，是候选人为空时**不降级到别人、直接阻断并提示配置错误**） | 若实现为"本人不可批，自动找上级"，实际结果是**系统替违规者找了一个签字的**；只有阻断才会被修 |
| **PA-3** | **本人是收款人 → 不得担任该笔付款的任何审批节点**，含复核、含第二签字 | 自付是最原始也最常见的舞弊路径 |
| **PA-4** | **`payroll.adjust.create` 与 `payroll.adjust.approve` 不得同人**（同一 `employee_id`，即使换了角色也不许） | 换角色绕过是最容易发生的规避方式 |
| **PA-5** | **服务账号（`account_type=SERVICE`）不得担任任何金额类、封账类审批的第二签字人** | 服务账号无人格，签字等于无签字（07 §12.4） |
| **PA-6** | 上述 5 条**违反时返回明确错误码**（如 `SELF_APPROVAL_FORBIDDEN`），**不得静默跳过该节点** | 静默跳过 = 单据看起来批完了，实际少一个人 |

> **PA-2 的常见错误实现**：把"本人不可批"做成前端隐藏按钮。后端仍可调接口，且**批量审批接口会绕过前端**。必须是服务端在候选人生成阶段就排除，且发起时校验候选集非空。

#### 1.6.6 字段级审批三场景（与 §5.4 对应）

> 字段级审批**不是给字段单独配一个审批权限**，是：审批单携带 `before_json` / `after_json`，审批页只渲染差异字段。限定三个场景，理由：只有这三个同时满足"字段少、金额敏感、事后必须举证"。

| 场景 | 差异字段 | 审批人需要判断的最小充分集 | 抄送 |
|---|---|---|---|
| 调薪 | `原薪资 / 新薪资 / 生效日 / 调整理由` | 这 4 个字段必须可改 | 财务 |
| 社保缴费基数调整 | `原基数 / 新基数 / 生效期 / 依据` | 4 个 | 财务、法人 HR |
| 银行卡变更 | `原卡（掩码）/ 新卡（掩码）/ 户名 / 变更原因` | 4 个 | 无 |

> **节点只做"降级"，不授予编辑权**：节点字段策略取值为 `visible/readonly/hidden`，来源是**角色级字段权限**再收窄。节点不能把 `hidden` 变 `visible`、不能把 `readonly` 变 `editable`。这条写死，否则实施会做成"节点授予编辑权"，就破了"审批视图是字段权限的消费方，不是第二个真相"。

### 1.7 `recruit` 招聘（对应 07 第 4 章）

> **数据范围维度**：成本组织（岗位归属哪个门店/区域）+ 招聘组织。**不看发薪法人**——招聘时不必然知道这个岗位最终由哪个法人发薪，用工主体在 offer 阶段才定。
> **依赖**：`recruit.demand.approve` 依赖 `org.headcount.view`（编制是需求的前置）；`recruit.offer.approve` 依赖 `payroll.profile.view`（薪资带宽）。
> **故意不设的点（**这一域最该小心**）**：
> - ① `recruit.candidate.filter_by_age` / `_gender` / `_hometown` / `_marriage`——**权限点表里永远不出现，且 MCP 层同步拒绝**（07 §4 红线）。写在这里是为了让"新增一个筛选器"变成一个**需要改文档的动作**，而不是前端加个下拉。
> - ② `recruit.candidate.export_all`——简历批量导出就是 `candidate.export` + 数据范围，且**单次上限写死 200 份**。
> - ③ `recruit.ai_rank.config_hidden`——AI 排序的权重**不可配置也不可隐藏**，必须公示，否则等于埋了一个歧视通道。

### 1.8 `perf` 绩效（对应 07 第 5 章）

> **数据范围维度**：考勤组织（门店）+ 考核单元。**跨门店的考核单元（如区域厨政）按考核单元授权，不按门店拆**。

### 1.11 `report` 报表与看板（跨册）

> **数据范围维度**：**取报表数据源的维度，不再造一套**。报表域自己不定义范围，它继承被取数对象的四维。
> **依赖**：全部依赖上游域的 `view` 权限——**报表不授予任何原始明细的可见性**，它只做聚合。
> **故意不设的点**：① `report.*.export` 单独一套——**每个报表都有独立导出点**（这是本域存在的理由，见下）；② `report.data.raw_view`——报表不给明细行，要看明细回原域（否则报表成了绕开字段权限的后门）；③ `report.kpi.define_hidden`——指标口径必须公示，不允许隐藏定义。

## 2. 数据范围 → 角色的映射（业务口径）

### 2.1 先定词表：**"不可见"与"只读"不是一回事**

> 这两个词在需求文档里最常被混成"无权限"，但实现与界面完全不同。**前者数据不返回，后者数据返回但不可改**。

| 词 | 含义 | 接口行为 | 界面行为 |
|---|---|---|---|
| **全集团** | 全集团范围内可见 | 返回全部 | 正常展示 |
| **辖区** | 仅本人管辖的组织范围（按 `employee_org_assignment` as-of 当时的管辖关系） | 按组织子树过滤 | 正常展示 |
| **本店** | 仅本人当前所属门店 | 按门店过滤 | 正常展示 |
| **本人** | 仅本人数据 | 按 `employee_id` 过滤 | 正常展示 |
| **仅派驻人员** | 仅本供应商派驻的人员 | 按 `supplier_id` + `record_owner` 过滤 | 正常展示 |
| **只读** | **能看到，但所有写操作返回 403** | **返回数据** | 展示 + 控件置灰 + 悬浮提示"无修改权限" |
| **不可见** | **数据根本不返回** | **不返回该字段/该行，接口不告警** | 该字段不渲染（不是灰的，是**不出现**） |
| **字段脱敏** | 返回但打码 | 返回掩码值 | 展示 `138****8888` |

> **"不可见"必须做到"字段不出现"而不是"灰掉"**。灰掉等于告诉对方"这里有个你不能看的东西"，反而暴露了信息结构；对工资、社保基数这类字段，**不渲染才是正确做法**。

### 2.2 四维归属必须分列（不可合并）

我们的归属是**四个维度**（03 §3.1.1）：发薪法人、参保主体、成本组织、考勤组织。任何角色的数据范围都要**四维各写一次**——写"看本门店"是不够的，因为一个人可能在 A 店上班、成本记 B 店、由 C 法人发薪、在 D 城市参保。

| 角色 | 发薪法人 `payroll_legal_entity_id` | 参保主体 `legal_entity_si_id` | 成本组织 `cost_org_id` | 考勤组织（门店） | 备注 |
|---|---|---|---|---|---|
| **门店 HR** | 本店所属法人（**只读**） | 本店所属参保主体（**只读**） | 本店 | 本店 | 门店 HR 能办业务但不能改法人级参数 |
| **区域 HR（HRBP）** | 辖区全部法人（可写，走审批） | 辖区全部参保主体（可写） | 辖区门店 | 辖区门店 | 辖区按 `employee_org_assignment` 当时的管辖关系判定 |
| **店长** | 本店所属法人（**只读**） | **不可见** | 本店 | 本店 | **店长不该看到社保明细**（见 §3 Q1） |
| **集团 HR** | 全集团（可写） | 全集团（可写） | 全集团 | 全集团 | — |
| **集团薪酬** | 全集团（可写） | 全集团（可写） | **不可见**（只管发钱不管成本归属） | 不可见 | 薪酬与成本分离，避免"自己算薪自己核成本" |
| **财务** | 全集团（只读） | 全集团（只读） | 全集团（可写） | 不可见 | 财务管成本账，不管现场考勤 |
| **员工本人** | 本人 | 本人 | **不可见** | 本人 | 员工只看自己，不看成本归属。**离职后 90 天内仍保留只读**，理由见下 |
| **外包供应商** | **不可见** | **不可见** | **不可见** | **仅本供应商派驻人员** | 见 §3 Q3，含离职人员 |
| **服务账号**（`SERVICE`） | 按绑定角色的范围 | 同左 | 同左 | 同左 | 但**审批类第二签字不可用服务账号**（07 §12.4） |

**成本组织一列里"成本中心"与"门店"是两类值，必须分列写清**（C6）：

| 角色 | 成本中心（`COST_ORG.kind = COST_CENTER`，如总部、中央厨房、区域仓） | 门店（`COST_ORG.kind = STORE`） | `include_sub` |
|---|---|---|---|
| 门店 HR | **不可见**（门店 HR 不带总部成本） | 本店 | 否 |
| 区域 HR | 辖区内成本中心（只读） | 辖区门店 | **逐条下放**，不是整体开关 |
| 店长 | **不可见** | 本店 | 否 |
| 财务 | 全集团（可写） | 全集团（可写） | 是 |
| 集团薪酬 | **不可见** | **不可见** | — |

> **`include_sub` 是逐条下放的**：给区域 HR"辖区门店 + 含下级"与"辖区门店 + 不含下级"是两个不同的授权，不能合成一个全局开关——否则集团一改开关，全集团 500 个门店的范围同时变。

**离职后 90 天只读通道：理由不是"方便员工"，是"降低企业的举证风险"。**

> 考勤与工资记录**由用人单位掌握**，举证责任在企业一侧。劳动者先证"存在加班/欠付的事实"，一旦主张成立而企业拒不提供其掌握的记录，**仲裁可推定劳动者主张成立**。
>
> 所以提供取数通道（**仅本人、仅本人历史、留取数日志**）等于把最准确的证据留在可核对的状态。这条**不是措辞问题，它会改变客户接受度**：「给员工开个查询口」听起来像让步，实际是在保护企业。

### 2.3 字段权限：与数据范围正交的第二道闸

数据范围管"哪些行"，字段权限管"哪些列"。以下六个字段是**全系统最高敏感级**，默认掩码，全值另开权限点：

| 字段 | 默认 | 全值权限点 | 谁能拿全值 |
|---|---|---|---|
| 身份证号 | 掩码 | `employee.profile_sensitive.view` | 集团 HR、本店门店 HR（办业务时） |
| 银行卡号 | 掩码 | `payroll.bank_account.view` | 集团薪酬、财务 |
| 社保缴费基数 | **不可见** | `payroll.si_base.view` | 集团薪酬、法人 HR；**店长与区域 HR 不可见** |
| 工资明细 | **不可见** | `payroll.payslip_others.view` | 集团薪酬、财务；**店长仅可见本店合计** |
| 体检结论 | **不可见** | `employee.cert_detail.view` | 门店 HR、食安负责人；**店长不可见** |
| 供应商单价 | **不可见** | `flex.contract_price.view` | 采购、财务、区域 HR；**店长不可见**（否则可反推人工成本结构） |

> **这张表跨域**：`employee.*` 两个点已在 §1 登记；`payroll.*` 三个点与 `flex.*` 一个点属后两册的域，**待那 10 个域推进时统一登记**，此处先占名、先定"谁能拿全值"。这样做的原因：字段全值权限点如果不和数据范围一起定，实施时一定会被"先给上，反正能改"的心态放开。
>
> **字段权限必须区分"看"与"改"**——本表列的是"看全值"。改敏感字段（银行卡号变更、身份证更正）另走审批。
>
> **但"看全值"与"改全值"不做成互斥权限点**（v0.4 修正）：`payroll` 域管理员天然既看又改，禁掉就没人能干活，实施会直接配一个超管绕过——**那比原问题严重得多**。真正的防线是两条：**变更前后值快照**（`before_json`/`after_json`，可回放）+ **四眼复核**（`payroll.adjust.create` 与 `payroll.adjust.approve` 不得同人，见 §1.6.1 PA-4）。
>
> 一句话：**"改完看不出改过"这个问题不能用权限解决，只能用留痕解决。**

### 2.4 三个"看起来该给、实际不该给"的授权

| 授权 | 看起来合理 | 实际风险 | 结论 |
|---|---|---|---|
| 店长 → 看本店员工工资明细 | "他要管本店成本" | 门店内工资差距一旦被看见，团队立刻出问题；且店长可据此推算同事工资 | **不给明细，只给本店合计**（`payroll.store_cost.view`） |
| 区域 HR → 导出全辖区花名册 | "他要做人力规划" | 花名册含身份证/手机号，导出即失控 | **给，但走审批 + 水印 + 留痕 + 单次人数上限** |
| 集团 HR → 看全部工资明细 | "他是 HR 负责人" | 有权看 ≠ 需要看；日常业务不需要看全集团每个人的工资 | **给，但每次查看留痕并进月度审计报告**（"无事可做时不该点"） |

## 3. 三个业务问题（我的判断 + 理由）

### Q1：店长能不能看到本店员工的社保缴纳明细与缴费基数？

**结论：不能。基线与明细都不给。** 但要给一个替代口子。

| 项 | 结论 | 理由 |
|---|---|---|
| 社保缴费基数（个人） | **不可见** | 基数 = 上年月均工资，看到基数等于看到工资的量级。门店管理完全不需要这个数 |
| 社保缴费明细（按险种） | **不可见** | 同上，且明细可反推工资结构 |
| 社保**单位成本合计**（本店） | **可见**（只读） | 店长要管门店人工成本，给他"这个月本店社保单位部分合计 X 元"就够用 |
| 缴费异常（如某员工断缴） | **可见状态，不可见金额** | 这会影响排班（如工伤未参保的风险），店长需要知道"有异常" |

> **实现建议**：把"社保"拆成三档——`payroll.store_cost.view`（本店单位部分合计，可见）/ `si_status`（缴费状态是否正常，可见）/ `payroll.si_base.view` + `si_detail`（个人基数与险种明细，不可见）。这样店长能管成本、能发现异常，但拿不到可反推工资的数。

### Q2：区域 HR 调岗到别的区域后，原辖区员工的历史考勤他还看不看？

**结论：业务事实按当时归属（默认不可见），但给一条"未结清单据只读期"。**

我倾向的不是纯"按当时归属"，因为纯口径在餐饮连锁里跑不通：区域 HR 调动频繁（半年一轮很常见），一刀切断会导致**历史单据无人能处理**——原区域的新 HR 没做过那些单据，被调走的人又没权限了。

| 情形 | 权限 | 说明 |
|---|---|---|
| 纯粹查历史考勤（无未结单据） | **不可见** | 业务事实按当时归属，不是"我曾经管过就永久能看" |
| 有**未结清**单据（未封账考勤、未三方签认的结算单、未完成的审批） | **只读，限期**（默认 90 天） | 保证交接期能收尾；到期自动收回 |
| 交接期写入（补卡审批、调整单） | **不可写** | 只读就是只读，避免"走后还改数据"；要改由新 HR 操作 |
| 已封账的工资数据 | **不可见** | 工资是最高敏感级，不随组织管辖漂移 |
| 审计与举证需要 | 走 `audit.record.view` 单独申请 | 不靠"历史管辖"开口子 |

> **一句话口径**：**"业务事实按当时归属、人员档案按当前授权、未结单据给限期只读"**——三段式，比单一规则更能在真实交接里跑得动。
>
> 这条影响客户接受度：如果客户坚持"调走就全断"，需要他们把交接流程前移到调岗审批单上（列清未结单据）；如果客户坚持"永久可查"，那就在 `audit.record.view` 层给只读导出，不进业务系统。

### Q3：外包供应商看到的"本供应商派驻人员"，按什么认定？离职的看不看？

**结论：按 `record_owner = SUPPLIER` + `supplier_id` 匹配，且包含离职人员；但字段范围严格限定在"对账所需"。**

| 认定维度 | 规则 |
|---|---|
| 人员范围 | `employment.record_owner = SUPPLIER` **且** `employment.supplier_id = 当前供应商` |
| 是否含离职 | **含**。`termination_date` 非空的仍可见（在其派驻期内 + 结算争议期内） |
| 时间窗 | 派驻期内（`hire_date` ~ `termination_date`）**+ 12 个月**（参数 `supplier_visibility_months`），之后只可见汇总，不可见个人明细 |
| 多供应商人员 | 同一人可能在两家供应商下有过任职段 → **各自只可见自己那一段**，不交叉 |

**可见字段（只给对账所需）**：

**白名单只有五个字段（v0.5 收窄，结论：再宽一格都不给）**：

| # | 可见字段 | 为什么必须有 |
|---|---|---|
| 1 | **姓名** | 不给人名无法核对自己派了谁 |
| 2 | **所属单位**（供应商侧主体） | 区分"我派的"和"别家派的" |
| 3 | **在场时间** | 对账唯一依据 |
| 4 | **健康证状态**（仅"有效/过期"，不含证号与结论） | 人上不了岗要知道原因 |
| 5 | **在场人数合计** | 与自己的申报数比对 |

| 不可见 | 为什么 |
|---|---|
| **身份证号、联系方式、银行卡号** | 核对到场人数不需要；给了等于把员工个人信息交给第三方保管 |
| **工资、社保基数、个税、成本归属、门店毛利** | 给了等于把我方付多少钱暴露在"供应商视角"——他据此可以反推我们的加价空间 |
| **供应商单价、合同金额**（在门户侧） | 单价是谈判结果，不进入对账界面 |
| 结算单明细行与发票 | **例外：仅自己那张结算单可见**（否则无法签认） |
| 绩效结果、健康证详情与体检结论 | 与对账无关 |
| 其他供应商的任何数据 | 越界即 0 行 |

> **范围判定必须是 `EXISTS` 空集语义，不是 `AND 1=0`。** 写成 `AND 1=0` 的过滤条件在拼接查询、报表下钻、导出三条路径上会各漏一次；写 `WHERE EXISTS (SELECT 1 FROM ... WHERE supplier_id = :me)` 则是"匹配不上就是空集"，**漏的路径不会返回别人的数据，只会返回 0 行**——错的方向是安全的那一侧。

**为什么离职的必须可见**：结算争议几乎总是发生在人员离职后（补差、扣款、工时异议），供应商若看不到离职人员的工时，就无法对账，最后只能"按总额砍一刀"——这正是 07 §7.3 想消灭的做法。

## 5. 审批流清单（业务侧）

### 5.0 写法与两条前置原则

**原则一：不照搬泛微/钉钉的表单引擎——这不是风格选择，是结构性理由。**

它们的字段可见/可写是**表单模板渲染的副产物**：字段权限挂在布局上，改个布局可能顺手改了权限，而**没有人会想到去查权限**。我们不照搬表单引擎，就同时避开了这个坑：**字段权限是独立矩阵（`sys_field_permission`），不依附任何布局**。

**原则二：审批页是字段权限的第五个出口，不是一个新体系。**

已定的四个出口是：查询 / 导出 / 报表 / AI 工具返回。**审批页如果不复用同一套判定，它就是唯一的绕过口**——泛微恰恰在这里分裂（布局判一次、脱敏模块判一次、打印判一次，同一字段三个答案）。所以：

```
输入：角色 × 字段 × 动作 × 四维快照
输出：可见(view) / 只读(readonly) / 脱敏(masked) / 不可见(hidden)
        ↑ 审批节点只能在这四态里「往窄里选」，不能往宽里改
```

**节点只做降级**：节点字段策略 = 角色级字段权限再收窄。节点**不能**把 `hidden` 变 `visible`、不能把 `readonly` 变 `editable`。要做"字段级审批"，用的是 `before_json`/`after_json` 差异渲染（§5.4），不是给节点提权。

### 5.1 机制口径（最小集 + 四条硬边界）

**节点类型：必须 12 种 / 可选 3 种 / 不做 5 种。** 注意：加签、转办、传阅、退回**是节点上的操作，不是节点类型**——把转办做成节点类型会让节点类型无限膨胀（这是泛微被诟病的地方之一）。

| 档 | 机制 | 备注 |
|---|---|---|
| **必须** | 审批节点（单/多处理人）、条件分支、会签（全通过）、或签（任一）、固定并行 | 条件分支必须带**条件全覆盖校验**，否则写错不报错、只是永远走不中 |
| **必须** | 退回（目标节点 + 重提后走法，两维独立）、撤回（发起人）、转办（真转交）、抄送/传阅（只读） | 退回目标 ∈ {上一节点/指定节点/发起人}；重提后 ∈ {重走全路径/直达退回节点}。**我们只做"退回发起人 + 重走全路径"**，理由见下 |
| **必须** | 超时（提醒 + 升级），**自动通过默认关**、代理（起止时间 + 范围）、自动节点（定时/归档触发） | 默认"什么都不做"是危险的，默认必须是**提醒 + 升级到上一级** |
| **可选** | 依次逐个处理（顺签）、加签（**深度硬上限 1 层**）、动态并行（按明细行生成会签人） | 加签必须填理由，且加签出的节点与原节点同属一个"审批段"（**SLA 不重置**） |
| **不做** | 机器人节点、自由流、动态 SQL 取审批人、加审/减审（与加签减签重复）、子流程节点 | 机器人节点 = 在工作流里内嵌脚本，不可测不可审不可回滚；动态 SQL 取审批人 = 权限逻辑进 SQL，500 门店必然失控 |

**四条硬边界（写死，不给配置项）**：

| # | 边界 | 为什么 |
|---|---|---|
| **B1** | **会签/或签必须是显式枚举 `sign_mode`，落进审批记录表** | 泛微靠"操作组批次是否相同"隐式表达，界面无标签 → 配错就是**一人点完全流程通过** |
| **B2** | **只做"退回发起人"，不做"退回上一节点/任意节点"** | 退回任意节点会导致路径组合爆炸，**审计还原不了"这张单走了哪条路"**；退回上一节点会绕开中间审批人，责任链断 |
| **B3** | **高风险审批的 SLA 按单据级算，不按节点级算** | 会签节点"只要有一人处理，超时计时就重新开始"——**会签越多越不会超时** |
| **B4** | **代理是"按单据类型 + 起止时间必填"，不是"按动作"** | 钉钉的代理粒度只能到单据类型，**表达不了"这张单可以同意但不能终审"**。所以"不可代理封账"必须由我们自己在业务规则里判：`seal`/`void` 类动作**一律禁止出现在代理授权范围内**，且代理人的审批记录上显式标"A 代 B"，不是只显示"存在代理关系" |

**一票否决**：引擎能力是"全通过才流转"，"任一否决即终止并回退发起人"是**业务语义规则**，由我们编排，不要指望引擎有 `veto=true` 开关。

**比例通过**：**不做。** 比例通过的通病是责任分散——"一半人同意了"不等于任何人负责，审计上无法定责。唯一勉强可用的"多店长投票"是**征求意见**不是审批，应做成独立对象（征询），不进审批流。

### 5.2 单据清单（对齐 `08` 编号，不新造单据名）

### 5.3 压缩审批链的规则（唯一正当理由）

> **只审不写数据的节点，一律可省。会写数据的节点，一律不可省。**

按这条规则直接砍掉的节点类型：

| 被砍的节点 | 原来为什么要它 | 为什么可以砍 |
|---|---|---|
| "区域 HR 知会" | 想看进度 | 改成**抄送**，不占审批位（抄送不阻塞流转） |
| "财务备案" | 怕事后不知道 | 改成**自动节点**（seal 后自动生成台账 + 通知） |
| "店长复核"（在店长已是发起人时） | 觉得"多一道" | **自审禁止**：发起人不能是自己这单的审批人（PA-2） |
| "HR 分管领导审批"（在 HR 已是经办人时） | 层级习惯 | 同一部门内的"领导批下属的活"不产生信息，只产生延迟 |

> **反过来说**：任何"会写数据"的节点都不能砍。这类节点在我们系统里只有 6 个动作——`seal`（封账）、`void`（作废重建）、`execute`（执行调动/离职）、`edit`（改分/改基数/改卡号）、`create`（生成结算单/补差单）、`approve`（本身不改数据但决定上面哪个发生）。**要砍链，只能砍不写数据的节点；要砍写数据的节点，等于砍掉控制点。**

### 5.4 字段级审批（三场景，不是五场景）

**它不是"给字段单独配一个审批权限"**，而是：审批单携带 `before_json` / `after_json`，审批页**只渲染差异字段**，其余字段按角色级字段权限处理。

| 场景 | 差异字段（审批人判断的最小充分集） | 为什么只有这三个 |
|---|---|---|
| 调薪 | 原薪资 / 新薪资 / 生效日 / 调整理由 | — |
| 社保缴费基数调整 | 原基数 / 新基数 / 生效期 / 依据 | — |
| 银行卡变更 | 原卡（掩码）/ 新卡（掩码）/ 户名 / 变更原因 | — |

**限定三场景的判据**：只有这三个同时满足"字段少、金额敏感、事后必须举证"。其他场景上字段级审批，只会让人多点一次，且**审批人会因为看到一堆无关字段而漏看关键那个**。

**节点字段策略的取值来源**（写死，不许实施改）：

```
节点可见字段 = 角色级字段权限 ∩ 本节点字段集
节点的作用   = 从「可见」里再去掉不需要判断的字段（降级）
节点不许做的 = 把「不可见」变「可见」、把「只读」变「可编辑」
```

### 5.5 与架构侧对齐的开口项（我不设计表结构，只交判据）

| # | 开口项 | 我的业务侧判据 | 需架构确认的 |
|---|---|---|---|
| A1 | 审批事实是否一等对象 | `approval_action` 必须是**业务表**（node_id / sign_mode / 批次 / 身份 / 代理关系 / 意见 / 时间 / ip），不能只靠日志 | 表结构与索引 |
| A2 | 自审禁止落在哪一层 | 落**候选人生成阶段**（服务器端），不是前端隐藏按钮；且批量审批接口必须同判 | 候选人解析器改造点 |
| A3 | 被代理人的可见性 | 被代理人界面必须显示"这期间我的排班由 X 代管"，**不是审批，是可见** | 通知/展示通道 |

### 6.2 "模板 + 减法"的三个真实场景（不支持减法，实施就会全手点）

| 场景 | 套装 | 减法 | 为什么必须支持 |
|---|---|---|---|
| 加盟店 HR 不需要导出 | `STORE_HR` | − `employee.profile.export` − `schedule.plan.export` − `attendance.daily.export` | 加盟店是独立法人，花名册出他手即失控 |
| 新店店长不带批量 | `STORE_MANAGER` | − `schedule.plan_bulk.edit` − `schedule.plan.delete` | 新店长上任第一周最常误操作的就是批量 |
| 区域 HR 兼做薪酬（小客户） | `AREA_HR` + `PAYROLL_SPECIALIST` | − `payroll.period.seal` 的确认（仍留财务） | 一人多岗在小客户是常态；但**封账确认不能一起给**，否则没有第二个人 |

### 6.3 三条反模式（写在这里，防止实施期"简化"）

> **为什么"不含"列是套餐里唯一能被验证的那一侧**（这条是判据，不是经验）：
>
> | 发现方式 | **漏授** | **错授** |
> |---|---|---|
> | 什么时候被发现 | **当天**——用户点不动，立刻反馈 | **永远不被发现**——点了就生效，没人会报"我不该有这个" |
> | 谁会发现 | 使用者本人 | 只有审计或事后追责 |
> | 补救成本 | 加一个点（分钟级） | 已经发生的越权行为（不可回滚） |
>
> 所以"含什么"是说明书，"**不含什么**"才是**控制项**。

| 反模式 | 后果 | 正确做法 |
|---|---|---|
| 建一个 **"全功能包"** 给管理员 | 它比"给超管"只慢一步，实施一定选超管。**"全能包"存在本身就是超管的备份方案** | 不建。要么走标准包 + 减法，要么走静态超管名单 |
| 把**套餐当角色**（一个套餐=一个角色实例） | 改套餐 = 改所有人。与 C2b"授予时展开"直接冲突 | 套餐只用于**批量勾选**，角色是展开后的实体行 |
| 按**部门**批量授套餐 | 部门有 20 人，20 份完全相同的权限；调走一个人时没人记得回收 | 按**岗位/角色**授，按人回收；部门只用于数据范围 |
