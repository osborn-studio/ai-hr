## 零、本文件解决什么

五条研究线交叉核对后，暴露出 **1 处正面冲突、6 处口径分歧、4 处建模缺陷**。这些如果不在此刻定死，会在写代码时才暴雷，代价是重构数据模型。以下逐条裁决，并给出可落库的结构。

## 一、正面冲突裁决：人力成本「跟人走」还是「跟岗走」

### 1.1 冲突原貌

| 立场 | 主张 | 依据 |
|---|---|---|
| 薪酬实践 | 成本跟人走：工资表只有一列「成本部门」，取自员工主档；支援店只是受益方，分摊走独立报表，不回写工资表 | 算钱只认总工时和主档成本部门 |
| 连锁餐饮客户需求 | 成本跟岗走：谁用人谁排班谁发薪，B 店排班则由 B 店结算 | 跨店支援需按天/按工时拆分 |

两条不能同时成立，但**都不是错的**——它们各自成立在不同的计薪方式上。

### 1.2 裁决：三层结构，一次解决

```
第一层：工资记录唯一（红线）
  一人 + 一个薪资期间 = 一条工资记录，发薪主体唯一。
  个税、社保永远按这一条算，不因成本分摊而拆分。
  → 防止：同月重复扣起征点、同月重复参保

第二层：成本归属按计薪方式分流
  cost_bearing_policy = home_org | working_org | split_by_days | split_by_hours
  默认值按用工类型取：
    月薪制 FT        → home_org      （跟人走）
    时薪 PT/LTPT/小时工 → working_org   （跟岗走）
    劳务派遣/外包     → working_org   （跟岗走，且不进工资表）
  允许租户/门店/人群级覆盖

第三层：分摊只落"成本分摊行"，不回写工资记录
  cost_allocation_line:
    员工 + 期间 + 成本门店 + 分摊天数/工时 + 分摊金额 + 分摊依据
  用途：门店人力成本报表、门店 P&L、财务凭证
  强制校验：Σ 各分摊行金额 = 工资记录应发合计，差额进异常清单
```

**为什么这样切**：月薪固定，支援店背成本会导致"支援店虚高、被支援店虚低"，且工资表与主档不一致会让年度对账失真；时薪按工时结算，工时发生在哪家店，成本天然该落哪家店，这才是"谁用人谁发薪"的真实含义。

### 1.3 必须写进 PRD 的禁止项

- ❌ 不得把成本分摊结果写回工资记录的「成本部门」字段
- ❌ 不得因成本分摊而把一条工资记录拆成多条
- ❌ 不得让 FT 与 PT 共用同一个 `cost_bearing_policy` 默认值

## 二、组织模型升级：4 维主体 + 2 条关系线

原设计只分离"用工主体"和"工作地点"两个字段，**维度不足**。定稿如下：

### 2.1 四个必须并存的归属维度

| # | 字段 | 含义 | 谁在用 | 合并会出什么事 |
|---|---|---|---|---|
| 1 | `legal_entity_payroll_id` | 发薪法人主体 | 工资单雇主栏、个税申报主体 | 一张工资表对应一个主体，合并即无法出表 |
| 2 | `legal_entity_si_id` + `si_city` | 社保参保主体 + 参保城市 | 社保公积金核算 | 可与发薪主体不同（A 公司发薪、B 城市参保＝集团代缴），合并则代缴场景无解 |
| 3 | `cost_org_id` | 工资成本部门/成本中心 | 人力成本归集、门店 P&L | 合并即成本归错门店，**门店毛利直接算错** |
| 4 | `attendance_org_id` | 考勤部门（实际出勤门店） | 排班、工时统计、跨店校验 | 与 3 合并则跨店兼岗员工成本归错门店 |

**硬约束：`cost_org_id ≠ attendance_org_id`，永不合并成一个「部门」字段。**
配套数据校验：成本部门必须属于发薪法人主体子树；考勤部门可在任意门店。

### 2.2 两个标记字段

| 字段 | 用途 |
|---|---|
| `primary_org_id` | 一人多店时的主门店，用于统计去重、排班默认、绩效归属 |
| `report_to_id` + `dotted_line_ids` | 管理汇报线（实线单人 + 虚线多人），用于审批路由、绩效打分、提成向上归集 |

### 2.3 两条独立关系线，允许交叉

- **管理汇报线**：可以跨越法人、跨越区域。
- **成本归属线**：挂在法人主体下，决定钱记在哪。

一个员工完全可以"成本归属 A 门店、汇报给 B 区域经理"。只靠部门树建模必然二选一，这是原设计的漏洞。

## 三、制度分两层：集团模板 + 主体参数

| 层 | 内容 | 存放 |
|---|---|---|
| L1 集团制度模板（全局唯一一份） | 算薪引擎、薪资项目、函数库、假种体系、考勤规则模板、审批模板 | 集团层 |
| L2 法人/城市参数（按主体覆盖） | 社保方案与基数规则、发薪日、币种、个税扣缴规则、报税主体、发薪银行 | 挂 `legal_entity` / `city` |

**架构落点**：组织表加 `policy_set_id` 指向参数集，法人层**只存差异项，不复制整套规则**。这是能否维护几十上百主体的分水岭。

## 四、日期语义治理（数据模型级要求）

| 字段 | 规则 |
|---|---|
| `hire_date` | NOT NULL，所有「入职天数区间」计算的锚点 |
| `termination_date` | **在职人员必须为 NULL**，禁止存 `''` / `'0'` / `'1970-01-01'`。DB 加 CHECK：`status=在职 → termination_date IS NULL` |
| `probation_end_date` | 试用期**结束日**（应然） |
| `regularization_date` | **实际转正生效日**（实然） |

**转正双口径不要二选一，两个都存**：
- 触发转正奖 → 引用 `probation_end_date`（不依赖 HR 是否按时办理）
- 按实际转正调薪 → 引用 `regularization_date`
- 两者不一致 → 生成「试用期超期」异常记录，供 HR 追责与合规审计

这条把餐饮高频的「逾期转正」劳动争议，变成了可监控指标。

## 五、人员同步与生命周期（替换原「组织变更」方案）

人员同步走**三段式**，不是人工逐个维护：

1. **全量替换 + 事务**：完整读取组织与分页成员，全部成功后在一个事务内替换。
2. **失败不清空**：接口失败、分页异常、空组织 → 保留已有数据，绝不删除。
3. **离开即停用不删档**：不在本次可见范围的成员 → 停用 + 撤销会话，**历史业务数据（档案、薪资、答卷、工龄）全部保留**。

配套规则：
- 多部门成员按 `primary_org_id` 合并去重
- 特殊节点（通讯录里存在但接口读不到的系统节点）必须显式排除，否则整次同步中断
- 餐饮流动率高的场景，「停用不删档」既立刻切断登录，又保住工龄与历史薪资——这是刚需不是优化

> 这条属于「人」的同步，不是「树」的同步，PRD 应写在员工生命周期章节。

## 六、权限机制：三轴正交 + 防自锁

```
权限 = (静态超管名单 ∪ DB 角色) × 数据域(品牌/区域/门店/本人) × 字段级(薪资可见性)
```

| 机制 | 做法 | 解决什么 |
|---|---|---|
| 静态超管名单 | 配置内，只读，页面不可改 | 防止管理员把自己锁死、越权自授 |
| DB 页面级追加授权 | 可增删，带审计事件 + 版本号乐观锁（冲突返回 409） | 防并发覆盖、可追溯 |
| 角色服务端实时计算 | 每次请求重算，前端不得指定角色 | 防前端伪造越权 |
| 撤权后降级 | 回到普通空间，保留历史数据 | 与「停用不删档」同一哲学 |

**MCP 客户端走同一套三轴，不设 AI 专用后门。**

## 七、薪酬三条最容易做错的地方

### 7.1 半月两次发薪：必须把「发薪批次」与「薪资期间」拆开

这是本项目**最高合规风险点**。

| 维度 | 正确口径 |
|---|---|
| 薪资期间 | 仍是一个自然月，一个期间只有一条工资记录 |
| 发薪批次 | 一个期间可拆 2 个（月中预付 + 月末结算），各有发薪日与银行文件 |
| 个税 | **同月两批合并为当月收入**申报，不得当成两个月分别计税 |
| 社保 | 同月只申报一次，不随批次重复 |
| 工资条 | 可发 2 张，但第二张必须显示「本月累计」 |

> `发薪批次` 是付款对象，不是计税对象。**禁止把"半月发薪"实现成"建两个薪资期间"。**

### 7.2 折算基准四选一，且分子分母必须同源

参数 `proration_basis = calendar | payroll_day | workday | scheduled_day`

| 基准 | 公式 | 陷阱 |
|---|---|---|
| 日历日 | 月薪 ÷ 当月天数 × 本月在职天数 | — |
| 计薪日 | 月薪 ÷ 21.75 × 本月计薪天数 | 21.75 需按当地确认 |
| 工作日 | 月薪 ÷ 当月应出勤工作日 × 本月实际出勤工作日 | — |
| 排班日 | 月薪 ÷ 当**该员工**排班天数 × 实际出勤排班天数 | 分子分母都必须是**该员工个人**排班，不是门店排班；新入职未排班时 divisor=0，**必须阻断不能出 0** |

**禁止一个字段两用**：
- `payroll_monthly_standard_hours`（默认 174 = 21.75×8）→ **只用于加班费换算**
- `proration_basis` 的计薪日基准 → **只用于缺勤/入离职折算**

二者可同源推导，但用途与变更审批独立。

### 7.3 同月离职又返岗 vs 一人多账套：判定主轴是「发薪主体 + 账套」

| 场景 | 工资记录 | 原因 |
|---|---|---|
| 同法人同期间，离职后返岗 | **合并 1 条**，下挂多段任职明细 | 否则同月重复参保、重复扣起征点 |
| 同人同时挂在不同客户/订单（人服代发） | **按客户拆多条**，各自账套 | 不同客户账单与结算对象 |
| 跨法人（集团内调岗） | **按法人拆多条** | 不同发薪主体、社保城市、发薪日 |

## 八、计薪方式扩到四种（补计件）

| 方式 | 计算式 | 数据来源 |
|---|---|---|
| 月薪 | 月薪 ÷ 基准 × 在职/出勤 | 薪资档案 |
| 时薪 | 时薪 × 总工时 | 考勤 |
| 日薪 | 日薪 × 出勤天数 | 考勤 |
| **计件** | Σ(完成量 × 单价版本) − 质量扣减 | **产量/单据系统，不是考勤** |

计件的三个特殊要求：取数来源非考勤、**单价版本化**（历史月份锁定当时单价）、返工/报废扣减规则。产品上做成独立「计量薪资项」，不硬塞进时薪模型。

## 九、自定义薪资项的六个开关

餐饮常见的水电费、餐损、奖罚、门店共创奖励，都走通用薪资项配置。每个薪资项必须能配置：

| 配置 | 说明 |
|---|---|
| 名称 / 类型 | 收入 or 扣减 |
| 取数来源 | 手工 / 考勤 / 业务系统 / 公式 |
| 计算表达式 | 引用可用因子 |
| **是否计税** | 影响个税基数 |
| **是否并入社保基数** | 餐饮最易错，餐补/津贴性质直接决定 |
| **是否计入人力成本** | 影响成本率口径 |
| **映射汇总列** | 决定报表归类 |

后四个开关是重点——它们决定同一笔钱在个税、社保、成本报表里是否被重复或漏计。

## 十、绩效双系数与奖金

- `个人绩效系数` 与 `门店/单元奖金池系数` 是**两个独立字段，不合并**
- 绩效奖金 = 基数 × 个人系数 × 门店系数（是否相乘可配）
- 一次性奖金需支持：计税方式（并入综合所得/单独计税）、是否并入社保基数、**是否分期发放**（内推到岗、过保分期）→ 需「应付计划」台账，跨月支付

## 十一、年假：从「余额字段」升级为「台账」

余额不是主数据，是台账计算结果的派生值。

```
年假台账 = 额度生成（工龄/司龄规则 × 在职月份折算）
          + 使用（请假核销）
          + 结转 / 清零（跨年规则）
          + 折现（离职结算）
```

- 人工只能「覆盖」并留痕（员工/原值/新值/原因/审批人），**不能直接改余额**
- 返岗场景：工龄连续（3 个月内以首次入职日为准）→ 额度按连续工龄生成；但若离职前当年度年假已休完 → 返岗后额度为 0（按年度已享额度扣减）
- 假期余额四态分列：应得 / 实得 / 借用（预支）/ 结转存量，四者不合并

## 十二、加班与工时：三处技术定稿

### 12.1 加班按类型分列，不用布尔开关

`ot_type ∈ {weekday_extend, rest_day, statutory_holiday, none}`

- 考勤侧输出**按类型分列的三列加班工时**
- 薪酬侧分别乘对应倍率（倍率为参数，需法务确认，不写死）
- **法定节假日对月薪制 FT 是「照付 + 另付」双逻辑**：不上班工资已含在月薪里不扣，上班则额外支付。因此排班/考勤侧需额外输出一个 `法定节假日上班天数`，不走"工时×倍数"那条路
- 时薪制则按 `法定节假日加班工时` 计算
- 两个值都要出，不能只出一个

### 12.2 工时校验必须双级

- 组内级：考勤组内日/周/月工时上限
- **员工级：员工当日全部门店工时合计**（派生字段 `daily_total_hours_by_person`）

否则员工在 A 店 5h + B 店 5h，单店都不超阈值，合计 10h 却规避了加班。**凡按考勤组算的工时校验，必须追加"另需跨组合并校验"。**

### 12.3 连续病假跨月滑动窗口

连续段由考勤侧用跨月滑动窗口计算，输出三个值：`{<N天病假天数, ≥N天病假天数, 跨月连续标记}`，薪酬不做二次判断。阈值 `sick_leave_threshold_days` 默认 4，参数化。

### 12.4 加班豁免名单

个别员工即使 FT 也不计加班，该名单只存在于薪酬侧。若考勤要向门店出"加班工时报表"，**报表必须标注口径**（如"本表含豁免人员加班工时，工资不计发"），否则门店会拿报表质疑工资单。

## 十三、考勤组与组织树的映射

| 关系 | 基数 | 说明 |
|---|---|---|
| 组织节点 → 考勤组 | **1:1**（同期） | 定义"哪些门店适用哪套规则"；带 `effective_date`，支持支援期临时改绑 |
| 员工 → 考勤组 | **N:1** | 主考勤组 + 兼岗/支援考勤组；兼岗员工同一天可在两个门店排班 |

两者不矛盾：前者是**规则归属**，后者是**人员归属**。PRD 只写前者，兼岗场景根本排不出来。

配套：`org_tag` 多值部门标签，支持同层跨部门按标签聚合统计而不改树结构。

## 十四、指标字典（禁止各模块自算）

`人力成本率 = 人力成本总额 ÷ 营业额`

三个边界必须定义清楚，否则绩效模块和薪酬模块永远对不上：

1. **人力成本含什么**：应发工资 + 单位社保公积金 + 奖金提成 + 福利 + 劳务费（派遣/外包）+ 中介费？→ 做成勾选项，但**必须有默认值且全系统一致**
2. **营业额口径**：含税/不含税、外卖平台抽成前/后、是否含储值消费确认
3. **期间对齐**：人力成本按「归属期间」（考勤发生月）还是「发放期间」；营业额按自然月

> 每个指标在字典里登记：公式、口径开关、数据来源表、责任人。绩效、薪酬、门店看板引用同一份定义。

## 十五、参数化清单（汇总）

| 参数 | 含义 | 默认 | 禁止 |
|---|---|---|---|
| `cost_bearing_policy` | 成本归属策略 | 按用工类型：FT→home_org，PT/小时工→working_org | 不得对 FT 与 PT 用同一值 |
| `cost_allocation_basis` | 分摊基准 | home_store | — |
| `payroll_monthly_standard_hours` | 计薪基准月工时（**仅加班换算**） | 174（21.75×8） | 不得字面写 216 |
| `proration_basis` | 折算基准 | calendar | 不得与上一项字段复用 |
| `compliance_monthly_cap` | 合规月上限（仅预警） | 按当地 | 不得与计薪基准复用 |
| `sick_leave_continuity_basis` | 病假连续判定基准 | calendar | 不得写死 |
| `sick_leave_threshold_days` | 连续病假扣款阈值 | 4 | 不得写死 |
| `ot_rate` | 加班倍率（三类） | 1.5 / 2 / 3 | 需法务确认后生效 |
| `temp_worker_settlement` | 临时工结算周期 | 月结 | 可按门店/用工类型覆盖 |
| `pay_batch_policy` | 发薪批次 | 单批次（月末一次） | 不得实现成多薪资期间 |
| `annual_leave_carryover` | 年假结转 | 可结转，次年 Q1 过期 | 需与四态余额联动 |
| `schedule_notice_days` | 排班最小发布提前量 | 3 天 | — |
| `offboarding_same_day_settle` | 离职当日结算 | 是 | — |

## 十六、关于「300+ 法人主体」的判断

**结论：本项目按 5–50 个法人主体设计，不做 300+ 的批量建档工程，但保留参数集机制。**

理由：
- 「300+ 主体统一工资模板」来自人力资源服务（代发薪/代账）场景，不是连锁餐饮集团场景。餐饮集团通常 5–50 个主体。
- 但 `policy_set_id` 参数集继承本身就足以撑到 300+，成本极低，属于"顺手做对"而非额外工程。
- 若将来要做人服 SaaS（HRO 多客户多账套），再补批量建档 UI 与多客户账单链路，届时数据模型不需要重构。
