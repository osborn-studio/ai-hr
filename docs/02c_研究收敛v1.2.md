## 一、薪酬侧修正与新增（6 条）

### V1 21.75 拆成两个参数（上一轮定位错误）

| 参数 | 用途 | 默认 |
|---|---|---|
| `daily_rate_divisor` | **日工资标准**：缺勤扣款、加班费折算的单价 | 21.75 |
| `proration_divisor` | **入离职折算分母** | 当月应出勤工作日（可选排班日） |

不能合用的理由：都用 21.75 会让大小月不平（31 天月少付、28 天月多付），餐饮月中入离职频繁会放大偏差；都用当月工作日则缺勤扣款单价逐月波动，同一件事两种价格。

保留「分子分母同源」校验：用 workday 作分母时，分子不得混入休息日，否则算出 >100%。

### V2 五个天数 + 两套维度（禁止互相推导）

| # | 天数 | 来源 | 用途 |
|---|---|---|---|
| 1 | 计划出勤 `planned_days` | 排班/支援单 | 预估工资、产能规划（**禁止作计薪输入**） |
| 2 | 应出勤 | 制度日历/排班 | 缺勤与加班的比较基准 |
| 3 | **实际出勤** | 打卡 + 考勤确认 | **计薪输入** |
| 4 | 计薪天数 | 薪酬口径 | 折算分母 |
| 5 | **成本归属天数** | 分摊基准 | 成本记谁账上 |

两套维度不可混用：

| 维度 | 算法 | 用途 |
|---|---|---|
| 员工维度 `attendance_days` | `COUNT(DISTINCT employee_id, work_date)` | 计薪分子、勤工津贴折算 |
| 门店维度 `store_work_days` | 按门店分组求和（不去重） | 门店工时、成本分摊、人效 |

同一兼岗员工：员工维度 1 天，门店维度 A 店 1 天 + B 店 1 天——**两者都对，但不能相加**。按 `COUNT(*)` 算员工维度会让日薪制直接翻倍。

### V3 用工类型与用工性质是两个正交维度

| 字段 | 取值 | 决定 |
|---|---|---|
| `employment_type` | FT / PT / LTPT | **怎么算钱** |
| `employment_nature` | 自有全职 / 自有非全日制 / 派遣 / 外包 / 第三方兼职 | **谁发钱、算不算人效、进不进工资表** |

**理由**：派遣的人可能是月薪制全职。合并后只有两种错法——把派遣当 PT 算（工资错），或把 PT 当派遣排除出人效（人效虚低）。

映射矩阵：

| 用工性质 | 常见用工类型 | 工资表 | 人效默认 | 社保 |
|---|---|---|---|---|
| 自有全职 | FT | 进 | 计入 | 本单位 |
| 自有非全日制 | PT / LTPT | 进 | 计入 | 非全日制口径 |
| 派遣 | FT 或 PT | 不进（供应商结算单） | 不计入 | 派遣单位 |
| 外包 | FT 或 PT | 不进（供应商结算单） | 不计入 | 外包方 |
| 第三方兼职 | PT | 进（代发通道） | 不计入 | 按协议 |

### V4 内部结算科目做类型级隔离，不靠开关

新增薪资项类型 `INTERNAL_SETTLEMENT`：

- **结构上不进入「应发合计」计算链**（不是开关关闭，是根本不参与求和）
- 只能出现在成本分摊行与内部往来单据
- 工资条渲染时**直接跳过该行**（不是显示 0）
- 五个固定属性：不计个税 / 不入社保基数 / 不进工资条 / 计入人力成本 / 映射成本分摊行

理由：靠开关控制，只要一项被误配成「计税」，个税就多算且极难发现（金额小、混在应发里看不出）。**开关是软约束，类型是硬约束**；误配时会因「金额对不上应发合计」被对账拦住。

### V5 分摊阈值必须同时作用于成本与系数

`allocation_min_share = 0.10`（统一为 10%）同时约束两处：

- 工时占比 < 10% → 不参与该单元的**系数加权**
- 工时占比 < 10% → 也**不承担该单元的成本**（成本退回主档）

否则会出现"B 店承担 15% 成本但不参与 B 店系数"的局部不同源——正是"双向不利"的缩小版。

### V6 绩效单元必须 ≤ 成本中心粒度

若存在「一个成本中心覆盖多店」（共享厨房、美食广场档口），**必须把成本中心拆细**，而不是让绩效单元向上兼容。

否则：一个成本中心 3 个档口、系数只有 1 个 → 3 个档口人力成本率全一样，店长一眼看出数据是假的。

PRD 加映射校验：每个绩效单元映射到唯一成本中心，且成本分摊可下钻到绩效单元粒度。

### V7 分摊表始终存在，不做策略分支

`allocation_basis = home_only | by_days | by_hours`（方案级，默认 `home_only`，支持人群级覆盖：PT 默认 `by_hours`、FT 默认 `home_only`）。

**无论哪种策略都建分摊子表**——`home_only` 就是「一行、100% 归主档」。做策略分支会导致客户换策略就要改表。

### V8 允许「解锁重锁 + 留痕」

锁数时序：营业额 T+3 → 人力成本 T+5 → 绩效系数 T+5 → 算薪 T+8。

中间只有 3 天窗口，5 日锁错 8 日就带着错数发工资。必须提供解锁重锁路径（留痕、需授权），而不是一次性定死。

## 二、组织侧确认（3 条）

### V9 工资记录唯一键

`UNIQUE (employee_id, pay_period, payroll_legal_entity_id)` —— 三元组，定稿。

### V10 成本组织校验拆两条

| 对象 | 规则 |
|---|---|
| 主档 `cost_org_id` | 必须在发薪主体子树内，违规阻断 |
| 分摊行 `cost_org_id` | 允许跨主体，但必须 `is_intercompany=true` 且关联已生成的结算单，否则阻断 |

### V11 归属必须版本化（新增，来自竞品对标）

新增 `employee_org_assignment` 时序表：

- 字段：employee_id、四维各一个 org_id、primary_org_id、生效日期、失效日期
- 约束：同一 employee 的生效区间不得重叠
- 用法：任何"过去某一天"的算薪/成本/审计，按业务发生日取当时版本，**禁止读主档当前值**

竞品有「组织架构与花名册每日时点快照」，我们没有——这是结构性缺口。不照抄每日快照（存储成本高），改用**区间版本表**，效果等价且更省。

## 三、竞品对标结论（三份同期 HCM 资料）

### 3.1 判断

竞品定位是**"引擎化 + 强配置 + 私有化交付"的知识型企业 HCM**，服务的是研发/知识密集型大型集团，**基因与餐饮连锁不匹配**。

### 3.2 值得学的 5 个点（已并入基线）

| # | 设计点 | 我们怎么用 | 优先级 |
|---|---|---|---|
| 1 | **组织与花名册时点版本化** | 改为 `employee_org_assignment` 区间版本表（见 V11） | **P0** |
| 2 | **表单引擎 + 流程引擎双引擎，且支持"数据引用"做校验** | 换班/支援/补卡/加班/调店/临时工入场全部走统一单据引擎；重点是**表单校验时能实时引用考勤/排班/假期余额/编制数据**（如申请加班自动带出当日排班工时并校验超时）——这条我们基线里没有 | P1 |
| 3 | **计薪三件套解耦**（计薪账套 / 社保基数库 / 薪酬模板） | 在三件套之上再加"口径层"（实发/管理成本），形成四层：`归属 → 账套 → 基数与政策 → 结构模板 → 口径输出` | P1 |
| 4 | **入薪全链路自动推送 + 出勤「员工确认留痕」** | 对餐饮是刚需：**按"门店 + 班次 + 人"三粒度出具出勤确认单**，店长与员工双向确认留痕，确认后才允许封账与算薪 | **P0** |
| 5 | **电子签/合同全生命周期闭环** | 按用工类型（全职/兼职/小时工/实习/外包）自动派生**应签文件包**（劳动合同、劳务协议、健康证、保密协议、宿舍协议），缺一件卡入职完成 | P1 |

### 3.3 不照搬的 3 个点

| # | 不照搬 | 原因 | 正确处理 |
|---|---|---|---|
| 1 | 胜任力模型 / 任职资格 / 九宫格盘点 / 干部管理 | 隐含前提是"人可长期培养"，餐饮一线占 85–95% 且任职周期常短于盘点周期，ROI 极低 | 只保留：店长/区域经理的**资格准入打勾**（能否独立带店）+ 一线员工的**技能标签**（能上哪个工作站）——后者直接服务排班（技能→可排岗位） |
| 2 | PBC 式目标绩效 + 单系数联动 | PBC 是季度/半年长周期范式；餐饮一线绩效是日/周颗粒度的营业额、人效、损耗、出餐时长、客诉。单系数也无法表达"门店超额但个人拖后腿" | 只借两个组件：**校准规则（强/弱分布可配）+ 双线审批路由**；评价逻辑坚持双系数，数据源接门店经营系统而非人工填报 |
| 3 | 年度总编制强管控（增编走外部审批、后期不可改） | 餐饮编制是"门店模型型"：标准店 = 店长1 + 值班经理2 + 全职8 + 兼职6 + 小时工按客流浮动，开店即生成、关店即回收 | 改为**门店编制模型**：按店型定义岗位编制模板 → 开店自动实例化 → 可临时上浮（带上浮有效期与审批）→ **编制直接驱动排班与招聘**（超编排班告警、缺编触发招聘） |

### 3.4 我们相对竞品的结构性优势（必须守死）

| 能力 | 竞品状态 |
|---|---|
| **四维归属 + 主门店 + 版本化** | 三个割裂挂载点拼出来，无统一模型、无版本化 |
| **双汇报线** | 单线；虚线仅存在于绩效审批路由 |
| **两套账（实发账 vs 管理成本账）** | 只有"多账套"（核算集合拆分），**语义完全不同** |
| **连锁排班（划线/批量/轮班/换班/跨店支援）** | 只有泛化"排班"一词 |
| **假勤四态余额台账** | 单值"剩余天数" |
| **考勤封账** | 未提及 |
| **灵活用工专门模型** | 未提及 |
| **外包协同闭环** | 只有供应商"档案" |
| **绩效双系数** | 单系数，且未产品化 |
| **MCP 全开放层** | 无；它把开放性做成"卖源码"，我们把开放性做成"产品能力" |

### 3.5 术语澄清（防止内部误判）

| 术语 | 含义 | 谁有 |
|---|---|---|
| **多账套** | 核算集合的拆分：同一员工被分到不同账套各算一次，多法人分别出账报税 | 竞品有 |
| **多口径账** | 核算口径的分叉：同一笔实发工资派生出实发口径与管理成本口径两份结果，同源派生、必须可对账 | **我们有，竞品无** |

讨论时若只说"竞品也有多账套"，会误判为我们已覆盖。**PRD 术语表必须把这两个词分开定义。**
