# 考勤月报与审批：让"这个月发多少钱"有一个能落笔的地方

> 记录日期：2026-11-15 ｜ 迁移 111–124 ｜ 断言从 385 条增加到 614 条

## 1. 问题不在算错，在于没人能改

在这之前，算薪直接从三个地方现算：考勤人日（`attendance_daily_store`）、打卡（`punch`）、请假单。
数据都在，算法也对，但现实流程不是这样跑的：

```
考勤机/手机打卡 → 系统汇总 → HR 看报表、核对、手调几个数 → 确认 → 传给薪资
```

中间那一步「报表」不存在，于是三件事没有答案：

| 场景 | 之前的处境 |
|---|---|
| HR 发现老王 11-03 漏打卡 | 改打卡表？下次同步就冲掉了。改人日？等于伪造一条打卡记录 |
| 月底 HR 说"这个数不对，我当时调过" | 系统里没有任何记录能对上 |
| 同一期间重算两次 | 结果可能不同（期间中间补录了考勤），而工资必须可重复 |

所以补的不是算法，是**一层可以确认、可以追溯、可以驳回的中间表**。

## 2. 现在的链路

```
考勤人日 / 打卡 / 请假          （原始数据，封账后不可改）
        ↓ fn_att_period_build
考勤月报 att_period_report     （一人一行，draft）
        ↓ HR 调整 / Excel 覆盖   ← 每一次都留痕、留版本
        ↓ 提交 submit
      pending（审批人已固定）
        ↓ 部门主管 / HR 主管批
      confirmed                    ← 薪资只认这一版
        ↓ fn_att_person_period
工资表 / 公式 / 规则
```

`fn_att_person_period` 的行为是：**有 confirmed 月报 → 用月报的数字；没有 → 退回实时汇总。**
这样上线不会一次改掉所有人的工资，而一旦 HR 确认了，数字就固定下来。

## 3. 三个数字，长得像但含义不同

这是最容易出错的地方，也是客户对不上账时最先怀疑的地方。

| 名字 | 是什么 | 从哪来 | 用在哪 |
|---|---|---|---|
| `work_days` 应出勤 | **这个月**该上几天班（20–23，常见 22） | 日历工作日（周一至周五，扣法定假、加调休）或排班天数 | 判断满勤、折算比例 |
| `PAY_DAYS_PER_MONTH` 月计薪天数 | 法定折算口径 21.75 = (365−104)/12 | 制度项 | **日薪、时薪**（事假扣款、加班费基数） |
| `calendar_days` 日历工作日 | 生成月报时看到的应出勤参考值 | `fn_calendar_workdays` | 改过 `work_days` 后仍能看出"原来多少" |

为什么不能统一成一个数：
- 应出勤写进日薪分母 → 2 月（20 天）与 12 月（23 天）请同一天假扣的钱不一样，**不合规**；
- 月计薪天数写进"该来几天" → 11 月实际有 21 个工作日，员工按 21.75 天算永远差一点，会来问。

这两条各有断言钉住（ATV1 / ATV3 / SL8 / RSD）。

## 4. 三档加班与劳动法依据

之前只算了 `OT_HOURS` 一个总数，没分档，也就没法算钱。这是硬缺口 ——
加班费是劳动争议里最容易败诉的一项，且举证责任在用人单位。

依据（查证过的）：

- 《劳动法》第 44 条 + 《工资支付暂行规定》（劳部发〔1994〕489 号）：
  平日延长 **150%**、休息日且不能补休 **200%**、法定休假日 **300%**；
- 《关于职工全年月平均工作时间和工资折算问题的通知》（劳社部发〔2008〕3 号）：
  月计薪天数 **21.75**、小时工资 = 月工资 ÷ **174** 小时；
  法定节假日本身**带薪**，折算时不剔除（所以是 21.75 而不是 20.83）。

三档怎么分（不额外要求客户填东西）：

| 情形 | 判定 | 计法 |
|---|---|---|
| 法定节假日上班 | `legal_holiday.is_workday = false` | **当天全部工时 × 300%** |
| 休息日上班 | 排了休息班，或周末（无排班时） | **当天全部工时 × 200%** |
| 调休上班日 | `is_workday = true` | 按平日处理 |
| 平日延长 | 当日工时 − 8 | 超出部分 × 150% |

休息日与法定节假日是"全部工时算加班"，平日只算"超出 8 小时的部分" —— 这两者混淆会让金额差一倍。

**倍数做成配置项**（默认 1.5 / 2 / 3，只能调高不能调低）。写低了会少付，而少付是违法；
多付只是成本，所以下限用触发器钉住（`E_OT_RATE_LOW`）。

`PAY_OT_AUTO` 默认 **off**：上线前后工资条一分不变。但界面上会提示"未启用加班费" ——
不合规不能靠"没报错"来掩盖。

### 按工时模式下只补差额

按工时计薪时，1 倍工资已经含在"时薪 × 工时"里了。加班再全额给 1.5 倍，等于付了 2.5 倍。
所以 hour 模式的加班费是「时薪 × (0.5 / 1 / 2 倍)」。这是两种计薪基础混用最容易多付的地方（OT4 断言钉住）。

## 5. 两种计薪基础

| | 按人天（day） | 按工时（hour） |
|---|---|---|
| 底薪 | 月薪标准 | 时薪 × 实际工时 |
| 事假 | 单独扣（天数 × 日薪） | **不另扣**（缺勤已在工时里） |
| 社保基数 | 月薪标准 | 月薪标准（不随工时少缴：少缴是欠缴） |
| 结构明细 | 原样 | 同比例缩放，BASE 吸收尾差 |

配置三层，越具体越优先：`employment.pay_basis`（个人）→ `PAY_BASIS`（公司）→ 默认 day。
连锁餐饮两种人本来就并存（店长月薪、店员小时工），所以不能全公司一刀切。

**按工时不再扣事假**是这一节最要紧的一条：再扣一次就是扣两次，而员工只会看到"这个月少了好几百"却查不出原因。

## 6. 多版本：自动留，不靠人记得点

| 动作 | source | 意义 |
|---|---|---|
| 生成月报 | `build` | 从日报汇总出来的那一版 |
| HR 手调 | `manual` | 每人每字段一版（合并会把"改了三次"写成一次） |
| Excel 导入 | `import` | 一次改几十人，最需要对比 |
| 提交 | `submit` | 审批人从此固定 |
| 审批通过 | `approve` | **发薪争议时看的就是这一版** |
| 驳回 | `reject` | 连同原因一起留 |
| 重开 | `reopen` | 把"确认过的样子"先存下来再改 |

版本存**全量快照**（jsonb）而不是变更集：只存变更要"回放到某一天"才知道当时的样子，
而回放依赖中间没有被改过 —— 这个前提在真实系统里从来不成立。快照笨，但它永远答得出"当时是多少"。

另有两个能力：`fn_att_period_version_restore`（回到某一版，恢复本身也留一版）、
`fn_att_period_version_diff`（两版对比：谁、哪个字段、从多少到多少）。

## 7. 审批：能改数的人不该同时是批数的人

```
draft →（提交，固定审批人）→ pending →（主管批）→ confirmed
                                  ↓（驳回，写原因）
                                draft
```

审批人解析顺序：

1. 本部门负责人（`org_unit.leader_person_id`）—— 餐饮门店就是店长；
2. 沿部门树向上（店长空缺时落到区域，而不是直接跳 HR）；
3. HR 岗位（按 `position.code`）；
4. HR 角色（`hr_ops` / `payroll_spec`）—— 岗位名是客户自己起的，角色一定配了；
5. 最后才是 `boss`（老板批全公司等于没有审批，只能兜底）。

都找不到 → **提交整批被拒**（`E_ATT_NO_APPROVER`），不允许"没人批就自动过"。

三条硬规矩（都写在库里，不靠界面藏按钮）：

- 提交人不能批自己（`E_ATT_SELF_APPROVE`）；
- 不是指定审批人不能批（`E_ATT_NOT_APPROVER`）；
- 只有待审批的能批，draft 不能直接确认。

**审批是独立权限 `att_report_approve`，不等于"能改考勤"**。
人事主管在权限矩阵里对考勤只有读 —— 那是对的（他看数、批数，不改数）。
如果为了让他能批就给他开考勤写权限，那"改数的人不能批自己"这条就被权限体系统开了。

## 8. 这一轮真踩的坑

| 坑 | 症状 | 教训 |
|---|---|---|
| **整数除法** | 应出勤从 21.75 改成 22（整数）后，`prorata` 算成 27 而不是 27.27 | PostgreSQL 里 `600*1/22` 是整数除法。折算必须 `::numeric`（117） |
| **旷工不冲减** | 出勤改成 21，旷工还留着 20 → 合计超过应出勤 | 两个数字互相矛盾却不报错，比报错难查（124） |
| **审批人没权限** | HR 主管点"通过"被 403 | 新建审批链时忘了给审批人授权（123） |
| **整期审批** | 31 人里 30 人归周杰、1 人归闫妍，周杰点通过被整批拒 | 多人审批要"只批分配给我的"，区分"没有待审批"与"不在名单里"（122） |
| **抄错函数版本** | 从 103 抽 `fn_payroll_calc` 重建，把 105 的多险种静默回退 | 永远从**最后一个改它的迁移**抽，不是"我记得的那个" |
| **约束挡住标记行** | 重开痕迹 before/after 都是 NULL，被 `ck_apa_changed` 拒 | 标记行要显式豁免（116） |
| **v_n 未初始化** | 提交成功但返回 0，调用方以为没提交 | plpgsql 未初始化的 integer 是 NULL，NULL+1 还是 NULL（119） |

## 9. 还没做的（登记为债，不是忘了）

- **农历节日没预置**：春节/端午/中秋是农历，必须按当年国务院公告维护。
  没维护的那几个月，应出勤会把法定假算成工作日（偏高 1–3 天），加班也会按平日算（偏低）。
  这是数据问题，界面上要提示。
- **病假工资**：法定不低于最低工资的 80%（各地细则不同），目前按事假口径处理。
- **未休年假折现**：应按日工资 300% 支付（含正常工资，即额外 200%）。
- **综合工时制**：需劳动行政部门审批，加班按周期内超出部分算，目前只支持标准工时。
- **补休抵扣**：休息日加班"能安排补休的不付 200%"，目前一律按 200% 算（多付，不少付）。
- **考勤月报的按部门批量提交**：现在是一期一次提交、按人分配审批人。
