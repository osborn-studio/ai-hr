## 2. 一句话结论

产品是「**六模块 + 九规则域**」（六模块：设置规则 / 排班 / 打卡 / 审批与异常 / 统计报表 / 工时确认；
九规则域：工作日历、班次、打卡、加班、假期、异常、权限、审批、报表）。

我们现在有：**打卡、人日、月报、封账、加班三档、假期额度与审批、划线排班（新）、固定班次排班、门店确认**。
缺的集中在两处：**排班的"批量与周期"**（第七种排法）和**排班规则这一整层**（合规/修改/发布/提醒）。

## 3. 划线排班：三处原文，一个定义

产品资料里它出现的三次，说法完全一致：

> 「划线排班是针对某天的**临时班次**场景，排班时**不需要再去添加班次**，直接**划出班次时长**即可」
> —— 白皮书 2.2.4

> 「兼职工/临时工考勤排班 —— **上到几点就划到几点**，自动设置排休规则及休息时长，
> 自动设置休息时间后，是否允许排班人修改」
> —— 官方 44 页 PPT，p16

> 「门店临时安排上班的情况，店长通过**临时排班**，只需一步，给员工快速划线一个临时排班即可。
> **再也不需要告知人事添加班次**，再来排上班次」
> —— 京兆刘福记案例（2024 餐饮方案 p36）

**定义：它不是"选一个班次"，是"给一段时间"。** 班次库里有没有这个班不重要 ——
这正是它的价值：门店临时叫人 4 点到 9 点，不该为了这件事先去建一个"4-9 点班"。

**我们怎么实现的（148）**：写 `schedule` + `schedule_segment`（段表本来就是任意时段），
挂一条虚拟班次 `LINE` 只为满足 `shift_id NOT NULL`；休息按制度项自动扣、允许排班人显式覆盖。

三件必须钉住的：
- 与同一天已有段**时段重叠 → 拒**（两段重叠 = 两倍工时，而工资按工时算）；
- 跨零点（22:00–02:00）算一段，落次日；
- 锁定之后不许再划。

## 4. 排班七种方式：现状对照

| # | 产品里的排法 | 我们 | 差距 |
|---|---|---|---|
| 1 | 按人员排班 | ✅ 145 `fn_roster_assign` | 无 |
| 2 | 按班组排班（班次相同的人成组，一人只在一组） | ❌ | 缺 `roster_team` + 组内批量排 |

## 5. 排班规则：产品有四层，我们一层都没有

白皮书 2.1 把规则拆得很清楚，这是**最该补的一层**，因为它不涉及新交互，只涉及校验：

| 层 | 产品做什么 | 我们 |
|---|---|---|
| **合规性** | 工作日/休息日/节假日可否排班；日/周/月最大工时；连续排班时长；月最小/最大排休；**日/周/月各 3 档风险预警值** | ❌ 全无 |
| **修改** | 已发生的排班是否可改；排休谁能改（按角色） | ⚠️ 只有"锁定后不许改" |
| **发布** | 保存即发布 / 手动发布 / 审批后自动 / 审批后手动 | ⚠️ 有门店确认四态，但语义是"认不认"，不是"发不发布" |
| **提醒** | 未排班提醒（提醒排班人或员工）；未排班是否可打卡 | ❌ 全无 |

★ 这里有个口径演进要记住：**2026-07 的最新方案里，"发布模式"这个说法消失了**，
只剩"排班/换班留痕可查"。所以发布模式按**可配开关**做、默认关（= 保存即生效），
不把它做成必经流程 —— 那是老版本的能力，新客户不会为它买单。

## 6. 假期：产品的能力面 vs 我们

| 能力 | 产品 | 我们 |
|---|---|---|
| 假种 | 年假/调休/病/事/婚丧产 + **哺乳假/育儿假/护理假/妇女节** 等地方性 | ⚠️ `leave_type` 可自定义（127），但**没有"按条件自动发放"**（如育儿假到子女满 3 岁止） |
| 发放 | 按天/按**月平均**发放；按对象/时间/额度/有效期 | ⚠️ 有 `annual_leave_tier`（按工龄档）+ 手工 `leave_grant`，**没有"按月平均"** |
| 余额 | 往年余额展示；多有效期导入；**扣减优先级** | ✅ 结转（132）+ 作废/折现（129）；⚠️ 无优先级配置 |

| 过期 | 清零 或 **转加班/折薪**；提前提醒 | ✅ 作废/折现（`expire_policy`）；⚠️ 无"转加班"、无提醒 |
| 预支 | 预支调休假 | ❌ |

## 7. 最新口径的三处演进（2025-2026 才有的）

1. **按打卡自动排班**（2025 版 p14）：「根据员工实际打卡，自动匹配班次，管理员不再需要事先排班」。
   这是给"排不准"的产线用的，与划线排班是两条路：一个事前划、一个事后对。
2. **多层级规则共享**（2025 版 p9-10）：集团定规则 → 事业群/公司**引用或自建**，`强控/弱控/叠加`，
   数据层层下钻。我们的 `policy_def` 有 `allow_org_override` + `override_floor`，**方向对，但只到组织不到"法人"**。
3. **借调成本分摊**（2025 版 p15）：跨考勤组借调，人力成本**按天自动分摊**到借入方。
   我们现在只有 `reason`（跨店要写原因），没有分摊。

## 8. 缺口清单（按"餐饮几十家门店会不会天天用"排）

### P0 · 排班规则层（不涉及新交互，全是校验，最容易验收）
- 存：`roster_rule`（按组织/考勤组：日/周/月最大工时、连续排班上限、月最少休息、预警阈值）
- 判据：排班时超限 → `E_ROSTER_OVER_LIMIT`（硬拦）；接近阈值 → 预警行（不拦）
- 为什么先做：**它不改任何交互**，只在写路径上加校验；而"排班工时超法定"是餐饮被罚的最常见原因

### P0 · 划线多段撞唯一键（已知缺陷，必须修）
`schedule` 的 `UNIQUE(employee_id, work_date, shift_id)` 让"同一天两段划线"直接 23505 ——
而"一天多班次"是产品明写的能力。改法：唯一键里加段的起始时刻，或划线不写 `shift_id`（置 NULL + 部分唯一索引）。

### P1 · 班组 + 周期（第七种排法）
- 存：`roster_team`（组、组内人、所属考勤组）、`roster_cycle`（周期规则：几天一轮、每天几个班、起始日）
- 判据：周期展开时**跳过**当日请假/调店/封账（产品原话），并留"跳过了哪几天"的记录

### P1 · 未排班提醒
- 存：`roster_rule.remind_before_hours`、`remind_target('manager'|'staff')`
- 判据：T-N 小时仍有空格 → 出一条待办（不自动补班）

### P2 · 借调单（审批 + 自动调入调回 + 成本分摊）
我们已有跨店 `reason`，缺的是"单据化"：`roster_dispatch`（人、原店、目标店、起止、审批人、成本归属）

### P2 · 假期：按月平均发放 + 请假最大时长 + 请假证明
三条都能挂在 `leave_type` / `leave_grant` 上，不需要新表。

### 不做（写清理由）
- **防作弊**（虚拟定位、人脸）：那是打卡端与硬件的事，不是 HR 库能解决的
- **按打卡自动排班**：要先有"打卡→班次匹配"的推断规则，而推断错会让工时算错；等 P0 规则层稳了再说
- **多层级强控/弱控/叠加**：我们的 `policy_def` 已能表达"能不能覆盖 + 覆盖下限"，
  再做一层"强控"会让同一个制度项有两个来源，违反「唯一出处」

## 9. 落地顺序（每步都能单独验收）

1. **修划线多段唯一键**（半小时，纯 bug）
2. **排班规则层**（P0，校验 + 预警，不改交互）
3. **班组 + 周期**（P1，批量排班的基础）
4. **未排班提醒**（P1，一条待办）
5. 假期三件（P2）

每一步都配断言：能写出一条"不改就红"的判断，才开工。
写不出判断的功能，先不做 —— 那是"看起来做了"。

## 10. 这份文档与代码的关系

`148_roster_line.sql` 是本文档 §3 的落地。它的文件头写着三处原文引用 ——
代码里能查到出处，比只写"按产品要求"有用：半年后有人问"为什么划线要拒重叠"，

## 12. 七处"产品自身也有边界"（必须知道，否则会承诺做不到的事）

1. **健康证过期拦截**：仅限已购买「数字证照」的客户 —— 没买就没有到期日，拦不了。
2. **调休假 / 哺乳假 / 育儿假"每个组织只能有一个"**：不能按门店各建一个（产品限制，不是我们）。
3. **必须专业版钉钉**：我们是独立库，这条反而更自由（不依赖钉钉版本）。
4. **批量补卡靠 ISV 套件**，原生没有；**跨店支援靠「人员调度套件」**，不是高级排班自带。
5. **年假按月发放、按性别/年龄发假依赖花名册字段**（首次工作时间、司龄、子女信息）——
   客户没维护就跑不出来。这是最容易承诺翻车的一条。
6. **请假证明、加班补偿金、工资台账**属于薪酬/证照模块，高级排班与假期里只是入口。
7. 价格有两套口径（2021 版 vs 2024 版），对外报价时不能混用。

  等规则层（149）跑稳再说 —— 先有校验，再有推断。
- **多层级规则强控/弱控/叠加**：`policy_def` 已能表达"能否覆盖 + 覆盖下限"，
  再加一层强控会让同一制度项有两个来源。
- **防作弊**（虚拟定位、人脸）：打卡端与硬件的事，HR 库解决不了。
