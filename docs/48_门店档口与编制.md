## 1. 一句话

**档口不是组织节点，是门店内部的一张编制明细表。**
`station`（集团档口词表）→ `store_station`（这家店有哪几个档口）→ `station_position`（这个档口配几个什么岗）。
组织架构图上画成第三层，靠前端拼，不靠改树。

一句话理由：加进 `org_unit` 会一次破 **5 处**现有机制，而且每一处都不在档口自己的测试里暴露。

## 2. 为什么档口不做 `org_unit.kind = 'station'`

"档口就是一个小部门嘛" —— 这句话对了一半。它确实是个分组，但它不是**组织**：
它不参与四维归属、不参与权限行闸、不参与编制下分。

| # | 破在哪 | 症状 | 依据 |
|---|---|---|---|
| ① | `ck_ou_kind` | 迁移当场失败，被迫改约束 ⇒ `SUITE.OG` 的判据面跟着变 | `076_org_dept.sql:39-41` |
| ② | `fn_rq_guard` | **所有门店级招聘需求报 `E_RQ_NOT_LEAF`** —— 需求只能挂叶子组织，档口一进树，门店全部变成非叶子，招聘功能整体瘫痪 | `025_recruitment.sql:174`、`:212-214` |
| ③ | `fn_hc_used` + `fn_hc_allocated` | 编制双计：`used` 按 `cost_org` 的 path 前缀累加子树，`allocated` 按直接子组织额度累加。人挂档口后同一批人被扣两次，`fn_hc_hireable` 静默变负，而"子项≤父项"校验照样通过。**已修：`178_hc_hireable_direct.sql` 把 `used` 换成直属口径** | `022_headcount.sql:113-126`、`:92-100`、`:178-193` |
| ④ | `fn_scope_people` | **门店 HR 一个人都看不到**：它用 `cost_org` **精确匹配** scope 节点，不是 path 前缀。人挂档口后 `a.org_id = 档口id` 匹配不上门店 → fail-closed 返回 0 行 | `170_scope_people.sql:29-45` |
| ⑤ | `/api/org/tree` 直属人数 | 门店卡片人数塌成 0（`WHERE a.org_id = t.id` 精确匹配） | `server.mjs` 原 2744 行 |

第 ④ 条最值得记住：**fail-closed 是那个函数的优点，但在这里它变成了"门店 HR 打开人事档案是空的"** ——
一个安全设计在错误的层级上，会以"数据没配上"的样子出现。

## 3. 为什么编制不能挂在 `position` 上

`083_position.sql:31`：`CONSTRAINT uk_pos_code UNIQUE (code)`。

"炉头"这个岗位**全集团只有一行**，10 家店共用。在这唯一一行上写 `headcount`，
只能写一个数 —— 没法表达"A 店 2 个炉头、B 店 3 个炉头"。

所以：**编制落在 `(门店, 档口, 岗位)` 三元组上**（`station_position`），
而 `position` 保持"集团岗位词表"的身份，`org_id` 留空（`083:25` 已允许"跨部门岗位"）。

同理不能复用 `headcount_budget` 加一列可空 `station_id`：那张表的形状是"一行 = 一个组织的额度"，
而 `fn_hc_quota / allocated / used / hireable / set / over / uncovered / slack` 八个函数、
`fn_hc_guard` 触发器、`/api/headcount/set`、MCP 工具 `headcount_set` 全建立在这个形状上。
加一列会让它们**全部**需要 `AND station_id IS NULL` —— 漏写一处就是编制翻倍，而漏写不报错。

## 4. 三张表

```
station（集团档口词表，带品牌线）
   └ store_station（这家店有哪几个档口，带启停区间）
        └ station_position（这个档口配几个什么岗、当期编几个）
```

### 4.1 `store_station` 用区间 + 排他约束，不用 `closed_at` + `UPDATE`

与 `014:28-32`（`ex_eoa_no_overlap`）、`083:51-53`（`ex_pp_no_overlap`）同法：

```sql
EXCLUDE USING gist (store_id WITH =, station_id WITH =,
                    daterange(opened_at, closed_at, '[]') WITH &&)
```

两个理由：
1. 关档口再开是真实事件（装修、旺季临时加个炸物台）。就地 `UPDATE closed_at` 会把这中间的空档抹掉，
   而"3 月到 6 月这家店没有烧腊档"正是成本分析要看的事实。
2. **到岗人数要唯一归属**：同店同档口同一时点只能有一个实例，靠约束守，不靠"记得先关再开"。

### 4.2 "不同门店配不同数量" = 编制数，不是档口实例数

- **不同种类**：`store_station` 里有几行就是几个档口。
- **数量**：由 `station_position.headcount` 表达 —— 三个灶 = `炉灶档 × 头灶岗 × 3`，
  缺 2 个灶 = 缺 2 人。

中餐"头灶/二灶/三灶"本身就是**岗位级别**（`position.name` + `level`），
再让同一档口出现多个实例，"档口编号"与"灶号"会变成两套编号打架。

> 会推翻这条的需求：连锁火锅的"1 号锅底档 / 2 号锅底档"若必须各自独立定编、独立考核，
> 就把 `station.code` 建成 `GUO1`/`GUO2`（词表多两行，零成本），而不是加 `instance_no`。

### 4.3 同一家店内，一个岗位只能属一个档口

不是洁癖，是**到岗人数没有第二解**：

```
员工 → person_position.position_id → (本店, position_id) → 哪个档口
```

若同一岗位在本店属于两个档口，这条推导有两个答案 → 两个档口各算一次 →
**档口到岗之和 > 实际人力，缺岗被低估，而每一行单独看都合规**。

由 `trg_sp_guard`（BEFORE INSERT）守，抛 `E_SP_CROSS_STATION`。
跨门店是允许的（`position` 是集团词表，A 店挂炉灶档、B 店挂中央厨房档互不影响）。

## 5. 三个数字

| 数 | 口径 | 实现 |
|---|---|---|
| 编制（hc） | 当期 `station_position` 里各 `(档口,岗位)` 的最大 `version` 之和 | `fn_store_station_quota` / `fn_station_fill` |
| 到岗 | 在编 + 在职 + `cost_org` 落在**这家店** + 当期任职在这个岗位上 | `fn_station_fill` |
| 缺岗 | 编制 − 到岗（**都按岗次**） | `fn_station_fill` |

### 5.1 三个数必须**一次取齐**

拆成"编制函数 + 到岗函数 + 缺岗函数"，三个数就来自三个时点。
页面把三个时点的数并排放，会算出"编制 8、到岗 8、缺 1"这种自相矛盾的一屏，
而每个数单独看都对。

所以 `fn_station_fill(p_store, p_on)` 一个函数返回 **粒度到 (档口, 岗位)** 的一份结果，
档口级与门店级由调用方用**同一份结果**聚合，不另发 SQL。

### 5.2 到岗必须是三个 `daterange`，一个都不能少

```sql
daterange(pp.valid_from, pp.valid_to, '[]') @> p_on   -- 当期在这个岗位上
AND daterange(e.hire_date, e.leave_date, '[]') @> p_on -- 当期在职
AND daterange(a.valid_from, a.valid_to, '[]') @> p_on  -- 当期归属
AND a.org_id = p_store                                 -- 归属是这家店（等值，不是 LIKE）
```

- 少第一个 → 已卸任的人还算在岗；
- 少第二个 → 离职的人还算在岗（`007:55-56`：离职日当天仍算在职）；
- 少第三个 → 历史归属串进来；
- `a.org_id` 用 **LIKE** → 跨店支援的人被串进来（"人在这家店、成本在那家店"天天发生）。

### 5.3 缺岗起始日：派生，不落列

口径：**使得到岗 ≥ 编制的最晚时点之后的下一个断点，就是缺口起点。**

到岗与编制都是分段常量，跳变点只有两类：某人的任职起止（`valid_to + 1`）、编制某期的 1 号。
断点集合有限且很小，逐点求值即可 —— 不回溯扫描、不建快照表、不起定时任务。

**不能落成一列 `gap_since`**：入职/离职/转岗/调编四条路径都要维护它，必然漂；
漂的表现是"缺岗 30 天"其实是 3 天。（与 `022:128-130` 同一条理由。）

> 一个已踩过的坑：不能写成"最后一次满足的断点 + 1 天"。
> 满足的最后一个断点是 03-01、下一个断点是 03-11（有人离职）时，
> 缺口起点是 **03-11**，不是 03-02。差 9 天，而两种写法都不会报错。

### 5.4 「未定编」≠「缺 0」

当期一行 `station_position` 都没有 → 编制与缺岗都返回 **NULL**。
沿用 `022:242-244`（"没额度就没有判据：占编 200 人也不会超编，而报表上一片绿"）
与 `server.mjs` 里既有的 `gap: q === null ? null : ...`。
前端用同一个 `orgGapTxt()`（`index.html:6211`）渲染成灰字"未定编"，**不进缺岗合计**。

## 6. 最容易搞混的那个点：门店数人头，档口数岗次

`083_position.sql:152-153` 已经定了：

> 一人多岗时，他在每个岗位下都算一次 —— 这是对的：编制看的是"岗位有没有人"，不是"人头去重"。

于是：

| 指标 | 口径 |
|---|---|
| 门店到岗 | **人头**（`count(DISTINCT person)`） |
| 档口到岗 | **岗次**（一人两岗算两次） |

一个人兼炉头 + 打荷 → 档口岗次 2、人头 1。
所以 **Σ档口岗次 ≥ 门店人头，这两个数不能相减，也不能放在同一行做合计。**

这不会在任何测试里"碰巧通过"：`station.mjs` 的 ST4a 就是拿 4 个岗次对 3 个人头。

> 页面文案里必须写这一句，否则演示现场第一个问题就是
> "6 个档口加起来 12 人，门店才 10 人？"

## 7. 外包与兼职

| 人群 | 占编 | 算到岗 | 为什么 |
|---|---|---|---|
| 外包人员 | 否 | 否 | `019:64-67` 明确"刻意没有 `person_id`" —— 一旦与内部自然人同表，个税/社保/工资条/编制的每一个"按 person"的清单都会自动包含他们，而排除要靠每处查询记得加条件。加对 12 处，第 13 处会忘 |
| 兼职 / 小时工（`pay_basis='hour'`） | **默认占** | **默认算** | 他的合同在我方、有工资条。不占编会出现"招进来不占编"的口子 |

- 外包**不进**三个数字，接口另给一栏"外包 48 小时 / 2 人 · 不占编"。
- 外包**不做 FTE 折算**：折算需要"标准月工时"，而全系统工时口径只有 `schedule_segment` 一处
  （`150:25-26` 明确"班组不承载工时……把组也当成工时来源就有了第二条算薪口径"）。
  宁可不给结论，也不造第二套口径。
- 兼职是否占编做成 policy `HC_STATION_PARTTIME`（`occupy` / `exclude`，`override_floor='region'`）。
  默认 `occupy`，因为另一条路要由客户显式选 —— 选了之后"招进来不占编"这个口子就永久存在了。
  实现上两件事**必须同进同出**（既不占编也不计到岗），只排除一边会出现"到岗 > 编制"。

## 8. 三级数字自洽

```
① Σ(该店档口编) ≤ 门店编                    ← trg_sp_guard 强制
② 门店编 − Σ档口编 = 「还没分到档口」        ← 店长/副店长这类不进档口的岗
③ 未定编的档口数要单独计（stations_unset）  ← 否则"全绿"掩盖"没定编"
```

第 ① 条不是为了好看：不约束会出现"门店 12/12 满编，炉灶档还缺 2 人" ——
系统给出两条互相矛盾的结论，而操作员会去调其中一条，把真实情况盖掉。

## 9. 品牌线

`station.brand_line`：`common` / `cantonese` / `sichuan` / `tempura` / `noodle` / `hotpot` / `western`。

`fn_station_choices(p_brand)` 返回 `common + 本线`，铺档口的下拉列表用它 ——
**天妇罗专门店才不会在候选里看见烧腊档、点心档、打荷档**。

品牌线**只在铺档口那一刻是筛选条件**，铺完之后 `store_station` 就是事实，不回头校验。
理由：门店换品牌（茶餐厅转做天妇罗）是真实事件，硬校验会让它变成"先删光档口"，
而删光会连带丢掉编制与全部历史。

## 11. 三条留给后来人的提醒

1. **不要**为了"让档口出现在组织树上"而给它加 `kind`。要出现在树上，改的是视图（前端拼），不是模型。
2. **不要**给 `position` 加 `headcount`。它是词表，10 家店共用一行。
3. **不要**把门店到岗与档口到岗相减。一个是人头，一个是岗次，它们本来就不该相等。

## 12. 关档 / 改配置 / 关档之后的历史，到底动谁

这一节回答三个最容易含糊的问题。每条都对应一条断言（`ST11a–d`）。

### 12.1 关档 = 加一条结束日期，不是删数据

`fn_store_station_close` 只做一件事：给 `store_station.closed_at` 写上日期。

- `station_position` **一行都不动**（它本身还被 `trg_sp_append_only` 挡着，改不了）；
- 关档后查**关档前**的那一天，那个档口和它的编制照常出现在列表里（`daterange(opened_at, closed_at, '[]')` 是区间语义）；
- 关档不是物理删除：`store_station` 上有外键被 `station_position` 引用，`DELETE` 会直接 `23503`。

所以"关档会不会把历史抹掉"这件事在库里做不到 —— 这一点由结构保证，不靠约定。

### 12.2 关档之后，那部分编制回到"还没分到档口"

Σ档口编只算**期末仍然开着**的档口（`fn_store_station_quota`，用期末日，与 `022:119-125` 的 `fn_hc_used` 同一个约定）。

为什么必须写这个条件：写 172 的时候漏了它，结果是 3-15 关掉一个档口之后，
守卫（判"超门店编"用的 `fn_store_station_quota`）仍按 5 算，页面（按还开着的档口聚合）按 3 算 ——
**"还没分到档口"在同一屏上算出两个数，而两个数都对得上自己的算式**。
差 2 个编不会报错，只会让下一次调编算错。`ST11a/ST11b` 就是钉这一对的。

用**期末日**而不是"当天"，是为了不让 3 月 30 日关一个档口把 3 月整月的编制追溯改小。

### 12.3 已经算过的工资不会跟着变

三个理由，从强到弱：

1. **这三张表不在工资链路上。** 全仓库引用 `station_position` / `store_station` 的只有
   `app/server.mjs`（读接口与这两个写路由）和 `tools/seed-*.mjs`（演示数据）。
   算薪 / 工资条 / 社保 / 个税的 SQL 里一次都没出现。
2. **口径上也不该变。** 编制是**计划**（该招几个人），工资是**结果**（实际发了多少）。
   调一次编就把上月已发的钱改了，等于把"当时批的预算"变成"事后能改的数"。
3. **封账本来就拦这件事。** `fn_atv_freeze` 让已封期间的工资不能就地改，重算要走重开流程。

唯一会跟着变的是**未来**的编制与缺岗 —— 那本来就该变，它描述的是计划。

### 12.4 一个岗位能不能同时挂在两个档口

| 范围 | 能吗 | 靠什么守 |
|---|---|---|
| 同一家店内 | **不能** | `trg_sp_guard` → `E_SP_CROSS_STATION` |
| 跨门店 | **能** | `uk_sp (store_station_id, position_id, period, version)` 只到档口，`position` 本身是集团词表 |

同店内不许跨档口，是因为**到岗人数没有第二解**：`员工 → person_position.position_id →
(本店, position_id) → 哪个档口`。两个档口都有它，这条推导就有两个答案，
两个档口各算一次到岗 → 档口到岗之和 > 实际人力，缺岗被低估，而每一行单独看都合规。

跨门店可以，是因为 `position` 全集团一行（"炉头"就是"炉头"），
A 店挂在炉灶档、B 店并进中央厨房，互不影响 —— 到岗的推导里带了 `a.org_id = 门店` 这一项。

> 注意这条约束是**按期**判的：同一个岗位在 2026-05 属炉灶档、2026-06 改属打荷档，是合法的
> （重组就是这么发生的）；只有"同一期内属两个档口"才拒。

| 函数 | HTTP | 权限 |
|---|---|---|
| `fn_station_choices` | `GET /api/org/station/choices?brand_line=` | `employee_roster` 读 |

### 12.6 响应里每个数字的**单位**（这一段是给下一个读代码的人写的）

同一个响应里同时有"编 / 人 / 岗次 / 人次"，是本模块最容易被问住的地方。

| 字段 | 单位 | 定义 | 什么时候是 null |
|---|---|---|---|
| `store.quota` | **编** | `fn_hc_quota(门店, 期)`（022 的唯一实现） | 门店没定编 |
| `store.headcount` | **人头** | `cost_org` 落在本店且在职的人数 | 从不（0 就是 0） |
| `store.quota_unallocated` | **编** | 门店编 − Σ已定编档口编 | 门店没定编 |
| `store.station_quota` | **编** | Σ 已定编档口的档口编 | 从不（没配档口就是 0） |
| `store.slots_filled` | **岗次** | Σ 各档口到岗岗次（一人两岗算两次） | 从不 |
| `store.holders` | **人次** | Σ 各档口到岗人头（跨档口会重复计） | 从不 |
| `store.gap` | **岗次** | Σ 各档口 `> 0` 的缺岗 | **没有档口 = null** |
| `station.gap` | 岗次 | 档口编 − 档口到岗 | 该档口未定编 |
| `position.headcount` | 岗次 | 该岗位的档口编 | 未定编 |

两条容易读错的：

- **`quota_unallocated` 的单位是「编」，不是「人」。** 门店编 4、一个档口都没配 → 它是 **4**，
  不是"没分到档口的 2 个人"。名字里带 `quota` 就是为了堵这个误读
  （原来叫 `unallocated`，同一个响应里 `headcount` 是人数，太容易被答成 2）。
  要"没分到档口的人"是另一个数：`headcount − holders`。
- **`gap` 在没有档口时是 `null`，`station_quota` 在同样情况下是 `0`** —— 这不是不一致：
  `gap` 是**判断**（缺不缺人），没有对象时这个判断无意义；
  `station_quota` 是对空集合求**和**，0 是确定答案，而且 `quota − 0 = 门店编`
  正好推出"全部还没分下去"。
  这一条由 `ST12a / ST12b` 两面对钉：没档口 = null、有档口且满编 = 0。
  `/api/org/tree` 的 `station_gap` 与 `/api/org/stations` 的 `store.gap` 必须是同一个答案
  —— 两个接口对同一件事给两个数，比任何一个数错了都难查。

### 12.7 两个"看不懂就别放过"的入口校验

- **品牌线写错 → `400 E_ARG_INVALID` 并列出可选值。**
  `fn_station_choices` 的条件是 `brand_line IN ('common', <传入值>)`，传错名字**不会报错**，
  只会退化成"只有 common 那几条"—— 一份看起来完全正常的清单。
  运营以为选的是专线，铺下去才发现少了烧腊档，而铺错之后要 close 再重开。
  前端传的是自己维护的 `STATION_BRANDS` 不会踩；会踩的是 MCP / curl / 以后的导入
  —— 那些是**没人盯着屏幕**的入口（`ST13`）。
- **非部门节点不给算档口 → `422 E_STN_NOT_STORE`（与 172 的 `fn_stn_guard` 同一个码）。**
  给区域返回一份空清单，看起来像"这个区域没配档口"，而事实是"档口这个概念只在门店里有"（`ST14`）。

★ 四条写路由都用 `headcount` 写权限，**不复用 `ledger`（建帐）**：
建部门是帐套级动作，档口只在门店内部换分法，两者不是一个量级；
而实测演示帐套里 group_hr / store_hr 都没有 `ledger` 写（那是建帐管理员的事），
用了它，真正要配档口的人反而配不了 —— 而"配不了"看起来像"功能没做"。

四条都还要过 `requireOrg(… dim:'cost_org', action:'write')`：
`E_OUT_OF_SCOPE` 与"返回一份空清单"是两件事，前者是拒绝、后者是一个结论。


## 13. 60 家店时为什么快不起来，以及怎么改的（174）

> 这一段记的是**性能是怎么塌的**，不是"我们做了个优化"。
> 因为塌的方式很典型：10 店秒开，60 店 11.4 秒 —— 说明它不是某个查询慢，
> 是 **O(门店数) × 每店一次** 的累加。

### 13.1 分段实测（60 店 / 374 人，同一台机，每段 3 次取最好）

| 段 | 耗时 |
|---|---|
| 递归树 + 基础列 | 1 ms |
| + `headcount` 直属（逐节点子查询） | 34 ms |
| + `subtree` 含下级（逐节点 `path LIKE` 全表） | **1786 ms** |
| 逐店调 `fn_station_fill`（60 次） | **8337 ms** |
| 整条 tree（一次执行，原样） | 3448 ms |

两处都是"每个节点各算一遍"，而它们算的东西本来就该一次算完：
60 家店的档口明细不是 60 个互不相干的问题，是同一张表按 `store_id` 分组的同一个问题。

### 13.2 改法

1. **档口**：`fn_station_fill` 的**函数体**改成一次算全部门店，拆成三件 ——
   `fn_station_fill_core(store, on)`（唯一实现，store 传 NULL = 全部）、
   `fn_station_fill(store, on)`（单店薄封装，**签名与返回列一个没变**）、
   `fn_station_fill_all(on)`（全量，多一列 `store_id`）。
   组织树改为调一次 `fn_station_fill_all` 再按 `store_id` 分组。
   ★ 单店版不另写一份：口径只有一处实现，是 172 全部判据的前提。
2. **subtree**：先把人按 `org_id` 聚合（`direct`），再沿 `path` 滚（`roll`）。
   「各节点去重人数之和」与「子树内去重」相等，因为 `ex_eoa_no_overlap`
   保证一个人同一维度同时只有一段有效归属。

### 13.3 一个"单店没事、多店爆炸"的坑（改这块时必看）

`gap_since` 原来是这么算的：

```sql
LEFT JOIN LATERAL (
  SELECT fn_sp_gap_since(...) AS since
   WHERE spx.configured AND spx.headcount - COALESCE(f.holders,0) > 0
) g ON true
```

单店调用时它只多跑几次（155ms 里看不出来）；一次算 60 家店时，
**函数被逐行求值 261 次 → 3.5 秒，占整条查询的 98%**。
把条件从"LATERAL 里的 WHERE"改成"先筛出一个 `gaps` CTE 再 join"，
缺口行只有 14 个，14 次调用 0.18 秒。

这类写法本文件踩了两次（还有 `st_heads` 那个相关子查询，同一形状）。
判断标准很简单：**相关子查询里套的是一个"每次都要重算的集合"**，
单店时行数少看不出来，门店数一多就是乘积。

### 13.4 结果

| | 改前 | 改后 |
|---|---|---|
| `/api/org/tree`（60 店） | 5.9 s（此机）/ 11.4 s（演示机） | **0.32 s** |
| `fn_station_fill_all` | — | 308 ms（261 行） |
| `fn_station_fill`（单店） | 177 ms | 111 ms |

**响应逐字节一致**（`sha256` 相同，13746 B）：优化只改计算路径，不改任何聚合口径。
字段顺序也刻意保持不变 —— 值一样、顺序不一样，JSON 就不再逐字节相同，
而"优化前后 diff 为空"正是这次的验收方式。

`ST15` 钉住 `fn_station_fill(store)` 与 `fn_station_fill_all()` 的单店切片**逐行逐列相同**：
拆了两个入口，但口径只能有一份 —— 不一样的那天，组织树和门店详情页会各显示一个数，
而两个都"算得通"。

### 13.5 顺手修的一个小 bug

组织树上的 `stations` 原来是 `count(*)`（**明细行数**），不是档口数。
本库里每个档口恰好只有一个岗位，所以两者相等、看不出来；
一个档口挂两个岗时会把它算成两个档口。改成按 `store_station` 去重后，
本库上的值不变（261），而"树"与 `/api/org/stations` 的 `station_count` 从此是同一个数。

### 13.6 第二个"单店没事、多店爆炸"的坑：**缓存计划**

走查在 8788 上验到：第一次 `/api/org/tree` 0.348s 正常，**第二次 25 秒超时，之后全站超时**，
日志里一条错误都没有（不是崩，是每条查询都慢 1000 倍）。他怀疑 OOM，我复现后发现**内存是平的**。

复现（同一进程、同一份库、同一条语句连跑）：

```
#1..#5   276 ~ 341ms
#6       272268ms      ← 就是第 6 次
#7       275176ms
内存全程 rss 348MB / external 199MB（平稳）
```

**第 6 次**这个数字是钥匙：PostgreSQL 的 `plan_cache_mode = auto` 会在同一条语句执行到
第 6 次时试着切到**通用计划**（generic plan）。`fn_station_fill_core` 只有两个参数，
而树那条路上 `p_store` **永远是 NULL** —— 通用计划只建一次、之后一直复用。
一旦那个计划是坏的（实测把 `ss` 的 join 变成 nested loop，`Rows Removed by Join Filter` 六万多行），
从第 6 次起每一次都慢三四个数量级。

**为什么看起来像"服务崩了"**：没有任何异常，只是每条查询都超时，外面的 curl 15~20 秒超时就
读成 `000`。**"进程被谁弄没的"目前无法确定** —— 现场只能证明"没有监听"（`curl` exit 7、
`lsof -iTCP:8788 -sTCP:LISTEN` 0 行），区分"被杀 / 被重启 / 自己退出"需要 `>>` 追加日志 +
重启计数。写这一段时特意不写"被 OOM kill"：**这一轮已经因为"日志只有一行 listening 就推断 SIGKILL"
栽过一次**（`>` 会截断，"只有一行"对任何一次正常启动都成立）。观测不足时，说"慢"就够，
不要替它补一个原因。

**改法在 179**（`179_plan_cache_mode.sql`）：`app_init_session()` 里
`set_config('plan_cache_mode','force_custom_plan', false)` —— **会话级**，覆盖所有语句，
两个驱动都盖到。改后连跑 15 次：**295 ~ 330ms 全部稳定**；走查在 60 店库上连打 12 次：
`0.878 → 0.610`，第 6 次 0.619s（修前 272s），不随次数上升。

> **教训一（写给要改这块的人）：已发布的迁移只读；要补就开新号，而且新号里的语句必须幂等。**
> 我一度把三条 `ALTER FUNCTION … force_custom_plan` 加进 `174`，后来撤了，原因两条：
> ① `createApp` 只在空库跑迁移、PGlite 没有账本，**改已应用的迁移，存量库拿不到** ——
>   那三条只对全新库生效，而这个 bug 恰恰是在存量库上出现的；
> ② `tools/migrate.mjs` 比 sha256，文件一变，**每个跑过 174 的真库从此每次 migrate 都挂一条
>   "文件已变更"** —— 那正是本轮一直在清理的那种假警报。
>
> **★ 但真正的判据不是"迁移文件神圣"，是一句更准确的话：能不能到存量库，取决于它写在哪个号里。**
> `179` 是正面示范 —— 它是**新号**，里面是 `CREATE OR REPLACE FUNCTION app_init_session()`（`179:46`），
> 所以存量库也拿到了那行 `set_config`。
> 而 station 那三条 `ALTER FUNCTION` 之所以没用，恰恰因为它们躺在**已发布的 `174`** 里。
> **同一个语句、换个载体：一个能到存量库，一个不能。文件本身没有神圣性。**
>
> **替代动作（准则的物理内容，不只是禁令）**：开新号，且新号里的语句必须**幂等** —— 能在存量库上重复执行：
> · 函数 / 视图 → `CREATE OR REPLACE FUNCTION` / `CREATE OR REPLACE VIEW`（`179:46`）
> · 给**已建表**加列 → `ALTER TABLE … ADD COLUMN IF NOT EXISTS`（本仓 **68 处**；先例 `065:177-178`、`068:22,53-54`、`069:26-28`、`117:29`）
> · 建表 → `CREATE TABLE IF NOT EXISTS`（本仓 53 处）
> · 改 / 删约束 → `DROP CONSTRAINT IF EXISTS` 再 `ADD CONSTRAINT`（本仓 19 处；约束变宽变窄**只能**重建，没有 `ALTER CONSTRAINT`）
> ⚠️ **`CREATE OR REPLACE` 只对函数/视图安全**：`CREATE TABLE` **不幂等**，重跑会炸 —— 只能靠 `IF NOT EXISTS` 或 `DO $$ … IF NOT EXISTS … $$`。
>
> **★ 这条不只适用档口线，它是全仓规矩。** 今晚同一结论被三个人从**三条不同路径**独立得出：
> · 一个**拒给 `022_headcount.sql` 加一行指针注释**（会触发上面第 ② 条的假警报，为一行注释不值得）；
> · 一个**否掉了"双保险迁移"**（同一个修复想在新号里再放一份；重复的载体不提高到达率，只多一处要维护）；
> · 一个把 **`174` 回滚到首版的原始字节**（哈希要回原值，否则第 ② 条的警报永远在）。
> 三条路径、同一个事实 —— 所以别把它当成"档口这条线的注意事项"。
>
> **怎么知道一个存量库停在哪一版？** 用 `code/tools/migrate-status.mjs`（**只读，绝不应用迁移**）：
> `PGLITE_DATA_DIR=… node tools/migrate-status.mjs`。它给三列——迁移号 / 有迹象·无迹象·无法判定 / 判据，
> 目前只对 172 / 174 / 178 / 179 / 180 / 181 / 182 七条写了指纹（其余故意"无法判定"：给 182 个迁移逐个写指纹，
> 写错的指纹比没有指纹更危险）。**它不建账本**：PGlite 这条路径从来没有 `schema_migration`，
> 而无账本时猜"跑到哪一版"，猜错就把旧库永久钉成最新 —— **错误的账本比没有账本更危险**。
> 退出码 0 只代表"没有反证"，不代表全对。
>
> **★ 真要撤，用 `git revert`，别手动删回去。**
> **不是为了哈希** —— blob 是**内容寻址**的：字节完全一致，哈希就一致（实测：原版 `5408` 字节 = `27639b7c…`；同一份内容末尾多一个空格 = `5409` 字节 = `2a2df138…`，完全是另一个文件）。手动删干净了，一样得到 `27639b7c`。
> 真正的理由是两条，都不是哈希：
> ① **机械性** —— revert 按 patch 逆推，**不可能只撤 98%**；手动删行很容易留一个空行、一个尾随空格、少一个换行，而它们都会让 blob 变成 `2a2df138` 那种"看起来一样、其实另一个"。
> ② **可读的意图** —— 历史里留下 `Revert "…"`，下次考古立刻知道"有人做错了又撤了"；手动改回去看起来只是普通编辑，**后人会以为那就是原版**。
>
> **★ 当时为什么会犯（这段比结论更防下一次）**：理由是"纯注释 + 过滤注释后 diff 为空 + 此刻哈希代价为零"。
> 前两条证明的是**语义**没变，而我们要的是**字节**没变；第三条是**当下的**代价，而代价会在第一个真库跑过 `migrate` 之后才兑现。

> **教训二：怎么判断"是哪一层在兜"。** 计划缓存现在有两个可能来源，用一条 SQL 就能分开：
> ```sql
> -- 函数级（写进 pg_proc.proconfig，重启后仍在）
> SELECT proname, proconfig FROM pg_proc WHERE proname LIKE 'fn_station_fill%';
> -- 会话级（179）：app_init_session 的正文里有没有 set_config
> SELECT position('force_custom_plan' in prosrc) > 0 FROM pg_proc WHERE proname = 'app_init_session';
> ```
> `proconfig` 里没有 `plan_cache_mode` 但会话是 `force_custom_plan` → **只有 179 在兜**（现在的状态）。
> 这与"修没修好"无关：**179 单独就够**，函数级只是个可选的定点保险。

> 这一段与 §13.3 是同一家族的第三个坑，但机理完全不同：
> 那两个是**写法**（相关子查询逐行求值），这一个是**执行计划缓存**。
> 共同点是：**单店/单次都看不出来，第二次、第六次才露头。**
> 所以这类改动必须"连跑 15 次"来验，而不是跑一次看着快就收工。

顺带：`part` 那个 CTE 原来写成 `SELECT DISTINCT store_id, (SELECT fn_policy_effective(store_id))`，
相关子查询是**每行求值**（261 次，DISTINCT 在之后才去重）。改成先 `SELECT DISTINCT store_id` 再查
（60 次）。这一条单独不足以解释劣化，但它是同一形状，一并改掉。

### 13.7 演示时的一条实须知：**别五个人同时点组织页**

PGlite 是**单进程**的（PostgreSQL 编译成 WASM，没有连接池、没有 worker 并行）。
请求在服务端是排队执行的，不是并发执行的。所以演示现场会出现两种"看起来像坏了"：

- **五个人同时点组织页 → 后点的那个转圈十几秒**。不是慢，是在排前面四个人的队。
  60 店库上 `/api/org/tree` 单次 0.4 秒，五个并发排到最后一个就是 2 秒量级 ——
  叠加浏览器自己的 6 连接上限，会摸到 10 秒。
- **一个人点开页面后立刻切标签再切回 → 也可能卡一下**。同一个会话的请求仍然要排队。

演示建议（不是代码问题，是使用方式）：

- **组织页一次一个人操作**，其他人看投屏。这是唯一一条硬建议。
- 真要多人同时看，先各自登录好、页面加载完，然后再点 —— 首屏那一下最贵。
- 别在演示中途重启服务。PGlite 起来要跑一遍 `createApp` 的启动核对（日志里会打迁移核对结果），
  那几秒页面是全白的。

## 14. 岗位能不能"改属另一个档口"（走查实测后定的口径）

走查在 2026-07 把「天妇罗师傅」从「天妇罗台」配到了「收银档」，**成功了** ——
因为 `trg_sp_guard` 的"同店同岗唯一归属"带 `sp2.period = NEW.period`，只约束**同一期**。

这是**有意为之，不是漏**。理由按强度排：

1. **禁止就等于禁止重组。** 门店调整分工（7 月起厨师转收银）是真实事件。
   若要求"一个岗位一辈子只能属一个档口"，那重组只能靠**删掉旧编制** ——
   而 `station_position` 是 append-only，历史删不掉；删不掉就只能"另建一个岗位"，
   于是"头灶"在库里变成头灶_1、头灶_2，岗位词表被重组撑爆。
2. **按期约束已经足够防止重复计数。** 到岗是**按期**算的：2026-06 这个岗位只属
   天妇罗台，2026-07 只属收银档。同一期内不会出现"两个档口各算一次"，
   也就是 ST 那套口径要防的事并没有发生。
3. **跨期改属是"可查的"。** 任何一期的 `fn_station_fill` 只显示该期有效的档口与岗位，
   把两期并排看就能看出变化 —— 不需要额外存一列。

### 14.1 明确的取舍：**没有做"7 月起该岗位改属"的页面提示**

要做的话得给 `station_position` 增一列 `moved_from_station_id`（或一张异动表），
并在明细里标一句。**本轮不做**，理由是：
- 它只在"同一个岗位跨期搬家"时才有内容，而那件事在演示数据里没有；
- 更便宜的等价物已经有了 —— 期次选择器换一下就能看见，而这正是"编制按期"的意思。

什么时候该做：客户开始按月对比档口编制、并问"这个岗位怎么跑到别的档口去了"的时候。
届时加的是**展示**，不要改成"禁止跨期"—— 那会把重组堵死（见上面第 1 条）。

#### 14.1.1 走查的保留意见（记录在案，不是被驳回了）

走查认可"允许改属"，但对"不做提示"有保留，理由很具体：
> 演示时若有人翻到 7 月看到「天妇罗师傅 → 收银档」，第一反应是"数据错"，而不是"这是重组"。

这条保留是对的。评审时**"看起来像错的数据"和"真的错的数据"代价一样高** ——
因为它们都要花时间解释。所以把它记在这里，而不是记成"已经决定过、无需再议"。

#### 14.1.2 痕迹已经在库里，不需要加列（实测可查）

`station_position` 是 append-only + 按期的，所以"这个岗位各期属于哪个档口"**现在就能查**：

```sql
SELECT sp.period, st.name AS 档口, sp.headcount
  FROM station_position sp
  JOIN store_station ss ON ss.id = sp.store_station_id
  JOIN station st      ON st.id  = ss.station_id
 WHERE ss.store_id = $1 AND sp.position_id = $2
   AND sp.version = (SELECT max(x.version) FROM station_position x
                      WHERE x.store_station_id = sp.store_station_id
                        AND x.position_id = sp.position_id AND x.period = sp.period)
 ORDER BY sp.period;
```

实测（造一个改属之后）：

```
2026-06  天妇罗台      1
2026-07  前厅服务档    1     ← 改属
2026-11  天妇罗台      1     ← 改回来
```

要批量找"哪些岗位跨期搬过家"：

```sql
SELECT ss.store_id, sp.position_id, count(DISTINCT st.id) AS 档口数,
       array_agg(DISTINCT st.name) AS 档口
  FROM station_position sp
  JOIN store_station ss ON ss.id = sp.store_station_id
  JOIN station st      ON st.id  = ss.station_id
 GROUP BY 1,2 HAVING count(DISTINCT st.id) > 1;
```

所以"没做提示"缺的从来不是**数据**，而是**把这段查法接到页面上**。

#### 14.1.3 已经接到页面上了（走查的一句话推动的）

走查当时提了一个我最初想绕过去的点：

> **能被 API 读到的事实，才算演示里可用的证据；写进文档的 SQL 是"可查"，不是"可答"。**

他说得对，而且戳中了我先前那个"本轮不做"的理由 —— 我说的是"要再走一遍改→灌→重启"，
但**加一个读接口只需要重启，不需要重灌**。理由站不住，就做了。

现在的行为（`/api/org/stations?detail=1`）：

```json
{ "position_code": "T_WOK", "position_name": "头灶",
  "prev_period": "2026-02", "prev_station_name": "打荷档" }
```

- 明细里渲染成：`头灶 1/2 ←2026-02 由打荷档改属`（紫色小字）；
- **只有搬过家的行才有这两个字段**，没搬过的不带 —— 空串会被读成"改属过但不知道从哪来"；
- 一店一次查询（不是一岗一次），只取"最近一个更早的期次"，因为期次可能不连续
  （演示库里只有 06 与 11 两期，"上一期"不能写死成"上个月"）；

`ST19c`（`detail` 不带时连 `positions` 都不返回）。

### 14.2 与"一个岗位能不能同时挂两个档口"的区别

| 问题 | 答案 | 守在哪 |
|---|---|---|
| 同一家店、**同一期**、一个岗位属两个档口 | **不能** | `trg_sp_guard` → `E_SP_CROSS_STATION` |
| 同一家店、**跨期**改属（6 月 A 档、7 月 B 档） | **能** | 不拦 —— 这就是重组 |
| 跨门店（A 店炉灶档、B 店中央厨房档） | **能** | `position` 是集团词表 |

一句话：**约束的是"同一时点的唯一归属"，不是"一辈子"**。
要防的是到岗人数出现两个答案，而"两个答案"只可能发生在同一期。

## 15. 组织页那一栏「缺编」到底拿哪个数比（有下级 vs 叶子）

补了集团/城市编制之后暴露出来的：

```
组织页集团行 → 缺 388     ← 错
组织页城市行 → 缺 148     ← 错
```

根因：`gap = 额度 − **直属**在编`。而集团/城市的额度是**下辖之和**，
直属在编是 0 人 → 差多少编就报缺多少。**两个数都各自算得对，比在一起就错了。**

### 15.1 改法

```
有下级（有启用中的子节点） → gap = 额度 − subtree（含下级）
叶子                       → gap = 额度 − headcount（直属）
```

`subtree` 本身已经包含自己（`sub.path LIKE t.path || '%'` 会命中 t），
所以叶子上这两个数**恒等**，分支只是为了说明"这一行比的是哪个数"。

实测（60 店 / 374 人，把集团与城市额度补成"下辖之和"之后）：

| 节点 | 编制 | 直属 | 含下级 | 缺编 |
|---|---|---|---|---|
| 集团 | 388 | 0 | 374 | **14** |
| 深圳 | 148 | 0 | 142 | 6 |
| 上海 | 120 | 0 | 117 | 3 |
| 义乌 | 19 | 0 | 17 | 2 |
| 南山青泊中心店（叶子） | 8 | 5 | 5 | 3 |

**集团行 14 == 5 家缺岗店之和 14**，城市行也各自等于其下辖门店之和 ——
说明没有"挂在城市直属"的人，三级数字对得上。

按旧口径集团会算成 `388 − 0 = 388`，正是改之前那一屏。

### 15.2 页面上要把"比的是哪个数"写出来

只改数不改标签，读者会拿 `编制 388 − 在编 0` 去对 `缺 14`，然后怀疑整张表。
所以：

- **树卡片**：有下级的节点，第二行的标签从「在编」变成「**直属**」（值不变），
  第三行仍是「含下级 374 · 缺 14」——三个数各有标签，算式就通了。
- **清单**：有下级的行，缺编后面标一个灰字「含下级」，并改了表下的说明。

### 15.3 缺岗用「含下级」、可招用「直属」—— 两个口径相反，而且都对

原来这里写的是「`fn_hc_hireable` 的『已占』是子树口径 —— 那一边本来就对」。
**178 之后这句反了**：`fn_hc_hireable` 的 `used` 已经改成直属。

现在要说清两件事，它们的口径**相反**：

- **缺岗**（组织页那一列）：父节点的额度是「下辖之和」，人数就必须用**含下级**。
  用直属会报成「集团编 388 − 直属 0 = 缺 388」，看着像全公司没人。
- **可招**（`fn_hc_hireable`）：额度**已经扣过下级**（`− 已下分`），人数只能再用**直属**。
  再用子树就是同一批人被扣两次，父节点静默变负（-374），而叶子全是对的
  —— 所以这个 bug 单看门店永远发现不了。

一句话记法：**额度是汇总 → 人数用汇总；额度已扣过下级 → 人数只用直属。**

★ **读代码时的一个坑（知道就行，不要去改 022）**：`022_headcount.sql:137-144` 里还留着
`hireable` 的**旧实现**（第三项是 `fn_hc_used`，子树），它被 178 的 `CREATE OR REPLACE` 覆盖了 ——
从 022 单独读到的仍是错的，以 `178_hc_hireable_direct.sql:36-51` 为准。
**这是本仓"最高号说了算"的机制预期内的代价，不是漏改**：`fn_change_apply` 在 163/169/173、
`fn_att_approver` 在 119/121/177 都是同一个样子，没人回头给旧文件加指针。
而不该去改 022 的理由是硬的——`tools/migrate.mjs:74-79` 对**已应用迁移**的哈希变更会**每次**打
`! 022_headcount.sql：文件已变更（库里的哈希不同）`，于是"某人动过已应用的 schema"这个警报
会长期挂在所有人的 migrate 输出里。要给指针就放在**下一个**碰编制的迁移文件头里。
（另：`022:132` 的注释一直写的是「**自身**已占」，所以那次改的是实现、不是注释——注释是对的，错的是代码。）

断言：`ST18a`（has_kids 标得对）、`ST18b`（有下级按 subtree）、
`ST18c`（★ **这条管缺岗、不管可招**：区域那一行的缺编**不能**改成「编制 − 直属」，
否则直属 0 人会报成"缺 388"——178 改的是 `hireable`，不是这里）、`ST18d`（叶子行为不变）、
`ST18e`（父额度 = Σ子额度 时，父缺口 = Σ子缺口）、
`Z13`（可下分 ≠ 可招：叶子看得见差异，父节点按**直属**占编算）、`Z14`（三层可招 ≥ 0，缺岗店 = 缺口数）。

### 15.4 上级留了「机动编」时，父缺口 ≠ Σ子缺口（不是错）

v5 灌完之后同一晚有两个人都在这儿卡住，卡法还相反 —— 一个把 `396` 当成"编制灌多了"，
一个把 `集团缺 22` 当成"缺岗算错了"。都不是 bug，是**机动编**这个概念没写在文档里。

实测（8788 → `/tmp/xxym-v5`，`period=2026-06`，`/api/org/tree` + `/api/headcount`）：

| 层 | quota | allocated | used | gap | hireable |
|---|---|---|---|---|---|
| 集团 | **396** | 394 | 374 | **22** | **2** |
| 城市（6 个） | 394 | 388 | 374 | 20 | 各 1 |
| 门店（60 个） | **388** | 0 | 374 | **14** | = gap |

三个数的关系：

```
396 = 388（门店编制） + 8（上级管理编）
8   = 6 个城市各留 1  + 集团留 2      ← RESERVE_CITY=1 / RESERVE_GROUP=2
集团缺口 22 = Σ门店缺口 14 + 城市机动 6 + 集团机动 2
```

**★ 机动编不是缺岗。** 缺岗是「有编没人」，机动是「有意空着的编」——
留着给新店开张、给临时顶班、给店长储备。两者在 `gap` 这一个数里被加在了一起，
所以**集团那一行显示 22，其中只有 14 是真空缺**。

- 想只要"真空缺"：看**门店层**的 Σgap（= 14）。演示口径就是这个。
- 想只要"还能招几个"：看 `hireable`（集团 2、城市各 1、门店 = 自己的 gap）。
- **不要把 396 当成 Σ门店编**：398 也不需要凑，388 才是门店那 60 家的编制总和。

**这条对 ST18e 的影响**：那条断言写的是「父额度 = Σ子额度 **时**，父缺口 = Σ子缺口」——
带条件，没错。但集团这层 `396 ≠ Σ城市 394`，条件不成立，此时正确等式要用**一般式**：

```
父缺口 = Σ子缺口 +（父编 − Σ子编）          ← 一般式，任何一层都成立
22     = 20       +（396 − 394）
7      = 6        +（149 − 148）           ← 深圳：那两家各缺 3 的店都在深圳
```

一般式比「Σ子缺 + 未下分编」好用：后者要求人脑先知道"上面留了多少机动"，
而 `(父编 − Σ子编)` 是**从库里能算出来的差值**。

所以谁要拿"父缺 − Σ子缺 = 8"来质疑，答案是：那 8 正是机动编，**不是算错**。

> **★ 这一段我是被纠正过两次才写对的，两个错法都值得记：**
> ① 我在实验库里手工把上级编补成「下辖之和」（388），得到「集团缺 14 == Σ门店缺 14」，
>    然后把 14 当成基准去要别人按它验收。**拿一个自己造的数当基线**，比读错代码更难发现，
>    因为它「看起来验证过了」。判断依据应该始终是**那条等式成立的前提**，
>    不是「上一次实验里恰好得到的数」。
> ② 我把深圳写成 `7 = 3 + 1`。真值是 `6 + 1` —— **那两家各缺 3 的店都在深圳**。
>    错因是拿「一家店缺几个」去凑「一座城缺几个」：分母单位不同，数值看起来却能凑上。
>    这与 §12.6「响应里每个数字的单位」是同一个病，**单位相同、量级不同时最容易被骗**。

## 17. 档口定编「定了就一直用」，以及它带出来的四件事（181 / 182）

| 2026-09（没配） | 0 / 8 / 0，`carried_from=2026-06` | 9 |
| 2026-04（早于最早一期） | 0 / 0 / 8，`quota_status=unset`（`quota` 为 NULL） | 0 |

### 17.2 为什么必须把"沿用"显式标出来

"这个月没配"和"这个月不需要人"在页面上长得一模一样。如果沿用又不标注，用户看到的
就是一个"没核过"的数，而它看起来像"核过了"。所以：

- 每个档口/岗位的编制格下面写 `沿用 2026-06`（一个档口里部分岗位沿用时写"部分沿用"）；
- 汇总行把"未定编 N 个"与"沿用上期 M 个"**并列**，不许合成一个数；
- `stations_unset` 的算法跟着改：原来按 `quota !== null` 数，沿用月会把"忘了配"从计数里抹掉 ——
  那正是这次改动的副作用，不改这一处就等于把新引入的盲区藏起来。

### 17.3 第四个状态 `moved`：不是多余，是防双计

岗位改组后（`prev_period` 那套），**旧档口的那一行不会消失**（append-only）。按
「档口 × 岗位」找"最近一期"，会把已经搬走的岗位在旧档口再编一份 —— 不报错，只让合计凭空变大。
所以沿用的单位是「**门店 × 岗位**」：

- 旧档口的那一格返回 `moved`（有痕迹、但不计入编制）；
- 三数函数里那个岗位**不出现在旧档口**。

把它压成 `unset` 是假话（明明配过），压成 `carried` 是双计。宁可多一个能读懂的态。

### 17.4 两个必须记住的坑

**① 收窄型能力位必须先排除超级角色。** `fn_role_can` 对 `is_super` 恒真（`063:117-121`）。
180 的 `payroll_slips_read_all` 是**放宽**，恒真无害；182 的 `people_station_scope` 是**收窄**，
恒真等于"给从没被授过的超级管理员上锁"。所以 `fn_station_scope` 第一步就显式排 super，
`STS4b` 钉住这一条。**以后任何收窄型能力位都要做这一步。**

**② 幂等与"静默跳过"在 `sys_role` 上是同一行代码。** 182 第一版写
`INSERT INTO sys_role VALUES (18,'station_chef') ON CONFLICT DO NOTHING` ——
角色 id 18 已被 `store_deputy` 占用，那行被**静默吃掉**，症状只有"档口长永远看整店"，零报错。
现在用 19，并加 `DO` 块：id 被占就 `RAISE E_ROLE_ID_TAKEN`。
**"幂等"是为了能重复执行，不是为了把冲突藏起来。**

### 17.5 演示须知：不要现场授位

演示库（`/tmp/xxym-v5`）里每个档口只配了 1 个岗位、1 个人，所以给某账号授了
`people_station_scope` 之后，花名册会从"整店 11 人"变成 **1 人**（店 3 炉灶档实测：
到岗 1、闸后 1，两个数一致）。这**不是越权也不是 bug**，是演示数据配不齐 ——
但现场被问到时很难解释。所以演示时**不现场授位**；说准确一点：**182 建的 `station_chef` 角色自带这个位**，只是这批演示账号里没有那个角色，所以今天谁登录都不受影响。真要演示，用**已有多人的档口**（店 3「前厅服务档」2 人、店 5「洗碗保洁档」2 人），别用只有 1 人的炉灶档。

### 17.6 门店编也沿用（183）—— 但安全阀换成了 `status`

用户看完 §17.1–17.5 后追加了一句：「**门店编也沿用，但要标出来**」。落地在 `183_hc_quota_carry.sql`。

**为什么这次比 181 危险**：`fn_hc_quota` 不是展示字段。它进 `fn_hc_allocated`（已下分）、
`fn_hc_available`（可下分）、`fn_hc_hireable`（可招）、`fn_hc_over` / `uncovered` / `slack`，
还进编制下达与招聘校验。181 改的是"档口这一层"，183 改的是**所有层**。

**做法与 181 同构，且只有一处实现**：

```
fn_hc_quota_effective(org, period)   ← 唯一实现，给 status / quota / period / carried_from
fn_hc_quota(org, period)             ← 改成读它（签名与返回类型不变，仍是 int）
allocated / available / hireable / over / uncovered / slack   ← 一行不改，自动跟着走
```

**三态**（沿用单位是组织节点，没有 181 的 `moved`）：

| status | 含义 | quota |
|---|---|---|
| `set` | 本期定过编 | 本期值 |
| `carried` | 本期没定，沿用 `< 本期` 的**最近一期** | 那一期的值 |
| `unset` | 从来没有定过 | **NULL**（不是 0） |

实测（8788 / `on=…` 走 `/api/org/tree`，`period=` 走 `/api/headcount`）：

```
on=2026-06-15  集团 396  status=set      gap 22
on=2026-09-15  集团 396  status=carried  carried_from=2026-06   gap 22
on=2027-02-15  集团 396  status=carried  carried_from=2026-11   gap 22   ← 取最近一期，不是最早一期
```

**安全阀是 `status`，不是沿用本身。** 沿用生效后，"这一期根本没定编"就再也无法从数字上看出来
—— 它和"定过、数与上期相同"完全一样。所以：

- `/api/org/tree` 每条 row 带 `quota_status` / `quota_carried_from`；`/api/headcount` 同样；
- 前端额度格里写成 `396 沿用 2026-06`；
- **谁把这两个字段从响应里删掉，这个改动就变成"静默把上期预算当成这期预算"**，比不改更坏。

**一条必须守住的边界**：沿用只在该节点**有过更早一期**的编制时发生。新开的店从没定过 →
仍是 `unset` + NULL（`Z16` 钉住：`status=unset quota=null fn_hc_quota=null hireable=0`）。
否则"没预算"会被永久掩盖，而那正是 `022` 全篇在防的那类"看起来正常"。

**一个必须说清的行为变化（有意为之）**：编制下达与招聘校验从此对"未来月份"有数了 ——
7 月没定编时，可招 = 沿用 6 月的额度 − 已下分 − 直属已占。这是"定了就一直用"的直接后果，
但它也意味着**"这月没批预算"不再自动等于"招不了人"**。所以上面那个状态字段是这段语义的唯一出口。

判据：`Z15`（三层的 `carried_from` 各不相同 —— 集团 2026-03、华南/F店 2026-01，证明取的是"最近更早"）、
`Z16`（从未定编 → unset + NULL）、`Z17`（沿用后可下分 == 编 − 已分，集团 500−30=470、华南 20−20=0；
若谁把 `fn_hc_quota` 改回精确匹配，这一条立刻红）。

### 17.7 一个只在凌晨出现的 403：授权的"生效日"用了两种"今天"

这条不是档口的事，但它是在做 182 的验收时被抓出来的，记在这里免得下次从头查。

**现象**：`test/station-scope.mjs` 在 00:55 跑，档口长账号访问花名册/考勤/排班全是 `403`，
`fn_role_can(user,'employee_roster','read')` 返回 false —— 而角色、授权行、资源码**全都对**。

**根因**：两个"今天"不是同一天。

```
app_today()  业务日（客户时区，Asia/Shanghai）   00:55 CST → 2026-11-16
sys_today()  系统日（固定 UTC，082 定的口径）     00:55 CST → 2026-11-15
```

授权判定 `fn_role_can` 用的是 `sys_today()`（082 的依据很硬：授权是系统动作，不该随业务时区变），
而 `tools/assign-roles.mjs` 写 `effective_from` 用的是 `app_today()`（业务日）。
于是**凌晨 00:00–08:00 这 8 小时里**新授的权落在"明天"：

```
daterange(2026-11-16, NULL, '[)') @> 2026-11-15  =  false   →  "这条授权明天才生效"
```

**为什么难查**：谁都没改权限；只有那个时间窗口内新写的授权会失效，过了 08:00 自己就好了 ——
表现成"偶发"，而且用户会描述成"系统时好时坏"。

**改法**（对齐 082 的口径，不动判定函数）：写侧改成 `sys_today()`。
`tools/assign-roles.mjs` 与测试夹具都改了；`fn_role_can` 一行没动。
判据 `PM11`：`sys_today()` 授的立刻生效、`sys_today()+1` 的不生效；
窗口内用 `app_today()` 授的必须不生效（窗口外两种写法等价 —— 所以这条断言不能写死 true，
否则它会随跑测试的时刻变红变绿，而"随时辰变红的断言"最后一定会被改成 `|| true`）。
