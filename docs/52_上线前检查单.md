# 52. 上线前检查单

> 这份单子只有在一种情况下有用：**你真的照着做了一遍**。
> 它不是"注意事项"，是一串能打勾的动作，每一条都写清了**不做会以什么形式暴露**。
>
> 写给谁：把这套系统从"演示机"交到"客户每天在用"这条路上的人。
> 演示机出错是丢面子；上线后出错是**钱算错了、工资条发给了不该看的人**。
> 这两件事的失败形态不一样，所以检查项也不一样。

**证据等级**（本仓的规矩：跑过的才敢说，没跑过的必须标出来）

| 标记 | 含义 |
|---|---|
| 【实测】 | 2026-11-16 在本机跑过，输出抄在下面（含时间与进程号） |
| 【读码】 | 只读了实现，没跑 —— 并写清为什么跑不了 |
| 【未验】 | 本机做不了（缺 PostgreSQL / 缺 launchctl 权限 / 缺第二台机器） |

> ★ 一条总则：**"服务起来了"不叫上线，"能回滚"才叫上线。**
> 下面 8 项里，只有第 2 项（备份恢复）和第 5 项（迁移前滚）是"出事时救命的"，
> 它们也是唯一两项**必须演练一遍**的。其余是防止出事。

## 0. 一页速查（8 个勾）

| # | 事项 | 一句判据 | 不做的后果 |
|---|---|---|---|
| 1 | 数据库形态选定了 | PGlite 单机 / 真 PostgreSQL 多人，二者选一且写在交接文档里 | 上线后第一次并发就排队，被当成"系统慢" |

## 1. 数据库形态：PGlite 还是真 PostgreSQL

**这是唯一一个"改起来最贵"的决定，所以先定它。**

| | PGlite（当前） | 真 PostgreSQL（未验证） |
|---|---|---|
| 形态 | 数据库跑在 Node 进程里，一个目录一条连接 | 独立服务端 + 连接池 |
| 并发 | **所有请求排队**（一次一人操作最顺） | 真并发 |
| 备份 | **必须停服**（或对副本做） | `pg_dump` 可热备 |
| 多副本 | 不可能（一个目录只能一个进程） | 可以 |
| 适合 | 单机演示、一台机器上一个人算薪 | 多人同时用、需要 7×24 |

```bash
# 你今天用的是什么（看有没有被设）
grep -E "PGLITE_DATA_DIR|DATABASE_URL" ~/Library/LaunchAgents/com.aihr.demo.plist 2>/dev/null \
  || lsof -nP -iTCP:8899 -sTCP:LISTEN
```

### 怎么切到真 PostgreSQL

```bash
# 0) 先有一个 PG 实例（本机没有 —— 没 brew / 没 docker / 没 postgres，见 §9）
createdb aihr

# 1) 建表：**用迁移工具，不要让服务顺手建**
DATABASE_URL=postgres://127.0.0.1:5432/aihr node tools/migrate.mjs --dry-run   # 先看它会跑哪些
DATABASE_URL=postgres://127.0.0.1:5432/aihr node tools/migrate.mjs             # 再真跑

# 2) 起服务（DATABASE_URL 在，PGLITE_DATA_DIR 就不起作用）
DATABASE_URL=postgres://127.0.0.1:5432/aihr PORT=8899 HOST=127.0.0.1 node app/server.mjs
```

**这条路本机未验证，必须写出来。** 具体缺三样：

1. **一个 PG 实例**。本机 `brew` / `docker` / `postgres` 都没有（§9 有实测）。
2. **一个可回滚的测试库**。切库的第一次一定跑不对（`schema_migration` 账本、`legacy_up_to=072`
   的判据、`app_init_session()` 在每条新连接上重灌权限 —— 这三处都只在真连接池下才暴露）。
   没有一个能一把删掉重建的库，就没有第二次尝试。
3. **契约测试要真的跑在 PG 上**：`test/db-contract.test.mjs` 的 D1–D5 定义了池化驱动必须满足什么
   （D1 = 慢事务失败不能带走别人的写入；AE5 = 池里新开的连接必须重灌临时表权限）。
   它现在只在 PGlite 上跑过。

> **`pg` 这个包是 optionalDependency**，本机 `node_modules/pg` 存在（【实测】）。
> 也就是说 `DATABASE_URL` 这条路的**代码路径是通的**，没验的是"它连上真 PG 之后对不对"。
> 这两件事差得很远，别混着说。

**不做的后果**：选 PGlite 却按"多人同时用"上线 —— 现场五个人同时点组织页，
最后一个等前四个跑完（60 店单次 0.4s，五个叠到 2s 量级），用户看到的是"这系统真卡"，
而监控上一切正常（CPU、内存都平的）。

## 2. 备份与恢复

### 2.1 现在有两条产物，用途不同，都要有

| 产物 | 命令 | 体积【实测】 | 用途 |
|---|---|---|---|
| 逻辑（有清单、有 sha256） | `PGLITE_DATA_DIR=<副本> node tools/backup.mjs --out <目录>` | **11.8 MB** `.tar.gz` + `.json` | 归档到异地、能逐表核对 |
| 物理（整目录） | `node tools/backup-cron.mjs --dir <副本> --out <目录>` | **67.4 MB** / 1752 个文件 | 出事直接换目录，最快回滚 |

逻辑备份的清单里记着：表数、业务函数数、14 张关键表行数、sha256。
恢复时 `restore.mjs` **先比 sha256、再比清单**，对不上就失败，不做"尽力恢复"。

### 2.2 运行中**不能**直接 cp（这是本节最重要的一条）

PGlite 把库跑在进程里，**一个目录同一时刻只能有一个写者**。运行中 `cp -R` 得到的是一份
**可能撕裂**的库 —— 而撕裂的库通常还能打开、还能查，只是少了一些行。这种"备份"比没有更贵。

两个工具现在都会拒绝（【实测】）：

```
$ node tools/backup.mjs                # PGLITE_DATA_DIR=/tmp/xxym-v5
E_DB_IN_USE: 库正被服务占用（PID 54606，端口 8899）。PGlite 单进程独占，
运行中打开会与服务互相覆盖 —— 要么先停服务，要么对副本备份

$ node tools/backup-cron.mjs --dir /tmp/xxym-v5 --out /tmp/bk
库正被服务占用（PID 54606，8899），拒绝备份（加 --allow-copy 也没用）。
```

> ★ 顺带一条踩过的坑：**沙箱里 `lsof -p <别人的 pid>` 会返回空**（exit 1、无输出、无报错），
> 于是"看不见占用"会被读成"没有占用"。所以 `backup-cron.mjs` 的闸门是**两层**：
> 先看 8899 有没有人监听（粗、可靠），再看谁开着这个目录（细、可能看不见）。
> 只有你显式写 `--allow-copy`（意思：我确认 --dir 是副本）才会越过第一层。

### 2.3 备份 → 恢复，必须演练一次

```bash
cd ~/ty-hr/code
# ① 停服（PGlite 单写者）—— 上线形态下这一步就是停机窗口
launchctl bootout gui/$(id -u)/com.aihr.demo     # 或 kill <pid>，确认 lsof 已无输出

# ② 备份
node tools/backup-cron.mjs --dir /tmp/xxym-v5                  # 物理
PGLITE_DATA_DIR=/tmp/xxym-v5 node tools/backup.mjs --out ~/bk  # 逻辑

# ③ 恢复到**另一个目录**（绝对不要就地覆盖）
node tools/restore.mjs --file ~/bk/aihr-<stamp>.tar.gz --to /tmp/aihr-restored

# ④ 查得出业务数据才算恢复成功（不是"文件在"）
PGLITE_DATA_DIR=/tmp/aihr-restored node -e '
  const { PGlite } = await import("@electric-sql/pglite");
  const db = await PGlite.create({ dataDir: process.env.PGLITE_DATA_DIR });
  const r = (await db.query(`SELECT r.id, r.period, count(p.id)::int slips,
                                    round(sum(p.gross_amount),2)::text gross
                               FROM pay_run r JOIN payslip p ON p.pay_run_id=r.id
                              GROUP BY 1,2 ORDER BY 1`)).rows;
  console.log(r); await db.close();'

# ⑤ 收拾干净：临时目录必须删（里面是真实薪酬数据）
rm -rf /tmp/aihr-restored
```

**2026-11-16 04:02 的那次演练（【实测】，源是 `/tmp/xxym-v5` 的副本）**

| 步骤 | 结果 |
|---|---|
| 逻辑备份 | `aihr-20261116T040235.tar.gz` · **11.8 MB** · sha256 `20e043d93b7f…` |
| 清单 | 表 168 · 业务函数 424 · person=374 payslip=1122 attendance=2724 |
| `restore.mjs --to /tmp/aihr-restored` | 校验和/清单**全部对上**，落盘 67 MB，PG_VERSION=18 |
| 只读查询 | 三期各 374 张工资条、应发各 `2,644,512.00`、组织 67 节点、净发合计 `6,467,894.80` |
| 物理备份 | `20261116T040454/data` · 67.4 MB / 1752 文件 · 副本打开核对 168 表 424 函数 |
| 物理恢复 | `cp -R` 回临时目录后同样查得出三期工资（证明"换目录"这条退路是通的） |

### 2.4 RPO 是多少（必须说清，因为现在很短）

| 备份方式 | RPO | 说明 |
|---|---|---|
| 手工（现在的做法） | **未知** —— 等于"上次想起来备份到现在" | 这是最危险的答案：没人能回答 |
| 定时 `backup-cron.mjs` 每天 03:30 | **≤ 24 小时**，且**要求那个窗口里服务是停的** | 服务常驻，所以它**必然**在 03:30 被拒（这是设计，不是 bug） |
| 真 PostgreSQL + `pg_dump` | ≤ 备份间隔（可热备，不需要停机窗口） | 【未验】本机没有 PG |

> 一句话结论：**在当前形态下，"能自动跑"和"不停服"是互斥的。**
> 想要每天自动备份又不停机，只有换真 PG 一条路；否则就要接受"每天有一个停机窗口"，
> 或者接受 RPO 是"上次手工备份"。

**不做的后果**：迁移写错了、有人 UPDATE 了一整列、卷坏了 —— 这三种都不是"重启能好"的，
没有一份能恢复的备份，就只能重灌演示数据，而客户真实的算薪记录没了。

## 3. 访问与 TLS

三种入口，**选一种并写进交接文档**（详细配置见 `docs/50` §3–§4）：

| 入口 | 怎么起 | 谁能访问 | TLS |
|---|---|---|---|
| 本机 | `HOST=127.0.0.1` | 只有这台机器 | 无（回环，可接受） |
| 局域网 | `HOST=0.0.0.0` ← **当前 launchd 就是这么配的** | 同网段任何人 | **无**：口令和 token 明文可抓 |
| 反代 HTTPS | 反代在前面，服务仍 `HOST=127.0.0.1` | 按反代策略 | 有 |

```bash
# 当前监听在哪
lsof -nP -iTCP:8899 -sTCP:LISTEN          # *:8899 = 0.0.0.0；127.0.0.1:8899 = 只本机
ipconfig getifaddr en0                    # 局域网 IP，别人访问 http://<这个IP>:8899
```

反代四条硬要求（少一条就出问题）：

| 要求 | 为什么 | 怎么验 |
|---|---|---|
| 转发 `Authorization` 头 | 会话 token 在这个头里；有的网关静默丢掉它 | `curl -H "Authorization: Bearer $TOK" https://<域名>/api/me` 不是 401 |
| 读超时 ≥ 60s | 组织页正常 0.4s，冷启动/排队会到秒级；20s 超时会被读成"服务挂了" | 反代配置里 `proxy_read_timeout` / Caddy 无默认超时 |
| 服务侧 `TRUST_PROXY=1` | 不设的话限流把**所有人**算在代理那一个 IP 上 | 见 §4 的"按来源"判据 |
| 只暴露一个入口 | 别把数据目录、`/tmp` 另开端口 | `lsof -nP -iTCP -sTCP:LISTEN \| grep node` 只有 8899 |

> ★ `TRUST_PROXY=1` 是"代理确实会覆盖 `X-Forwarded-For`"才打开。
> 打开而代理不覆盖 = **让攻击者自己选来源**，比不做更坏。

**不做的后果**：局域网入口没有 TLS 却当成"内部系统够安全" —— 同网段任何人
`tcpdump` 就能拿到 HR 的会话 token，而 token 能看全集团工资条。

## 4. 登录限流：30 次 / 15 分钟，按来源计

| 事实 | 判据 |
|---|---|
| 同一来源失败 30 次锁 15 分钟 | 【实测】`fn_policy_effective('RATE_LOGIN_FAIL_PER_15M',1,current_date)` → `30` |
| **按来源 IP 计，成功不清零** | 设计如此：清零的话攻击者用自己的账号登一次就能继续试别人 |
| **刷新页面会续锁** | `index.html` 每次加载都自动 `login(1)`；user 1 登不上时刷新 = 把锁续上 |
| 别做自动重试 | 重试只会延长窗口（实测，不是推理） |

```bash
# 现在生效的阈值（只读）
PGLITE_DATA_DIR=<库> node -e '
  const { PGlite } = await import("@electric-sql/pglite");
  const db = await PGlite.create({ dataDir: process.env.PGLITE_DATA_DIR });
  console.log((await db.query("SELECT value_num FROM fn_policy_effective(\x27RATE_LOGIN_FAIL_PER_15M\x27,1,current_date)")).rows);
  await db.close();'

# 演示机临时放宽到 200（【实测】在副本上跑过；**上线形态不要放宽**）
INSERT INTO policy_value(policy_code, effective_from, value_num, published_by, reason)
VALUES ('RATE_LOGIN_FAIL_PER_15M', current_date, 200, 'group_hr', '演示机临时放宽，记得改回')
ON CONFLICT (policy_code, effective_from) DO UPDATE SET value_num = 200;
```

现场处置顺序（从便宜到贵）见 `docs/50 §5.5`：等 15 分钟 → 换账号 `/?u=2&pwd=demo1234`
→ 调阈值 → 清 `login_attempt`（**必须先停服**，单写者）。

**不做的后果**：上线当天十个同事同时试错口令，整个出口 IP 被锁，所有人的登录都 429 ——
而错误信息看起来像"密码错"，于是大家继续试，锁得更久。

## 5. 迁移前滚：只对账，绝不自动追平

```bash
# ① 对账（只读，绝不写库）
PGLITE_DATA_DIR=<库> node tools/migrate-status.mjs
#    退出码 0 = 没有反证；1 = 有"无迹象"；2 = 对不了账（库被占/路径不对/没 lsof）

# ② 前滚：先备份、一个号一个事务、必须显式写号
PGLITE_DATA_DIR=<库> node tools/migrate-apply.mjs --only 186 --dry-run   # 先看
PGLITE_DATA_DIR=<库> node tools/migrate-apply.mjs --only 186             # 再跑
```

**2026-11-16 12:00 与 12:20，对 `/tmp/xxym-v5` 的副本各对账一次（【实测】）**

```
12:00  可确认生效 10 条 / 无迹象 1 条 / 无法判定 175 条
       186 | 无迹象 | 签收表与 append-only 触发器都在，且 v_payslip_ack_progress 视图存在

12:20  可确认生效 11 条 / 无迹象 0 条 / 无法判定 175 条
       186 | 有迹象 | 签收表与 append-only 触发器都在，且 v_payslip_ack_progress 视图存在
```

两次之间线上库从 168 张表变成 169 张 —— 差的正好是 `186` 建的 `payslip_ack`。
**这不是工具出错，这是一个活的例子**：今天有人在 12:00 到 12:20 之间把 186 补到了库里。
它说明两件事：

1. `无迹象` 是**当时那一刻**的结论，过期就失效。**发布前重跑，别引用别人昨天的绿。**
2. "代码走在前、库跟在后面"在这个仓里是常态（今天一个上午就发生了两次），
   所以对账不是发布会前的仪式，是每次改完都要跑的一条命令。

**为什么绝不自动追平**（`docs/48 §13.6`）：这个库从来没有 `schema_migration` 账本，
"缺哪几条"只能靠指纹推；猜错就把旧库**永久钉成最新** —— 错误的账本比没有账本更危险
（没有账本时人还会怀疑，有了错账本连怀疑都不会有）。启动时只**警告**，不做动作。

> `migrate-apply.mjs` 会先把整目录复制一份 `<dataDir>.bak-<本地时间>` 再动库，
> 所以它的"回滚"就是停服 + 把 `.bak-` 换回去。

**不做的后果**：`npm` 装了新代码、重启了服务，库里少一条迁移 —— 表现是
`column xxx does not exist` 或某个功能静默不生效，而重启永远修不好它。

## 6. 监控：两个探针，**现在没人看**

| 端点 | 证明什么 | 判据 |
|---|---|---|
| `/livez` | 进程还在、事件循环没卡住（**不查库**，库挂了不该重启进程） | 200 + `{"ok":true,"uptime_s":…}` |
| `/readyz` | 能干活（真查一次库） | 200 + `db_ms`；库查不动 → **503** |

两者都**免认证**（K8s/Docker 的探针不会带 token；要凭据的探针等于永远 unhealthy，
于是会被删掉，然后服务挂了没人知道）。响应体只回三个数，不回表名/版本 —— 它是最容易被扫的地址。

```bash
# 人肉版（上线前 5 分钟就用这个）
for p in livez readyz; do
  printf "%-7s " "$p"; curl -s -o /dev/null -w "%{http_code} %{time_total}s\n" http://127.0.0.1:8899/$p
done
```

**接法一：launchd（本机，每 60 秒一次）【未验 —— 装不了 launchctl】**

```xml
<key>StartInterval</key><integer>60</integer>
<key>ProgramArguments</key>
<array>
  <string>/bin/sh</string><string>-c</string>
  <string>curl -sf --max-time 5 http://127.0.0.1:8899/readyz >> "$HOME/Library/Application Support/aihr-demo/logs/probe.log" 2>&1 || echo "$(date -u +%FT%TZ) readyz FAIL" >> "$HOME/Library/Application Support/aihr-demo/logs/probe.log"</string>
</array>
```

**接法二：systemd timer（Linux，等价物）【未验 —— 本机没有 systemd】**

```ini
# aihr-probe.service
[Service]
Type=oneshot
ExecStart=/bin/sh -c 'curl -sf --max-time 5 http://127.0.0.1:8899/readyz >/dev/null || logger -t aihr "readyz FAIL"'
# aihr-probe.timer
[Timer]
OnBootSec=1min
OnUnitActiveSec=1min
```

**现在的实况**：`KeepAlive` 只会在进程**退出**时重拉它。
如果进程活着但每条查询都慢 1000 倍（`docs/48 §13.6` 那个计划缓存坑），
或者端口被别的进程抢走、应用自己以 0 退出（`SuccessfulExit=false` 时不重拉）——
**没有任何人会知道，直到有人来问"系统怎么打不开"**。

**不做的后果**：凌晨 3 点挂了，早上 9 点客户上班才发现；而你手上没有 3 点到 9 点之间的任何数据。

> 现在 `people_station_scope` 授给了 `station_chef`，于是档口长看到的是**自己档口的人**
> （演示库里每个档口只配 1 个岗 1 个人 → 花名册从"整店 11 人"变成 **1 人**）。
> `docs/50 §6.3` 写的是"别现场授予"，但库里**已经授了**。

> ① 承认它是产品行为，演示时主动解释；
> ② 收回（`DELETE FROM sys_role_resource WHERE resource_code='people_station_scope'`，**先停服**）；
> ③ 承认它但把演示库的档口编制补齐（否则客户看到"档口长只有 1 个下属"）。

## 10. 我认为上线最大的三个风险（按严重度）

### ① 备份"有"但没在正确时刻产生 —— 撕裂的库

- **暴露形式**：出事那天 restore 成功、服务也起来了，只有**某几天的考勤/工资条少了行**。
  没有报错、没有告警，是财务对不上账时才发现的。
- **为什么最容易发生**：PGlite 是单写者，而备份脚本最自然的写法就是 `cp -R`；
  服务是常驻的，所以"运行中 cp"是默认路径，"停服再备"才是要额外努力的那条。
- **判据**：`node tools/backup-cron.mjs` 在服务运行时**必须**拒绝（现在会）。
  但注意：你如果养成"加 `--allow-copy` 就过了"的习惯，这道闸就白设了。

### ② 迁移/配置"代码走在前，库跟在后面"

- **暴露形式**：重启后某个功能静默不生效，或 `column does not exist`；
  更要命的是**迁移跑了一半**（建了表没建触发器、建了触发器没建函数）——
  这种状态比"完全没跑"更危险，因为一半的闸看起来是通的。
- **为什么最容易发生**：这个库**没有迁移账本**，启动只警告不追平（这是对的），
  于是"谁在什么时候对哪个库跑了哪几条"全靠人记。今天上午就演了一次：
  12:00 的副本上 `186 无迹象`，12:20 再对一次 `186 有迹象` —— 二十分钟里库的位置变了一次。
- **判据**：发布前 `migrate-status` 必须**没有"无迹象"**；有就人工看，别自动追。

### ③ 权限闸"在"但口径不对 —— 不报错的那种错

- **暴露形式**：老板点了算薪没被拒（或者被拒的理由是"已封账"而权限其实没拦）；
  档口长花名册只有 1 人；员工能看到同事工资条。**全都是 200，全都看起来正常。**
- **为什么最容易发生**：`fn_role_can` 对超级角色恒真、`CROSS JOIN` 授全资源、
  收窄型能力位忘了排除 super —— 每一处都是"多给了"而不是"少给了"，
  而"多给了"不会触发任何断言，除非有人专门写一条。
- **判据**：§7 那四条 SQL 跑一遍，并且**把实测值抄进交接文档**；
  特别是 182 现在是**开着的**（授给了 `station_chef`），与 `docs/50 §6.3` 的说法相反，
  上线前必须有人拍板。
