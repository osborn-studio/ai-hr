# 46 · 考试与绩效的四层

> 156 / 157（考试）、158 / 159（绩效）合起来是一件事：把「分」从一个人填的数字，变成一条能回答
> "谁给的、怎么算的、改过没有、错在哪"的记录。本文只写**为什么这么设计**与**不这么做会怎样**。

## 1 一句话结论

| 层 | 迁移 | 堵住的洞（客户原话的形状） |
|---|---|---|
| 限时 / 限次 | `156_exam_limit.sql` | 「不及格就一直重考，考到蒙过」「一道题想多久想多久」——这张成绩是要报监管的 |
| 任务层 / 错题 / 分段 / 切屏 | `157_exam_task.sql` | 「A 店本周考、B 店下周考怎么办」「考完不知道自己错哪」「及格率 60% 是题难还是有人不会」「切屏 3 次是哪 3 次」 |
| 评分人 / 改分台账 / 0 人档 | `158_perf_scorer.sql` | 「这个分是谁给的」「78 改成 88，78 去哪了」「A 档一个人都没有，是没人还是方案没这档」 |
| 指标库 / 权重 / 折分 / 汇总 | `159_perf_metric.sql` | 「92 分是哪项拖的腿」——只给一个总分，最后一定变成店长凭印象填数 |

## 2 考试

### 2.1 限时与限次

**超时只记不拦。** 酷学院那套是「倒计时 + 超时自动判 0」。我们照做倒计时与截止时刻，**唯独不判 0**：
超时仍判分、仍算一次机会，只把 `late_seconds` 记下来（`fn_exam_attempt_stamp_late`）。
不这么做：网断在最后 30 秒、人被叫去前厅、手机没电——全部变成「判 0 → 申诉 → HR 手工改分」，
而**改分口子一开，这张卷就不能拿去报监管了**。超时的本质是「时限到了」，不是「作弊」；
判据留给能负责的人（店长看一眼 `late_seconds` 决定认不认），不留给定时器。

**限次只数已交卷的。** `fn_exam_attempt_prepare` 数次数时带 `submitted_at IS NOT NULL`（`156:83`）。
不这么做：点开卷子、断线、重进 → 吃掉一次机会；`max_attempts=1` 的卷连开两次就再也考不了，
而他一道题都没答。147 已保证「同人同卷未交卷最多 1 份」，两个约束合起来才不会攒出 10 份没交的卷。
还剩几次必须**开考之前**就能查（`fn_exam_ledger`）：让人答完一整张 100 分的卷才被告知「没机会了」，
比一开始不让他考更糟。

### 2.2 任务层与时间窗

**任务层是可选的。** `exam_task` 是「题库 → 试题 → 试卷 → **考试任务**」的最后一层（卷 + 给谁 +
什么时间窗），但 `fn_exam_task_check` 第一句是 `IF v_n = 0 THEN RETURN`（`157:209`）：
**这张卷没有任何任务 → 放行**。不这么做：升级当天，147 时代直接挂课程的卷与全部存量答卷一起变成
「不在时间窗内」，而升级窗口正是最不能停摆的时候。加一层批次，不等于「以后每张卷都要先建任务」。

组织匹配认 `attendance_org` 与 `cost_org` **两个维度**（`157:177`）：真实客户有的门店挂成本组织、
有的挂考勤组织，只认一个会让一半门店「没有待考任务」。`is_required` 只影响排序与提示、
**不改变能不能考**——把非必考锁死，「想补学的人」就考不了。

**时间窗闸在 BEFORE INSERT，不在服务层。** `fn_exam_attempt_prepare` 在开考那一刻
`PERFORM fn_exam_task_check(...)`（`157:487`），是 156 那个函数的**原文照抄 + 一处新增**。
不这么做：闸做成「请调用方记得调」的函数就等于没闸——新写一个接口、或直接在 psql 里插一行
`exam_attempt`，就发出一份窗口外的卷，而它的分数与正常卷在表里完全同形。
147 的原则是「分数由库算」，时间窗是同一条原则的另一半。`EXAMT1` 验的就是这条。

### 2.3 错题回顾与成绩分段

**交卷前不给、交卷后给，是两件事。** `fn_exam_review` 见 `submitted_at IS NULL` 就抛
`E_EXAM_NOT_SUBMITTED`（`157:266`），它是除 `fn_exam_submit` 之外**唯一**下发
`exam_question.answer` 的入口。两个方向都是事故：交卷前给 → 一屏带正确答案，等于把卷子送出去，
147 的下发防作弊全部作废；交卷后也不给（147 的原始状态）→ 考完不知道错哪，这张卷只剩「卡人」。
同一份数据靠 `submitted_at` 一个判据分成两个时刻，所以它只能是「错题回顾」，不能是「成绩单」。

**分段固定 6 行。** `fn_exam_stat` 用 `VALUES` 写死 6 个桶（all + 90-100 / 80-89 / 70-79 / 60-69 /
<60）再 `LEFT JOIN`（`157:346`），**0 人的段也出行**，`pass_rate` 为 NULL。不这么做：从结果表
`GROUP BY` 出发，方案 5 段只用到 3 段就只出 3 行，「这段没人」与「这段没查」长得一模一样——
店长不会去猜，他会以为系统漏了人。三条口径写死：一人一行取**最高分**（补考过了就是过了，
「后来又考了低分所以变回没通过」不是真事）；`pass_rate` 分母是**已交卷人数**（算上没交就变成考勤率，
那是 `fn_exam_missing` 的活）；分段按**原始分**不归一化（卷面 120 分时「85」与及格线不在同一刻度，
归一化后店长会问「按哪个数」）。

### 2.4 切屏证据

`exam_cheat_log` 存**时间点**，不存「切屏 3 次」（`157:518`）：时间由库端 `clock_timestamp()` 给——
收客户端时间就能伪造「我当时没切屏」，而这条记录的全部价值就是「几点几分」；用 `clock_timestamp()`
而非 `now()`，否则同一事务连记三条得到三个相同时刻，「切了三次」与「切了一次」分不开。
写入后**不许改、不许删**（`E_EXAM_CHEAT_APPEND_ONLY`）：证据能改等于没有证据，要更正就再记一条。
已交卷的答卷**不许补记**（`E_EXAM_SUBMITTED`）：交卷后加三条切屏等于事后栽赃，而它与当时真记的
三条在表里同形。`fn_exam_flagged` 按**答卷**聚合不按人（`157:634`）：两次考试要能分开看，
否则第二次的清白会被第一次的记录带累。

## 3 绩效

### 3.1 评分人与改分台账

**为什么必须有 `scored_by`。** 051 的 `fn_perf_score` 收了 `p_by`，函数体里一次都没用（`158:10`）。
于是答不出「这个分是谁给的」，改分后也答不出「上一版是谁给的」——上一版根本不存在。
绩效分要拿去定系数、定钱，**必须有签字的人**。`fn_pr_scorer_required` 三条规则：改分只能从入口
进来（会话标记 `aihr.perf_scoring`）——只判「两列非空」不够，直接 `UPDATE` 会**继承旧值**，
台账上变成「上一个人又改了一次」，那是数据库自己伪造的签名；只写一半 = 拒（说不出什么时候的签字
没有意义）；INSERT 两列全空 = 放行（026 种子与历史导入是直接插行，一律非空会让建库就炸），
代价是那些行 `scored_by` 明确为 NULL，`kpi.unsigned` 把它们数出来，**不编名字把它做成 0**。

**改分不拦，但必留痕；台账由触发器写。** `perf_result_log` 由 `trg_pr_log`（BEFORE UPDATE）自动写，
服务层一行代码都没有。不这么做：服务层写日志意味着「绕过服务层就没有日志」，而绩效分恰恰是最想
被绕过的数——封存前的最后一天、发钱前的最后一个人；放进触发器，`psql` 也躲不开。为什么不拦改分：
026 已把「封存后不许改」做成硬拦（钱发出去之后的事），封存前的改分是正常流程（复核、校准会），
拦了只会让人绕开系统；要拦的是「改了没人知道」，不是「改了」。几个细节：`UNIQUE(cycle_id,
employee_id, version)` 保证「改过 N 次」不会有两个答案；`changed_count`（数台账）与 `version`
（触发器加）**两个独立来源**，不相等本身就是信息；`changed_by` 兜底到 `current_user`，报表上看到
`postgres` 就等于「这一版不是从入口改的」。`trg_pr_frozen` 字母序在前，封存后的改分先在 026 被拒，
**不会留下一条「改了但没生效」的台账**。

### 3.2 权重与折分

**权重合计在存的时候校验。** `fn_perf_item_set` 第一遍全部校验、累加，`abs(sum-1) > 0.001` 抛
`E_PERF_WEIGHT_SUM`，**一行不删、一行不写**（`159:256`）。不这么做：等到汇总才发现加起来 0.95，
那时已经有人按「评过了」在沟通、在谈心、甚至口头承诺了系数。同一理由带出另两条：
`E_PERF_DUP_METRIC`（同一指标两行各 0.2，汇总时权重悄悄翻倍）、`E_PERF_ITEMS_IN_USE`
（已被打分引用的方案拒绝整方案覆盖，因为先删后插会让明细指向不存在的项，或悄悄改掉已评过那批人的口径）。

**三个折分口径，各防一件事。** `fn_perf_item_score` 是唯一算单项得分的地方，别处不许再算一遍：

| 口径 | 公式 | 防的是什么 |
|---|---|---|
| `up` | `LEAST(actual/target, 1.5) × 100` | 一个店做到 300% 就把整个季度抹平；超额靠「加分项」显式表达，那是可审计的 |
| `down` | 目标 0：`actual<=0 → 100`，否则 0；目标非 0：`LEAST(target/actual,1) × 100` | 零客诉已满分，再给 150 会让「不出事」比「做出业绩」更值钱 |
| 目标值 NULL | 录入值直接当分 | 行为价值观没法按比例折；硬折就得先编目标值，而编出来的目标值是假的 |

得分越过 `perf_metric.score_min/max`（**该项得分的上下限**，不是完成率）且没写 ≥4 字说明
→ `E_PERF_SCORE_RANGE`。业务上确实有特批，但特批必须留下「为什么」，否则复盘时只有一个突兀的高分。

### 3.3 汇总与强制分布

**缺项按 0 计，但不重新归一。** `fn_perf_total` 用 `COALESCE(ri.score, 0)` 加权，缺的项名
`RAISE WARNING`（`E_PERF_ITEM_MISSING`）并随接口的 `missing` 清单给出（`159:448`）。不这么做：
4 项只打 3 项若按剩余归一，`66` 会变成 `82.5`（66 ÷ 0.8）——「少打一项」变成「分数被抬高」，而少打的那项通常
恰是没人敢评的弱项；归一化让漏评得到奖励。汇总必须**穿过** `fn_perf_score` 回写，不直接
`UPDATE perf_result`：档位重算、封存拦截、改分留痕都在那条路上，直接改表会让「改分」与「算分」
在表里同形。总分封顶 100（`E_PERF_TOTAL_CAP` 告警），因为档位表只覆盖百分制；单项的 150% 只在
单项里生效。

**强制分布 0 人档也出行。** `fn_perf_distribution` 从 `perf_grade` 出发 `LEFT JOIN` 统计，
不是从 `perf_result` 出发 `GROUP BY`（`158:474`）。不这么做：方案 5 档只用了 3 档就出 3 行，
「A 档没人」与「方案里没有 A 档」完全同形，而处置**相反**——前者是执行没到位（要有人去谈），
后者是方案没配（不用管）。仍然**只报不拦**（026 ④）：拦的后果是有人去调分，而调过的分与真分
在表里同形。`pct` 在 `total = 0` 时为 NULL（没有分母），不是 0；`target_pct` 为 NULL = 不参与强制分布。

落 `SUITE.API-EXAML / API-EXAMT / API-PERFS / API-AX` 四条判据。

## 5 与产品 / 法规的边界（本仓不做）

| 不做 | 为什么不是「没做」 |
|---|---|
| 监考与摄像头 | 只有浏览器事件（blur/hidden/paste/screenshot），`screenshot` 也只是「按了截屏键」这个动作。上视频监考要存储、带宽、个人信息合规三件事同时到位，且离线考试无解 |
| 题库抽题组卷 | 现在题目逐条写进某张卷。上抽题要「每次开考生成变体卷」，而变体卷会让「这张卷的及格率」不再是同一个分母——报表口径先坏 |
| 跨组织的考试任务共享 | `exam_task.org_id` 只有组织维度、没有法人维度。跨法人共享会让「这个法人的人能不能考另一个法人的卷」变成权限问题，而成绩是要报监管的 |
| 绩效 360（多评分人） | `perf_result` 一行一个分、一个签名。上 360 要另开「评分人 × 权重」一层，会与 `perf_item.weight` 打架——同一方案两套权重，谁解释得清 |
| 绩效申诉流 | 台账能回答「改过几次、谁改的」，但申诉是**单据**：要状态机、时效、经办人。现在没有页面承载，先做等于做一个没人走的流程 |
| 跨法人共享绩效方案 | `perf_scheme` 没有法人列，`fn_perf_scheme_asof` 只按日期取全局版本。分法人会让「同期两个法人两套档位」出现，而工资侧按法人发薪——口径先对不上的是工资 |

## 6 已知缺口（都还差一步）

- **没有「到点自动交卷」**：`deadline_at` 只在交卷那一刻用来算 `late_seconds`；人开着页面不交直接关掉，答卷就永远挂着，没有后台任务收口——`board` 的 `open_attempts` 是这个数的体温计。
- **试卷建好后改不了**：没有 PUT/PATCH，限时、限次、及格线要改只能新建一张卷，旧答卷仍挂旧卷。
- **错题回顾没有「只看错题」开关**：`fn_exam_review` 返回全卷，服务层再在 JS 里筛 `wrong`，题量大时整卷回传。
- **绩效指标库没有写入接口**：`/api/perf/metrics` 只有 GET，`perf_metric` 目前靠 SQL 种子插。
- **两个分布接口并存**：`/api/perf/distribution`（旧）只回 `{rows}`、`/api/perf/dist` 回 `{cycle_id, rows, kpi}`，前端要按形状分别解；而且旧那条在 `perf.mjs` 里没有 `requireSession`，与 `/dist` 不是同一套鉴权面。
- **重叠任务下「应考人数」不唯一**：窗口刻意允许重叠，`fn_exam_missing` 按人去重，报表上看不出他属于哪一批。
- **方案体检没有断言**：`fn_perf_item_check` 与 `GET /api/perf/check` 都在，但不在任何断言组里——它能列问题，却没有人验证它列得对。
- **`fn_perf_item_set` 是整方案覆盖**：改一项也要把全部项重发一遍，漏发一项就是「权重和 ≠ 1」——报错是对的，操作是笨的。
